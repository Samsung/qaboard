## Performance
Measure with `npm run bench` before and after (`BENCH_OUTPUTS=5000 BENCH_COMMITS=1000` magnifies). On a busy machine its `cpu` column (main-thread time) varies much less than `time`.
- [ ] **Commit page polling**: refreshes send back the commit's ETag and keep their data on a `304` (`get_unless_unchanged` in `src/api/queries.js`): nothing is downloaded when nothing changed (2.3 MB per refresh for 5000 outputs before). The main-thread cost of a refresh didn't change measurably (55-70 ms in `npm run bench`, "commit page: refresh, nothing changed"), and the server still serializes the whole commit to hash it (`conditional_json` in `backend/backend/api/commit.py`). Next, if servers are busy: a cheap fingerprint from SQL, or the summary first (`with_outputs=false`), to answer `304` without serializing. The intervals (`pendingRefetchInterval`) could then be shorter for big commits.
- [ ] The commit page's chunk imports the tuning views (`TuningForm`, `BatchesEditor`, `TuningAnalysis`) and `BatchLogs` (with the log viewer and `ansi-to-html`) even when they're not shown: `lazy()` would take ~60 kB gzip off it. No gain was measured in October 2026 (the shared chunks and icons arrive later anyway): measure again if the page's other chunks shrink.
- [ ] `src/api/queryClient.js`: TanStack's persister dehydrates the whole cache on every cache event (we skip writing when nothing persisted changed, not the dehydration). Each output card adds 2 manifest queries, so it grows with the Visualizations.
- Measured in October 2026, not worth changing: the IndexedDB restore (4-13 ms with 600 projects; restoring before the first render delayed the first paint), lazy-loading the command palette (Rolldown splits the modules it shares into chunks that are still preloaded), lazy Home/Explore (`/` shows 200-500 ms later), `@popperjs/core` (Blueprint's `Tooltip` needs it), debouncing `TuningForm`'s saves to localStorage (under 0.1 ms per keystroke with 50 kB of preferences, 30 ms with 2 MB). `qs` stays: `src/selection.js` relies on nested keys (`compare[1][commit]=b`).

- [ ] **Blueprint's icon paths are 18-25% of the JS** of Home and the commits list (November 2026, `vite preview`, gzip): the default loader imports *all* 16px paths (~100 kB gzip) and, once one icon is 20px or more (`NonIdealState`, big buttons), all 20px paths (~100 kB more). Home downloads ~570 kB of JS, the commits list ~800 kB, a commit page ~1.1 MB. Try `Icons.setLoaderOptions({ loader })` with a loader that imports one icon's module (`@blueprintjs/icons/lib/esm/generated/{16,20}px/paths/<name>.js`, through `import.meta.glob` so Vite splits them), or preload the ~100 icons we use. Measure with `npm run bench` and watch for icons popping in late. The icon fonts (`blueprint-icons.css`, ~50 kB woff2 per size) are imported too: check what still uses them.
- [ ] The commit page's chunk (`CiCommitResults`, 240 kB gzip) carries `yaml` (94 kB raw, for the batch files' editor, `optimize_config.js` and `batchesDiff.js`), `ExportPlugin.jsx` (48 kB) and the tuning reports (`TuningReport`, `OptimizationReport`, `OptimizeSetup`, ~110 kB raw) that only some views show. Complements the item above on `TuningForm`/`BatchesEditor`: measure them together.
