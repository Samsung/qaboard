# Inference gateway: a QA-Board example

The (fictional) inference gateway of a robot fleet, wrapped with QA-Board: a small Rust program, `gateway-bench`, runs
the gateway (request queue, dynamic batching, CPU workers running a small model, a result cache) and an open-loop load
generator in one process. `qa/main.py` runs it on a load profile and turns what it measured into latency percentiles,
throughput, CPU per request, plots and a CPU flame graph. [`SPEC.md`](SPEC.md) describes everything it computes;
`story.yaml` is the six weeks of history the QA-Board docs show.

## Run it

You need [Rust](https://rustup.rs) (stable) and a Linux machine with 4 CPUs or more. Nothing else to download: the
load profiles are generated, the model's weights come from a fixed seed.

```bash
pip install qaboard                    # qa/main.py only needs the standard library and PyYAML (with qaboard)
cd examples/serving-latency

qa run --input profiles/steady-high.yaml        # 6,000 requests/s for 2 x 4 s, about 10 s
qa batch ci                                     # 5 load profiles, about 45 s
qa batch capacity                               # the load ramps up to 120% of 6,000 requests/s
qa --label nightly batch nightly                # every profile, 3 repeats each
```

- The first run builds `gateway-bench` (`cargo build --release` in `gateway/`, a couple of minutes), then measures this
  machine once to size the model and the responses (`qa/build.py`, kept in `gateway/target/calibration.json`): the
  load levels are fixed numbers of requests/s, so this keeps the gateway as loaded as on the machine the docs were
  made with. To build ahead of time: `uv run qa/build.py`.
- Performance runs never run in parallel (`runners.local.concurrency: 1`): they would measure each other. Close what
  you can: a busy laptop makes for a slow gateway, and noisy tails.
- Without `--share` or a CI, results are saved in `output/`. To see them in QA-Board, start a server
  ([quickstart](https://samsung.github.io/qaboard/docs/get-started/quickstart)), and use `qa --share` or run in CI.

## How it's wired

| File | What it does |
|---|---|
| `qaboard.yaml` | Project name, inputs (`inputs/profiles/*.yaml`), visualizations, the quality gate's rules |
| `qa/main.py` | `run(context)`: runs `gateway-bench` with the commit's flags and the input's profile, then the metrics and plots |
| `qa/build.py` | Builds `gateway-bench` and sizes requests for the machine |
| `qa/plots.py`, `qa/flame.py` | Plotly figures (latency percentiles on a log tail, breakdown, timeline...), and the flame graph's JSON |
| `qa/make_profiles.py` | Writes the load profiles: steady, bursty and heavy-tail at 2,000, 4,000 and 6,000 requests/s, and a ramp |
| `qa/metrics.yaml`, `qa/batches.yaml` | Metrics (labels, units, targets) and batches (`ci`, `capacity`, `nightly`, `sweep-batching`) |
| `gateway/` | The Rust crate: `src/gateway.rs` (ingress and workers), `src/batcher.rs` (queue policies), `src/cache.rs`, `src/model.rs` (the MLP, fp32 and int8), `src/bench.rs` (the load generator, repeats, measurements) |

**Flags** describe the code's choices (batching, queue policy, cache, allocator...): `qa/main.py` reads them from
`build/flags.json`, over its defaults, and tuning parameters override them. `gateway-bench --help` lists them.

```bash
echo '{"cache": "shared", "cache_entries": 4096}' > build/flags.json   # the coding agent's shared cache
qa run --input profiles/steady-high.yaml
qa batch sweep-batching --tuning-search '{"parameter_search": {"max_batch": [1, 16, 64], "max_delay_us": [0, 250, 1000, 4000]}}'
```

**Determinism:** the load (arrival times, keys, payload sizes and contents) depends only on the input and `$QA_SEED`,
so every commit is measured on the same requests. Everything measured varies from run to run: that's why each run
repeats its measurement and reports medians, and why the docs' screenshots come from a snapshot.
