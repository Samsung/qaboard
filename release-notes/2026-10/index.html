October 5, 2026
qaboard v1.1.1

A new image viewer, readable configuration diffs, a dark theme and a commit page that stays fast with 1000 runs. QA-Board now works with GitHub and other git hosts, and comes with a quickstart, a tutorial and a user guide. Admins: read "Before you upgrade" first; at SIRC, also install `qaboard-site-sirc` when you upgrade qaboard.

Users

A new image viewer

Compare images side by side, with a wipe, one at a time in place, or as their difference, measured perceptually or in ΔE 2000. Zoom in to read the pixels' own values, even 16-bit or float, run a blind test, and rank the runs of a page by how much their images changed. Videos compare the same way, frame by frame.

Learn more →
Users

See what changed in a configuration

Runs show how their configuration differs from their reference run's, like gain: 3 → 4, and hide the settings all runs share. Lists and tuning parameters are readable, and runs are compared with the reference run whose configuration is closest. Copy a run's settings as qa options.

Learn more →
Users

Fast with 1000 runs and years of commits

On a commit with 1000 runs, filtering takes half a second instead of freezing the page for 7, and the Metrics Table opens in a third of a second instead of 7. The Filter box searches all of a project's commits, and long commit lists and the projects list load as you scroll.

Learn more →
Users

Dark theme and more room for results

Switch to a dark theme, or follow your system's. Collapse the sidebar to icons, dock the View options on the right (o), and switch commit lists to Compact. Press ? for the keyboard shortcuts and the filter syntax.

Users

Logs, files and reruns

Logs update live, with search, and failed LSF runs say why LSF stopped them. Browse a run's files under /s/, edit your batches in Available Tests with errors flagged as you type, and redo only the runs you filtered, with the batch's runner and concurrency.

Project integration

GitHub, other git hosts and a quality gate

QA-Board works with GitHub and GitHub Enterprise as well as GitLab, and receives the push events of Gitea, Forgejo and Bitbucket Cloud. qa batch sets a commit status that links to the results, you can start GitHub Actions workflows from the web app, and the experimental qa gate fails the CI when quality regresses.

Try QA-Board on your computer with one Compose file and demo projects, then follow the tutorial: it shows the steps for your server, git host, CI and runners. A user guide explains the web app, and release notes pop up in it once a month is over.

Web app​

Comparing images​

  • Compare images like videos: side by side, with a wipe, one at a time in place (Single), or as their difference. Pick the mode above any image, or with the keys 1 to 4: it applies to all the images of the page, and links keep it. The swap button, or t, swaps the sides (around the difference too); when one image shows, it shows the other, then their difference, then the first again. It does it in every viewer of the page, so they all show the same one, and the keys work anywhere on the page, not only over an image. See comparing images.
  • Compare an image with another file of the same run, like its ground truth or the input, side by side or as their difference: pick it in vs reference ▾ above the image, where the likeliest files come first. Every run of the page then compares with its own file of that name, or only the run you're looking at with Apply to: This run, and c switches back and forth with the reference. See comparing with another file.
  • Run a blind test: Blind test above the images (or h) shows each viewer's images in a random order, called A and B everywhere, then Reveal shows which was which, and Done goes back to new first. See blind test.
  • See the difference between the new and reference images, all three in sync, with a cross on the pixel under your mouse in each, measured perceptually (YIQ), as ΔE 2000, per channel or as any change at all. Click Difference again, or press 4 again, to see it alone and larger. See the difference.
  • Zoom in and read the values of the pixels, written on them: the image's own values (10-bit, 16-bit, float, raw...) or the 8-bit colors on screen, picked from the 123 button above the images. Hover a pixel to see both, in both images, and their difference; p hides them. 8-bit images show one set of values: the screen shows them as they are. See pixel values.
  • Compare images in full screen: the button at the right of the image viewer's toolbar, or f, gives the screen to the images, with all the viewer's tools, and the difference under them when that makes them larger. See full screen.
  • Adjust how images look with brightness, contrast, gamma, sharpening, one channel (R, G, B or luma), false colors or inverted colors. They apply to both images and to the same visualization of the other runs; the pixel values, the difference and the histograms stay the images'.
  • Highlight a range of values on the images: drag on the histogram and stripes show the pixels in the range, with the share of each image they cover. Click R, G, B or Y above the histogram to show one channel alone and pick its values. The channels' areas blend where they overlap, and the axis has ticks. See histograms.
  • Find your way in large images: a minimap shows where you are once you zoom in, the zoom level says how many screen pixels an image pixel takes, 1:1 goes to 100%, and the histogram button overlays the histograms of the new and reference images in view.
  • Step through the regions of interest with their thumbnails above the images, or with [ and ]. The regions menu finds where images differ most, by perceptual difference, SSIM or ΔE 2000: one region per place that changed, with how much it changed (e.g. #1 · 3.2%). The region set you pick applies to every viewer of the same file on the page, and searches like Where they differ only run on the page where you pick them.
  • Copy or save the new, reference or difference image as you see them, or open the original files, from the copy button above the images.
  • Find which runs' images changed most: Where they differ, in all N runs… in the image viewer's regions menu compares every run of the page with its reference and ranks them, from the largest difference to the identical ones. Show takes you to a run, on the region that changed most. The list says which runs it's comparing and for how long, and which wait for their turn. See which runs changed most.
  • Pick how images are compared in the View options (Compare images), which replaces the Image diff switch. Links made with Image diff on open in difference mode.
  • Use QA-Board's image viewer in your own React apps: it builds as a package (npm run build:image-viewer), with its props documented in its README.

Videos​

  • Compare videos with a wipe, one at a time in place (Single), or as their difference, besides side by side. Zoom with the mouse wheel or a pinch and drag to pan: both videos follow, and zoomed in you see the actual pixels. See comparing videos.
  • Step through videos frame by frame with the arrow keys, scrub, slow down to 0.1× or loop: new and reference stay on the same frame, and wait for each other when one is still downloading.
  • Copy the current frame of a video (new, reference or their difference) to the clipboard, or save it as a PNG.
  • Compare videos like images: the difference between the videos or alone, perceptual or in ΔE 2000, display adjustments, a blind test, full screen (f) and a minimap when zoomed in.
  • Highlight a range of values on the videos, like on images: drag on the histogram of the frames, and pick its channels with R, G, B or Y. See histograms.
  • See which frame each video shows when paused, numbered like in the file even with variable frame rates, and whether both show the same frame. See which frames you are looking at.
  • Read the decoded values of the pixels (e.g. 10-bit Y′, Cb, Cr) of the very frame shown, under the pointer and written on the pixels when zoomed in, next to the 8-bit values your browser displays.
  • See what's in the video files side by side (codec, pixel format, chroma subsampling, color range and matrix, frame rate, keyframes, dropped frames), with what differs highlighted and what it means for what you see.
  • Find where two videos differ: the timeline shows how much each frame differs, n and N go to the frames that differ most, and regions show where and when they differ most, in the whole video or in the frame shown. See where the videos differ.
  • Change the speed of videos with < and > (they were [ and ], which now step through regions, like in the image viewer).

Point clouds and trajectories​

  • See point clouds (*.pcd files) in 3D: the new run's, the reference's and a ground truth on the same axes, each in its own color, that you can show or hide, orbit, pan and zoom. See point clouds and trajectories.
  • See 6DoF trajectories across the run's card, with the path in 3D next to the plots of each axis, at the same scale on every axis.

Test reports​

  • See a run's JUnit XML test report (pytest, GoogleTest, CTest, Maven, Gradle...) as a tree of its tests, compared with the reference's: new failures, fixed, added, removed, newly flaky and skipped tests at a glance. Click the counts or the changes to filter, search tests and messages, press n for the next failure, and read each failure's message, trace and output next to the reference's. Files named junit.xml or TEST-*.xml open in it (test reports).

Configurations and reference runs​

  • See at a glance what's specific to each run: settings that all the runs shown share are hidden behind "··· N shared" tags, and listed once at the top of the page. It follows the filter. Turn it off with Hide them in each run (reading configurations).
  • Read lists in configurations: [1, 0.98, 0.95], long lists with their size (… 64 values, 3×3) and where they changed (…0.619, 0.7 → 0.635, 0.651…). Tuning parameters show as settings like the others, with a wrench.
  • Copy a run's settings as qa options (-c … --tuning …), as JSON or as a tuning search space, and a setting as text or JSON, from their hover menu.
  • See how a run's configuration differs from its reference run's: added settings in green (+), removed ones struck through in red (−), changed values as gain: 3 → 4, and only the changed part of strings: conf/[day → night].yaml. Changes all runs share are listed once, at the top of the page. Hover the Config tag for a git diff-like view.
  • Runs are compared with the reference run whose configuration is closest: the fewest different settings, then the most similar values (base-v1 is closer to base-v2 than to other). The Config tag says when other reference runs were as close.

The commit page​

  • The commit page's view options are now a panel docked on the right that makes room for the results instead of covering them. Collapsed, a rail shows a dot on the sections that differ from the project's defaults, and hovering lists the changes. Press o to show or hide it, or drag its edge to resize it. See View options.
  • See and change what the commit page shows from Files to show (formerly Dynamic options): each option says which visualization it's for and lists the values of all runs. Options are linked across runs: a run that doesn't have the selected value shows the closest one and says so, and you can pick a value per run. See the user guide.
  • Open the export box from the new Export button next to the Visualizations and Output Files titles; press Enter to export, and find the last export's paths when you reopen it.
  • Run cards fit the window when qaboard.yaml doesn't set their width (outputs.style.width): they used to be 1500 px wide, wider than a laptop's screen.
  • Metrics Diff colors small changes and shows them precisely ("-0.37%" instead of "-0%"). The Summary's bars say how many runs met their metric's target.
  • Find more explanations on hover: run statuses, aggregated metrics, new/ref, targets in the metrics tables, and milestones. The reference's bar says when it's the same commit as the new one.
  • Pages use the width next to the sidebar instead of jumping between fixed widths, and the commit page fits laptop screens: its header cuts long commit messages and branches with "…".
  • The Tuning Analysis view of a qa optimize experiment plots its convergence itself: each iteration's objective and the best one so far, even when matplotlib isn't installed where qa optimize ran.
  • The commit page tells you when a commit's artifacts were deleted (when, and by whom) or are incomplete, what's missing, and lets you recreate them with your CI.
  • Compare with several references, one at a time: hover the reference's bar and Stack a reference (a commit, a branch, a milestone, or the same one with another batch or filter), then switch with their tabs or r / Shift r. Drag tabs to reorder them, right-click them or click their ⋯ to duplicate, rename or remove them. They are in the URL. See several references.
  • See each stacked reference under one name, in its tab, the reference's bar and the viewers: the first is "ref", the ones you add "ref 2", "ref 3"..., copies are <name> copy, and they keep their names when you reorder or remove references. Tabs say only what tells them apart: their batch or filter, their commit or branch, when the others' differ. Many tabs scroll sideways, with the mouse wheel too. See several references.
  • Hover a reference's tab to see its commit, message, author, branch, batch, filter, and how many runs it has and how many failed.
  • See everything you compare in the tabs: the top bar's results come first, then "vs" the references, and the two in the bars are lit. Swap the bars from their tabs' menus, or by dragging the first tab on a reference: the same comparison, reversed, and nothing is replaced. "Switch new/reference" is now Swap the bars.
  • Name what you compare: click new or ref to call them ISP v2 and ISP v1. The names are in the URL, and the page uses them: the images and videos' labels, the legends of plots, text diffs, flame graphs, HTML outputs, the Summary and the columns of Metrics Table and Metrics Diff. Milestones are called by their name.
  • See which is which by color: new is blue, references purple, magenta, teal and violet, in their bars, tabs, the viewers' labels, and the plots (the Summary's box plots, overlaid Plotly plots), in the light and dark themes. A reference keeps its color when you reorder, switch or remove references, and a color freed by a removed reference goes to the next one you add. The reference is no longer orange, a color that says "warning".
  • Errors from redo, delete and tuning actions show a readable message instead of the raw server response.
  • When you are logged out, actions that need a login (redo, delete, rename, tuning, restoring artifacts...) are greyed out next to a Log in button, instead of failing with an error. If your session expires, one message asks you to log in again.

Logs, batches and redoing runs​

  • The Logs view filters runs (all, failed, running) and tags failed runs with the reason (e.g. "LSF: out of memory"). The sidebar's Logs entry shows how many runs failed, or are still running.
  • Show only the runs that succeeded: with Successful in the Logs view, or with status:success in the commit page's filter boxes. See the filter syntax.
  • In the Logs view, each run fits on one line, with buttons to open its output directory, copy its Linux or Windows path, redo it, mark it as failed or delete it. Its full configuration shows when you open its logs.
  • Switch between a run's log.txt, log.lsf.txt and log.dask.txt. For LSF runs, a summary shows the exit reason, host, run time and memory used vs requested, with hints that point to the batch's lsf: options.
  • Batches started from QA-Board (tuning, "Run Tests") show whether qa batch is waiting for LSF, running, failed (with the error) or didn't start any run, with a link to its logs.
  • See where the logs of each command that started a batch are: in the CI job (with a link), or in QA-Board (one click shows them). The batch's own log.txt only shows when it exists. See the user guide.
  • Show more of very long logs: they show their last 50,000 lines to stay fast, and say if the hidden lines have errors or matches for your search.
  • When you filter a batch's runs, the commit bar menu redoes only the runs that match the filter. Follow redone runs in the Logs view, under "Started from QA-Board". See the user guide.
  • The Available Tests view is a real editor for your private and shared batches: it flags YAML mistakes and inputs qa batch can't use as you type, shows whether your changes are saved (Ctrl+S), keeps them if you leave, and warns instead of overwriting someone else's changes. See the user guide.
  • Available Tests warns about what qa batch would ignore or misread: unknown keys like inpts (Did you mean "inputs"?), values of the wrong type, unknown runners and runner options, and input types the commit's qaboard.yaml doesn't define. Values defined at the top level and reused in batches with YAML anchors (database: *lab-db) aren't flagged as batches. See the user guide.
  • The Available Tests view lists the batches in each file: go to one, list the tests it resolves to on the commit, or run it in one click.
  • When a batch has no tests in Available Tests or Run Tests / Tuning, see why: a batch file missing from the commit's artifacts (with the path QA-Board looked for), invalid YAML, a batch that no file defines, or inputs the server didn't find. See the user guide.
  • Redoing runs or starting tuning on a commit with missing artifacts first brings them back, instead of failing or running from a broken folder.
  • Redo buttons work again on commits whose artifacts were deleted.
  • The tuning form checks your settings while you type, and lists what would make the batch fail (unknown batch, invalid automated tuning configuration, unknown platform...) before you click Send.
  • The tuning form warns when the commit's artifacts are missing and will be restored first.
  • Get an email when a batch you start from the tuning form ends: one email when its last run ends, with how many runs failed, the main metrics vs their targets, the best parameters and links to the failed runs' logs. See the user guide.

Finding commits and projects​

  • Search all of a project's commits from the commit list's Filter... box, not only those in the date range: by message, committer, branch, batch or hash. Use branch:, committer:, batch:, message: or id: to look at one field, and -word to exclude (searching commits).
  • Jump to a branch from the Filter... box: when your search can be a branch name (one word, or a branch: term), it suggests the most recently active branches that match, even in projects with thousands of branches.
  • Scroll through long commit lists: they show the 50 latest commits, then more as you scroll, so big projects open much faster, and Older commits at the end looks a week further back. Branch pages still get their whole date range at once (up to 1000 commits), for their metrics chart.
  • Switch commit lists to Compact to see one commit per line, in aligned columns, with the full message, metrics and other batches on hover. The web app remembers your choice.
  • Open the projects list much faster on sites with hundreds of projects: it downloads less, and shows more projects as you scroll.
  • Find your way around from the History page: the sidebar shows the project's navigation (the branch's commits, Code, History, Integrations, Milestones), and moving between these pages no longer reloads the app.
  • Add up a metric over a batch's runs: the charts over commits, on History and above a branch's commits, offer sum next to median and average, e.g. to follow the number of tests of all your test suites (History).

File browser​

  • Open a folder under /s/ in your browser to get the new file browser: sort and filter files (e.g. *.png), copy their Linux or Windows paths, paste a path to go there, and navigate with the keyboard (press ?). Scripts and curl still get nginx's plain index.
  • In the file browser, a bar shows the run whose folder you are in, with its status and a link to its results: redo it, delete it or mark it as failed from there.
  • Sign in from the file browser with any of your server's sign-in methods, single sign-on included: Sign in opens the sign-in page, then brings you back to the file.

Git hosts and integrations​

  • Follow links to code, commits and branches on your project's own git host, with the right URLs for GitHub, GitLab, Gitea/Forgejo and Bitbucket, instead of a hardcoded GitLab server.
  • The sidebar's Code menu links to the commit, its files, your subproject's folder, the branch and the repository on your git host.
  • Start the GitHub Actions workflows declared in your project's qaboard.yaml from the Integrations menu, follow the run you started, and see the status of each workflow's latest run for the commit. Only users who can access the project can see or start them (GitHub Actions).
  • See your git host's defaults in the Integrations menu of branch pages, when your project configures none and QA-Board knows its git host: GitLab's pipeline status, or a link to GitHub Actions (default integrations).
  • See commit authors' avatars from GitHub, Gitea/Forgejo and Bitbucket, learned from push events, or else their Gravatar. Avatars and badges from public git hosts load directly, which is faster.
  • The Jenkins integration accepts params (what the server used) and parameters (what the docs said), and no longer fails without them.

Look and feel​

  • Switch to a dark theme with the theme button next to "What's new" in the sidebar, the projects list or the file browser. By default the web app follows your system's theme; plots, editors and viewers follow it too, and metrics tables only highlight clear improvements and regressions.
  • Collapse the sidebar to a rail of icons for more room, with Collapse at its bottom or Ctrl+\ (⌘\ on macOS). Hover an icon for its name; the web app remembers your choice.
  • A calmer, more consistent look: every view's title sits above its flat card, configurations are grey tags, run statuses are small icons, and filters have their help and a clear button inside the box. Hover a view in the commit page's sidebar to see what it shows; your login moved to its bottom.
  • Pages say what's happening instead of staying blank or showing empty views: while they load, when they fail (with a Retry button), and when there's nothing to show yet, with what to do next and a link to the docs. For example, a commit without results explains how to get some, and an empty Metrics Diff says why there is nothing to compare.
  • Deleting runs, batches or a commit's results, redoing a whole batch and resetting the tuning form ask you first, with how many runs are affected. Notifications name what was acted on, and starting runs offers to show their logs.
  • The commit, batch and run action menus open on click instead of hover, so they no longer open by accident and work on touch screens. When a run has no reference and there's no Windows path to choose, its folder and copy buttons act directly.
  • The footer stays at the bottom of the window, with links to What's new, the cheat sheet and QA-Board on GitHub.
  • The web app says "runs" everywhere, like the docs ("8 runs", "Redo failed runs"), and page titles match the sidebar's names: Metrics Table instead of "Quality report", Metrics Diff instead of "Improvement report", and the Analysis view is now Tuning Analysis.
  • See who made a commit at a glance: when there's no avatar picture, committers, users and projects show their initials on a color that stays the same everywhere.
  • Buttons that were only icons have labels for screen readers, and the menus they open can be reached with the keyboard.
  • The "Quotas" links show only when the server has a quota dashboard, and the error page links to your server's support page.

Milestones​

  • Save milestones in your account: they follow you on every computer. The star next to a commit's hash opens a dialog that shows what you save (the commit, its batch, the filter and how many runs match), suggests a name, and asks for an optional group, notes, and whether everyone on the project sees it. See milestones.
  • Organize milestones in groups, like releases or tuning/denoiser: menus list them by group, and remember the groups you collapse.
  • Find milestones faster: the Change menu and the sidebar's Milestones menu list your favorites first, then your milestones, then the project's, with a search box that matches their name, group, notes, branch, batch, filter or owner.
  • Add milestones to your favorites with the heart: the sidebar lists them, one click away.
  • Share a link to a milestone, /<project>/milestone/<id>-<name>: it opens its results, and keeps working when the milestone is renamed. Add ?vs=<id>-<name> to link to a comparison of two milestones.
  • Manage milestones in a table: sort them by update, creation, name or group, open one, use one as the reference, compare two, or move, share and delete several at once. See managing milestones.
  • Add a whole group of milestones to your favorites: its milestones, even future ones, are listed first.
  • Find milestones by dataset: milestones remember the datasets, qa batches and platforms their runs used. Search dataset:indoor or qa-batch:nightly, or pick a dataset in Manage milestones…, which also shows each milestone's notes.
  • Find out what happened when a milestone link is broken: the page says which milestone was deleted, and still opens the other one of a comparison.
  • Save several milestones on the same batch, for example one per filter. When the results you look at are a milestone, its name shows next to the star.
  • Milestones you saved in your browser before (the "private" ones) move to your account the next time you log in with that browser.

Accounts, tokens and admins​

  • Create API tokens in Settings → Access tokens, with only the scopes they need (read, send results, act), for some projects only, and with an expiry date or none. The token is shown once, with how to use it (APIs).
  • See when and from where your tokens were last used, and revoke them. Settings → CLI & devices lists the logins of qa auth login, and Activity your recent sign-ins and token changes.
  • Approve qa auth login from any browser: open the link it prints and check the code.
  • Keep your preferences (theme, list density, favorites...) from browser to browser and computer to computer when you're signed in.
  • See who really sent a run: runs sent with a token show it, the others can be marked as unverified.
  • Admins: see users, their tokens and last sign-ins, disable accounts and make admins, revoke any token, read the audit log and change settings in the new Admin panel, with a security checklist (user management).
  • Read why you can't do something: errors say what's wrong and what to do, e.g. that a token expired or lacks a scope.
  • Sign in with your company's single sign-on, when your admins set it up: its button comes first on the new sign-in page.
  • See where you're signed in in Settings → Sessions, and sign out of the browsers you don't use anymore, or of all of them but this one.
  • Add another way to sign in to your account, or remove one, in Settings → Sign-in methods.
  • Ask for access: when your admins approve new accounts, you can sign in and say why you need QA-Board, and you get an email when they decide.

Help, What's new and links​

  • Read the release notes in the new "What's new" panel, with a search box (/#whats-new opens it). It pops up once a month is over; the current month's notes show as a preview, tagged "In progress".
  • The sidebar's help button opens the new user guide.
  • Press ? for a cheat sheet: keyboard shortcuts, QA-Board's words, the filter syntax and links to the docs. The sidebar's ? button opens it too.
  • The URL keeps everything you select (date range, metrics shown, highlighted commits, filters, view and plot options), but only what differs from the defaults, so links stay short. Share it, reload, or use the back button: you get the same view. Typing filters no longer adds entries to the browser's history.
  • Link to History with or without the breakdown per test, or relative to the first commit: ?breakdown_per_test=false and ?relative=true in the URL now work.

CLI and project setup​

Signing in​

  • Sign in from the CLI with qa auth login: open the link it prints in any browser, even when qa runs over SSH, and approve the code. The token is saved per server in your config folder, never in your projects, so it works in every checkout and worktree. qa auth status, qa auth logout and qa auth token (signing in).
  • Set QABOARD_TOKEN in CI to send verified results (CI tokens). QA_TOKEN and ~/.qaboard/secrets.yaml still work.
  • Read why the server refused your token (expired, revoked, missing a scope...) and what to do, instead of a stack trace. The advice fits where you are: in CI it's about QABOARD_TOKEN, never about signing in from a browser.
  • CI jobs fail when QA-Board refuses their results, before running anything, instead of passing with nothing saved.
  • qa auth logout only revokes the tokens qa auth login created: a token you saved with --with-token (e.g. your CI's) keeps working, unless you add --revoke.
  • qa auth status says where the server's address comes from, and lists the other servers you're signed in to. A wrong QABOARD_URL or a server that's down is reported as such, not as a bad token.
  • qa gate --server no longer sends your token for the default server to another server.
  • qa batch says when the server won't show it the batch's runs (e.g. it requires signing in), and stops instead of running them all again when you asked to skip, sync or post-process the existing ones (--action-on-existing).

Project setup and the qa CLI​

Server and administration​

  • Users, tokens and admins: an admin panel, settings in the database, and an audit log (user management).

    • Change settings from Admin → Settings without restarting the server: requiring sign-in, local sign-up, token lifetimes, how results are authenticated. Environment variables still win when they're set.
    • Require tokens to send results: ingest.auth (or QABOARD_INGEST_AUTH) goes from off (the default) to warn (qa asks users to sign in) to token (results sent by qa).
    • Find sign-ins, failed sign-ins, token changes, CLI logins and admin changes in the audit log, with who and from which IP.
    • Tokens are stored hashed, can have scopes, projects and an expiry date, and expire when unused for long if you want.
    • Disabled accounts stop working at once: their sessions and tokens are refused at the next request.
  • Single sign-on with OpenID Connect (Keycloak, Entra ID, Okta, Google...), next to LDAP, SAML and local accounts (sign-in and single sign-on).
    • Set QABOARD_OIDC_ISSUER, QABOARD_OIDC_CLIENT_ID and QABOARD_OIDC_CLIENT_SECRET; add more providers from Admin → Sign-in.

    • Keep users' accounts when they move to single sign-on: match them by user name when your identity provider shares LDAP's directory, or by verified email.
    • Send users straight to your identity provider with auth.sso_auto_redirect; /login?local=1 keeps a way in for local admins.
  • Decide who gets an account with auth.access_policy: everyone, emails of some domains, or after an admin approves. Admins get an email and a webhook message (Slack, Teams, Mattermost) when someone waits.
  • Sessions are stored on the server: they end after sessions.idle_days without activity and sessions.max_days in any case, users and admins can end them, and disabling a user ends theirs. Nobody is signed out by the upgrade.
  • Use LDAP over TLS: ldaps:// in QABOARD_LDAP_HOST, or QABOARD_LDAP_START_TLS=true.
  • Sign-in, sign-up and qa auth login are rate-limited by the shipped nginx configuration. Behind a load balancer or an ingress, set QABOARD_TRUSTED_PROXY_HOPS=1 to record users' IPs in the audit log.
  • Keep the commit lists of projects with many runs per batch fast: list them in QABOARD_SKIP_METRICS_AGGREGATION (project ids, or their start like group/), and their commit lists skip the batches' aggregated metrics, which commit pages still show (environment variables).

    • Security: the server only writes, deletes or runs code in the folders listed in QABOARD_STORAGE_ROOTS (default: /mnt/qaboard), and refuses results stored elsewhere. If your projects store results in other folders, set it before upgrading (see environment variables).
    • Security: the server only loads avatars and badges for the web app from your GitLab hosts and gravatar. If your projects' avatar_url or badges (integrations[].src) come from other hosts, list them in QABOARD_PROXY_HOSTS (see environment variables).

If you may roll back, set what matters with environment variables. Downgrading the database (alembic downgrade) deletes the tokens.

  • The batch menu says Move the filtered runs to another batch when you filter runs, instead of the other way around.
  • The automated tuning example names the solver's acq_func option correctly.
  • Copying the path of an output, batch or commit directory gives the right path when folder names contain characters like #, and the confirmation shows the copied path.
  • Notifications show at the bottom of the window again, instead of at the bottom of the page's first screen where they were out of sight once you scrolled down.
  • Move on quickly from the sidebar's Integrations and Milestones menus: they close once the mouse leaves them, instead of staying up to 3 seconds over the page.
  • Links to the LSF docs and to the getting-started page work again, and the retired chat link now points to your server's support page (by default, QA-Board's GitHub issues).

Commit page​

  • Run cards draw the visualizations of projects that still list them under their old name, outputs.detailed_views, instead of empty cards under the View options' switches.
  • The controls panel shows the sort actually used, the project's default metric, instead of Name, and Output Files no longer shows an empty visualization filter.
  • Run cards grow to fit a plot wider than their configured width (outputs.style.width), instead of the plot spilling out of the card.
  • Run cards with a configured width (outputs.style.width) get narrower when the page is, e.g. when the View options are open, instead of going under them and hiding the image viewer's zoom and settings.
  • Visualization cards line up from the left, instead of being pushed to the edges of the page.
  • The Tuning Analysis view's efficient frontier colors points by nested tuning parameters (like denoise.strength) instead of drawing black dots.
  • Dynamic options no longer show an empty card when a run doesn't have the selected value, sort numbers as numbers (2 before 10), and no longer split into options like frame_1234 that control nothing. Whether an option is linked is no longer remembered across projects.
  • A run's card in full screen has a button to leave it, and scrolls when it's taller than the screen, instead of its content sticking to the screen's edges.
  • Hiding a visualization shown by default takes one click instead of two.
  • The reference commit's refresh button works again: it was disabled once the commit had loaded.
  • The error page shows the error as text, instead of inserting it in the page as HTML.
  • Artifacts & Configs shows the artifacts again when the commit loads after the view, instead of "Could not find" them.

Metrics and tables​

  • A run is compared with the reference run of the same platform: when the reference batch had the same input and configuration on two platforms, the other platform's run was picked.
  • The Improvement report showed "=" for metrics that changed, and badges for those that didn't.
  • The Summary's change in % has the right sign for metrics with negative values, and runs that return no value (null) for a metric no longer count as 0 in its median.
  • The Summary only warns that it mixes runs with different parameters when the runs it aggregates really have different parameters: filter the runs to compare one configuration.
  • In the Metrics Table, the New and Ref headers stay over their columns when a filter leaves out every run that has some metric, and metrics without a target show just their unit, like [s].
  • Removing a metric from a table's metric picker no longer also drops the selected metrics that the current batch doesn't have.
  • The Summary's box plots on a log scale show a few round ticks, instead of labels that overlapped.
  • Output Files tags runs Bit-accurate when their output files match the reference's: like qa check-bit-accuracy, it only checks the files that match bit_accuracy.patterns in qaboard.yaml (all files by default, except logs, run.json and metrics.json). The other files are still listed when they differ, greyed and tagged "not checked". See bit-accuracy tests.

Image viewer​

  • In the image viewer, changing a Dynamic Option (e.g. a slider over your pipeline's stages) keeps the zoom and the selected ROI, for the new and reference images, instead of zooming out to the whole image, most often when the reference's image showed up. Images with another aspect ratio fit the selected ROI again.
  • The regions where images differ most (formerly Auto ROIs) are centered on the differences, instead of starting at them.
  • Images show in the image viewer on servers that don't set QABOARD_IMAGE_SERVERS: the default is now Cantaloupe's /iiif/2/ endpoint, instead of a /iiif URL that Cantaloupe couldn't answer.
  • JPEG images show in the image viewer again, instead of an "Image Download Error": the image server only sent them as JPEG tiles, and the viewer asks for PNG ones. They now come as PNG tiles, with the exact pixel values for the pixel tooltip and the diff. Update the cantaloupe image to get the fix.
  • The image viewer's Auto ROIs finds regions again, instead of failing with an error.
  • The image viewer's ROI thumbnails show the image the viewer shows: they no longer break for runs that save a TIFF instead of a PNG, or for images served by another image server (QABOARD_IMAGE_SERVERS).
  • ROIs set on inputs of another size than the output images are placed right on non-square images, in the thumbnails and when you zoom on them.
  • In the image viewer, selecting a region (the selection button, or c) draws it again and shows its histograms, instead of panning the image.
  • The image viewer's diff threshold slider no longer jumps to its maximum and gets stuck: it moves step by step after you turn the diff on.

Videos, plots and other viewers​

  • Point clouds take the colors and names of what you compare, like the other viewers: blue for new, the reference's color and its name, e.g. a milestone's, instead of orange for new and blue for the reference.
  • In the video viewer, n and N go to the frames that differ more than the frames around them. On videos where every frame differs, like with a new denoiser, they no longer only go back to the first frame.
  • Text diffs stay side by side in narrow run cards, as the Side-by-side button says, and inline diffs are tall enough to show every changed line.
  • Playing or pausing a video that has no reference no longer raises errors ("pause is not a function").
  • Videos your browser can't play (e.g. HEVC) say so, with the command to convert them, instead of staying black. Animated .webp and .gif files now show, side by side with the reference's, instead of a black box or their bytes as text.
  • In point clouds, WASD moves while the key is pressed, not after it's released.
  • Plots saved with side_by_side: false draw the reference run's traces on the same axes, instead of nothing when a figure has several traces. Traces keep their own dash style.
  • Differential flame graphs are colored by what changed: red for frames that take more time than in the reference, blue for less, orange for new ones. The colors no longer exaggerate changes near the root.
  • The SLAM and tuning plots no longer have Plotly's "Send to Cloud" button, so their data can't be uploaded to Plotly's public cloud.
  • Text viewers set to show only differences hide identical files, and videos play without a reference.
  • Text files in a run's output files show again when the reference run doesn't have them, and their diff with the reference no longer breaks when you press t to swap the sides.
  • HTML outputs (like a run's report) show their images and links, which are relative to their own folder, and their styles no longer change the rest of the page: they show in a frame, without running scripts.

Commits, branches and history​

  • Clicking a run's name opens its History from 3 days before the commit, so you see the commits before it without picking dates.
  • Projects without a qaboard.yaml use master as their reference branch in the web app, like the server and qa, instead of develop.
  • Reloading a page, opening a shared link or using the back button shows what the URL says: the selected commits, batches and filters could disagree with it.
  • The back button takes you back in one click after following links inside QA-Board: some links added two entries to the browser's history.
  • The chart above a branch's commits shows the branch's metrics, the median or average over each commit's runs, instead of staying empty. Each commit row also shows the median and average of the default metric over its CI runs.
  • History's "Performance over time" chart shows your project's metrics again, instead of asking you to define them.
  • The History page's per-test tables show their metric columns again, in tabs named "Metrics Table" and "Metrics Diff" like on commit pages.
  • On the History page, picking metrics updates the metrics distribution too.
  • Selecting a milestone from qaboard.yaml selects the latest commit of its branch.
  • The batch selector no longer jumps back to the top while you scroll it, and its keyboard navigation works again. It now opens on the selected batch, marked with a check.
  • Switching to a branch you had opened in a previous visit no longer crashes the commits list ("setHours is not a function").
  • Commit pages and the branch list no longer break when results were sent without a branch.
  • The projects list shows the description from qaboard.yaml (project.description) for projects that aren't on GitHub or GitLab too.
  • The chart above a branch's commits leaves out the commits that don't have the metric, instead of drawing gaps in its line.
  • Typing a commit id in the commits list's search and pressing Enter no longer leaves "[object Object]" in the search box.
  • Editing your own shared milestone no longer asks whether to overwrite it.

Runs, batches and tuning​

  • Run qa --share batch with an edited qaboard.yaml to see its new visualizations and metrics on that batch, while the commit's other batches, CI included, keep the commit's. Each qa batch used to replace the commit's qaboard.yaml for all its batches.
  • The automated tuning form's feedback link goes to your server's support page, and is left out when the server has none.
  • Redoing runs from QA-Board respects the batch's concurrency, and uses the runner the runs were started with (e.g. Dask) and its settings. QA-Board used to start each run with its own qa batch, so they all ran at once, with the default runner.
  • Runs that start again (redo, qa batch...) no longer show as failed, and count as failed, until they finish: their status is reset when they are pending or running.
  • Finished runs whose metrics don't include is_failed count as successful, instead of neither successful nor failed.
  • A stuck run's "Mark as Finished" action is now labelled "Mark as Failed", which is what it does.
  • Moving runs to another batch closes the dialog, and saving a milestone no longer risks losing it.
  • The tuning form shows a readable error instead of the server's raw response.
  • The tuning form remembers the "Overwrite" option, and setting the number of iterations no longer crashes.
  • Run Tests / Tuning runs as you when you open it from a link: it no longer asks for a user it can't let you type, with Send disabled.
  • The Tuning Analysis view plots each iteration's metrics (those in the objective) next to the objective, for tunings run from now on: qa optimize used to get no metrics from the server.
  • Projects whose inputs are inside the project (a relative inputs.database, like inputs) see their tests in the Run Tests / Tuning form and in Available Tests: they are looked for in the commit's artifacts, where the runs started from QA-Board run, instead of in a folder of the server. In monorepos, from the root qaboard.yaml's folder, like qa does.
  • Run Tests / Tuning and Available Tests find the inputs of projects whose inputs.database uses {project} or {subproject} (e.g. /datasets/{project.name}), instead of looking for them from /.
  • When several of a commit's batch files define the same batch, Run Tests / Tuning and Available Tests use the last one, like qa batch, instead of the first.
  • Listing a batch's tests no longer fails for commits that QA-Board saw before qa sent their qaboard.yaml (e.g. opened by branch name): it uses the project's, and the commit gets its own the next time qa runs on it.
  • Run Tests / Tuning lists the tests of batches whose name contains +, & or #.
  • When a batch has an input it can't use, like an empty - or a number, qa batch says which batch, in which file and at which line, instead of "Could not understand the inputs in the batch" followed by all its inputs. Available Tests and Run Tests / Tuning show the same error.
  • Stopping a batch whose runs can't be stopped reports the error instead of failing.
  • The tuning form no longer asks for an Android device, which runs never received.
  • qa batch --runner=local (or any --runner) uses the batch's and the input type's settings for that runner, e.g. its local concurrency and timeout, also when the project's default runner is another one, like LSF.

CLI​

  • Give a batch its own concurrency (under local:, lsf: or dask:) or local timeout: its runs now use it instead of the command's. Command-line options like --local-concurrency still win, even when they equal the value in qaboard.yaml.
  • Runs over their local timeout fail, and qa batch kills what they started and goes on with the other runs, instead of stopping with a TimeoutError and leaving them pending.
  • Inputs with their own settings can set their platform:, and no longer make qa batch fail with KeyError: 'platform' in batches that set one.
  • qa batch '*' runs your batches only, instead of also running every input as a batch named aliases.
  • qa batch --action-on-existing assert-exists leaves the runs that already succeeded as they are, instead of failing them with a command that doesn't exist.
  • qa wait exits with an error when the run it waited for failed, so qa wait ... || ... works.
  • qa optimize works without --checkpoint, instead of failing with a TypeError.
  • qa check-bit-accuracy --reference-platform finds the reference's runs on the other platform when runs have configurations, instead of saying there is no reference.
  • qa tells you to run qa init, not qatools init, when it can't find qaboard.yaml, and qa batch --help says that --local-concurrency -1 runs one run per CPU.
  • With LSF job arrays and the Dask runner, qa run no longer deletes the log file its output goes to: errors are no longer lost.
  • Runs on Dask workers are headless, like with LSF: they use matplotlib's agg backend and no DISPLAY, instead of opening X11 connections back to the display of whoever started the batch.
  • Runs started from a git worktree checkout are saved under their commit, instead of their branch name. Submodules with a relative .git pointer also work.
  • On Windows, qa works in a git worktree whose .git pointer holds an absolute Linux path: it is translated with the site's path mappings (QABOARD_PATH_MAPPINGS).
  • qa starts even when the git HEAD cannot be read, e.g. an unresolvable worktree pointer: it warns and continues with <local:user> commit placeholders instead of crashing at startup.
  • On Windows, qa batch finds existing results for projects whose name contains a "/", instead of failing with "could not find any data on commit ID": --action-on-existing works there.
  • qa optimize works with recent versions of scikit-optimize, instead of failing with "cannot import name 'Integer'".
  • qa optimize no longer fails at the end when matplotlib isn't installed: it only skips its convergence plot.
  • qa batch --tuning-search runs a grid search when the JSON doesn't say search_type, as the docs show, instead of failing with KeyError: 'search_type'.
  • qa no longer warns that it doesn't know where your server is when you set QABOARD_URL=http://localhost:5151.
  • qa no longer prints a git error when the commit it runs on isn't in the local clone (e.g. shallow CI clones): it only did without the commit's details. QA_VERBOSE=1 still shows it.
  • With Python 3.12 and later, qa no longer prints a SyntaxWarning: invalid escape sequence when it starts.
  • qa batch accepts a single input written as text (inputs: a.jpg), and says that a batch written as a list (my-batch: [a, b]) must be a mapping with inputs:, also in the web app (the server used to call exit() there).
  • qa get works with Python 3.13: it said "Could not find" for every variable.
  • bit_accuracy.on_reference_failed_ci: compare-first-parent goes back up to bit_accuracy.max_parents_depth parents, instead of two at most.
  • bit_accuracy.failed_ci_job_name works again: qa check-bit-accuracy only looks at that job (<job> <subproject> in subprojects).
  • qa check-bit-accuracy counts skipped CI jobs as successful, instead of waiting for them.
  • Windows test vectors no longer fail bit-accuracy on hex outputs whose end-of-lines differ.

Server and administration​

  • Show the demo projects' latest commits in the quickstart's commit list: the demo data's dates, and its files' modification times, move to when QA-Board first starts, instead of keeping the day the demo data was made (quickstart).
  • The project's settings (metrics, visualizations, storage...) are no longer replaced by those of whichever branch got new results last: they come from the reference branch (project.reference_branch in qaboard.yaml), or from the project's first results.
  • nginx starts on hosts without IPv6, instead of failing on its listen [::]:80 line.
  • Repositories whose clone is broken are cloned again, instead of failing until an admin deletes them. The broken clone is only replaced once the new clone succeeded.
  • Tag pushes record the tag's whole name: its first character was cut.
  • Pushes to repositories with files or folders whose name only looks like qaboard.yaml (for example an agent skill folder named qaboard-yaml) no longer fail: only files named exactly qaboard.yaml or qatools.yaml define projects.
  • Jenkins integrations show the status of the builds they trigger when Jenkins' own URL uses another hostname than the integration's build_url (for example a full domain name): checking them failed with a 403 because no credentials matched that hostname in JENKINS_AUTH.
  • Jenkins integrations trigger jobs that have no parameters, and when Jenkins refuses a build the error says why (HTTP status, Jenkins' message, a hint about JENKINS_AUTH or build_url) instead of showing a whole HTML page about a missing location header.
  • Servers outside SIRC no longer show avatars from SIRC's directory for GitLab users without one: set QABOARD_AVATAR_URL to use your own (environment variables).
  • Backend workers no longer risk crashing, or losing Sentry events, when Sentry is enabled: Sentry starts in each uWSGI worker, and uwsgi.ini sets py-call-uwsgi-fork-hooks, as Sentry's SDK requires. Keep it if you use your own uwsgi.ini.
  • The cleanup also deletes commits that never had runs, and uses each project's own storage.garbage settings instead of the first project's.
  • storage.garbage.artifacts.keep now works with artifact group names, and also accepts folders and globs.
  • Commits whose artifacts were only partly restored are no longer marked as usable.

Security and data safety​

  • Requiring sign-in now blocks anonymous requests to the API itself, not only the web app's pages.
  • API tokens are no longer stored in clear, and a token in a URL (?token=) is only accepted to read. Requests made with a token no longer open a session cookie.
  • Session cookies are HttpOnly and SameSite=Lax, and Secure when QABOARD_URL is https. Changes made with cookies must come from QA-Board's own pages.
  • Signing in with SAML only sends you back to QA-Board's own pages (open redirect), and lands on the home page instead of an empty error page when there's nowhere to go back to.
  • Logging in no longer sends everything the directory knows about you to the browser.
  • Reading the values of an image's or a video's pixels, what's in a video, and finding where images or videos differ now require a login, and only read files in the storage (QABOARD_STORAGE_ROOTS) that you're allowed to see. Signed out, the viewers show the displayed values and say to sign in for the rest. These endpoints could read images anywhere on the server, without a login.
  • The unused PDF report of the regions where images differ (/api/v1/output/diff/report) is removed: it could write files anywhere on the server, without a login.
  • Marking a run as failed or deleting it now requires a login.
  • On servers that restrict projects to some users, only users allowed on a project can stop, rename, move or delete its batches, delete a commit's results, save its artifacts, or change its milestones. Exporting runs also checks you can access the reference's project.
  • QABOARD_LOGIN_RESTRICTED=false (or 0) turns project restrictions off, as you would expect: any non-empty value used to turn them on.
  • Deleting results no longer deletes the contents of folders that they link to.
  • When a restricted project saves its results in a folder per user (e.g. /algo/outputs/{user}), the project's files are now restricted in every user's folder, not only in the server's.
  • The API qa uses to update batches no longer lets anyone without a login delete runs. qa optimize still replaces its previous best iteration's runs, and only those.
  • When qa fails to update QA-Board, its warning no longer prints your API token (QA_TOKEN).
  • When signing up with a user name or email that is already used, the server answers "already taken" instead of an error that included the password's hash, and no longer writes the password to its logs.
  • Logging in with an empty password is refused, and LDAP logins escape the user name.
  • The server only deletes the git clones it made: it refuses repository paths inside a clone, or that hold other clones.
