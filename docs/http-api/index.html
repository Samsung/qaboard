HTTP API

The web app reads everything from QA-Board's HTTP API, and your scripts, CI jobs and agents can too, in any language. This page shows how to authenticate, get everything about one commit, and read the answers.

Your server'sAddress
API<your-qaboard>/api/v1
API reference, to browse and try requests<your-qaboard>/api/v1/docs
OpenAPI document<your-qaboard>/api/v1/openapi.json

<your-qaboard> is the address of your QA-Board, the one you open in a browser, like https://qaboard.example.com.

Python and the shell

From Python, qaboard.runs(url) gets the runs a web app page shows, and qa gate --json compares a commit with its reference: they call this API for you. See Results in scripts. Use HTTP from other languages, or for what they don't cover.

Your first request​

Ask for the latest commits of a project that have results:

QABOARD_URL=https://qaboard.example.com
curl "$QABOARD_URL/api/v1/commits?project=kitefin/detector&limit=5" | jq '.[] | {id, branch, message}'
{
  "id": "7622c33790d16cf1a04ad6a5c7b1a1d2a3b4c5d6",
  "branch": "quant/int8",
  "message": "feat(quant): percentile calibration (99.99)\n\nMinmax let a few outliers set the scale..."
}
...

project is the project's id, as in the web app's URLs: <your-qaboard>/kitefin/detector/commit/7622c337.

If you get 401 and "reason": "sign_in_required", your server or the project requires signing in: send a token, as below.

Authenticate​

Reading is anonymous, unless your server requires signing in or the project isn't public. Changing things needs a token, except sending results when your server still accepts them anonymously. To get one:

  1. In the web app, open Settings → Access tokens and create a token (how). Give it only the scopes it needs: Read to read results. For a CI job, prefer a service account's token: it keeps working when people leave.
  2. Keep it in an environment variable, never in your code or in URLs. If you signed in with qa auth login, qa auth token prints yours. 
    export QABOARD_TOKEN=qab_pat_...
  3. Send it in the Authorization header: 
    curl -H "Authorization: Bearer $QABOARD_TOKEN" "$QABOARD_URL/api/v1/user/me/"
    {
      "is_authenticated": true,
      "user_name": "arjun",
      "token": {"name": "nightly report", "scopes": ["read"], "projects": ["kitefin/*"], "expires_at": "2027-02-04T00:00:00Z"}
    }
    /user/me/ says who you are and which token you use: check your setup with it.

A token can do what its scopes allow, on the projects its user can see, and only on the projects it's restricted to, if any:

ScopeLets the token
readRead projects, commits, runs and files.
ingestSend results (qa run, qa batch), and add metrics to runs.
actRedo runs, start or delete batches, save milestones.
adminUse the admin API (admins only).
When a token is refused: the reasons

Errors are JSON, with what went wrong in error and a stable code in reason:

{"error": "This token expired on 2026-10-01.", "reason": "token_expired"}
StatusreasonWhat to do
401sign_in_requiredSend a token.
401token_invalidThe token is mistyped, or was deleted: check it, or create another.
401token_expired, token_idle_expired, token_revokedCreate another token.
401token_in_urlSend the token in the Authorization header: ?token= is only accepted to read.
403missing_scopeThe token needs the scope in required.
403token_projectThe token is restricted to other projects.
403missing_role, forbidden_projectYou can't see or change this project. With missing_role, owners lists whom to ask.
403cross_site_writeA browser sent a change from another website, with your session: use a token.
From a browser, a token in a URL
  • In a browser signed in to QA-Board, requests to the API use your session: the API reference page works without a token.
  • Changes sent with a session from other websites are refused (cross_site_write). Pages on another site send a token instead.
  • ?token=<token> is accepted for GET requests to the API, for tools that can't send headers. Avoid it: URLs end up in logs and browser histories. Files under /s/ only accept the header.

Everything about one commit​

The four requests most scripts need, for a commit's CI batch. In the API, runs are called outputs, and the CI batch's label is default (the web app shows it as CI).

1. Get the commit, its batches and runs​

curl -H "Authorization: Bearer $QABOARD_TOKEN" \
  "$QABOARD_URL/api/v1/commit/7622c337?project=kitefin/detector&batch=default"

The commit can be a sha or its first characters, a branch (its latest commit with results), or a tag. Without batch, you get all the commit's batches. The answer, shortened:

{
  "id": "7622c33790d16cf1a04ad6a5c7b1a1d2a3b4c5d6",
  "branch": "quant/int8",
  "message": "feat(quant): percentile calibration (99.99)",
  "committer_name": "Arjun Sethuraman",
  "authored_datetime": "2026-11-05T13:58:40+00:00",
  "outputs_url": "/s/mnt/qaboard/kitefin/detector/outputs/7622c337",
  "data": {"qatools_config": {"project": {"reference_branch": "main"}}},
  "batches": {
    "default": {
      "id": 1204,
      "label": "default",
      "origin": "ci",
      "valid_outputs": 7,
      "pending_outputs": 0,
      "failed_outputs": 1,
      "outputs": {
        "184467": {
          "id": 184467,
          "test_input_database": "/mnt/datasets/kitefin",
          "test_input_path": "slices/indoor",
          "configurations": ["fp32", "size-320"],
          "extra_parameters": {},
          "platform": "linux",
          "metrics": {"mAP": 0.612, "latency_ms": 18.4},
          "is_pending": false,
          "is_failed": false,
          "output_dir_url": "/s/mnt/qaboard/kitefin/detector/outputs/7622c337/default/slices-indoor"
        }
      }
    }
  }
}

Get a run's metrics with .batches.default.outputs[] | {test_input_path, metrics} in jq. A run has finished when is_pending is false; it succeeded when is_failed is also false. All the fields are below.

Big commits

A batch can have thousands of runs. with_outputs=false leaves them out: you get the batches' counts, and with metrics={"mAP": 0.5}, each batch's median, average and sum of these metrics (aggregated_metrics.mAP_median).

2. List a run's files​

curl -H "Authorization: Bearer $QABOARD_TOKEN" "$QABOARD_URL/api/v1/output/184467/manifest"
{
  "output.png": {"st_size": 1843211, "md5": "9b2c1e0f4f6d3a8c7e5b1a2d3c4e5f60"},
  "detections.json": {"st_size": 20480, "md5": "2f1e0d9c8b7a6f5e4d3c2b1a09f8e7d6"}
}

3. Download a file​

The *_url fields are paths on your server. Add your server's address before them, and the file's path after:

curl -H "Authorization: Bearer $QABOARD_TOKEN" -O \
  "$QABOARD_URL/s/mnt/qaboard/kitefin/detector/outputs/7622c337/default/slices-indoor/detections.json"

On the machines that mount the storage, the same file is at the path after /s: /mnt/qaboard/kitefin/detector/.... Read it there instead of downloading large files.

4. Compare with the reference​

The numbers of the Summary and Metrics Diff views: each metric's median against the reference's, and each run against the reference run of the same test. qa gate decides from them.

curl -H "Authorization: Bearer $QABOARD_TOKEN" \
  "$QABOARD_URL/api/v1/commit/7622c337/compare?project=kitefin/detector&batch=default&reference=main"
{
  "status": "complete",
  "messages": [],
  "commit": {"id": "7622c337...", "batch": "default", "runs": {"total": 8, "valid": 7, "failed": 1, "pending": 0, "running": 0}},
  "reference": {"requested": "main", "type": "branch", "id": "51f0e2a9...", "batch": "default", "runs": {"total": 8, "valid": 8, "failed": 0, "pending": 0, "running": 0}},
  "metrics": {
    "mAP": {
      "smaller_is_better": false,
      "target": 0.55,
      "new": {"median": 0.612, "count": 7, "pass_rate": 0.86},
      "ref": {"median": 0.598, "count": 8, "pass_rate": 0.75},
      "delta": 0.014,
      "delta_relative": 0.023
    }
  },
  "tests": [
    {
      "id": 184467,
      "reference_id": 183902,
      "reference_mismatch": null,
      "test_input_path": "slices/indoor",
      "is_failed": false,
      "metrics": {"mAP": {"new": 0.612, "ref": 0.601, "delta": 0.011, "delta_relative": 0.018}}
    }
  ]
}
  • Check status first. The numbers are final only when it's complete. running means some runs aren't done; missing means runs or the reference are missing, and messages says what.
  • reference is a branch (its latest commit with runs in the batch), a commit sha, or a shared milestone's label. Without it, the commit's gate.reference in qaboard.yaml, else the project's reference_branch.
  • Whether a change is better depends on smaller_is_better. When it's null, QA-Board doesn't know which way is better: don't call the change an improvement or a regression.
  • reference_mismatch isn't null when the reference run isn't the same test (another input, configuration or platform): it says what differs.

All the parameters are in the quality gate's docs.

The same from Python​

A script that prints, for each test of a commit's CI batch, its metric and the reference's. Save it as compare.py and run uv run compare.py 7622c337:

compare.py
# /// script
# dependencies = ["requests"]
# ///
import os
import sys

import requests

server = os.environ.get("QABOARD_URL", "https://qaboard.example.com")
api = requests.Session()
if os.environ.get("QABOARD_TOKEN"):
    api.headers["Authorization"] = f"Bearer {os.environ['QABOARD_TOKEN']}"


def get(path, **params):
    response = api.get(f"{server}/api/v1/{path}", params=params, timeout=60)
    if not response.ok:
        sys.exit(f"{response.status_code} {path}: {response.json().get('error', response.text)}")
    return response.json()


project, commit = "kitefin/detector", sys.argv[1]
comparison = get(f"commit/{commit}/compare", project=project, batch="default", reference="main")
if comparison["status"] != "complete":
    sys.exit(f"Not comparable yet ({comparison['status']}): {comparison['messages']}")

metric = "mAP"
info = comparison["metrics"][metric]
print(f"{metric}: {info['new']['median']} vs {info['ref']['median']} (smaller is better: {info['smaller_is_better']})")
for test in comparison["tests"]:
    cell = test["metrics"].get(metric) or {}
    print(f"{test['test_input_path']:<30} {cell.get('new')} vs {cell.get('ref')}")

Dates are ISO 8601. Those without a time zone, like 2026-11-05T14:02:11.391000, are in UTC.

Other requests​

Lists of commits, branches and projects​

  • GET /commits?project=<project>: the commits with results, newest first. By default those of the last days with commits, or of from and to (2026-10-01T00:00:00.000Z). /commits/<branch> for a branch's, committer=<name> for a committer's.
    • limit (at most 1000) and offset give pages: the X-Has-More response header (true or false) says if there are more.
    • q searches the whole history, with the syntax of the web app's search box, e.g. q=branch:release -wip.
    • only_ci_batches=true or batch=<label> keep one batch per commit; with_outputs=true adds their runs.
  • GET /commit?project=<project>&branch=<branch>: the branch's latest commit with successful runs, with its runs.
  • GET /project/branches?project=<project>: the branches with results (q=quant for those whose name contains it).
  • GET /projects?summary=true: the projects you can read, by id. GET /project?project=<project> for one's qaboard.yaml and metrics definitions.
  • GET /batches?project=<project>: the latest batches, each with its commit; scope=mine for yours in every project.
curl -i "$QABOARD_URL/api/v1/commits?project=kitefin/detector&q=committer:arjun&limit=50&offset=50"

Milestones​

GET /milestones?project=<project> lists the shared milestones, and yours when you send a token: each with its label, group, notes, commit, batch and filter. Compare with one with reference=<label>.

Add metrics to a run​

A script can add the metrics it computed to a finished run. It needs a token with the ingest scope and the developer role on the project:

curl -X PATCH -H "Authorization: Bearer $QABOARD_TOKEN" -H "Content-Type: application/json" \
  -d '{"metrics": {"sharpness": 0.42}, "source": {"script": "sharpness.py"}}' \
  "$QABOARD_URL/api/v1/output/184467/metrics"

QA-Board records who added each metric, when and with which script, in the run's data.added_metrics. Metrics the run returned itself are refused (409, metrics_exist) unless you send "overwrite": true. From Python, run.log_metrics() does it: see Add metrics to runs.

Starting runs and batches​

Redoing runs and starting batches from the API needs a token with the act scope. These endpoints serve the web app, aren't in the reference yet, and may change: from scripts, prefer qa batch in a checkout of the project, or start your CI.

QA-Board can start Jenkins builds with its own Jenkins credentials (Jenkins builds). From a script, send a token with the act scope:

curl -X POST -H "Authorization: Bearer $QABOARD_TOKEN" -H "Content-Type: application/json" \
  -d '{"build_url": "https://jenkins.example.com/job/my-job", "params": {"key": "value"}}' \
  "$QABOARD_URL/api/v1/jenkins/build/trigger/"

Without a token, QA-Board only starts the jobs listed in the project's qaboard.yaml.

API reference​

Your server describes its API at:

  • <your-qaboard>/api/v1/docs: the reference, to browse the endpoints, their parameters and answers, and try them. If you're signed in to QA-Board in the same browser, requests use your session; otherwise click Authorize and paste a token.
  • <your-qaboard>/api/v1/openapi.json: the same as an OpenAPI 3.1 document, for client generators, Postman, and agents.

Both are public, also when the server requires signing in: they describe the API, not your data.

The reference covers the endpoints on this page: those to read results, and to add metrics to runs. The others serve the web app and may change without notice. The document is written by hand for now; generating it from the backend's code is on the roadmap.

For coding agents​

Agents use the same API. What helps them get it right:

  • Fetch <your-qaboard>/api/v1/openapi.json first: it has every parameter and field, with descriptions.
  • To judge a change, use /commit/<sha>/compare: check status, then read smaller_is_better before calling a change better. Report the tests that regressed, not only medians.
  • Read the token from QABOARD_TOKEN, send it in the header, never in a URL or a log.
  • Read files on the storage, never change them: runs' folders are shared with everyone.

The qaboard-results skill teaches agents all of this, with the Python SDK and qa gate.
