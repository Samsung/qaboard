LSF Integration

QA-Board can use the LSF job management system to submit batch jobs.

Reminder

If you don't want to use LSF, read here how to make qa batch use a different backend.

tip

LSF jobs will have your project name as LSF project (-P).

LSF project options​

All settings are optional. You can change the default LSF configuration with:

qaboard.yaml
runners:
  # In doubt, ask advice from your manager / CAD / bqueues.
  lsf:
    queue: your_queue             # default: the cluster's default queue ($LSB_DEFAULTQUEUE, or DEFAULT_QUEUE in lsb.params)
    # project: my/project         # default: your QA-Board project's name
    # priority: 2000              # default: 2000, or 1000 for tuning runs
    # max_threads: 8              # ask for eg 8 max threads when sending jobs to LSF (0=default)
    # max_memory: 8000            # ask for eg 8000M memory when sending jobs to LSF (0=default)
    # resources: RESOURCE_STRING
    # priority: 10                # LSF priority (-sp)
    # options: "-W 24:00"         # Specifiy freely other LSF options that bsub accepts
                                  # Will be added after all other CLI flags.
tip

Your organization's site package can set defaults for all projects, e.g. runners.default: lsf and the queue. See Site defaults.

Limiting concurrency​

By default all the runs from a qa batch are sent at once. To limit how many run at the same time:

qaboard.yaml
runners:
  lsf:
    concurrency: 20              # 0=unlimited (default)
    # concurrency_strategy: array  # default

or qa batch --lsf-concurrency 20 my-batch.

Two strategies are available:

  • array (default): runs with identical LSF options are sent as a single job array with a slot limit (-J "name[1-n]%20"). It's a sliding window, and a single bsub call. If runs need different LSF options (e.g. per input type), each group gets its own array and its own limit.
  • waves: runs are sent by groups of concurrency jobs, each group waiting for the previous one to end (-w "ended(...)"). Slow runs delay the next wave. Use it only if job arrays don't work for you.

In both cases job names keep the batch prefix, so stopping a batch from QA-Board still works.

Logs​

Each run has 2 log files in its output directory:

  • log.txt: what qa run and your code print from Python, written live. You get it with every runner.
  • log.lsf.txt: everything the LSF job printed, written live, including output that doesn't go through Python (subprocesses, native code, crashes). When the job ends, LSF appends its job report: exit code, why LSF terminated the job (e.g. TERM_MEMLIMIT), the host, run time, memory usage...

In QA-Board's Logs view:

  • Failed runs get a tag explaining why LSF ended them (e.g. "LSF: out of memory"). Above the logs, a summary of LSF's job report says what to do about it, and shows the host, run time, and memory used vs requested.
  • You can switch between log.txt and log.lsf.txt, search (Ctrl/Cmd+F, then Enter), and jump to errors.
  • While runs are running, logs update live. We only download what was added since the last update, and for large logs, only the end of the file at first.
note

With job arrays (see above), all runs share the same bsub -o file name. To get each run's job report in its own log.lsf.txt, qaboard creates symlinks to the runs' output directories in {batch_dir}/lsf/{job_array_name}/{index}, and uses -o "{batch_dir}/lsf/{job_array_name}/%I/log.lsf.txt".

Many short runs? Use a pool of workers​

Each run is an LSF job, and pays LSF's scheduling overhead. If you have many short runs, run them instead on a few long-lived workers, themselves started as LSF jobs: read the Dask integration docs.

LSF options per batch​

qa/batches.yaml
you-can-give-an-LSF-configuration:
  lsf:
    max_memory: 10000
    max_threads: 4
  configurations:
    - base
  inputs:
  - images/A.jpg
  - images/B.jpg
you-can-give-an-LSF-configuration-per-input:
  lsf:
    max_memory: 1000
  configuration:
    - base
  inputs:
    images/A.jpg:
    images/B.jpg:
      lsf:
        max_memory: 200

LSF options on the CLI​

You can use CLI options to override the defaults:

qa batch --help
# --snip--
  --lsf-max-threads INTEGER    restrict number of lsf threads to use. 0=no
                               restriction
  --lsf-max-memory INTEGER     restrict memory (MB) to use. 0=no restriction
  --lsf-queue TEXT             LSF queue (-q)
  --lsf-resources TEXT         LSF resources restrictions (-R)
  --lsf-priority INTEGER       LSF priority (-sp)
  --lsf-options TEXT           Other LSF options (as 1 string, like '-W
                               24:00') that bsub can understand. Will be added
                               after all other CLI flags.
  --lsf-concurrency INTEGER    Max number of LSF jobs from this batch running
                               at the same time. 0=unlimited
note

--lsf-threads was renamed --lsf-max-threads, and --lsf-fast-queue was removed.

Connecting to LSF via a "bridge" host​

It's needed for the server, that runs in a container, and sometimes to send LSF jobs from windows. There are two options:

  1. Via environment variables:
export QA_RUNNERS_LSF_BRIDGE='ssh my_host_with_lsf_access {bsub_command}'
export QA_RUNNERS_LSF_BRIDGE='ssh my_host_with_lsf_access su {user} {bsub_command}'
  1. Via project configuraton:
qaboard.yaml
runners:
  lsf:
    # --snip--
    bridge: 'ssh bridge_host'
tip

When using bridges, qa will explicitely ask LSF to run in your current working directory, so no need to play games with ssh 'cd {cwd} && {bsub_command}'...
