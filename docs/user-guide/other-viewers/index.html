Plots, flame graphs, 3D and more

Runs show more than images and videos: plots, CPU profiles, transcripts, the reports your code writes, 3D maps and trajectories. Each viewer puts the reference's result next to the new one, or over it, so you see what the change did.

If your outputs are…you'll see…
Curves, bars, heatmaps: a detector's precision-recall curves, a server's latency percentilesPlots, the reference's drawn over the new ones, or next to them
CPU profiles of a server or a pipelineFlame graphs, colored by what got slower or faster
Unit and integration test reports (JUnit XML)Test reports: each test against the reference, with what started failing, what got fixed and what disappeared
Text: an LLM agent's transcripts, logs, tablesText diffs, line by line
Reports your code writes as web pagesHTML reports, the new one above the reference's
A robot's maps and 6DoF trajectoriesPoint clouds and trajectories, in 3D, with the ground truth
Many files per run: an ISP's stages, the frames of a sequence, the images of a test setA slider that picks the file every card shows
Images and videosThe image viewer and the video viewer

They all show in the Visualizations view of the commit page, in each run's card. Your project chooses what each card shows; what it hides by default has a switch in the View options, under Visualizations. The full-screen button at the top right of a card gives its viewers the whole screen, e.g. for 3D views and deep flame graphs.

note

When the reference run's file is the same as the new one, the card says Identical to the reference: there is nothing to look at in that viewer.

Plots​

Your project's code draws the plots: curves, bars, heatmaps, 3D plots... Each plot is either drawn over the reference's, on the same axes, or next to it: the project picks, plot by plot.

Overlaid, the change is where the curves part. With a shared result cache, every latency percentile of the inference gateway is a hundred times the reference's or more:

  • The legend says which curve is which: new | Latency and ref | Latency, or the names you gave what you compare.
  • When a plot picks its colors, the reference's curve is dashed and faded, in the same color: with one curve per class, each class keeps its color. Otherwise, the curves take the colors of what you compare: blue for new, and each reference its own color.
  • The reference's lines are a bit wider: where nothing changed, the new line runs right on top of it.
  • Hover a curve for its values. Drag to zoom on a region, double-click to zoom back out. Click a legend entry to hide or show its curve, double-click it to show only that one. The toolbar that shows at the top right when you hover the plot saves it as a PNG.

Side by side, the new run's plot comes first, then the reference's. Nothing on them says which is which, and each zooms on its own. Projects use it for plots that would hide each other, like heatmaps:

More about plots
  • Plots saved as web pages (*.plotly.html) always show side by side, each in its own frame.
  • When the project gives a ground truth, overlaid plots draw it too, in green, named groundtruth.
  • When the reference run doesn't have the plot, the new one shows alone.
  • In the dark theme, plots that don't choose their colors get colors that read on a dark background.
  • Projects choose, with side_by_side in qaboard.yaml, how each plot compares: see the Plot.ly viewer.

Flame graphs​

A flame graph shows where a program spends its CPU time. Each bar is a function, as wide as the time spent in it, with the functions it calls below it. Against the reference, QA-Board draws a differential flame graph: the new run's profile, colored by what changed.

  • Red functions take more time than in the reference, blue ones less: the darker, the bigger the change. Orange ones are new. Light gray ones didn't change. Look for the wide red and orange bars first: that's where the time went.
  • Hover a function: its name, its share of the samples and their number show below the graph.
  • Click a function to zoom into it and what it calls. Zoom Out goes back.
  • Type a function's name in Highlight frames: the bars that match turn magenta, and below the graph, you read what share of the samples they take.
  • The menu below the graph picks what to draw:
ChoiceWidthsColors
What did happen (the default)The new run's profileWhat changed
What will happenThe reference's profileWhat changed: functions the change removed show here, in blue
After, BeforeThe new run's profile, or the reference'sBy function, as in any flame graph
After & BeforeBoth, one above the otherBy function
More about flame graphs
  • Functions are matched between the two profiles by their call stack: the same function, called from somewhere else, is another bar.
  • Highlight frames is case-sensitive, and reads regular expressions: lock|wait highlights both.
  • Without a reference profile, the flame graph shows alone, by function.
  • In the inference gateway example, widths are microseconds of CPU per 1,000 requests: the profile's unit is what your project records.
  • To record flame graphs with your code, read Creating and viewing flame graphs, and Brendan Gregg's differential flame graphs.

Test reports​

When a run is a test suite, its card shows the suite's tests compared with the reference run's: which ones started failing, which got fixed, which are new, gone, skipped or flaky, and why each failure happened.

To review a change to the tests:

  1. Read the numbers at the top. Each status has its count and its change vs the reference. The colored chips below name the changes: new failures, fixed, added, removed, newly flaky, newly skipped.
  2. Click a chip or a number to see only those tests. Shift-click numbers to combine them, e.g. failed and errors.
  3. Click a test to see its details on the right: its status here and in the reference, its time, the failure's message and trace, and its output. When the reference failed differently, its failure shows too.
  4. Press n to go to the next failure, p to the previous one: the groups above it open.

The list opens on the first new failure, with the groups that have failures or changes open. A removed test is struck through: the reference ran it, this run didn't, which a green CI doesn't tell you.

  • Search tests by name, group or failure message: every word must match, and -word leaves out the tests that have it, e.g. codec -fuzz. / goes to the search, Esc clears it and the filters.
  • Sort by failures first (the default), by name (tests stay in the order they ran), or slowest first.
  • Groups are the packages, modules, classes or suites of the report. Each shows how many of its tests failed or are flaky, its most important change, a bar of its tests' statuses, how many tests it has and their time.
  • Much slower tests took twice as long as in the reference and at least 100 ms more.
Keyboard shortcuts and more

Click in the list, then:

KeysWhat they do
↑ ↓, Home End, PgUp PgDnMove in the list

  • The ⌘ button above the list shows these shortcuts.
  • A group's details have Search this group, to see only its tests, and Open all below.
  • Tests are matched with the reference's by their id: their class (or file) and name. A renamed test shows as removed, and its new name as added.
  • Flaky tests are those the report marks as failed, then passed when run again. Not every test runner says it.
  • Without a reference report, the new one shows alone, without changes.
  • The viewer stays fast with tens of thousands of tests: only the rows you see are drawn.

Text diffs​

Text files are diffed with the reference's, line by line, in the code editor of VS Code: the reference on the left, the new run's on the right, what was removed in red and what was added in green. It works for any text: logs, tables, configuration files, an LLM agent's transcripts.

  • The tag next to the file name says which side is where, reference ➡️ new: press t to swap them.
  • Next diff jumps to the next change.
  • Side-by-side switches to an inline diff, removed lines above added ones, which reads better in a narrow card. Click it again (it says Inline diff) to go back.
  • The editor shows up to 40 lines: scroll in it for the rest. Click in it and press Ctrl+F (⌘+F on a Mac) to search.
More about text diffs
  • Files that no other viewer reads show as text.
  • The color codes that terminals use are removed from logs. YAML, JSON, Python and JavaScript files are highlighted.
  • Without a reference file, the new file shows alone.
  • To diff any file a run wrote, not only those your project shows, use Output Files.

HTML reports​

Your project's code can write its own report, as a web page: a summary, tables, the worst images. Each card shows the new run's report, then the reference's below it, under headings with their names.

  • A report is as tall as what's in it: scroll the page, not the report.
  • Its images and links work as they do next to the report's file, and links open in a new tab.
More about HTML reports
  • Reports show in a frame of their own: their styles don't change the page around them.
  • Scripts don't run in reports: a chart drawn by a script stays empty. Ask your project to save it as a plot instead.

Point clouds and trajectories​

For robots and 3D sensors, QA-Board draws maps and trajectories in 3D: the new run's, the reference's, and the ground truth when the project has one.

Point clouds, like the map a robot built, show on the same axes, in the colors of what you compare, like in the other viewers: the new run's in blue, the reference's in its color (purple for the first reference), and the ground truth in green. The checkboxes above the view name each cloud like the commit page does, e.g. with a milestone's name.

  • Drag to orbit, right-drag to pan, scroll to zoom. Reset view goes back to the start.
  • The checkboxes show or hide each cloud, with its number of points. Hide the reference to compare the new map with the ground truth alone.
  • Where two clouds should overlap and don't, one of the maps is wrong.
  • Point clouds are large: projects may hide them by default. Switch them on in the View options, under Visualizations.

Trajectories (6DoF: the position and orientation over time) show each value of the pose over time, on the left, and the path in 3D, on the right, with x and y at the same scale.

  • The legend names the new run, the reference and the ground truth: click one to hide it.
  • Hover a curve for its values. Drag to zoom on a time range, double-click to zoom back out. In 3D, drag to rotate and scroll to zoom.
  • The reference's lines are a bit wider: where the new line covers them, the trajectories are the same.
  • Find the moment the new trajectory leaves the ground truth, then look at what the robot saw then. When the project saves the camera as a video, it plays in sync with the reference's, in the video viewer:
More about point clouds and trajectories
  • The project sets the size of the points, the ground truth's file, and whether trajectories have a 3D view: see Point clouds and trajectories.
  • An older viewer shows a time-of-flight camera's runs frame by frame: depth maps and point clouds.

Step through pipeline stages and frames​

Some visualizations have several files per run: one per stage of a camera pipeline, per frame of a sequence, per image of a test set. A card shows one at a time, and Files to show, in the View options, picks which, for every run at once.

  1. Open the View options (press o). Under Files to show, each option is named after what varies in the files' names, like Stage or Image.
  2. Move the slider, or pick a value in the list: a slider when the values are consecutive numbers, a list otherwise. Every card shows that file, new and reference, with its path above the viewer, like stages/3.jpg.
  3. To follow one spot stage after stage, zoom in on an image first: the image viewers keep their zoom and region as you change files.
  • Until you pick a value, each run shows its own default: its last one when the values are numbers (its last frame, for instance), else its first. The panel says so, for instance Each run's last. The reset button next to the option goes back to it.
  • Runs don't need to have the same files. A run without the value you picked shows the closest number, and its card says which.
  • To pick a different file in each card, turn on Per run: each card gets its own slider or list. Same for all runs, in a card, turns it off again.
  • Hover an option's name to see which visualizations it's for, and the values found in the runs.
More about stages and frames
  • Some visualizations show all their files at once, one after the other, instead of one at a time: the project chooses.
  • How projects declare these files, and how options are named: see Dynamic visualizations.
