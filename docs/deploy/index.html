Starting a QA-Board server

Set up a QA-Board server for your team: by the end, your users sign in to the web app, and qa saves their results to it. This page uses Docker Compose on one Linux host. On Kubernetes, follow Running QA-Board on Kubernetes instead.

Try it first

The quickstart starts QA-Board on your computer with one Compose file, and demo projects to look at.

What you need​

  • A Linux host with Docker Engine, docker compose 2.24 or newer (docker compose version), git and python3. For its size: deployments/production.env runs 2 backend replicas of up to 8 uwsgi processes each, the Helm chart asks for 1 CPU and 4 GiB of memory per replica, and services/db/qaboard.conf has PostgreSQL settings for an 8-core, 32 GB host.
  • Disk on the host, in Docker's volumes and images (/var/lib/docker by default): QA-Board's images (deploy.py keeps those of the last 3 versions), the database, the clones of your git repositories, and caches: decoded images, up to 20 GB (QABOARD_IMAGE_CACHE_GB), and the image server's tiles, kept 5 days.
  • The results storage: a folder that the server and every machine that runs qa (CI runners, workstations, cluster nodes) mount at the same path, e.g. an NFS share at /mnt/qaboard. qa writes the output files there itself, and only sends their path to the server, which reads them there.
  • A hostname that your users, CI runners and git hosts reach, e.g. qaboard.example.com, and a TLS certificate for HTTPS.
  • One port: the web app, the API and the webhooks answer on port 5151 (QABOARD_PORT_HTTP), or 443 with HTTPS.
The admin services stay on the host

docker-compose.yml also publishes pgAdmin (5050), RabbitMQ (5672, its management UI on 15672) and Flower (8888), on the host itself only (127.0.0.1): from another computer, use an ssh tunnel. RabbitMQ has a guest:guest account until you set one, and anyone who reaches it can run commands on Celery workers: see passwords and admin services before you publish it for workers on other hosts.

1. Get QA-Board​

On the host:

git clone https://github.com/Samsung/qaboard.git
cd qaboard

You deploy from this checkout: it has the compose files, nginx's and PostgreSQL's configuration, and deployments/deploy.py. The code comes from the images. To deploy a release, check out its tag (git checkout v<version>), so that both match.

2. Create the results storage​

To start on a single host, a local folder works. Share it later:

sudo mkdir -p /mnt/qaboard
sudo chmod 777 /mnt/qaboard

If your storage is a share, mount it on the host at the path the runners use. To use another path than /mnt/qaboard, use it in the overlay below, list it in QABOARD_STORAGE_ROOTS, and set storage in your projects' qaboard.yaml (see where is the data saved).

Shared storage

Read how to set up NFS or Samba, and the options for NFS volumes in compose files. In the cloud, use a file storage like AWS EFS or GCP Filestore. Object storage, like S3, is on the roadmap.

3. Describe your site​

A site overlay adds your volumes, settings and nginx configuration to docker-compose.yml, without changing it. Create one in a folder for your site, starting from deployments/example.yml:

deployments/mysite/mysite.yml
services:
  backend:
    volumes:
    # The results storage, at the same path as on the runners
    - /mnt/qaboard:/mnt/qaboard
    environment:
    # The address users open: links in emails, single sign-on redirects
    - QABOARD_URL=http://qaboard.example.com:5151
    # Your user name: you're an admin once you sign in (step 6)
    - QABOARD_ADMINS=alice
  proxy:
    volumes:
    # nginx serves /s/<path> from /var/qaboard/<path>
    - /mnt/qaboard:/var/qaboard/mnt/qaboard:ro
  cantaloupe:
    volumes:
    # The image server reads /iiif/2/<path> from /repository/<path>: each storage root, read-only
    - /mnt/qaboard:/repository/mnt/qaboard:ro
  • The storage is mounted at the same path in the backend, and under /var/qaboard/ in nginx, which serves it at /s/: browsers that open a folder there get QA-Board's file browser. The image server (Cantaloupe) sees only what you mount in it, at the same paths as in nginx.
Upgrading

docker-compose.yml used to mount the host's whole filesystem in the image server. If the image viewers show no images after you upgrade, mount your storage in cantaloupe like above.

  • QABOARD_URL: use https:// only once HTTPS works (below): session cookies are then only sent over HTTPS.
  • Other settings go in services.backend.environment too: see environment variables.

4. Write the env file and the secrets​

deploy.py reads an env file per environment: the compose files, the compose project, and the settings docker compose reads itself. Copy deployments/production.env and add your overlay:

deployments/mysite/production.env
COMPOSE_PROJECT_NAME=qaboard
COMPOSE_FILE=docker-compose.yml:production.yml:deployments/mysite/mysite.yml
QABOARD_BACKEND_REPLICAS=2
QABOARD_UWSGI_PROCESSES=8
QABOARD_UWSGI_CHEAPER=4
QABOARD_UWSGI_CHEAPER_INITIAL=8
# QABOARD_PORT_HTTP=5151

Put the secrets in .env, at the root of the checkout (chmod 600 .env). Generate them with openssl rand -base64 32:

.env
# Push webhooks must send it (step 8)
QABOARD_WEBHOOK_SECRET=...
# Signs sessions. Generated and kept in the backend's data volume if unset: set it to move hosts without signing everyone out
# SECRET_KEY=...
# The database, and the admin services (see below)
QABOARD_DB_PASSWORD=...
PGADMIN_DEFAULT_EMAIL=admin@example.com
PGADMIN_DEFAULT_PASSWORD=...
# Only if Celery workers connect to RabbitMQ (QABOARD_TUNING_RUNNER=celery). URL-safe characters
# QABOARD_RABBITMQ_USER=qaboard
# QABOARD_RABBITMQ_PASSWORD=...
# Optional: Flower (the task queue's UI) also asks for this login. At /flower/, only QA-Board's admins get it
# FLOWER_BASIC_AUTH=admin:...
Where each setting goes
  • .env: secrets. The backend gets all its variables.
  • The env file: what docker compose reads itself: COMPOSE_*, QABOARD_PORT_HTTP, QABOARD_BACKEND_REPLICAS, QABOARD_IMAGE... deploy.py gives it to docker compose, which then doesn't read .env for those.
  • The overlay's services.backend.environment: the other settings. docker-compose.yml sets QABOARD_LOGIN_TYPE, QABOARD_LOGIN_REQUIRED, QABOARD_LOGIN_RESTRICTED, QABOARD_LOGIN_RESTRICTED_YAML, QABOARD_ADMINS and QABOARD_INGEST_AUTH from the env file, which wins over .env: set them in the overlay or in the env file, never in .env.

Passwords and admin services​

deploy.py passes these passwords from .env to docker compose, for the ${...} of the compose files.

  • The database is created with QABOARD_DB_PASSWORD (default: password), and the backend and the backups use it. To change the password of an existing database, see database password.
  • RabbitMQ is created with QABOARD_RABBITMQ_USER and QABOARD_RABBITMQ_PASSWORD (default: guest:guest). Celery workers run the commands of the tasks they get: anyone who can connect to RabbitMQ can run commands on them. For an existing RabbitMQ, add the user with docker compose exec rabbitmq rabbitmqctl add_user and set_permissions, or change the password with rabbitmqctl change_password. For workers on other hosts, publish it with QABOARD_RABBITMQ_HOST_IP=0.0.0.0 in the env file, and give each team its own account (sharing the broker).
  • The admin services are only published on the host itself (127.0.0.1): RabbitMQ (QABOARD_PORT_RABBITMQ, 5672, and its management UI on QABOARD_PORT_RABBITMQ_MNGT, 15672), Flower (QABOARD_PORT_FLOWER, 8888) and pgAdmin (PGADMIN_PORT, 5050). nginx serves Flower at /flower/ to QA-Board's admins only.

5. Deploy​

# The first time: --init allows a new compose project, with an empty database
deployments/deploy.py deployments/mysite/production.env up --version <version> --init

<version> is a release, like 1.2.0. deploy.py pulls its images (ghcr.io/samsung/qaboard:<service>-<version>), runs the database migrations, starts the services, and records the version, so that rollback can come back to it. Without --version, it deploys the latest images of master; with --build, it builds the images from your checkout. Plain docker compose --env-file deployments/mysite/production.env up -d works too, without zero-downtime upgrades.

Check it worked:

deployments/deploy.py deployments/mysite/production.env status
curl -fsS http://localhost:5151/api/v1/health

status lists the containers: all running, and the backend replicas healthy. The health check answers "status": "ok" once the backend reaches its database. Open http://<your-host>:5151: the web app opens, with no projects yet. If something is wrong, see Troubleshooting.

6. Make yourself an admin​

Admins see Admin in the user menu: users, sign-in, settings, and the jobs that clean the storage.

  • The user names in QABOARD_ADMINS (step 3) are admins as soon as they sign in.

  • To sign in before LDAP or single sign-on work, create a local admin account. It asks for the password:

    deployments/deploy.py deployments/mysite/production.env compose exec backend qaboard-admin create-admin admin --password

Check it worked: sign in with Sign in, at the top right, and open Admin. Its Overview has a security checklist of what to look at next. More in User management.

7. Choose how users sign in​

By default, users have local accounts, and anyone can create one from the sign-in page (Create one). Instead:

  • Single sign-on with OpenID Connect (Keycloak, Entra ID, Okta, Google...): see Sign-in and single sign-on.
  • LDAP or SAML: set QABOARD_LOGIN_TYPE and their settings in the overlay, see authentication providers.

Then decide who gets an account, and whether anonymous users see anything.

To apply changes to .env or to the overlay, deploy again: deploy.py <env file> up recreates the backend with them, without downtime. Check it worked: qaboard-admin check-sign-in in the backend's container, or Admin → Sign-in → Test, then sign in.

8. Connect your git hosts​

QA-Board reads your repositories for committers' avatars and each pushed commit's qaboard.yaml, and learns about pushes from webhooks.

  1. Tokens: add them to .env, e.g. GITHUB_ACCESS_TOKEN, or GITLAB_HOST and GITLAB_ACCESS_TOKEN. For other hosts, or several, see Git hosts.
  2. Webhooks: in each repository, send push events to <QABOARD_URL>/webhook/github (or gitlab, gitea, bitbucket), with your QABOARD_WEBHOOK_SECRET: see Connect your git host.

Check it worked: push a commit. The git host shows that the webhook's latest delivery got 200.

9. Save the first results​

On a machine that mounts the results storage at the same path as the server, e.g. a CI runner, install qa and point it to the server:

pip install qaboard
export QABOARD_URL=http://qaboard.example.com:5151

In a project wrapped with qa, qa --share batch <batch> saves the results and prints a link to them: Your project on QA-Board walks through it. Check it worked: the link opens the commit page with your runs and their output files.

10. Secure the server​

Before you open it to your team:

  • Serve it over HTTPS (below), with QABOARD_URL=https://....
  • Require tokens to send results: by default, anyone who can reach the server can send results. Move ingest.auth from off to warn to token once your CI jobs have tokens (results sent by qa).
  • Set QABOARD_WEBHOOK_SECRET (step 4), and the same secret in your webhooks: without it, anyone can send fake push events.
  • Turn off local sign-up (auth.local_signup) if only admins create accounts, and require signing in if anonymous users shouldn't see results.
  • Set the passwords of the database and the admin services (step 4), and only expose QA-Board to networks you trust.
  • Sandbox the runs' HTML files: by default, the HTML and SVG files of runs run their scripts as whoever opens them. Set QABOARD_SANDBOX_HTML=true once your users know (HTML reports).

The security checklist in Admin → Overview checks the sign-in, token and HTTPS settings. SECURITY.md lists the known issues and their mitigations.

HTTPS and reverse proxies​

Use your own copy of services/nginx/conf.d/qaboard.conf in the site overlay (keep its include snippets/... lines: they serve the files and the file browser). Files mounted under /tmp/deployment/nginx/conf.d/ in the proxy container are added to (or replace) services/nginx/conf.d/:

deployments/mysite/nginx/qaboard.conf (copied from services/nginx/conf.d/qaboard.conf)
server {
  # ...
  listen 443 ssl;
  ssl_certificate_key /ssl/cert.key;
  ssl_certificate /ssl/cert.pem;
  # ...
}

Mount it, and the key and certificate:

deployments/mysite/mysite.yml
services:
  proxy:
    ports:
    - "443:443"
    volumes:
    - "./deployments/mysite/nginx/qaboard.conf:/tmp/deployment/nginx/conf.d/qaboard.conf:ro"
    - "somewhere/cert.key:/ssl/cert.key"
    - "somewhere/cert.pem:/ssl/cert.pem"

Then set QABOARD_URL=https://..., and deploy again.

Getting a certificate from your IT

Generate a key and a certificate signing request (CSR), and send the CSR to your IT:

openssl genrsa -out cert.key 2048
openssl req -new -sha256 -key cert.key -out cert.csr

If they send back a .cer certificate in the DER format, convert it to PEM: openssl x509 -in cert.cer -inform der -outform pem -out cert.pem.

To use your own reverse proxy instead, e.g. nginx, set QABOARD_PORT_HTTP=8080 in the env file and the config below. QA-Board's nginx passes the X-Forwarded-Proto and X-Forwarded-Host headers your proxy sets to the backend (the single sign-on redirects need them), else its own:

server {
  listen 80;
  server_name default_server;
  location / {
    proxy_pass http://localhost:8080/;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host $http_host;
  }
}

Behind your proxy, a load balancer or an ingress, set QABOARD_TRUSTED_PROXY_HOPS=1, so that the audit log records users' IPs (see rate limits and proxies).

Run it day to day​

  • Upgrade: read the release notes ("Before you upgrade"), check out the new release, then deploy.py <env file> up --version <version>. If it goes wrong, rollback: see Upgrades and rollbacks.
  • Back up the database, and test a restore: see Backups.
  • Free disk space in the results storage: see Cleanup.
  • Follow errors in Sentry (monitoring), and the runs stuck as running in Runs activity.

Backups​

The cron-backup-db service in production.yml makes daily backups of the database to /backups, and keeps those of the last 14 days (QABOARD_BACKUP_RETENTION_DAYS). Mount a host directory there, in the db service too (restore-db reads the backups from it), and copy the backups off the host. Without it, the backups fail.

deployments/mysite/mysite.yml
services:
  cron-backup-db:
    volumes:
    - /srv/qaboard/backups:/backups
  db:
    volumes:
    - /srv/qaboard/backups:/backups

To restore one: deployments/deploy.py <env file> restore-db <file>.dump. See Backups.

Cleanup​

Schedule the cleanup in Admin → Storage: delete old results as each project's qaboard.yaml says, delete for good the runs users deleted, delete old artifacts, with each run's log and errors. See cleaning the storage.

Or use cron jobs on the host:

# Weekly cleanup of old results, on Saturdays
# https://samsung.github.io/qaboard/docs/storage/deleting-old-data
59 1 * * 6 cd qaboard && docker compose --env-file deployments/mysite/production.env exec -T backend qaboard_clean

# Weekly removal of unused docker images, on Sundays, so that they don't fill the disk
59 1 * * 0 docker image prune --force

qaboard_clean --help lists the command's options.

  • Upgrades and rollbacks

    Zero-downtime deploys, rollbacks, backups and restores, a staging copy, PostgreSQL settings.

  • Project access and roles

    Owners, private projects, groups from your directory or identity provider.

  • Cleaning the storage

    Delete old results and what users deleted, find what QA-Board doesn't track, on a schedule.

  • Troubleshooting

    Logs, restarts, a full disk.

Problems starting a server? Create an issue. For development, read the READMEs of the backend and the frontend.

Emails​

QA-Board can email users when the batches they start end, from the web app or with qa --share batch (what users get). Once the backend has an SMTP server, everyone gets them, except in CI. Users turn them off in the terminal with QA_NOTIFY=none. Configure it in your overlay, and the SMTP password, if any, in .env:

deployments/mysite/mysite.yml
services:
  backend:
    environment:
    - QABOARD_SMTP_HOST=smtp.example.com
    - QABOARD_EMAIL_FROM=QA-Board <qaboard-noreply@example.com>
    - QABOARD_EMAIL_REPLY_TO=qaboard-support@example.com
    # Users without an email address in their account get emails at <username>@example.com
    - QABOARD_EMAIL_DOMAIN=example.com
    - QABOARD_URL=https://qaboard.example.com
  • The emails are designed for Outlook 2016/2019 as well as recent clients, in HTML with a plain text version. They are marked as automated (Auto-Submitted), so out-of-office replies aren't sent back, and have X-QABoard-Project, X-QABoard-Batch and X-QABoard-Status headers for mail rules.
  • They're sent by the backend when it saves the last run of a batch. If the SMTP server fails, the error is in the backend's logs and in the batch_notifications table, and the run is saved anyway.
  • To check how they look, or test your SMTP settings, run uv run backend/backend/notifications/preview.py: it renders examples, and --send you@example.com emails them to you.
  • Like results, the requests to email users when their qa batch ends come from the CLI without a login: anyone who can reach the server could have QA-Board email a user about a batch. QA-Board only emails the address of the user's account (or <username>@$QABOARD_EMAIL_DOMAIN), and at most once per qa batch.
