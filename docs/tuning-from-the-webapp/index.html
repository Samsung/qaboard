Starting tuning experiments from QA-Board

How to do tuning or trigger extra runs from QA-Board​

When doing QA or during development, you often want to run the code/configs from a given commit on new tests. QA-Board lets you define and runs batches of tests with extra tuning parameters:

When the batch doesn't start​

QA-Board starts your batch by running qa batch (as an LSF job, with Celery, or locally on the server). If it fails or takes a while, there are no runs to look at, so the batch's page tells you what's going on:

  • Waiting for LSF: the job is queued, the cluster may be busy.
  • Starting your batch…: qa batch is running.
  • Failed: why, e.g. qa batch exited with code 1 with the error from its logs (ModuleNotFoundError: ...), or why LSF killed it (out of memory...).
  • Didn't start any run: e.g. there were no inputs, or all the runs already existed.

In the Logs view, Started from QA-Board lists the last batches you started, each with the qa batch command, its logs and LSF's report. They are saved in the batch directory, under qaboard-batches/.

Enabling tuning from QA-Board​

note

Tuning parameters that will be merged into context.params and appended to context.configs: in most cases you don't have to do anything special

1. Build artifacts​

You must have defined and be using artifacts

2. Distributed task queue​

You need to configure a task runner, that will execute tuning runs asynchronously. QA-Board ships with a celery integration so you'll just have to register a "worker" to get started. Read more here!

The QA-Board server starts tuning runs with the runner chosen by its QABOARD_TUNING_RUNNER environment variable: local (default, on the server itself), celery or lsf (via QA_RUNNERS_LSF_BRIDGE). See the server's environment variables.

3. Logged-in users​

Starting tuning experiments requires a logged-in user, and runs are started as that user. See user management.

Tips for users​

How to start runs is described in the user guide. A few shortcuts:

  • To start from an existing run's parameters, hover its configuration tags and choose Copy full config in tuning format, then paste it in the manual tuning editor.
  • Pasting lines of key=value in the manual tuning editor converts them to the tuning format: block.threshold=10 becomes "block.threshold": [10], and space-separated matrices like [1 2 3] become JSON arrays.
  • In the Available Tests view, where you can define your own batches, Ctrl+S (or Cmd+S) saves the batches file you are editing.
  • Once runs are done, the Analysis view (selected_views=optimization) shows the tuning exploration plots: sensitivity to each parameter and to pairs of parameters (box plots, contours), a parallel coordinates plot, the trade-off between two metrics, and for qa optimize experiments the best parameters and the convergence. See the user guide.
