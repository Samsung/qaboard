Coming from another tool

You already run evaluations at scale: MLflow Projects on Kubernetes, W&B Launch, ClearML agents, job arrays on Slurm or LSF, Kubernetes Jobs, CI matrices. This page maps what you have to qaboard.yaml, tool by tool, so your batches run on the same compute. What you gain: every commit's results compared with your reference branch, input by input, with viewers for images, videos, plots and reports, and tuning from the web app.

Jump to your tool: MLflow Projects, W&B Launch, ClearML Agent, Slurm and LSF job arrays, Kubernetes Jobs, Argo and Kueue, Ray and Dask, CI matrices.

Wrap your evaluation once​

Whatever tool you come from, the first two steps are the same. Say your evaluation is eval.py, which evaluates a model on a slice of your test set:

  1. Call it from run(), in qa/main.py. qa calls run() once per input and configuration, with where to write the outputs, and records the metrics it returns:

    qa/main.py
    import json
    import subprocess


    def run(context):
        model = "int8" if "int8" in context.configs else "fp32"
        command = ["python", "eval.py", "--model", model, "--slice", str(context.input_path),
                   "--output", str(context.output_dir)]
        # Tuning parameters, e.g. {"score_threshold": 0.3} from the web app
        for name, value in context.params.items():
            command += [f"--{name.replace('_', '-')}", str(value)]
        process = subprocess.run(command, stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True)
        print(process.stdout)  # saved in the run's log
        if process.returncode != 0:
            return {"is_failed": True}
        metrics = json.loads((context.output_dir / "metrics.json").read_text())
        return {**metrics, "is_failed": False}

  2. List what to run in a batch, instead of a list of jobs, an array or a matrix:

    qa/batches.yaml
    ci:
      inputs:
      - slices/indoor
      - slices/outdoor
      - slices/warehouse
      - slices/small-objects
      configs: ['${matrix.model}']
      matrix:
        model: [fp32, int8]

  3. Pick the runner that sends the runs where your tool sent them: the sections below.

  4. Run it: qa --share batch ci. The 8 runs execute on your compute, and qa prints the link to their results.

qa init creates qaboard.yaml and qa/: see Set up a project, and Run your code for run().

MLflow Projects on Kubernetes​

You have an MLproject file, and you run it as Kubernetes Jobs with mlflow run . --backend kubernetes --backend-config kubernetes_config.json -P slice=slices/indoor. MLflow builds an image with your project, pushes it to repository-uri, and creates a Job from your template:

MLproject
name: detector-eval
docker_env:
  image: registry.kitefin.example/algo/eval-env:2026.11
entry_points:
  main:
    parameters:
      slice: path
      model: {type: string, default: fp32}
    command: "python eval.py --model {model} --slice {slice}"
kubernetes_config.json
{
  "kube-context": "my-cluster",
  "repository-uri": "registry.kitefin.example/algo/detector-eval",
  "kube-job-template-path": "kubernetes_job_template.yaml"
}

In QA-Board, the entry point's command goes in run(), each -P combination is a run of a batch, and the backend configuration becomes the kubernetes runner's settings:

qaboard.yaml
runners:
  default: kubernetes
  kubernetes:
    context: my-cluster                                   # kube-context
    image: registry.kitefin.example/algo/eval-env:2026.11 # docker_env.image: it isn't rebuilt
    job_template: k8s/eval-job.yaml                        # your Job template, without the placeholders
    mounts:
      - path: /mnt/qaboard
        pvc: qaboard-results

What differs: QA-Board doesn't build or push an image per run. Pods use your image for the dependencies, and read your code and inputs from the shared storage. Remove the {replaced-with-...} placeholders from your template: QA-Board sets the name, image and command. Your environment variables reach the pods, but not secrets like MLFLOW_TRACKING_TOKEN: add them to the template from a Secret, see give the runs a token. MLflow's tracking stays useful for training; QA-Board compares the outputs of every input, commit after commit.

W&B Launch​

You have a launch queue whose configuration is a Kubernetes Job spec, with variables like ${image_uri}, a launch agent in the cluster (the launch-agent Helm chart, or wandb launch-agent -q <queue> -j <max-jobs>), and you push jobs with wandb launch -j <job> -q <queue> -c config.json.

In QA-Board:

W&B LaunchQA-Board
The queue's Job specrunners.kubernetes.job_template, and settings like resources, node_selector, tolerations
The queueThe runner, its namespace, and a Kueue queue
The agent's max_jobsconcurrency
resource_args in a launch configRunner settings per batch
wandb launch -q <queue>qa --share batch <batch>, or Run Tests / Tuning in the web app
SweepsBatches with a matrix, tuning from the web app, qa optimize

What differs: there is no agent. qa batch creates the Jobs with your kubeconfig, so users need permissions in a namespace: see Run batches on Kubernetes. People without them start batches from the web app: the QA-Board server starts qa batch in a pod of the namespace, as them, and that pod creates the Jobs with a ServiceAccount the admins set up, see Run batches from the web app. Like a launch queue, a namespace is shared by a team: its users trust each other. Launch builds images from your code; QA-Board uses one image and the shared storage.

ClearML Agent​

You have agents on your GPU machines (clearml-agent daemon --queue default --docker --gpus 0), or the ClearML Kubernetes glue that turns queued tasks into pods from a template. You enqueue tasks from the ClearML UI, or with clearml-task --project <project> --name <name> --script eval.py --queue default --args model=int8.

In QA-Board:

  • Agents on your machines become Celery workers, listening to a queue, e.g. one run at a time on each GPU machine:

    celery -A qaboard.runners.celery_app worker --concurrency=1 --queues gpu
    qaboard.yaml
    runners:
      default: celery
      celery:
        broker_url: pyamqp://camera:${QA_CELERY_PASSWORD}@<your-qaboard-host>:5672/camera
        task_routes:
          qaboard: gpu

    <your-qaboard-host> is your QA-Board server, whose RabbitMQ can give each team its own account, camera here: see sharing the broker. Unlike an agent's tasks, the runs get the environment of qa batch, without its secrets, not the worker's.

  • The Kubernetes glue becomes the kubernetes runner, with your pod template as job_template.

  • Enqueuing from the UI, cloning a task and editing its hyperparameters becomes Run Tests / Tuning on a commit page: pick a batch, write the parameters to try, start. See Running from the web app.

What differs: a ClearML agent clones your repository and installs its requirements for each task. QA-Board runs in an environment you prepared: the commit's artifacts, like your build, on the shared storage, and its .envrc or your image.

Slurm and LSF job arrays​

You have a job array script, with a list of inputs and a limit on how many run at once:

eval.sbatch
#!/bin/bash
#SBATCH --array=0-99%20
#SBATCH --cpus-per-task=4
#SBATCH --mem=16G
INPUT=$(sed -n "$((SLURM_ARRAY_TASK_ID + 1))p" inputs.txt)
python eval.py --model int8 --slice "$INPUT" --output "results/$SLURM_ARRAY_TASK_ID"

On LSF, the same with bsub -J "eval[1-100]%20" and $LSB_JOBINDEX.

In QA-Board, inputs.txt becomes a batch, %20 becomes concurrency, and qa names the output folders:

  • LSF
  • Slurm

The LSF runner sends job arrays itself, with the same slot limit:

qaboard.yaml
runners:
  default: lsf
  lsf:
    queue: <your-queue>
    concurrency: 20
    max_threads: 4
    max_memory: 16000  # MB

The Dask runner starts a few workers as Slurm jobs, and keeps 20 runs in flight on them:

qaboard.yaml
runners:
  default: dask
  dask:
    concurrency: 20
    cluster:
      type: slurm
      queue: <your-partition>
      cores: 4       # runs per worker job
      memory: 64GB   # per worker job: for its 4 runs
      walltime: "08:00:00"

What you gain: no index arithmetic or output naming; failed runs you redo from the web app; LSF's reason for killing a run, like its memory limit, shown next to its log. What differs on Slurm: each Slurm job is a Dask worker that does several runs, not one run: size its memory for cores runs at once.

Kubernetes Jobs, Argo Workflows and Kueue​

You have an Indexed Job whose pods pick their input from $JOB_COMPLETION_INDEX, an Argo Workflow that fans out with withItems or withParam, or Jobs labeled with kueue.x-k8s.io/queue-name to wait in a Kueue queue.

In QA-Board, the kubernetes runner creates the same Indexed Jobs for you:

Your Job or workflowqaboard.yaml
completions, the list of inputsThe batch
parallelism, Argo's parallelismconcurrency
Your Job's YAMLjob_template, merged under what QA-Board generates
volumes and volumeMountsmounts
kueue.x-k8s.io/queue-namequeue
priorityClassName, nodeSelector, tolerations, resourcespriority_class, node_selector, tolerations, resources
securityContext.runAsUserrun_as: user, your UID by default

Keep Argo for what it does well, like build, then test, then deploy: run qa batch ci in the test step, from a pod that mounts the storage. qa then uses the pod's ServiceAccount to create the runs' Jobs: bind it to the runner's Role. The runner needs Kubernetes 1.29 or later.

Ray and Dask​

You have a Dask cluster and client.map(evaluate, inputs), or Ray tasks (@ray.remote) that evaluate each input.

In QA-Board, the Dask runner sends the runs to your scheduler, at most concurrency at a time:

qaboard.yaml
runners:
  default: dask
  dask:
    scheduler_address: tcp://<your-scheduler>:8786
    concurrency: 20

Or let qa batch start the Dask workers itself, on your HPC scheduler or on Kubernetes: see Dask on HPC schedulers.

What differs: there is no Ray runner. On a Ray cluster on Kubernetes, use the kubernetes runner on the same nodes, or keep Ray inside run(), for the parallelism of one run.

CI matrices​

You have a CI job per combination, with a matrix:

  • GitHub Actions
  • GitLab CI
.github/workflows/evaluate.yml
# An evaluation fanned out with a CI matrix: one CI job per model and slice of the test set.
# docs/coming-from-other-tools.mdx shows how the matrix moves to a QA-Board batch.
name: Evaluate
on: push
permissions:
  contents: read

jobs:
  evaluate:
    runs-on: [self-hosted, linux]
    strategy:
      max-parallel: 4
      matrix:
        model: [fp32, int8]
        slice: [indoor, outdoor, warehouse, small-objects]
    steps:
      - uses: actions/checkout@v4
      - run: python eval.py --model "${{ matrix.model }}" --slice "slices/${{ matrix.slice }}"

Not run in our CI: adapt it to your setup.

.gitlab-ci.yml
# An evaluation fanned out with a CI matrix: one CI job per model and slice of the test set.
# docs/coming-from-other-tools.mdx shows how the matrix moves to a QA-Board batch.
evaluate:
  tags: [gpu]
  parallel:
    matrix:
      - MODEL: [fp32, int8]
        SLICE: [indoor, outdoor, warehouse, small-objects]
  script:
    - python eval.py --model "$MODEL" --slice "slices/$SLICE"

Not run in our CI: adapt it to your setup.

In QA-Board, the matrix moves to the batch, as above, and one CI job runs qa batch ci: the runner fans the runs out to your cluster, and the CI job waits for them. The CI keeps doing what it's for: building, and starting the evaluation on every push. See CI integration.

What you gain: one CI job instead of one per combination; every commit's results compared with the reference branch's, and shown on the commit page; a CI that fails when metrics regress, with the quality gate (experimental).

What differs from all of them​

Compared in November 2026, with the tools' public docs.

  • A shared storage, at the same paths. The machines that run your code read it, and your inputs, from a shared storage, and write their outputs there. QA-Board doesn't build an image for each run or copy your code: it runs a commit's artifacts. Clusters without a shared storage can't run batches yet: see the roadmap.
  • Your cluster's scheduler, not a queue of its own. QA-Board sends the runs to LSF, Slurm, Kubernetes or Celery, and leaves the quotas and priorities to them, e.g. to Kueue. W&B Launch and ClearML have queues served by their agents.
  • Results of each input, for each commit. Tracking tools excel at logging a training run's metrics as it goes. QA-Board compares the final metrics and output files of every input, between commits, branches and experiments, with viewers for images, videos, point clouds and reports.
