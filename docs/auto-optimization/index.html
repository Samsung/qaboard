Automated tuning with qa optimize

Experimental
Experimental

qa optimize and its configuration file may change without notice: the keys of the file, the objective's options, and the solver, which may move from scikit-optimize to another library or offer several.

qa optimize searches the parameters that optimize your metrics: it runs a batch with parameters chosen by an optimizer (scikit-optimize, installed with qaboard), reads the metrics, picks the next parameters, and so on, for the number of evaluations you give it.

On the detector, the int8 model still lost 7% of its AP on small objects against fp32, after a better calibration. An automated tuning searched the quantization and post-processing settings, 20 evaluations on the two slices where quantization hurts most, and the Tuning Analysis view showed which settings mattered:

Run an automated tuning​

  1. Describe the search in a YAML file: how many evaluations, the parameters and their ranges, and the objective, built from your metrics. The detector's:

    qa/tune-int8.yaml
    # Search space and objective for tuning the int8 model with `qa optimize` (scikit-optimize):
    #   qa --label tune-int8 optimize --batch quant-search --config-file qa/tune-int8.yaml --checkpoint tune-int8.pkl
    # Each evaluation runs the quant-search batch (int8 at 320 px on the outdoor and small-objects slices) with the
    # parameters as tuning parameters: qa/main.py uses them over its flags.
    evaluations: 20
    solver:
      random_state: 42
      n_initial_points: 8

    # Maximize AP on small objects and mAP (means over the batch's runs), and keep the model small: nodes left in fp32
    # make it bigger. 0.005 per MB: 2 MB more must win 0.01 of AP.
    objective:
      ap_small:
        weight: 1
        reduce: sum
        loss: identity
      map:
        weight: 1
        reduce: sum
        loss: identity
      model_mb:
        weight: 0.005
        reduce: sum
        loss: identity

    search_space:
      - Categorical:
          name: quant_percentile
          categories: [99.9, 99.99, 99.999]
      - Categorical:
          name: quant_keep_fp32
          categories: [none, first-conv, head, first-conv+head]
      - Real:
          name: score_threshold   # below 0.2, the K3 brakes for shadows
          low: 0.2
          high: 0.45
      - Real:
          name: nms_iou
          low: 0.4
          high: 0.7

    Source: examples/detection-eval/qa/tune-int8.yaml

  2. Start it, on a batch of tests:

    qa --share --label tune-int8 optimize --batch quant-search --config-file qa/tune-int8.yaml --checkpoint tune-int8.pkl

    Each evaluation runs qa batch with the label tune-int8|iterN and the chosen parameters as tuning parameters, which your code reads like any other (see how parameters reach your code). qa optimize reads each evaluation's metrics from QA-Board: from your computer, --share saves the runs there, as the CI does.

  3. Look at the results. On the commit page, select the experiment's batch, tune-int8, then the Tuning Analysis view: the best parameters found, every iteration, and the convergence of the objective. The batch holds the runs of the best iteration so far.

From the web app, the Automated tuning tab of Run Tests / Tuning starts the same thing on a commit's code. It shows a commented template of the configuration file:

The objective​

qa optimize minimizes the objective. For each metric under objective, it computes a loss on each run, reduces the losses over the batch's runs, divides by the number of runs, and adds the results, each multiplied by its weight. Failed runs are left out.

KeyDefaultMeaning
weight1How much the metric counts.
lossidentityThe loss of one run: identity (the metric's value), shift (minus its target), relative (minus its target, divided by its target). Prefix relu_ to only count values worse than the target (relu_shift, with an optional margin), or square_ to square it.
reducesumHow runs' losses combine: sum (their mean, once divided by the number of runs), relu (the sum, if it's positive), or l1, l2 (norms).

Which way is better comes from each metric's smaller_is_better in your metrics file: metrics where bigger is better count negatively, and metrics without smaller_is_better are "smaller is better". Metrics that aren't in the metrics file, or have smaller_is_better: null, stop the optimization with an error. With shift or relative losses, the target is the metric's target in your metrics file, or, with an objective.target section, the value of the matching run of a reference:

qa/tune.yaml
objective:
  ap_small:
    loss: shift
  target:
    branch: main     # or `id:` a commit
    batch: default   # the reference's batch

The search space​

search_space lists the parameters, in scikit-optimize's syntax: Integer and Real with low and high (and prior: log-uniform for scales like a learning rate), Categorical with categories. preset_params gives parameters a fixed value for every evaluation.

Options​

  • evaluations: how many times to run the batch.
  • solver: the optimizer's settings, passed to scikit-optimize's Optimizer, like n_initial_points (random evaluations before it models the objective) or random_state.
  • --checkpoint: the optimizer's state is saved there after each evaluation, and loaded if it exists, to restart an interrupted optimization.
  • parallel_sampling in the configuration file, or --parallel-param-sampling: how many parameter sets are evaluated at the same time (default 1).
  • keep_all_best_iters: true: by default, the runs of the previous best iteration are deleted when a better one is found. Use it to keep them.
  • QA_SEED: the random seed (default 101), for reproducible optimizations.

Iterations that aren't the best so far have their output files deleted: their parameters and objective stay, for the plots. During the optimization, qa sets QA_OPTIM_DIR to the experiment's batch directory, where it saves a convergence plot (plot_convergence.png) if matplotlib is installed.

To try parameters you choose yourself, a grid or a sample, see tuning from the web app or qa batch --tuning-search.
