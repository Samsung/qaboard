Settings and secrets

Admins change how the server works in Admin → Settings, without a deploy: sign-in, git hosts and their tokens, Jenkins servers, email, what the web app shows. Changes apply to every replica within a few seconds, are audited, and live in the database, so they're in its backups.

Change a setting​

Settings are grouped by what they're about: Sign-in, Git hosts, Jenkins, Email, Security... Search them by name, description or environment variable (press /), or show only those Changed, From the environment, the Secrets, or what Needs attention. The search and filter are in the URL, and /admin/settings?setting=email.smtp_host links to a setting.

  • Switches and choices save at once, and the toast offers to Undo.
  • Texts, numbers and lists show Save and Cancel once you change them. Enter saves, Esc cancels.
  • Lists of servers, like the Jenkins servers or the git hosts, are edited in a dialog, one at a time.
  • Reset to default deletes what's saved: the default applies again.

Where a value comes from​

Each setting has three layers, and the first one set wins:

  1. Environment: the setting's environment variable, e.g. QABOARD_INGEST_AUTH. The page shows it read-only: change it where the server is deployed. An invalid value is ignored, and the page and the security checklist say why.
  2. Saved here: what admins saved in the database, from this page or qaboard-admin settings set.
  3. Default: some depend on something else, e.g. local sign-up is on with QABOARD_LOGIN_TYPE=LOCAL, and the page says so.

Click a setting's badge (Default, Saved here, Environment) to see what each layer says, who saved the value and when.

Move a setting from the environment to the database​

Settings that used to need an environment variable, sometimes as JSON (JENKINS_AUTH, GITLAB_AUTH, QABOARD_GIT_HOSTS...), are easier to manage here. For each one the environment still sets:

  1. Click Save it here: the server copies the environment's value to the database, secrets encrypted.
  2. The page says The same value is saved here. Remove the variable from the server's environment (.env, your site overlay, the Helm values) and redeploy.

The setting now shows Saved here, and you change it from the page.

Secrets and the encryption key​

Tokens and passwords (the Jenkins API tokens, git host tokens, webhook secrets, the SMTP password, sign-in providers' client secrets...) are encrypted before they're saved, and never sent back to the browser: the page says Set, and you can only replace or clear them. The audit log records that they changed, never their value.

They're encrypted with the server's encryption key, that is never stored in the database: a dump, a backup or a staging copy of the database would otherwise hold both the secrets and what decrypts them. The server takes, in this order:

  1. QABOARD_ENCRYPTION_KEY: any long random text, e.g. from openssl rand -base64 32. Recommended, and needed when the replicas don't share a data folder.
  2. QABOARD_ENCRYPTION_KEY_FILE: a file holding the key, e.g. a Docker or Kubernetes secret mounted as a file.
  3. Else, a key it generates the first time a secret is saved, in its data folder ($QABOARD_DATA_DIR/encryption_key, readable only by the server), like the generated SECRET_KEY. Nothing to configure, but you must back it up.

Security → Encryption of the stored secrets shows the key's fingerprint (it identifies the key without revealing it), where it comes from, and how many secrets it decrypts. The Helm chart generates QABOARD_ENCRYPTION_KEY once and keeps it across upgrades.

Back up the key​

Database backups don't include the key: keep a copy apart from them, in your secret store. If the server generated it, print it from the server's shell and save it as QABOARD_ENCRYPTION_KEY:

docker compose exec backend qaboard-admin encryption show-key

When the key changes or is lost​

Every stored secret says which key encrypted it. When the server's key can't decrypt some of them (a restore on another server, a new key without the old one), QA-Board uses their defaults, and the page, the security checklist and qaboard-admin encryption status list them: restore the key, or enter them again.

A server that generated its own key never encrypts new secrets while the database holds secrets it can't decrypt: that's what happens when replicas don't share their data folder, and each would encrypt with its own key. It asks you to set QABOARD_ENCRYPTION_KEY on every replica instead.

Change the key​

  1. Set the new key in QABOARD_ENCRYPTION_KEY, and the old one in QABOARD_ENCRYPTION_KEY_PREVIOUS. Deploy: every secret still decrypts. The generated key, if there was one, always decrypts too: moving it to QABOARD_ENCRYPTION_KEY needs no other step.
  2. Click Re-encrypt in Security, or run qaboard-admin encryption rotate.
  3. Remove QABOARD_ENCRYPTION_KEY_PREVIOUS.

Secrets saved before they were encrypted (the access requests webhook of older versions) are encrypted the same way.

From the command line​

qaboard-admin, in the backend's container, reads and changes the same settings, audited as done by qaboard-admin:

qaboard-admin settings list --changed            # where each value comes from
qaboard-admin settings set ingest.auth warn
qaboard-admin settings set jenkins.build_token   # secrets are read from the terminal or stdin
qaboard-admin settings reset ingest.auth
qaboard-admin settings export > settings.json    # e.g. to copy them to a staging server
qaboard-admin settings import settings.json
qaboard-admin encryption status

settings export leaves the secrets out. With --include-secrets it exports them encrypted: they can only be imported on a server with the same key.

What only the environment sets​

Some settings are needed before the server reaches its database (the database itself, QABOARD_URL, QABOARD_DATA_DIR), or are security boundaries that someone who takes over an admin's session must not be able to move: the storage roots, the admins of QABOARD_ADMINS, the commands the server runs, SECRET_KEY and the encryption key. The page shows them read-only, in their group, with why: see the environment variables.
