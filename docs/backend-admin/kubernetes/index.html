Running QA-Board on Kubernetes

QA-Board has a Helm chart. Each release publishes it at oci://ghcr.io/samsung/charts/qaboard, with images built and tested by CI (ghcr.io/samsung/qaboard). The chart's source is in charts/qaboard, and helm show values oci://ghcr.io/samsung/charts/qaboard lists all its settings, with comments.

Quickstart on your laptop (kind)​

You need docker, kind, kubectl and helm (3.8 or later; with helm 4, avoid 4.2.1: it waits out the whole --timeout after running the chart's migrations, see helm#32214). Then:

git clone https://github.com/Samsung/qaboard.git
cd qaboard
mkdir -p /tmp/qaboard
kind create cluster --name qaboard --config charts/qaboard/kind.yaml
helm install qaboard charts/qaboard -f charts/qaboard/quickstart.yaml --wait --timeout 15m
kubectl port-forward svc/qaboard-proxy 5151:80

Open http://localhost:5151. The first install downloads QA-Board's images, which can take a few minutes.

Tested in CI

GitHub CI runs these same commands on every commit (the helm-e2e job), with the images it just built. Then it checks the demo data (a small test project) through the API and in a browser, runs a qa batch in the cluster, checks its results through the web server, and upgrades the release.

What quickstart.yaml sets up: a PostgreSQL pod, one replica of each service, the Cantaloupe image server, no ingress (hence the port-forward), the results storage in /tmp/qaboard, and the docs' demo projects (demoData). Before the backend first starts, an init container restores their database, unless it already has QA-Board's tables, and their results, in a volume of their own mounted at /mnt/qaboard, the path their database has. Without demoData, the projects list is empty until you save results.

Save results from your laptop​

The qa CLI saves results in a folder, and tells the server where they are: the server must see them at the same absolute path. kind.yaml shares your computer's /tmp/qaboard with the cluster at the same path, and the chart mounts it in QA-Board's pods. Point the CLI to the server and to this folder:

uv tool install qaboard   # or: pip install qaboard
export QABOARD_URL=http://localhost:5151
qaboard.yaml
storage: /tmp/qaboard

Then run qa --share batch ... (or qa batch in CI) in your project, and open the link it prints.

tip

/tmp/qaboard works on Linux and macOS without sudo, but your system may clean /tmp. To keep results elsewhere, change the path in kind.yaml (both hostPath and containerPath), in quickstart.yaml (results.mountPath and results.hostPath.path), and in your qaboard.yaml. Create the folder before the cluster: otherwise docker creates it, owned by root.

You can also run qa inside the cluster: the backend image ships the CLI. Mount the results volume at the same path, like CI does in .github/scripts/helm_e2e.py.

Other local clusters​

Any cluster works if its node sees the results folder at the same path as your computer (not tested in CI):

  • k3d: k3d cluster create qaboard --volume /tmp/qaboard:/tmp/qaboard
  • minikube: minikube start --mount --mount-string=/tmp/qaboard:/tmp/qaboard

Then run the same helm install and kubectl port-forward commands.

Clean up​

kind delete cluster --name qaboard

On a real cluster​

helm install qaboard oci://ghcr.io/samsung/charts/qaboard \
     --namespace qaboard --create-namespace -f my-values.yaml --wait --timeout 15m
  • Versions: helm installs the latest release, --version picks another one. The chart has QA-Board's version and installs that release's images: the chart 1.2.0 runs ghcr.io/samsung/qaboard:backend-1.2.0... Each commit on master also publishes a development version, like 1.2.1-dev.42: helm only installs them with --devel or an explicit --version.
  • Images: image.version picks other images, e.g. a commit (1a2b3c4d) or latest (the latest master). To use a mirror, set image.repository and imagePullSecrets. Forks of the repository publish their own images and chart, at ghcr.io/<owner>/qaboard and oci://ghcr.io/<owner>/charts/qaboard.
  • Settings: config sets the backend's environment variables, secret its secrets (SECRET_KEY, QABOARD_DB_PASSWORD, the git hosts' tokens: GITLAB_ACCESS_TOKEN, GITHUB_ACCESS_TOKEN and the variables named by token_env and webhook_secret_env in QABOARD_GIT_HOSTS, QABOARD_WEBHOOK_SECRET, LDAP credentials...). Prefer creating the secret yourself (e.g. with external-secrets) and referencing it with secret.existingSecret. SECRET_KEY signs sessions: keep it when you migrate, or everyone is logged out.
  • Migrations: the migrations Job gets config too: data migrations need e.g. the git hosts, so give QABOARD_GIT_HOSTS in config as JSON, not as the path to a file the Job doesn't mount.

Results storage​

Runs save their results (outputs and artifacts) in a shared storage, and tell the server where. Everything must see this storage at the same absolute path: the server, and the runners (CI runners, LSF or Celery workers, laptops). The chart's results mounts it in the backend (at results.mountPath), in nginx (which serves it under /s/) and in Cantaloupe (which reads the images). It also sets QABOARD_STORAGE_ROOTS: the backend only writes, deletes or runs code there.

Your runners must mount the same storage, so use a file storage that both the cluster and the runners can mount, with ReadWriteMany access:

StorageValues
An NFS serverresults.nfs: {server: nas.example.com, path: /exports/qaboard}
AWS EFSresults.storageClass: a StorageClass of the EFS CSI driver (e.g. efs-sc), or results.nfs with the file system's DNS name
Google Cloud Filestoreresults.storageClass: standard-rwx (GKE's Filestore CSI driver)
Azure Filesresults.storageClass: azurefile-csi (built into AKS)
Nodes that mount the storage themselvesresults.hostPath: {path: /mnt/qaboard}
my-values.yaml
results:
  enabled: true
  mountPath: /mnt/qaboard
  nfs: {server: nas.example.com, path: /exports/qaboard}

With a storage class, the chart creates a PersistentVolumeClaim (results.size, results.accessMode), and the storage provisions a new share for it: runners outside the cluster must mount that share. To use a share you already have, set results.nfs, or create the claim yourself and set results.existingClaim. Uninstalling the release never deletes the claim.

Your projects must save their results under mountPath: set storage in their qaboard.yaml. Other storage can still be mounted with backend.extraVolumes/extraVolumeMounts (and the same for proxy and cantaloupe): add it to config.QABOARD_STORAGE_ROOTS, and mount it at /var/qaboard/<path> in the proxy, /repository/<path> in Cantaloupe.

The backend also needs a volume for its own data (git clones, caches), backend.data. With several replicas, it must be ReadWriteMany too.

Database​

  • CloudNativePG (recommended): database.cnpg.enabled: true creates a PostgreSQL cluster with a primary, replicas and automatic failover. It needs the CloudNativePG operator in the cluster: 
    helm repo add cnpg https://cloudnative-pg.github.io/charts
    helm upgrade --install cnpg cnpg/cloudnative-pg --namespace cnpg-system --create-namespace
  • An external PostgreSQL (e.g. managed by your cloud or IT): set database.host, and QABOARD_DB_PASSWORD in the secret.
  • database.embedded runs a single PostgreSQL pod: only to try the chart.

Ingress and TLS​

The chart creates an Ingress for ingress.host, for any ingress controller. Its default annotations are for ingress-nginx (no limit on uploads, slow API calls): set your controller's equivalents. With cert-manager:

my-values.yaml
config:
  QABOARD_URL: https://qaboard.example.com
ingress:
  className: traefik
  host: qaboard.example.com
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
  tls:
    - secretName: qaboard-tls

Users and the qa CLI then use QABOARD_URL=https://qaboard.example.com.

Authentication​

Set the sign-in settings in config, and their secrets in the secret:

  • LOCAL (default): users stored in QA-Board's database.
  • LDAP: QABOARD_LOGIN_TYPE: LDAP, QABOARD_LDAP_HOST, QABOARD_LDAP_USER_BASE, QABOARD_LDAP_USER_FILTER... and QABOARD_LDAP_PASSWORD in the secret.
  • SAML (SSO): QABOARD_LOGIN_TYPE: SAML, and QABOARD_SAML_DIR pointing to the SAML settings, mounted from a Secret with backend.extraVolumes and backend.extraVolumeMounts.

QABOARD_LOGIN_REQUIRED blocks anonymous users. To restrict who can read the files of some projects, see user management and proxy.restrictFiles.

Keep QA-Board on a trusted network

The API that qa uses to save results is not authenticated, even when sign-in is required: anyone who can reach the server can create or delete results, and make the server act on files in its storage. Only expose QA-Board to networks you trust (an internal load balancer, a VPN, an allowlist on the ingress), never to the internet, until the API supports tokens for saving results.

Backups​

  • With CloudNativePG, configure continuous backups to object storage (S3, GCS, Azure Blob), for point-in-time recovery: see database.cnpg.backup and CloudNativePG's backup docs.
  • Otherwise, backup.enabled: true runs a daily pg_dump to a volume (backup.storage), and keeps backup.keepDays days. To restore a dump, stop the backend meanwhile: 
    kubectl -n qaboard scale deploy/qaboard-backend --replicas 0
    pg_restore --clean --if-exists --no-owner -h <database host> -U qaboard -d qaboard qaboard.dump
    kubectl -n qaboard scale deploy/qaboard-backend --replicas 2   # backend.replicas
  • The results live in your storage: use its snapshots or backups. Keep a copy of the secret too (SECRET_KEY).

Upgrades and rollback​

helm upgrade qaboard oci://ghcr.io/samsung/charts/qaboard \
     --namespace qaboard -f my-values.yaml --wait --timeout 15m --rollback-on-failure  # helm 3: --atomic
helm -n qaboard history qaboard
helm -n qaboard rollback qaboard   # to the previous revision
  • Without --version, it upgrades to the latest release.
  • Upgrades are rolling: database migrations run first in a Job (if they fail, nothing running changes), then pods are replaced one by one, new ones first.
  • --rollback-on-failure rolls back automatically if the new pods don't become ready.
  • A rollback doesn't revert database migrations. If a new version's migrations must be undone, restore a backup.
  • Read the release notes before upgrading.

Differences with docker compose​

  • Old frontend bundles are not kept: with compose, the bundles of previous versions stay in a volume, so clients that didn't reload keep working. On Kubernetes each proxy pod only has the current bundle, so a client with an old tab gets errors when it lazy-loads a page, until it reloads.
  • The backend runs as root: it can use sudo to delete outputs as their owner, and uwsgi drops privileges (UWSGI_UID). Namespaces with the restricted Pod Security Standard won't accept it: use baseline.

Troubleshooting​

kubectl -n qaboard get pods
kubectl -n qaboard get events --sort-by=.lastTimestamp
kubectl -n qaboard logs deploy/qaboard-backend          # one of the replicas
kubectl -n qaboard logs job/qaboard-migrations          # failed migrations (the Job is deleted when they succeed)
kubectl -n qaboard exec -it deploy/qaboard-backend -- bash
helm -n qaboard history qaboard
