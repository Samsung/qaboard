## Web app

### Image viewer
- See new and every reference you stacked together in the image viewer, each in its tile, zoomed together and compared with new, or with the reference you click to make it the anchor, in grid, wipe, single or difference mode. Untick a reference's tab to leave it out, or pick **One at a time** after the tabs ([several references](/docs/user-guide/image-viewer#several-references-at-once)).
- Find which images differ: a panel gives the pixel's values in every image and how far apart each pair is on screen, so zoom into a region to compare it. Click a pair to see it alone. **Images as a contact sheet** shows each run's images in one row ([how far apart](/docs/user-guide/image-viewer#how-far-apart), [contact sheet](/docs/user-guide/image-viewer#contact-sheet)).

### Logged series
- Follow what runs log while they run, like a training's loss at each step: their card plots each series, the reference run's dashed on the same axes, and keeps up with runs that are still running. Smooth noisy curves, switch to a logarithmic scale, and compare by step or by time ([logged series](/docs/user-guide/other-viewers#logged-series)).
- Compare the trainings of a batch on the same plots, in the **Summary** view: one line per run, named by what tells the runs apart. Hide and show runs, hover one to bring it forward, color the runs by a parameter like the learning rate, and add their reference runs, dashed ([compare all the runs](/docs/user-guide/other-viewers#compare-logged-series)).

### Run cards
- See the test reports, benchmark files and profiles of runs created with `qa upload` or `qaboard.start_run()` on their cards, without anything in *qaboard.yaml*: the files are recognized by their names, like *junit.xml* or *\*.benchmarks.json* ([what you can upload](/docs/upload-results#files)).

### Logs
- Run a batch again as it ran, even after its batch files changed: **Run again…** next to a command in **Logs** fills in **Run Tests / Tuning** with its batches as they were defined then, its tuning and platform, or gives them as a YAML file with the commands to run them from a terminal ([run a batch again](/docs/user-guide/logs#run-again)).
- See whether a batch's definitions changed since the reference batch, or since an earlier command: **Batches that ran**, at the top of **Logs**, says *Same batches* or which batches changed, and shows the diff ([did the batches change?](/docs/user-guide/logs#compare-batches)).
- See every command that started a batch in one list at the top of **Logs**, from QA-Board, a terminal or the CI, most recent first, with what was typed, the batches it ran and the files they come from ([batch commands](/docs/user-guide/logs#batch-commands)).

### Tuning
- See how to get missing artifacts back: when a commit's artifacts are missing, **Run Tests / Tuning** says QA-Board can ask your CI to recreate them ([recreating artifacts](/docs/storage/deleting-old-data#recreating-artifacts)).

### Metrics
- Find the runs that changed most: click a metric in the **Metrics Diff** to sort the runs by the size of their change vs their reference run, better or worse, or pick **Change of …** in **Sort runs** ([Metrics Diff](/docs/user-guide/metrics#metrics-diff)).

## CLI and project setup

### Results without a shared storage
- Set `storage` in *qaboard.yaml*, or install your site package, to keep saving results in the shared storage: projects without any `storage` setting now send their results to the server over HTTP, which servers refuse unless they accept files ([where results are saved](/docs/storage/where-is-the-data)).
- Save files other tools wrote as a run, with `qa upload` (experimental): `qa upload junit.xml` in a CI job brings in a test report, a benchmark file or a profile, without a `run()` function or a *qaboard.yaml*, from any language. Test reports and benchmark files give the run its metrics; projects with a shared storage can upload from machines that don't mount it ([upload results from any tool](/docs/upload-results)).
- Send runs' files to the server over HTTP where the shared storage isn't mounted, like GitHub-hosted runners (experimental): leave `storage` out of *qaboard.yaml*, or set `storage: upload` or `QA_STORAGE=upload`. The log is sent while the run goes on, the rest when it ends; bit-accuracy checks and tuning work too. It needs a token, and a server that accepts files ([without a shared storage](/docs/storage/uploads)).
- Start runs and tuning from the web app without a shared storage: `qa save-artifacts` sends the commit's artifacts to the server, which runs batches from them on its machine or on Kubernetes, whose pods download them ([artifacts without a shared storage](/docs/storage/artifacts#uploaded)).

### Runs from Python
- Create runs from your own code, without `qa run` (experimental): `qaboard.start_run()` in a training loop, a notebook or a script, then `run.log({"train/loss": loss}, step=step)`, `run.log_metrics()`, `run.log_params()` and `run.log_artifact()`. The run shows in the web app like a `qa run`, while it runs; `resume=True` continues one that was interrupted ([log from your code](/docs/log-from-code)).
- Plot series written by programs in any language: save a *series.jsonl* in the run's folder, one JSON object per line with the step and the values, and list it in your visualizations ([the format](/docs/viewers#series)).

### Batches
- Keep what your batches ran: `qa --share batch` and `qa batch` in CI send QA-Board the batches as they were defined when they started, with only the batches they ran and the aliases that reached them, nested ones too. Batches started from the web app read the same kind of file, instead of copies of the whole shared and private batch files ([what is saved](/docs/user-guide/logs#run-again)).

### Scripts, agents and the HTTP API
- Have QA-Board start a batch on a pushed commit from a script, a CI job or a coding agent: `qa --label <name> batch --commit <commit> <batch>` (and `qa optimize --commit`) runs it as the web app's **Start** does, from the commit's artifacts, prints the batch's page and returns. Send batch files you didn't commit with `--batches-file` ([start batches from a terminal](/docs/tuning-from-the-webapp#from-the-command-line)).

## Server and administration
- Let runs send their files to the server over HTTP (experimental), on by default in `/mnt/qaboard` (the chart's results volume); with your own storage roots, set `QABOARD_UPLOAD_ROOT` (`off` turns them off). Files need a token. Turn on `QABOARD_SANDBOX_HTML` before you expose the server. Give projects their own mounted bucket in **Admin → Storage** ([storage locations](/docs/backend-admin/uploads#storage-locations)).
- Batches started from the web app for projects without a shared storage get a token of whoever started them, for their project only and a day after the runs stop. On Kubernetes it is in the driver pod's environment, readable by whoever can read the namespace's ConfigMaps: keep one namespace per team. With Docker Compose they reach the server through the proxy (`QABOARD_HOST`) ([uploads](/docs/backend-admin/uploads#security)).
- Fail runs that stop reporting, e.g. when their machine is killed: runs from the new `qa` and `start_run()` report every two minutes, and are failed after 15 minutes of silence ([runs that stop reporting](/docs/backend-admin/storage#silent-runs)).
- Add `include snippets/qaboard-app-headers.conf;` to the `/` and `/assets/` locations if your site has its own nginx configuration, as in `services/nginx/conf.d/qaboard.conf`: other websites can then no longer show the web app in a frame, and nginx no longer sends its version.
- If your site has its own nginx configuration, change its upload location to `location ~ ^/api/v1/(output/[0-9]+|commit/[0-9a-f]+/artifacts)/files/`, as in `services/nginx/conf.d/qaboard.conf`: else nginx refuses large artifacts.

## Documentation
- Install `qa` from PyPI to get every feature the docs describe: `qaboard` 1.2.0 has them, so the pages no longer ask you to install it from the repository ([install qa](/docs/installation)).
- Read on the [roadmap](/docs/roadmap#compare-more-than-two) what's left of comparing more than two results, now that the image viewer shows several references together.

## Fixes
- Fixed adding metrics to a finished run from a script or the HTTP API failing with a server error ([add metrics to runs](/docs/http-api#add-metrics)).
- Filter **Runs activity** and **Storage usage** by their totals from the keyboard, and hear what status, lock and info icons mean with a screen reader.
- Fixed API calls on runs or batches with an id that isn't a number, or without a batch label, failing with a server error: they now answer 404 or 400 with a message, and a batch is never saved without a label. Asking for the value of a pixel outside an image answers 400 too, instead of an error, or of a pixel from the other edge for negative coordinates.
- Find what your executables and native code print in the run's *log.txt*, not only what Python prints: no need to capture their output and print it anymore. They still write to a terminal, so colors and progress bars stay. On Windows, *log.txt* still only has what Python prints ([running an executable](/docs/running-your-code#run-an-executable)).
- Fixed `qa` crashing on Windows when project files, like *qaboard.yaml* or batch files, have accents or other non-ASCII characters. Fixed `qa run` failing when `run()` returns metrics without `is_failed`.
- Fixed deleting runs failing on folders their owners made private (like `0700`) or read-only, or on someone else's files in them. When a file still can't be deleted, the error says which folder blocks it, its permissions and who can delete it.
