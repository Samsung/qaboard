## Web app

### Comparing images
- Compare images like videos: side by side, with a wipe, one at a time in place (**Single**), or as their difference. Pick the mode above any image, or with the keys 1 to 4: it applies to all the images of the page, and links keep it. The swap button, or `t`, swaps the sides (around the difference too); when one image shows, it shows the other, then their difference, then the first again. It does it in every viewer of the page, so they all show the same one, and the keys work anywhere on the page, not only over an image. See [comparing images](/docs/user-guide/comparing-results#image-viewers).
- Run a blind test: **Blind test** above the images (or `h`) shows each viewer's images in a random order, called A and B everywhere, then **Reveal** shows which was which, and **Done** goes back to new first. See [blind test](/docs/user-guide/comparing-results#blind-test).
- See the difference between the new and reference images, all three in sync, with a cross on the pixel under your mouse in each, measured perceptually (YIQ), as ΔE 2000, per channel or as any change at all. Click **Difference** again, or press `4` again, to see it alone and larger. See [the difference](/docs/user-guide/comparing-results#the-difference).
- Zoom in and read the values of the pixels, written on them: the image's own values (10-bit, 16-bit, float, raw...) or the 8-bit colors on screen, picked from the **123** button above the images. Hover a pixel to see both, in both images, and their difference; `p` hides them. 8-bit images show one set of values: the screen shows them as they are. See [pixel values](/docs/user-guide/comparing-results#pixel-values-the-images-or-the-displayed-ones).
- Compare images in full screen: the button at the right of the image viewer's toolbar, or `f`, gives the screen to the images, with all the viewer's tools, and the difference under them when that makes them larger. See [full screen](/docs/user-guide/comparing-results#full-screen).
- Adjust how images look with brightness, contrast, gamma, sharpening, one channel (R, G, B or luma), false colors or inverted colors. They apply to both images and to the same visualization of the other runs; the pixel values, the difference and the histograms stay the images'.
- Highlight a range of values on the images: drag on the histogram and stripes show the pixels in the range, with the share of each image they cover. Click R, G, B or Y above the histogram to show one channel alone and pick its values. The channels' areas blend where they overlap, and the axis has ticks. See [histograms](/docs/user-guide/comparing-results#histograms).
- Find your way in large images: a minimap shows where you are once you zoom in, the zoom level says how many screen pixels an image pixel takes, **1:1** goes to 100%, and the histogram button overlays the histograms of the new and reference images in view.
- Step through the regions of interest with their thumbnails above the images, or with `[` and `]`. The regions menu finds where images differ most, by perceptual difference, SSIM or ΔE 2000: one region per place that changed, with how much it changed (e.g. *#1 · 3.2%*). The region set you pick applies to every viewer of the same file on the page, and searches like **Where they differ** only run on the page where you pick them.
- Copy or save the new, reference or difference image as you see them, or open the original files, from the copy button above the images.
- Find which runs' images changed most: **Where they differ, in all N runs…** in the image viewer's regions menu compares every run of the page with its reference and ranks them, from the largest difference to the identical ones. **Show** takes you to a run, on the region that changed most. The list says which runs it's comparing and for how long, and which wait for their turn. See [which runs changed most](/docs/user-guide/comparing-results#which-runs-changed-most).
- Pick how images are compared in the View options (**Compare images**), which replaces the Image diff switch. Links made with Image diff on open in difference mode.
- Use QA-Board's image viewer in your own React apps: it builds as a package (`npm run build:image-viewer`), with its props documented in its [README](https://github.com/Samsung/qaboard/tree/master/webapp/src/image-viewer).

### Videos
- Compare videos with a wipe, one at a time in place (**Single**), or as their difference, besides side by side. Zoom with the mouse wheel or a pinch and drag to pan: both videos follow, and zoomed in you see the actual pixels. See [comparing videos](/docs/user-guide/comparing-results#video-viewer).
- Step through videos frame by frame with the arrow keys, scrub, slow down to 0.1× or loop: new and reference stay on the same frame, and wait for each other when one is still downloading.
- Copy the current frame of a video (new, reference or their difference) to the clipboard, or save it as a PNG.
- Compare videos like images: the difference between the videos or alone, perceptual or in ΔE 2000, display adjustments, a blind test, full screen (`f`) and a minimap when zoomed in.
- See which frame each video shows when paused, numbered like in the file even with variable frame rates, and whether both show the same frame. See [which frames you are looking at](/docs/user-guide/comparing-results#which-frames-you-are-looking-at).
- Read the decoded values of the pixels (e.g. 10-bit Y′, Cb, Cr) of the very frame shown, under the pointer and written on the pixels when zoomed in, next to the 8-bit values your browser displays.
- See what's in the video files side by side (codec, pixel format, chroma subsampling, color range and matrix, frame rate, keyframes, dropped frames), with what differs highlighted and what it means for what you see.
- Find where two videos differ: the timeline shows how much each frame differs, `n` and `N` go to the frames that differ most, and regions show where and when they differ most, in the whole video or in the frame shown. See [where the videos differ](/docs/user-guide/comparing-results#where-the-videos-differ).
- Change the speed of videos with `<` and `>` (they were `[` and `]`, which now step through regions, like in the image viewer).

### Configurations and reference runs
- See at a glance what's specific to each run: settings that all the runs shown share are hidden behind "··· N shared" tags, and listed once at the top of the page. It follows the filter. Turn it off with **Hide them in each run** ([reading configurations](/docs/user-guide/comparing-results#reading-configurations)).
- Read lists in configurations: `[1, 0.98, 0.95]`, long lists with their size (`… 64 values`, `3×3`) and where they changed (`…0.619, 0.7 → 0.635, 0.651…`). Tuning parameters show as settings like the others, with a wrench.
- Copy a run's settings as `qa` options (`-c … --tuning …`), as JSON or as a tuning search space, and a setting as text or JSON, from their hover menu.
- See how a run's configuration differs from its reference run's: added settings in green (+), removed ones struck through in red (−), changed values as `gain: 3 → 4`, and only the changed part of strings: `conf/[day → night].yaml`. Changes all runs share are listed once, at the top of the page. Hover the **Config** tag for a `git diff`-like view.
- Runs are compared with the reference run whose configuration is closest: the fewest different settings, then the most similar values (`base-v1` is closer to `base-v2` than to `other`). The **Config** tag says when other reference runs were as close.

### The commit page
- The commit page's view options are now a panel docked on the right that makes room for the results instead of covering them. Collapsed, a rail shows a dot on the sections that differ from the project's defaults, and hovering lists the changes. Press `o` to show or hide it, or drag its edge to resize it. See [View options](/docs/user-guide/commit-page#view-options).
- See and change what the commit page shows from **Files to show** (formerly Dynamic options): each option says which visualization it's for and lists the values of all runs. Options are linked across runs: a run that doesn't have the selected value shows the closest one and says so, and you can pick a value per run. See the [user guide](/docs/user-guide/commit-page#the-controls-panel).
- Open the export box from the new **Export** button next to the Visualizations and Output Files titles; press Enter to export, and find the last export's paths when you reopen it.
- Run cards fit the window when *qaboard.yaml* doesn't set their width (`outputs.style.width`): they used to be 1500 px wide, wider than a laptop's screen.
- Metrics Diff colors small changes and shows them precisely ("-0.37%" instead of "-0%"). The Summary's bars say how many runs met their metric's target.
- Find more explanations on hover: run statuses, aggregated metrics, `new`/`ref`, targets in the metrics tables, and milestones. The reference's bar says when it's the same commit as the new one.
- Pages use the width next to the sidebar instead of jumping between fixed widths, and the commit page fits laptop screens: its header cuts long commit messages and branches with "…".
- The Tuning Analysis view of a `qa optimize` experiment plots its convergence itself: each iteration's objective and the best one so far, even when matplotlib isn't installed where `qa optimize` ran.

### Logs, batches and redoing runs
- The Logs view filters runs (all, failed, running) and tags failed runs with the reason (e.g. "LSF: out of memory"). The sidebar's Logs entry shows how many runs failed, or are still running.
- In the Logs view, each run fits on one line, with buttons to open its output directory, copy its Linux or Windows path, redo it, mark it as failed or delete it. Its full configuration shows when you open its logs.
- Switch between a run's `log.txt`, `log.lsf.txt` and `log.dask.txt`. For LSF runs, a summary shows the exit reason, host, run time and memory used vs requested, with hints that point to the batch's `lsf:` options.
- Batches started from QA-Board (tuning, "Run Tests") show whether `qa batch` is waiting for LSF, running, failed (with the error) or didn't start any run, with a link to its logs.
- See where the logs of each command that started a batch are: in the CI job (with a link), or in QA-Board (one click shows them). The batch's own `log.txt` only shows when it exists. See the [user guide](/docs/user-guide/commit-page#logs).
- Show more of very long logs: they show their last 50,000 lines to stay fast, and say if the hidden lines have errors or matches for your search.
- When you filter a batch's runs, the commit bar menu redoes only the runs that match the filter. Follow redone runs in the Logs view, under "Started from QA-Board". See the [user guide](/docs/user-guide/running-from-the-webapp).
- The Available Tests view is a real editor for your private and shared batches: it flags YAML mistakes and inputs `qa batch` can't use as you type, shows whether your changes are saved (`Ctrl+S`), keeps them if you leave, and warns instead of overwriting someone else's changes. See the [user guide](/docs/user-guide/commit-page#available-tests).
- Available Tests warns about what `qa batch` would ignore or misread: unknown keys like `inpts` (*Did you mean "inputs"?*), values of the wrong type, unknown runners and runner options, and input types the commit's *qaboard.yaml* doesn't define. See the [user guide](/docs/user-guide/commit-page#available-tests).
- The Available Tests view lists the batches in each file: go to one, list the tests it resolves to on the commit, or run it in one click.
- When a batch has no tests in Available Tests or Run Tests / Tuning, see why: a batch file missing from the commit's artifacts (with the path QA-Board looked for), invalid YAML, a batch that no file defines, or inputs the server didn't find. See the [user guide](/docs/user-guide/commit-page#available-tests).

### Finding commits and projects
- Search all of a project's commits from the commit list's **Filter...** box, not only those in the date range: by message, committer, branch, batch or hash. Use `branch:`, `committer:`, `batch:`, `message:` or `id:` to look at one field, and `-word` to exclude ([searching commits](/docs/user-guide/finding-results#searching-commits)).
- Jump to a branch from the **Filter...** box: when your search can be a branch name (one word, or a `branch:` term), it suggests the most recently active branches that match, even in projects with thousands of branches.
- Scroll through long commit lists: they show the 50 latest commits, then more as you scroll, so big projects open much faster, and **Older commits** at the end looks a week further back. Branch pages still get their whole date range at once (up to 1000 commits), for their metrics chart.
- Switch commit lists to **Compact** to see one commit per line, in aligned columns, with the full message, metrics and other batches on hover. The web app remembers your choice.
- Open the projects list much faster on sites with hundreds of projects: it downloads less, and shows more projects as you scroll.
- Find your way around from the History page: the sidebar shows the project's navigation (the branch's commits, Code, History, Integrations, Milestones), and moving between these pages no longer reloads the app.

### File browser
- Open a folder under `/s/` in your browser to get the new [file browser](/docs/user-guide/files): sort and filter files (e.g. `*.png`), copy their Linux or Windows paths, paste a path to go there, and navigate with the keyboard (press `?`). Scripts and `curl` still get nginx's plain index.
- In the file browser, a bar shows the run whose folder you are in, with its status and a link to its results: [redo it, delete it or mark it as failed](/docs/user-guide/files#runs) from there.

### Git hosts and integrations
- Follow links to code, commits and branches on your project's own git host, with the right URLs for GitHub, GitLab, Gitea/Forgejo and Bitbucket, instead of a hardcoded GitLab server.
- The sidebar's **Code** menu links to the commit, its files, your subproject's folder, the branch and the repository on your git host.
- Start the GitHub Actions workflows declared in your project's `qaboard.yaml` from the Integrations menu, follow the run you started, and see the status of each workflow's latest run for the commit. Only users who can access the project can see or start them ([GitHub Actions](/docs/triggering-third-party-tools#start-github-actions-workflows)).
- See your git host's defaults in the Integrations menu of branch pages, when your project configures none and QA-Board knows its git host: GitLab's pipeline status, or a link to GitHub Actions ([default integrations](/docs/triggering-third-party-tools#default-integrations)).
- See commit authors' avatars from GitHub, Gitea/Forgejo and Bitbucket, learned from push events, or else their Gravatar. Avatars and badges from public git hosts load directly, which is faster.

### Look and feel
- Switch to a dark theme with the theme button next to "What's new" in the sidebar, the projects list or the file browser. By default the web app follows your system's theme; plots, editors and viewers follow it too, and metrics tables only highlight clear improvements and regressions.
- Collapse the sidebar to a rail of icons for more room, with **Collapse** at its bottom or `Ctrl+\` (`⌘\` on macOS). Hover an icon for its name; the web app remembers your choice.
- A calmer, more consistent look: every view's title sits above its flat card, configurations are grey tags, run statuses are small icons, and filters have their help and a clear button inside the box. Hover a view in the commit page's sidebar to see what it shows; your login moved to its bottom.
- Pages say what's happening instead of staying blank or showing empty views: while they load, when they fail (with a **Retry** button), and when there's nothing to show yet, with what to do next and a link to the docs. For example, a commit without results explains how to get some, and an empty Metrics Diff says why there is nothing to compare.
- Deleting runs, batches or a commit's results, redoing a whole batch and resetting the tuning form ask you first, with how many runs are affected. Notifications name what was acted on, and starting runs offers to show their logs.
- The commit, batch and run action menus open on click instead of hover, so they no longer open by accident and work on touch screens. When a run has no reference and there's no Windows path to choose, its folder and copy buttons act directly.
- The footer stays at the bottom of the window, with links to What's new, the cheat sheet and QA-Board on GitHub.
- The web app says "runs" everywhere, like the docs ("8 runs", "Redo failed runs"), and page titles match the sidebar's names: Metrics Table instead of "Quality report", Metrics Diff instead of "Improvement report", and the Analysis view is now Tuning Analysis.
- See who made a commit at a glance: when there's no avatar picture, committers, users and projects show their initials on a color that stays the same everywhere.
- Buttons that were only icons have labels for screen readers, and the menus they open can be reached with the keyboard.
- The "Quotas" links show only when the server has a quota dashboard, and the error page links to your server's support page.

### Milestones
- Save milestones in your account: they follow you on every computer. The star next to a commit's hash opens a dialog that shows what you save (the commit, its batch, the filter and how many runs match), suggests a name, and asks for an optional group, notes, and whether everyone on the project sees it. See [milestones](/docs/user-guide/comparing-results#milestones).
- Organize milestones in groups, like `releases` or `tuning/denoiser`: menus list them by group, and remember the groups you collapse.
- Find milestones faster: the Change menu and the sidebar's Milestones menu list your favorites first, then your milestones, then the project's, with a search box that matches their name, group, notes, branch, batch, filter or owner.
- Add milestones to your favorites with the heart: the sidebar lists them, one click away.
- Share a link to a milestone, `/<project>/milestone/<id>-<name>`: it opens its results, and keeps working when the milestone is renamed. Add `?vs=<id>-<name>` to link to a comparison of two milestones.
- Manage milestones in a table: sort them by update, creation, name or group, open one, use one as the reference, compare two, or move, share and delete several at once. See [managing milestones](/docs/user-guide/comparing-results#managing-milestones).
- Add a whole group of milestones to your favorites: its milestones, even future ones, are listed first.
- Find milestones by dataset: milestones remember the datasets, qa batches and platforms their runs used. Search `dataset:indoor` or `qa-batch:nightly`, or pick a dataset in **Manage milestones…**, which also shows each milestone's notes.
- Find out what happened when a milestone link is broken: the page says which milestone was deleted, and still opens the other one of a comparison.
- Save several milestones on the same batch, for example one per filter. When the results you look at are a milestone, its name shows next to the star.
- Milestones you saved in your browser before (the "private" ones) move to your account the next time you log in with that browser.

### Help, What's new and links
- Read the release notes in the new "What's new" panel, with a search box (`/#whats-new` opens it). It pops up once a month is over; the current month's notes show as a preview, tagged "In progress".
- The sidebar's help button opens the new [user guide](/docs/user-guide/overview).

## CLI and project setup

### Project setup and the qa CLI
- At SIRC, upgrading `qaboard` now requires also installing `qaboard-site-sirc`, see the [installation instructions](/docs/installation). Site packages provide a base `qaboard.yaml` that every project's configuration is merged on ([site defaults](/docs/project-init#site-defaults)): `qa init` shows the inherited values instead of overriding them.
- `qa init` creates a configuration that runs locally: LSF is commented out, and storage defaults to `/mnt/qaboard` like the server.
- The CLI reads your `QA_TOKEN` from `$QA_TOKEN` or `~/.qaboard/secrets.yaml`, and warns if other users can read that file.
- `QABOARD_API_VERIFY` controls the TLS verification of the CLI's requests to the server: `true` (the default), `false`, or the path to a CA bundle.
- Site packages (company-specific plugins) are no longer ignored on Python 3.8 and 3.9, and the package includes the `qatools` compatibility package.

### Runners: LSF, Dask and Windows
- LSF runs write their output live to `log.lsf.txt`, with LSF's job report at the end. `qa batch` no longer passes an LSF queue or project when none is set, and fails fast when `bsub` is missing.
- With `--no-wait` and an existing Dask cluster (`scheduler_address`), the Dask runner now enforces `concurrency`: a driver LSF job sends the runs, as without `scheduler_address`. See the [Dask runner](/docs/dask-integration).
- `qa batch --runs-file runs.json` does a list of runs, each with its input, configurations, parameters and runner options. QA-Board uses it to redo runs together. See the [CLI tips](/docs/using-the-qa-cli).
- Read the logs of `qa --share batch` and `qa optimize` started from a terminal in QA-Board, with the batch's commands: they save what they print in the batch directory (under `qa-batch-logs/`), errors included. `qa optimize` includes the output of its iterations. In the CI, the CI keeps the logs. See the [CLI tips](/docs/using-the-qa-cli).
- Configure the Windows runner: PowerShell's `$ErrorActionPreference` per job (the batch's `error_action:` option) or with `QA_RUNNER_ERROR_ACTION`, and how long `qa batch` waits for its Jenkins builds, now 2 hours by default (`QA_JENKINS_TIMEOUT`, `QA_JENKINS_STATUS_INTERVAL`).
- Batches list their inputs in the same order on every machine: the inputs found by `globs` are sorted by path, instead of coming in the order the filesystem lists them.

### GitHub, CI and the quality gate
- Fail the CI when quality regresses, with the experimental `qa gate`: set rules in *qaboard.yaml* (`gate:`) on the median of a metric vs a reference branch, milestone or commit, on each test, on failed runs or on bit-accuracy. It prints a table (or Markdown, or JSON), fills the GitHub Actions job summary, and can post a commit status to GitHub or GitLab that links to the Metrics Diff. See [Quality gate](/docs/quality-gate).
- Compare with any milestone in `qa gate`: `--reference '#12'` (or `gate.reference`) uses the milestone whose link is `/<project>/milestone/12-...`, shared or not, and the gate compares with the milestone's batch ([quality gate](/docs/quality-gate)).
- `qa batch` sets a commit status that links to the results on GitHub too ([CI integration](/docs/ci-integration)).
- `qa check-bit-accuracy` waits for the GitHub checks of the reference commit too, like it does for GitLab pipelines ([bit-accuracy](/docs/bit-accuracy)).
- In GitHub Actions, `qa` records the pull request's branch and last commit instead of the temporary merge commit, and the tag of tag builds ([CI integration](/docs/ci-integration#example-with-github-actions)).
- `qa` finds your git host, its API and its token in `QABOARD_GIT_HOSTS` too, and sends `GITHUB_ACCESS_TOKEN` only to github.com and the GitHub hosts you configured ([git hosts](/docs/backend-admin/git-hosts#the-cli)).
- In CI, `qa`'s Sentry reports are tagged with its version, and `QABOARD_SENTRY_VERIFY` (or `SENTRY_CA_CERTS`) can be the CA bundle that signed your Sentry server's certificate, or `system` ([the qa CLI](/docs/backend-admin/monitoring#the-qa-cli)).

### qaboard.yaml
- Get completion, docs on hover and warnings for typos when you edit *qaboard.yaml* and batch files, in VS Code or any editor using the YAML language server: QA-Board publishes their JSON schemas ([project setup](/docs/project-init#checking-qaboardyaml-and-batch-files-in-your-editor)).
- Set the frame rate of a video visualization with `fps` in *qaboard.yaml*, when the web app's guess is wrong. See [the video viewer](/docs/visualizations#video-viewer).
- Warn users who start tuning on branches whose commits have no artifacts: list the branches your CI saves them for in *qaboard.yaml*'s `tuning.branches`. The tuning form offers the platforms listed in `inputs.platforms` ([tuning from QA-Board](/docs/tuning-from-the-webapp)).
- Summarize metrics per tag of the inputs (their metadata's `tags`) on the History page, with `dashboard_breakdown_by_tag: true` in your metrics file ([metrics](/docs/computing-quantitative-metrics)).

## Server and administration
- Free more storage: the cleanup of old results (`qaboard_clean`) keeps only the batches that are milestones, not all the batches of their commit ([deleting old data](/docs/storage/deleting-old-data)).
- Delete a commit's runs from the web app even when it has milestones: its milestone batches are kept.
- Upgrade the database with a migration that moves shared milestones from the projects' data to their own table; the old data stays for rollbacks.
- Get your shared milestones back on servers where the upgrade failed to copy them because the projects' data was in an older format: the next upgrade converts it and copies them.
- **Before you upgrade**: settings to check and data to move first.
  - Records each existing project's git host, with a migration that uses the deploy's git host settings. **Before upgrading, keep `GITLAB_HOST` set**, or list your GitLab in `QABOARD_GIT_HOSTS` with the hostnames older projects used ([upgrading](/docs/backend-admin/git-hosts#upgrading-from-older-versions)).
  - Security: the server only writes, deletes or runs code in the folders listed in `QABOARD_STORAGE_ROOTS` (default: `/mnt/qaboard`), and refuses results stored elsewhere. **If your projects store results in other folders, set it before upgrading** (see [environment variables](/docs/deploy#optional-environment-variables)).
  - Security: the server only loads avatars and badges for the web app from your GitLab hosts and gravatar. **If your projects' `avatar_url` or badges (`integrations[].src`) come from other hosts, list them in `QABOARD_PROXY_HOSTS`** (see [environment variables](/docs/deploy#optional-environment-variables)).
  - Daily database backups older than 14 days are deleted after each successful backup, but never the newest 3, nor dumps with other names. Set `QABOARD_BACKUP_RETENTION_DAYS` to keep them longer (`0` keeps them all). **Before upgrading, move the old daily backups you want to keep** ([backups](/docs/backend-admin/deployment#backups)).
  - Versions from before October 2026 don't start on a database migrated by this one: to roll back to them, first undo the newer migrations ([rollbacks](/docs/backend-admin/deployment)).
  - The `website` image (the docs your server serves) is built from the repository's root, like the `frontend` image: if you build it without `docker compose`, run `docker build -f website/Dockerfile .`.
  - At SIRC, QA-Board no longer serves the storage over WebDAV (`/davs/algo/`): it let anyone write and delete files. `services/nginx/webdav.conf` explains how to bring it back.
- **Deploying: Compose, Kubernetes, quickstart**: zero-downtime deploys, published images, a Helm chart and a quickstart.
  - Zero-downtime deploys with [deployments/deploy.py](/docs/backend-admin/deployment): images tagged per version, several backend replicas behind nginx, rolling updates, `rollback`, `status` and `restore-db`.
  - `deploy.py seed-db` fills a staging database with only production's recent data.
  - Pull QA-Board's images from `ghcr.io/samsung/qaboard`: `docker-compose.yml` uses them by default, each release has its own tags (e.g. `backend-1.2.0`), and `QABOARD_IMAGE` picks another registry.
  - Run QA-Board on Kubernetes with the [Helm chart](/docs/backend-admin/kubernetes) published with each release, `oci://ghcr.io/samsung/charts/qaboard`.
  - Try QA-Board on your laptop with kind: `charts/qaboard/quickstart.yaml` and `charts/qaboard/kind.yaml` start a small cluster with the docs' demo projects (the chart's new `demoData` setting), where the `qa` CLI can save results (see [the quickstart](/docs/backend-admin/kubernetes)).
  - Mount the storage where runs save results with the chart's new `results` setting (an existing claim, a new volume, NFS or a node folder): the chart mounts it where the backend, nginx and Cantaloupe expect it, and sets `QABOARD_STORAGE_ROOTS`.
  - The Helm chart's migrations Job gets the chart's `config:` settings, which data migrations need ([Kubernetes](/docs/backend-admin/kubernetes)).
  - Try QA-Board on your computer with demo projects to look at: download one Compose file, `deployments/quickstart/compose.yml`, and run `docker compose up -d --wait` (see the [quickstart](/docs/get-started/quickstart)). It only answers on your computer.
  - Build the website image behind a proxy that blocks some of the docs' media: with `QABOARD_MEDIA_MISSING=remote`, readers' browsers load them from the media host or your mirror (`QABOARD_MEDIA_BASE_URL`), and with `placeholder` they render as placeholders, instead of failing the build.
  - The backend has a `/api/v1/health` endpoint, shuts down gracefully, and keeps working when redis is down.
  - The web app links to the docs served by your server at `/docs/`, which match its version, instead of the public website. Set `QABOARD_DOCS_ROOT` to use another docs site.
  - Add pages for your own users to the docs your server serves: put them in `website/site-docs/<site>/` and build with `QABOARD_SITE=<site>`. They get their own menu, and the installation page links to them. At SIRC, "At SIRC" has the install commands and SIRC specifics.
- **Git hosts and webhooks**: GitHub, GitLab, Gitea/Forgejo and Bitbucket, with safer tokens and webhooks.
  - Configure all your git hosts (GitHub and GitHub Enterprise, GitLab, Gitea/Forgejo, Bitbucket, other git servers), each with its own token and webhook secret, with `QABOARD_GIT_HOSTS` ([git hosts](/docs/backend-admin/git-hosts)).
  - Keeps your current git settings working: `GITLAB_HOST` (also without a scheme, or with credentials), `GITLAB_ACCESS_TOKEN`, `GITHUB_ACCESS_TOKEN`, `QABOARD_GITHUB_HOSTS` for GitHub Enterprise, and `QABOARD_GITLAB_HOSTS`, whose hostnames are other names of `GITLAB_HOST`. A GitLab and a GitHub host can share a hostname ([backward compatibility](/docs/backend-admin/git-hosts#backward-compatibility)).
  - Receives the push events of repositories on Gitea, Forgejo and Bitbucket Cloud, at `/webhook/gitea` (or `/webhook/forgejo`) and `/webhook/bitbucket` ([webhooks](/docs/backend-admin/git-hosts#webhooks), [project setup](/docs/project-init#optional-connect-your-git-host)).
  - Require a secret in push webhooks: set `QABOARD_WEBHOOK_SECRET`, and the same secret in your repositories' webhooks, so that only your git hosts can send push events ([webhooks](/docs/backend-admin/git-hosts#webhooks)).
  - Stops saving git tokens in new clones' `.git/config`, or showing them in error messages: git gets them from a credential helper, and only for their own host (it needs git 2.31 or newer). Clones made by older versions still have the token in their remote URL: [remove it](/docs/backend-admin/git-hosts#tokens).
  - Stops sending git tokens, and GitLab session cookies, to another host when git or API calls are redirected there, and reads tokens and webhook secrets only from its environment, not from the CLI's shared secrets file (`QA_SECRETS`).
  - Webhooks are stricter. They refuse push events: without a webhook secret once any host has one or `QABOARD_WEBHOOK_SECRET` is set (`401`), from git hosts the server doesn't know (`403`; pushes to `/webhook/gitlab` from unknown hostnames still go to your GitLab), that would move a project to another git host (`409`), or over 25 MB (`413`). They ignore other events, like GitHub's `ping`, and answer `503` while the git host settings are invalid, instead of the server failing to start.
- **Security and access to files**: logins for actions, and who can read which files.
  - Security: actions that run commands (redo, tuning, stopping or deleting batches...) now require a login and run as the logged-in user, and their inputs are escaped. See SECURITY.md.
  - Redoing, deleting or marking a run as failed now requires access to its project, for restricted projects.
  - Each batch started from QA-Board gets its own folder with its scripts and logs, under the batch's `qaboard-batches/`.
  - Restrict who can read the files of restricted projects, or of the folders you list under `paths` in `users_restrict.yml`: nginx asks the backend before sending each file (see [user management](/docs/backend-admin/user-management#restricting-who-can-read-files)). If you use your own nginx configuration, include `snippets/qaboard-files.conf` in the `/s/` locations to get the file browser.
  - In the folders listed in `QABOARD_FILES_UNIX_PERMISSIONS` (e.g. `/home`), users only read the files that their own Unix account can read (see [user management](/docs/backend-admin/user-management#unix-permissions)).
  - Without a complete `/etc/passwd`, e.g. with LDAP or SSSD, `QABOARD_ACCOUNTS_COMMAND` (and `QABOARD_GROUPS_COMMAND`) gives the backend the users' accounts, refreshed daily: the file browser shows owners' names instead of their ids (see [users' accounts](/docs/backend-admin/user-management#users-accounts)).
- **Settings**: quota, support and login hints, simpler result uploads.
  - Configure the quota dashboard and support links with `QABOARD_QUOTA_URL_TEMPLATE` and `QABOARD_SUPPORT_URL`.
  - Tell users which credentials to use when they can't log in, with `QABOARD_LOGIN_HINT`, and where to install WebCDE, which opens runs with a `cde.sh`, with `QABOARD_WEBCDE_INSTALLER` ([environment variables](/docs/deploy#optional-environment-variables)). The tuning form's feedback link goes to `QABOARD_SUPPORT_URL`.
  - Scripts can send results that describe their commit with only `commit_sha` and `commit_authored_datetime`: the other `commit_*` fields (branch, message, committer, parents) are optional, and the server doesn't need access to the git repository.
- **Database**: faster commit lists, safer migrations, tunable PostgreSQL.
  - Lists of commits answer many times faster on big projects, and use much less memory: they no longer load every output of every commit.
  - Adds two indexes on `ci_commits`, to list commits faster. They are built without blocking writes, which can take a few minutes on big databases. If building one fails, the next deploy builds it again.
  - Starts even when the database has migrations it doesn't know, made by a newer version, e.g. after a rollback: it keeps them.
  - Tune PostgreSQL with a settings file: use `services/db/init.sh` as the database's entrypoint and it includes `services/db/qaboard.conf` (or your own, `QABOARD_DB_CONFIG`) in PostgreSQL's configuration at every start, and in new databases right away, with the `pg_stat_statements` extension ([database settings](/docs/backend-admin/deployment#database-settings)).
  - Size the backend's database connection pools with `QABOARD_DB_POOL_SIZE` and `QABOARD_DB_MAX_OVERFLOW` (default 4 and 2 per uwsgi process, instead of 10 and 5): PostgreSQL's `max_connections` can stay small. The backend checks connections before using them, so it keeps working after a restart of the database.
  - The database gets two minutes to stop cleanly (`stop_grace_period` in *production.yml*), instead of being killed after 10 seconds and replaying its log at the next start.
- **Monitoring with Sentry**: traces from the browser to the database.
  - See where the backend spends its time in Sentry: traces of API requests include their database queries, and a share of the backend's processes are profiled (`SENTRY_PROFILE_SESSION_SAMPLE_RATE`). Celery workers report their errors and tasks too ([Monitoring with Sentry](/docs/backend-admin/monitoring)).
  - See the web app's page loads, web vitals (LCP, CLS, INP) and the API requests they make in the same Sentry trace as the backend's work, with readable stack traces: set `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT` and `SENTRY_URL` when you build the `frontend` image to upload its source maps, that are then no longer served.
  - Sentry is enabled by `SENTRY_DSN` alone (it also required `FLASK_ENV=production`), tags events with `SENTRY_ENVIRONMENT` and the release, traces 20% of requests by default (`SENTRY_TRACES_SAMPLE_RATE`), and checks the Sentry server's certificate (`CA_CERT_URL` build argument or `SENTRY_CA_CERTS`). Users are identified by their username only, tokens are filtered out, and `SENTRY_FRONTEND_DSN` sends the web app's events to their own project.
- **API**: for scripts, agents and the image viewer.
  - Get the numbers of the Summary and Metrics Diff views from scripts and agents, with the experimental `/api/v1/commit/<sha>/compare`: each metric's median vs a reference, each run vs its reference run, and how many runs failed. See [Quality gate](/docs/quality-gate#from-scripts-and-agents).
  - API: page through `/api/v1/commits` with `limit` and `offset` (the `X-Has-More` header tells if there are more) and search them with `q`, find branches with `/api/v1/project/branches?q=...`, and get a much smaller list of projects with `/api/v1/projects?summary=true` ([lists of commits](/docs/apis#lists-of-commits-branches-and-projects)). Without these parameters, they answer as before.
  - The API reads the values of a region of an image, for the image viewer's pixel values: `GET /api/v1/output/image/pixels` with `image_url`, `x`, `y`, `w` and `h` (up to 256×256 pixels), as JSON, or as binary with `format=binary` (their type and shape in the `X-Pixels-Dtype` and `X-Pixels-Shape` headers).
  - The API finding where two images differ (`POST /api/v1/output/image/diff`) returns regions as `x`, `y`, `w`, `h` with the peak's `value` (comparable across images) and its fraction of the largest (`diff`), instead of a center and radius. It takes the reference's file name as `path_ref`, answers 404 for a missing file and 400 for images of different sizes, and keeps its results.
  - Images whose pixel values users read are decoded once and kept on disk, up to `QABOARD_IMAGE_CACHE_GB` (20 GB by default, the least recently used are removed), in `QABOARD_IMAGE_CACHE_DIR`. See [the server's settings](/docs/deploy).
  - The server reads videos with FFmpeg (PyAV, in the backend's image), for the video viewer: what's in them (`GET /api/v1/output/video/info`), the decoded values of a frame's pixels (`GET /api/v1/output/video/pixels`, like images' with a `frame`), and where two videos differ, frame by frame (`POST /api/v1/output/video/diff`). Results are kept for a month in `videos/`, in `QABOARD_IMAGE_CACHE_DIR`.

## Performance

### Commit pages with 1000 runs
- Type in the filter box of a commit page without the page freezing: the results update in half a second, instead of after 7 seconds of a frozen page. Sorting runs, and matching them with their reference, no longer freeze the page either.
- Open the Metrics Table in a third of a second instead of 7 seconds, with a fraction of the memory (40 MB instead of 640 MB): big tables only render the rows on screen.
- Open the Visualizations twice as fast: cards download their files as they scroll into view, and files shared by several cards or viewers are downloaded once. Batches with more than 300 runs show more cards as you scroll, or all of them with "show all".
- Commit pages load in 0.6 s instead of 1 s.
- Open tuning batches faster: runs that have an exact match in the reference no longer go through a name-similarity search.

### Everywhere in the web app
- Start the web app faster: it downloads a quarter less JavaScript on first load (date picker, error reporting and number formatting load only when needed), and servers send precompressed files.
- Come back to a page you already visited, or reload, and it shows up at once from your browser's cache, then refreshes in the background. Commits with running outputs keep updating.
- Open commits sooner: hovering a commit in a list starts loading its page, and a project's commits no longer wait for its configuration.
- Hover the History plot and image-heavy pages more smoothly: the page updates once you pause on a commit, and image viewers you've left no longer keep redrawing in the background.

### Logs
- Scroll through hundreds of runs in the Logs view without slowdowns.
- Open very long logs (tens of thousands of lines) several times faster, and search them without the page freezing for seconds.
- See the diff of big text files (logs, configurations...) with the reference sooner: the editor loads while the files download, instead of after.

### Images
- Find where images differ faster: on a 12 MP image in under a second instead of 4 to 8 seconds, on a 96 MP image in 4 to 5 seconds instead of 6 to 18 (under a second for another way to compare), and at once the next time. Differences of a few pixels in large images are no longer missed.
- Read the values of pixels in large 16-bit or raw images without waiting: the image viewer loads them by tiles of 64×64 pixels and keeps them, the server sends them as binary, decodes each image once even when many users open it at the same time, and no longer decodes images again after 20 others.

### Runs, batches and tuning
- Redoing runs from QA-Board respects the batch's concurrency, and uses the runner the runs were started with (e.g. Dask) and its settings. QA-Board used to start each run with its own `qa batch`, so they all ran at once, with the default runner.
- Runs that start again (redo, `qa batch`...) no longer show as failed, and count as failed, until they finish: their status is reset when they are pending or running.
- Finished runs whose metrics don't include `is_failed` count as successful, instead of neither successful nor failed.
- A stuck run's "Mark as Finished" action is now labelled "Mark as Failed", which is what it does.
- Moving runs to another batch closes the dialog, and saving a milestone no longer risks losing it.
- The tuning form shows a readable error instead of the server's raw response.
- The tuning form remembers the "Overwrite" option, and setting the number of iterations no longer crashes.
- Run Tests / Tuning runs as you when you open it from a link: it no longer asks for a user it can't let you type, with Send disabled.
- The Tuning Analysis view plots each iteration's metrics (those in the objective) next to the objective, for tunings run from now on: `qa optimize` used to get no metrics from the server.
- Projects whose inputs are inside the project (a relative `inputs.database`, like `inputs`) see their tests in the Run Tests / Tuning form and in Available Tests: they are looked for in the commit's artifacts, where the runs started from QA-Board run, instead of in a folder of the server. In monorepos, from the root *qaboard.yaml*'s folder, like `qa` does.
- Run Tests / Tuning and Available Tests find the inputs of projects whose `inputs.database` uses `{project}` or `{subproject}` (e.g. `/datasets/{project.name}`), instead of looking for them from `/`.
- When several of a commit's batch files define the same batch, Run Tests / Tuning and Available Tests use the last one, like `qa batch`, instead of the first.
- Listing a batch's tests no longer fails for commits that QA-Board saw before `qa` sent their *qaboard.yaml* (e.g. opened by branch name): it uses the project's, and the commit gets its own the next time `qa` runs on it.
- Run Tests / Tuning lists the tests of batches whose name contains `+`, `&` or `#`.
- When a batch has an input it can't use, like an empty `-` or a number, `qa batch` says which batch, in which file and at which line, instead of "Could not understand the inputs in the batch" followed by all its inputs. Available Tests and Run Tests / Tuning show the same error.
- Stopping a batch whose runs can't be stopped reports the error instead of failing.
- The tuning form no longer asks for an Android device, which runs never received.

### CLI
- With LSF job arrays and the Dask runner, `qa run` no longer deletes the log file its output goes to: errors are no longer lost.
- Runs started from a `git worktree` checkout are saved under their commit, instead of their branch name. Submodules with a relative `.git` pointer also work.
- On Windows, `qa batch` finds existing results for projects whose name contains a "/", instead of failing with "could not find any data on commit ID": `--action-on-existing` works there.
- `qa optimize` works with recent versions of scikit-optimize, instead of failing with "cannot import name 'Integer'".
- `qa optimize` no longer fails at the end when matplotlib isn't installed: it only skips its convergence plot.
- `qa batch --tuning-search` runs a grid search when the JSON doesn't say `search_type`, as the docs show, instead of failing with `KeyError: 'search_type'`.
- `qa` no longer warns that it doesn't know where your server is when you set `QABOARD_URL=http://localhost:5151`.
- `qa` no longer prints a git error when the commit it runs on isn't in the local clone (e.g. shallow CI clones): it only did without the commit's details. `QA_VERBOSE=1` still shows it.
- With Python 3.12 and later, `qa` no longer prints a `SyntaxWarning: invalid escape sequence` when it starts.
- `qa batch` accepts a single input written as text (`inputs: a.jpg`), and says that a batch written as a list (`my-batch: [a, b]`) must be a mapping with `inputs:`, also in the web app (the server used to call `exit()` there).
- `qa get` works with Python 3.13: it said "Could not find" for every variable.
- `bit_accuracy.on_reference_failed_ci: compare-first-parent` goes back up to `bit_accuracy.max_parents_depth` parents, instead of two at most.
- `bit_accuracy.failed_ci_job_name` works again: `qa check-bit-accuracy` only looks at that job (`<job> <subproject>` in subprojects).
- `qa check-bit-accuracy` counts skipped CI jobs as successful, instead of waiting for them.

### Server and administration
- The project's settings (metrics, visualizations, storage...) are no longer replaced by those of whichever branch got new results last: they come from the reference branch (`project.reference_branch` in *qaboard.yaml*), or from the project's first results.
- nginx starts on hosts without IPv6, instead of failing on its `listen [::]:80` line.
- Repositories whose clone is broken are cloned again, instead of failing until an admin deletes them. The broken clone is only replaced once the new clone succeeded.
- Tag pushes record the tag's whole name: its first character was cut.
- Pushes to repositories with files or folders whose name only looks like *qaboard.yaml* (for example an agent skill folder named `qaboard-yaml`) no longer fail: only files named exactly *qaboard.yaml* or *qatools.yaml* define projects.
- Jenkins integrations show the status of the builds they trigger when Jenkins' own URL uses another hostname than the integration's `build_url` (for example a full domain name): checking them failed with a 403 because no credentials matched that hostname in `JENKINS_AUTH`.
- Jenkins integrations trigger jobs that have no parameters, and when Jenkins refuses a build the error says why (HTTP status, Jenkins' message, a hint about `JENKINS_AUTH` or `build_url`) instead of showing a whole HTML page about a missing `location` header.
- Servers outside SIRC no longer show avatars from SIRC's directory for GitLab users without one: set `QABOARD_AVATAR_URL` to use your own ([environment variables](/docs/deploy#optional-environment-variables)).
- Backend workers no longer risk crashing, or losing Sentry events, when Sentry is enabled: Sentry starts in each uWSGI worker, and *uwsgi.ini* sets `py-call-uwsgi-fork-hooks`, as Sentry's SDK requires. Keep it if you use your own *uwsgi.ini*.

### Security and data safety
- Reading the values of an image's or a video's pixels, what's in a video, and finding where images or videos differ now require a login, and only read files in the storage (`QABOARD_STORAGE_ROOTS`) that you're allowed to see. Signed out, the viewers show the displayed values and say to sign in for the rest. These endpoints could read images anywhere on the server, without a login.
- The unused PDF report of the regions where images differ (`/api/v1/output/diff/report`) is removed: it could write files anywhere on the server, without a login.
- Marking a run as failed or deleting it now requires a login.
- On servers that restrict projects to some users, only users allowed on a project can stop, rename, move or delete its batches, delete a commit's results, save its artifacts, or change its milestones. Exporting runs also checks you can access the reference's project.
- `QABOARD_LOGIN_RESTRICTED=false` (or `0`) turns project restrictions off, as you would expect: any non-empty value used to turn them on.
- Deleting results no longer deletes the contents of folders that they link to.
- When a restricted project saves its results in a folder per user (e.g. `/algo/outputs/{user}`), the project's files are now restricted in every user's folder, not only in the server's.
- The API `qa` uses to update batches no longer lets anyone without a login delete runs. `qa optimize` still replaces its previous best iteration's runs, and only those.
- When `qa` fails to update QA-Board, its warning no longer prints your API token (`QA_TOKEN`).
- When signing up with a user name or email that is already used, the server answers "already taken" instead of an error that included the password's hash, and no longer writes the password to its logs.
- Logging in with an empty password is refused, and LDAP logins escape the user name.
- The server only deletes the git clones it made: it refuses repository paths inside a clone, or that hold other clones.
