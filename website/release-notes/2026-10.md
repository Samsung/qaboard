## Web app

### Runs activity
- See what waits and runs now, what ended recently and the batches that start soon in **Runs activity**, from your
  profile menu or a project's sidebar: your runs or everyone's, with a timeline of the load and the busiest projects,
  users and queues ([runs activity](/docs/user-guide/runs-activity)).
- Group runs by batch, commit, project, user, `qa batch` command, runner, queue, platform, status or any job option,
  and open each group's runs with their job options, when they were queued, started and ended, and links to their
  results, log and files.
- See the runs from before the upgrade too: they count as started when they were created, and ended after the time
  `qa run` measured them computing.
- Spot runs pending for over a day, mark your stuck runs as failed (their jobs aren't stopped), or stop a batch, from
  Runs activity.

### Storage usage
- See how much storage your runs use in **Storage usage**, from your profile menu or a project's sidebar: by project,
  batch, commit, branch and folder, the biggest first, filtered by project, branch, age or search
  ([storage usage](/docs/user-guide/storage-usage)).
- Paste the folder from a quota alert in **Folders** to see what QA-Board knows there, and open its subfolders.
- Delete the files of many runs at once: check batches, commits or branches, or everything that matches the filters.
  QA-Board says how much space it frees and what it keeps (milestones, other people's runs, running runs), asks you to
  type a confirmation for big deletions, and shows the deletion's progress and errors.
- Find out why IT's quota says something else, with the commands that measure a folder and find your biggest files and exports.
- See who uses the most storage in **Storage usage → Users**: a leaderboard with each person's share and biggest
  project, for everyone's runs or a project's. Click someone to see their runs; admins then delete them. Users see
  other people's usage only in the projects where they're developers or owners
  ([who sees what](/docs/backend-admin/storage#users-storage-usage)).
- Show all projects again in one click when **Storage usage** was opened from a project.
- Explore folders faster in **Storage usage → Folders**: it starts where your runs split, and skips folders that only
  lead to one subfolder.
- See each batch's and commit's message, author and date in **Storage usage**, and each branch's latest commit. Click a
  project, branch or person in a row to filter by it, and a row to select it.
- See how much space your deleted runs still take: deleting runs keeps their manifests, and the files written after
  they ended. QA-Board now measures what's left when it deletes runs.
- See what QA-Board deletes automatically, when, and what it keeps, on **Storage usage** and on the project's commit
  list (e.g. *Results deleted after 1 month*), with what the project's *qaboard.yaml* says. Several rules are summed
  up in a line: open it to see them all.
- Find your exports in **Storage usage → Exports**: their size, the runs they come from, and delete them without a
  terminal. Exports are links to the runs' files by default: QA-Board says how much space only frees once the runs are
  deleted too ([exports](/docs/user-guide/storage-usage#exports)).
- See what you own on disk that QA-Board doesn't track, from the latest storage scan, in **Storage usage → Not
  tracked**: old exports, runs QA-Board doesn't know, what deleted runs left, other files. Delete the folders that are
  all yours ([files QA-Board doesn't track](/docs/user-guide/storage-usage#files-qa-board-doesnt-track)).
- **Storage usage** replaces the *Quota* links: `QABOARD_QUOTA_URL_TEMPLATE` is no longer used.

### Comparing images
- Compare images like videos: side by side, with a wipe, one at a time in place (**Single**), or as their difference. Pick the mode above any image, or with the keys 1 to 4: it applies to all the images of the page, and links keep it. The swap button, or `t`, swaps the sides (around the difference too), or shows the other image in **Single**, and never changes the mode. It does it in every viewer of the page, so they all show the same one, and the keys work anywhere on the page, not only over an image. See [comparing images](/docs/user-guide/image-viewer).
- Compare an image with another file of the same run, like its ground truth or the input, side by side or as their difference: pick it in **vs reference ▾** above the image, where the likeliest files come first. Every run of the page then compares with its own file of that name, or only the run you're looking at with **Apply to: This run**, and `c` switches back and forth with the reference. The pick is for the page: another commit or batch compares with the reference again. See [comparing with another file](/docs/user-guide/image-viewer#compare-with-another-file-of-the-run).
- Run a blind test: **Blind test** above the images (or `h`) shows each viewer's images in a random order, called A and B everywhere, then **Reveal** shows which was which, and **Done** goes back to new first. See [blind test](/docs/user-guide/image-viewer#blind-test).
- See the difference between the new and reference images, all three in sync, with a cross on the pixel under your mouse in each, measured perceptually (YIQ), as ΔE 2000, per channel or as any change at all. **With the images** next to the modes, **Difference** again, or `4` again, shows it alone and larger. See [the difference](/docs/user-guide/image-viewer#the-difference).
- Zoom in and read the values of the pixels, written on them: the image's own values (10-bit, 16-bit, float, raw...) or the 8-bit colors on screen, picked from the **123** button above the images. Hover a pixel to see both, in both images, and their difference; `p` hides them. 8-bit images show one set of values: the screen shows them as they are. See [pixel values](/docs/user-guide/image-viewer#pixel-values).
- Compare images in full screen: the button at the right of the image viewer's toolbar, or `f`, gives the screen to the images, with all the viewer's tools, and the difference under them when that makes them larger. See [full screen](/docs/user-guide/image-viewer#full-screen).
- Adjust how images look with brightness, contrast, gamma, sharpening, one channel (R, G, B or luma), false colors or inverted colors. They apply to both images and to the same visualization of the other runs; the pixel values, the difference and the histograms stay the images'.
- Plot the row and column profiles of the view next to its histogram: the average of each column and row, with a ±1 std dev or min–max band, or the values along the row and column under the pointer. Hover a profile to see where it is on the images. The analysis button, in the toolbar above the images, opens a panel with three views, and remembers the one you picked last (`a` shows or hides it). See [profiles](/docs/user-guide/image-viewer#profiles).
- Analyze raw images by channel of their sensor: pick **Image values** in the analysis panel to get the statistics, row and column profiles and histograms of R, Gr, Gb and B, or of each sub-pixel, on the image's own values at full resolution. The card above shows the color filter array with a diagram, and where each value comes from: the image's metadata, guessed from the pixels (Bayer, Tetra, Nona… up to 9×9 cells), or what you set. Set the pattern and the black level once per project: your browser remembers them. See [raw images](/docs/user-guide/image-viewer#image-values).
- Read the statistics of the view per channel and image: mean, standard deviation, SNR, min, percentiles, max and the shares clipped at 0 and 255, with the differences between the images. Copy the table to paste it in a spreadsheet. See [statistics](/docs/user-guide/image-viewer#statistics).
- Highlight a range of values on the images: drag on the histogram and stripes show the pixels in the range, with the share of each image they cover. Click R, G, B or Y above the histogram to show one channel alone and pick its values. The channels' areas blend where they overlap, and the axis has ticks. See [histograms](/docs/user-guide/image-viewer#histograms).
- Find your way in large images: a minimap shows where you are once you zoom in, the zoom level says how many screen pixels an image pixel takes, **1:1** goes to 100%, and the histogram button overlays the histograms of the new and reference images in view.
- Step through the regions of interest with their thumbnails above the images, or with `[` and `]`. The regions menu finds where images differ most, by perceptual difference, SSIM or ΔE 2000: one region per place that changed, with how much it changed (e.g. *#1 · 3.2%*). The region set you pick applies to every viewer of the same file on the page, and searches like **Where they differ** only run on the page where you pick them.
- Copy or save the new, reference or difference image as you see them, or open the original files, from the copy button above the images.
- Find which runs' images changed most: **Where they differ, in all N runs…** in the image viewer's regions menu compares every run of the page with its reference and ranks them, from the largest difference to the identical ones. **Show** takes you to a run, on the region that changed most. The list says which runs it's comparing and for how long, and which wait for their turn. See [which runs changed most](/docs/user-guide/image-viewer#which-runs-changed-most).
- Pick how images are compared in the View options (**Compare images**), which replaces the Image diff switch. Links made with Image diff on open in difference mode.
- Use QA-Board's image viewer in your own React apps: it builds as a package (`npm run build:image-viewer`), with its props documented in its [README](https://github.com/Samsung/qaboard/tree/master/webapp/src/image-viewer).

### Videos
- Compare videos with a wipe, one at a time in place (**Single**), or as their difference, besides side by side. Zoom with the mouse wheel or a pinch and drag to pan: both videos follow, and zoomed in you see the actual pixels. See [comparing videos](/docs/user-guide/video-viewer).
- Step through videos frame by frame with the arrow keys, scrub, slow down to 0.1× or loop: new and reference stay on the same frame, and wait for each other when one is still downloading.
- Copy the current frame of a video (new, reference or their difference) to the clipboard, or save it as a PNG.
- Compare videos like images: the difference between the videos or alone, perceptual or in ΔE 2000, display adjustments, a blind test, full screen (`f`) and a minimap when zoomed in.
- Highlight a range of values on the videos, like on images: drag on the histogram of the frames, and pick its channels with R, G, B or Y. See [histograms](/docs/user-guide/video-viewer#histograms).
- See which frame each video shows when paused, numbered like in the file even with variable frame rates, and whether both show the same frame. See [which frames you are looking at](/docs/user-guide/video-viewer#which-frames-you-are-looking-at).
- Read the decoded values of the pixels (e.g. 10-bit Y′, Cb, Cr) of the very frame shown, under the pointer and written on the pixels when zoomed in, next to the 8-bit values your browser displays.
- See what's in the video files side by side (codec, pixel format, chroma subsampling, color range and matrix, frame rate, keyframes, dropped frames), with what differs highlighted and what it means for what you see.
- Find where two videos differ: the timeline shows how much each frame differs, `n` and `N` go to the frames that differ most, and regions show where and when they differ most, in the whole video or in the frame shown. See [where the videos differ](/docs/user-guide/video-viewer#where-the-videos-differ).
- Change the speed of videos with `<` and `>` (they were `[` and `]`, which now step through regions, like in the image viewer).

### Point clouds and trajectories
- See point clouds (`*.pcd` files) in 3D: the new run's, the reference's and a ground truth on the same axes, each in its own color, that you can show or hide, orbit, pan and zoom. See [point clouds and trajectories](/docs/viewers#point-clouds-and-trajectories).
- See 6DoF trajectories across the run's card, with the path in 3D next to the plots of each axis, at the same scale on every axis.

### Test reports
- See a run's JUnit XML test report (pytest, GoogleTest, CTest, Maven, Gradle...) as a tree of its tests, compared with the reference's: new failures, fixed, added, removed, newly flaky and skipped tests at a glance. Click the counts or the changes to filter, search tests and messages, press `n` for the next failure, and read each failure's message, trace and output next to the reference's. Files named *junit.xml* or *TEST-\*.xml* open in it ([test reports](/docs/user-guide/other-viewers#test-reports)).

### Configurations and reference runs
- See at a glance what's specific to each run: settings that all the runs shown share are hidden behind "··· N shared" tags, and listed once at the top of the page. It follows the filter. Turn it off with **Hide them in each run** ([reading configurations](/docs/user-guide/comparing-results#reading-configurations)).
- Read lists in configurations: `[1, 0.98, 0.95]`, long lists with their size (`… 64 values`, `3×3`) and where they changed (`…0.619, 0.7 → 0.635, 0.651…`). Tuning parameters show as settings like the others, with a wrench.
- Copy a run's settings as `qa` options (`-c … --tuning …`), as JSON or as a tuning search space, and a setting as text or JSON, from their hover menu.
- See how a run's configuration differs from its reference run's: added settings in green (+), removed ones struck through in red (−), changed values as `gain: 3 → 4`, and only the changed part of strings: `conf/[day → night].yaml`. Changes all runs share are listed once, at the top of the page. Hover the **Config** tag for a `git diff`-like view.
- Runs are compared with the reference run whose configuration is closest: the fewest different settings, then the most similar values (`base-v1` is closer to `base-v2` than to `other`). The **Config** tag says when other reference runs were as close.

### The commit page
- The commit page's view options are now a panel docked on the right that makes room for the results instead of covering them. Collapsed, a rail shows a dot on the sections that differ from the project's defaults, and hovering lists the changes. Press `o` to show or hide it, or drag its edge to resize it. See [View options](/docs/user-guide/commit-page#view-options).
- See and change what the commit page shows from **Files to show** (formerly Dynamic options): each option says which visualization it's for and lists the values of all runs. Options are linked across runs: a run that doesn't have the selected value shows the closest one and says so, and you can pick a value per run. See the [user guide](/docs/user-guide/commit-page#view-options).
- Open the export box from the new **Export** button next to the Visualizations and Output Files titles; press Enter to export, and find the last export's paths when you reopen it.
- Run cards fit the window when *qaboard.yaml* doesn't set their width (`outputs.style.width`): they used to be 1500 px wide, wider than a laptop's screen.
- Metrics Diff colors small changes and shows them precisely ("-0.37%" instead of "-0%"). The Summary's bars say how many runs met their metric's target.
- Find more explanations on hover: run statuses, aggregated metrics, `new`/`ref`, targets in the metrics tables, and milestones. The reference's bar says when it's the same commit as the new one.
- Pages use the width next to the sidebar instead of jumping between fixed widths, and the commit page fits laptop screens: its header cuts long commit messages and branches with "…".
- The Tuning Analysis view of a `qa optimize` experiment plots its convergence itself: each iteration's objective and the best one so far, even when matplotlib isn't installed where `qa optimize` ran.
- The commit page tells you when a commit's artifacts were deleted (when, and by whom) or are incomplete, what's missing, and lets you recreate them with your CI.
- Compare with several references, one at a time: hover the reference's bar and **Stack a reference** (a commit, a branch, a milestone, or the same one with another batch or filter), then switch with their tabs or `r` / `Shift r`. Drag tabs to reorder them, right-click them or click their **⋯** to duplicate, rename or remove them. They are in the URL. See [several references](/docs/user-guide/comparing-results#several-references).
- See each stacked reference under one name, in its tab, the reference's bar and the viewers: the first is "ref", the ones you add "ref 2", "ref 3"..., copies are `<name> copy`, and they keep their names when you reorder or remove references. Tabs say only what tells them apart: their batch or filter, their commit or branch, when the others' differ. Many tabs scroll sideways, with the mouse wheel too. See [several references](/docs/user-guide/comparing-results#several-references).
- Hover a reference's tab to see its commit, message, author, branch, batch, filter, and how many runs it has and how many failed.
- See everything you compare in the tabs: the top bar's results come first, then "vs" the references, and the two in the bars are lit. Swap the bars from their tabs' menus, or by dragging the first tab on a reference: the same comparison, reversed, and nothing is replaced. "Switch new/reference" is now **Swap the bars**.
- Name what you compare: click **new** or **ref** to call them `ISP v2` and `ISP v1`. The names are in the URL, and the page uses them: the images and videos' labels, the legends of plots, text diffs, flame graphs, HTML outputs, the Summary and the columns of Metrics Table and Metrics Diff. Milestones are called by their name, and you can rename them on the page too: the milestone's name then shows next to its star.
- See which is which by color: new is blue, references purple, magenta, teal and violet, in their bars, tabs, the viewers' labels, and the plots (the Summary's box plots, overlaid Plotly plots), in the light and dark themes. Results keep their color when you reorder, switch or remove references, or swap the bars, and a color freed by a removed reference goes to the next one you add. The history, the dashboard and the artifacts' files use the names and colors of what you compare too. The reference is no longer orange, a color that says "warning".
- Errors from redo, delete and tuning actions show a readable message instead of the raw server response.
- When you are logged out, actions that need a login (redo, delete, rename, tuning, restoring artifacts...) are greyed out next to a **Log in** button, instead of failing with an error. If your session expires, one message asks you to log in again.

- Filter output files from one line above them: **File options** (show all files, expand all folders, color-blind friendly...) moved to the View options, and the button says which are on. See [Output Files](/docs/user-guide/commit-page#output-files).
- See where a dragged reference tab will go: a bar marks the gap between the two tabs, and the tabs' row says "Move ref 3 between ref and ref 2".
- Open an input's History from its run's menu, or by hovering its name: the name is no longer a link you click by mistake.
- See tuning parameters in full in the run cards: they are never hidden behind "N shared" or cut short, and come first in the Logs view's one-line summaries.

### Logs, batches and redoing runs
- See how long each run ran in the Logs view, and find what you know about it in its **⋯** menu: its input's History, batch, input path, who ran it, its compute time, date and storage. See [Logs](/docs/user-guide/logs).
- The Logs view filters runs (all, failed, running) and tags failed runs with the reason (e.g. "LSF: out of memory"). The sidebar's Logs entry shows how many runs failed, or are still running.
- Show only the runs that succeeded: with **Successful** in the Logs view, or with `status:success` in the commit page's filter boxes. See the [filter syntax](/docs/user-guide/finding-results#filter-syntax).
- In the Logs view, each run fits on one line, with buttons to open its output directory, copy its Linux or Windows path, redo it, mark it as failed or delete it. Its full configuration shows when you open its logs.
- Switch between a run's `log.txt`, `log.lsf.txt` and `log.dask.txt`. For LSF runs, a summary shows the exit reason, host, run time and memory used vs requested, with hints that point to the batch's `lsf:` options.
- Batches started from QA-Board (tuning, "Run Tests") show whether `qa batch` is waiting for LSF, running, failed (with the error) or didn't start any run, with a link to its logs.
- See where the logs of each command that started a batch are: in the CI job (with a link), or in QA-Board (one click shows them). The batch's own `log.txt` only shows when it exists. See the [user guide](/docs/user-guide/logs).
- Show more of very long logs: they show their last 50,000 lines to stay fast, and say if the hidden lines have errors or matches for your search.
- When you filter a batch's runs, the commit bar menu redoes only the runs that match the filter. Follow redone runs in the Logs view, under "Started from QA-Board". See the [user guide](/docs/user-guide/running-from-the-webapp).
- The Available Tests view is a real editor for your private and shared batches: it flags YAML mistakes and inputs `qa batch` can't use as you type, shows whether your changes are saved (`Ctrl+S`), keeps them if you leave, and warns instead of overwriting someone else's changes. See the [user guide](/docs/user-guide/available-tests).
- Available Tests warns about what `qa batch` would ignore or misread: unknown keys like `inpts` (*Did you mean "inputs"?*), values of the wrong type, unknown runners and runner options, and input types the commit's *qaboard.yaml* doesn't define. Values defined at the top level and reused in batches with YAML anchors (`database: *lab-db`) aren't flagged as batches. See the [user guide](/docs/user-guide/available-tests).
- The Available Tests view lists the batches in each file: go to one, list the tests it resolves to on the commit, or run it in one click.
- When a batch has no tests in Available Tests or Run Tests / Tuning, see why: a batch file missing from the commit's artifacts (with the path QA-Board looked for), invalid YAML, a batch that no file defines, or inputs the server didn't find. See the [user guide](/docs/user-guide/available-tests).
- Redoing runs or starting tuning on a commit with missing artifacts first brings them back, instead of failing or running from a broken folder.
- Redo buttons work again on commits whose artifacts were deleted.
- The tuning form checks your settings while you type, and lists what would make the batch fail (unknown batch, invalid automated tuning configuration, unknown platform...) before you start the runs.
- The tuning form warns when the commit's artifacts are missing and will be restored first.
- See which batch files a batch started from the tuning form came from: the Logs view names them next to its `qa batch` command, e.g. *from qa/batches.yaml*, and says which file defines each batch when you open it. When several files define a batch, they're listed in order: the last one wins. See the [user guide](/docs/user-guide/logs#started-from-qa-board).
- Get an email when a batch you start from the tuning form ends: one email when its last run ends, with how many runs failed, the main metrics vs their targets, the best parameters and links to the failed runs' logs. See the [user guide](/docs/user-guide/running-from-the-webapp#emails-when-batches-end).

### Finding commits and projects
- See your own work first: signed in, a project's page lists the batches you started (from the web app or your terminal), the latest first, with their progress, and where the reference branch is. **Everyone** and the *N commits by everyone* count show everyone's, and the page remembers your choice ([yours or everyone's](/docs/user-guide/finding-results#yours-or-everyones)).
- Hide the CI's batches from commit lists with **Hide the CI**, to see what people ran from the web app or their terminal.
- Compare two batches from a project's **Batches** list: tick them, then **Compare**.
- Add the other emails of your git config in **Settings → Profile**, so that your commits count as yours.
- Search all of a project's commits from the commit list's search box, not only those in the date range: by message, committer, branch, batch or hash. Use `branch:`, `committer:`, `batch:`, `message:` or `id:` to look at one field, and `-word` to exclude ([searching commits](/docs/user-guide/finding-results#searching-commits)).
- Jump to a branch from the commit list's search box: when your search can be a branch name (one word, or a `branch:` term), it suggests the most recently active branches that match, even in projects with thousands of branches.
- Find commits by where their batches come from or who started them: `origin:webapp`, `origin:local` or `origin:ci`, and `user:kaito` in the commit list's search box ([searching commits](/docs/user-guide/finding-results#searching-commits)).
- Scroll through long commit lists: they show the 50 latest commits, then more as you scroll, so big projects open much faster, and **Older commits** at the end looks a week further back. Branch pages still get their whole date range at once (up to 1000 commits), for their metrics chart.
- Switch commit lists to **Compact** to see one commit per line, in aligned columns, with the full message, metrics and other batches on hover. The web app remembers your choice.
- Open the projects list much faster on sites with hundreds of projects: it downloads less, and shows more projects as you scroll.
- Start from a home page about you: signed in, `/` shows your projects, your batches running now with their progress and logs, those with failed runs this week (dismiss them once looked at), your recent batches with their main metric, and on demand what your teammates ran in your projects. New users see how to get their runs there ([your home page](/docs/user-guide/finding-results#home)).
- Browse projects by their path in **Explore**, at `/projects` (the home page when you're signed out): subprojects go under their repository, projects that share a prefix under a folder, and each card shows when people last used the project and its runs over 30 days. Open and close groups: the web app remembers them ([pick a project](/docs/user-guide/finding-results#projects-list)).

## CLI and project setup

### Signing in
- Sign in from the CLI with `qa auth login`: open the link it prints in any browser, even when `qa` runs over SSH,
  and approve the code. The token is saved per server in your config folder, never in your projects, so it works in
  every checkout and worktree. `qa auth status`, `qa auth logout` and `qa auth token` ([signing in](/docs/installation#signing-in)).
- Set `QABOARD_TOKEN` in CI to send verified results ([CI tokens](/docs/ci-integration#tokens)). `QA_TOKEN` and
  *~/.qaboard/secrets.yaml* still work.
- Read why the server refused your token (expired, revoked, missing a scope...) and what to do, instead of a stack trace.
  The advice fits where you are: in CI it's about `QABOARD_TOKEN`, never about signing in from a browser.
- CI jobs fail when QA-Board refuses their results, before running anything, instead of passing with nothing saved.
- `qa auth logout` only revokes the tokens `qa auth login` created: a token you saved with `--with-token` (e.g. your
  CI's) keeps working, unless you add `--revoke`.
- `qa auth status` says where the server's address comes from, and lists the other servers you're signed in to.
  A wrong `QABOARD_URL` or a server that's down is reported as such, not as a bad token.
- `qa gate --server` no longer sends your token for the default server to another server.
- `qa batch` says when the server won't show it the batch's runs (e.g. it requires signing in), and stops instead of
  running them all again when you asked to skip, sync or post-process the existing ones (`--action-on-existing`).

### Project setup and the qa CLI
- At SIRC, upgrading `qaboard` now requires also installing `qaboard-site-sirc`, see the [installation instructions](/docs/installation). Site packages provide a base `qaboard.yaml` that every project's configuration is merged on ([site defaults](/docs/project-init#site-defaults)): `qa init` shows the inherited values instead of overriding them.
- `qa init` creates a configuration that runs locally: LSF is commented out, and storage defaults to `/mnt/qaboard` like the server.
- The CLI reads your `QA_TOKEN` from `$QA_TOKEN` or `~/.qaboard/secrets.yaml`, and warns if other users can read that file.
- `QABOARD_API_VERIFY` controls the TLS verification of the CLI's requests to the server: `true` (the default), `false`, or the path to a CA bundle.
- Site packages (company-specific plugins) are no longer ignored on Python 3.8 and 3.9, and the package includes the `qatools` compatibility package.
- `qa save-artifacts` saves the subprojects' *qaboard.yaml*: without it, runs redone from the artifacts used the parent project's configuration and were saved in the parent project.
- Get an email when the runs of `qa --share batch` end (`export QA_NOTIFY=none` to stop them). It's never sent in CI, and batches started by other batches, like pipeline steps, count as part of the first one. See the [CLI tips](/docs/using-the-qa-cli#email-when-the-runs-end).
- See the link to your results when `qa batch` ends, not only when it starts.
- Tell your users how to get storage for new projects from your site package, with `QABOARD_STORAGE_HELP` ([docs](/docs/project-init#site-defaults)).
- `qa` tells QA-Board where it runs: from the web app, your terminal, or a CI pipeline (GitLab, GitHub Actions, Jenkins, Buildkite…, with links to the pipeline). QA-Board uses it to show you your own runs and leave out the CI's. Older versions of `qa` keep working: QA-Board guesses as before.
- `metadata(context)` in your entrypoint gets the run's context, like `run(context)`: filter batches on the configurations, the platform or the batch's name. `metadata(absolute_input_path, database, input_path)` still works. See [Input metadata](/docs/metadata-integration-external-databases#creating-metadata).

### Runners: LSF, Dask and Windows
- LSF runs write their output live to `log.lsf.txt`, with LSF's job report at the end. `qa batch` no longer passes an LSF queue or project when none is set, and fails fast when `bsub` is missing.
- With `--no-wait` and an existing Dask cluster (`scheduler_address`), the Dask runner now enforces `concurrency`: a driver LSF job sends the runs, as without `scheduler_address`. See the [Dask runner](/docs/dask-integration).
- `qa batch --runs-file runs.json` does a list of runs, each with its input, configurations, parameters and runner options. QA-Board uses it to redo runs together. See the [CLI tips](/docs/using-the-qa-cli).
- Read the logs of `qa --share batch` and `qa optimize` started from a terminal in QA-Board, with the batch's commands: they save what they print in the batch directory (under `qa-batch-logs/`), errors included. `qa optimize` includes the output of its iterations. In the CI, the CI keeps the logs. See the [CLI tips](/docs/using-the-qa-cli).
- Configure the Windows runner: PowerShell's `$ErrorActionPreference` per job (the batch's `error_action:` option) or with `QA_RUNNER_ERROR_ACTION`, and how long `qa batch` waits for its Jenkins builds, now 2 hours by default (`QA_JENKINS_TIMEOUT`, `QA_JENKINS_STATUS_INTERVAL`).
- Batches list their inputs in the same order on every machine: the inputs found by `globs` are sorted by path, instead of coming in the order the filesystem lists them.
- The Windows (Jenkins) runner sends your token. Without one, the server only starts the Jenkins jobs listed in your *qaboard.yaml* ([docs](/docs/jenkins-integration)).
- Keep Celery passwords out of git: the URLs of `runners.celery` in *qaboard.yaml* expand environment variables, like `${QA_CELERY_PASSWORD}`. Admins can give each team its own RabbitMQ account ([sharing the broker](/docs/celery-integration#sharing-the-servers-broker-between-teams)).

### GitHub, CI and the quality gate
- Fail the CI when quality regresses, with the experimental `qa gate`: set rules in *qaboard.yaml* (`gate:`) on the median of a metric vs a reference branch, milestone or commit, on each test, on failed runs or on bit-accuracy. It prints a table (or Markdown, or JSON), fills the GitHub Actions job summary, and can post a commit status to GitHub or GitLab that links to the Metrics Diff. See [Quality gate](/docs/quality-gate).
- Gate pass/fail metrics with `aggregate:` on `qa gate` rules: `{metric: unsafe_actions, max: 0, aggregate: max}` fails as soon as one test is unsafe, and `aggregate: mean` checks a pass rate, where the median said little ([quality gate](/docs/quality-gate#passfail-metrics)).
- Compare with any milestone in `qa gate`: `--reference '#12'` (or `gate.reference`) uses the milestone whose link is `/<project>/milestone/12-...`, shared or not, and the gate compares with the milestone's batch ([quality gate](/docs/quality-gate)).
- `qa batch` sets a commit status that links to the results on GitHub too ([CI integration](/docs/ci-integration)).
- `qa check-bit-accuracy` waits for the GitHub checks of the reference commit too, like it does for GitLab pipelines ([bit-accuracy](/docs/bit-accuracy)).
- `qa check-bit-accuracy` asks QA-Board where the reference's runs are, instead of guessing their folders. Offline, or for runs QA-Board doesn't know, it looks in the storage, in every user's folder when your storage settings have a `{user}`, and says where it looked when a run is missing ([where runs are found](/docs/bit-accuracy#where-runs-are-found)).
- Compare with the reference's closest runs: `qa check-bit-accuracy --reference-match closest` picks, on each input, the reference run the web app would show, with the closest configurations, tuning parameters and platform, and says how it differs ([options](/docs/bit-accuracy#options)).
- In GitHub Actions, `qa` records the pull request's branch and last commit instead of the temporary merge commit, and the tag of tag builds ([CI integration](/docs/ci-integration#example-with-github-actions)).
- `qa` finds your git host, its API and its token in `QABOARD_GIT_HOSTS` too, and sends `GITHUB_ACCESS_TOKEN` only to github.com and the GitHub hosts you configured ([git hosts](/docs/backend-admin/git-hosts#the-cli)).
- In CI, `qa`'s Sentry reports are tagged with its version, and `QABOARD_SENTRY_VERIFY` (or `SENTRY_CA_CERTS`) can be the CA bundle that signed your Sentry server's certificate, or `system` ([the qa CLI](/docs/backend-admin/monitoring#the-qa-cli)).

### qaboard.yaml
- Get completion, docs on hover and warnings for typos when you edit *qaboard.yaml*, batch and metrics files, in VS Code or any editor using the YAML language server: QA-Board publishes their JSON schemas, and the files `qa init` creates declare them ([project setup](/docs/project-init#checking-qaboardyaml-and-batch-files-in-your-editor)).
- Set the frame rate of a video visualization with `fps` in *qaboard.yaml*, when the web app's guess is wrong. See [the video viewer](/docs/viewers#videos).
- Warn users who start tuning on branches whose commits have no artifacts: list the branches your CI saves them for in *qaboard.yaml*'s `tuning.branches`. The tuning form offers the platforms listed in `inputs.platforms` ([tuning from QA-Board](/docs/tuning-from-the-webapp)).
- Summarize metrics per tag of the inputs (their metadata's `tags`) on the History page, with `dashboard_breakdown_by_tag: true` in your metrics file ([metrics](/docs/computing-quantitative-metrics)).
- Add `recreate_artifacts` to *qaboard.yaml* to have QA-Board rebuild a commit's deleted artifacts with a GitlabCI job, a Jenkins job or a webhook, when users redo runs or start tuning. Pass who asked (`${user.email}`, `${user.full_name}`) and the commit (`${commit.short_id}`, `${commit.message}`...) to your CI ([docs](/docs/storage/deleting-old-data#recreating-artifacts)).

## Server and administration
- Stop a deploy when a database migration fails: the output says which migration and why, and nothing running is changed. Migrations used to be skipped silently instead, leaving a database the backend then failed on, with errors like *column … does not exist*. The backend also doesn't start on a failed migration. If your database misses migrations because of this, find the latest one it has, then `alembic stamp <revision> && alembic upgrade head` in the backend's container ([deployment](/docs/backend-admin/deployment)).
- Upgrading saves where batches come from and who started them, and who wrote commits (their email). The migration fills in existing batches a few thousand at a time, so results keep coming in meanwhile: expect a few minutes on big databases. Results sent with a service account's token always count as the CI's.
- Upgrading adds a `project_views` table (who opened which project, written at most once an hour per user and project), for the projects you look at. `/api/v1/projects` also says when people last used each project, its batches per day, and how many users viewed it, and to signed-in users when they last ran or committed there (`my_latest_activity`).
- `/api/v1/batches` lists the batches of several projects (`projects=a,b`, skipping those you can't read), others' batches (`scope=others`), those with waiting or failed runs (`status=pending|failed`, over the last 30 days by default, 90 at most), recent ones (`since_days=`), and each project's default metric (`metrics=default`).
- Upgrading adds an index of the failed runs by batch (small: few runs fail), built without blocking writes: the home page finds your batches with failed runs without reading all their runs.
- **Users, tokens and admins**: an admin panel, settings in the database, and an audit log ([user management](/docs/backend-admin/user-management)).
  - Make admins with `QABOARD_ADMINS`, from the admin panel, or with `qaboard-admin create-admin` in the backend's container. Approve or disable accounts waiting for an admin.
  - Change settings from **Admin → Settings** without restarting the server: requiring sign-in, local sign-up, token
    lifetimes, how results are authenticated. Environment variables still win when they're set.
  - Require tokens to send results: `ingest.auth` (or `QABOARD_INGEST_AUTH`) goes from `off` (the default) to `warn`
    (`qa` asks users to sign in) to `token` ([results sent by qa](/docs/backend-admin/user-management#results-sent-by-qa)).
  - Find sign-ins, failed sign-ins, token changes, CLI logins and admin changes in the audit log, with who and from which IP.
  - Tokens are stored hashed, can have scopes, projects and an expiry date, and expire when unused for long if you want.
  - Disabled accounts stop working at once: their sessions and tokens are refused at the next request.
  - Create service accounts for the whole server in **Admin → Service accounts**: bots with their own `qab_svc_…`
    tokens, a role on all projects or none, that projects' owners add to their projects. Projects' owners create
    their own from the Access tab ([service accounts](/docs/backend-admin/user-management#service-accounts)). Upgrading adds two columns to `users`.
- **Roles on projects** (viewer, developer, owner), managed by projects' owners from the web app
  ([project access and roles](/docs/backend-admin/project-access)). Nothing changes on upgrade: projects are public and
  signed-in users developers, until you set `projects.default_visibility` and `projects.signed_in_role`.
  - Create groups in **Admin → Groups**, filled by hand or by sign-in claims: SSO groups, LDAP `memberOf`, email domains.
  - Give users or groups a role on all projects, private ones included.
  - Projects in `QABOARD_LOGIN_RESTRICTED_YAML` stay restricted: they're private, the users its rules match their developers.
  - Files of private projects under `/s/` follow their roles, and tokens limited to other projects can't read them.
  - Users' groups are updated every day, and as soon as you change a rule: LDAP accounts from the directory's
    `memberOf` (optionally with Active Directory's nested groups), single sign-on accounts with refresh tokens if you
    enable **Refresh groups daily** on the provider. **Update now** in **Admin → Groups** runs it at once.
  - Rules can read nested claims, like Keycloak's `realm_access.roles`, and signing in with LDAP or single sign-on
    keeps the groups the other gave.
- **Clean the storage from the admin panel** ([cleaning the storage](/docs/backend-admin/storage)).
  - Delete for good the runs users deleted, in **Admin → Storage**: choose projects with patterns (`group/*`, with
    exceptions) and the runs' dates, count them, and start a dry run first. Milestones are never deleted.
  - Purge the runs whose folder was deleted outside QA-Board (quota scripts, users...): only their metadata is deleted.
    Runs are never purged from a folder missing right under a storage root, in case the storage isn't mounted.
  - Delete commits' artifacts: by project and by how long commits went without runs, keeping milestones' artifacts, the
    reference branch's, and what you list (groups, paths, globs).
  - Follow each job's progress and log, and see every error with the file and its owner, grouped by kind, owner and
    project, or download them as CSV. Errors don't stop the job: the runs are kept and the next job tries again.
  - Schedule jobs with cron expressions in your time zone, instead of cron jobs on the server: hard deletes, and
    *Delete old results* (like `qaboard_clean`), with a default age for the projects whose *qaboard.yaml* says nothing.
  - Get an email when a scheduled job fails or ends with errors, with the first errors and a link to the job: admins
    get it by default, `jobs.failure_email_to` sends it to others, `jobs.failure_emails` turns it off
    ([schedule jobs](/docs/backend-admin/storage#schedule-jobs)).
  - Get a Sentry issue when a job fails, ends with errors or is given up, one per kind of job, and when the jobs worker
    itself runs into errors ([Monitoring with Sentry](/docs/backend-admin/monitoring#jobs-worker)).
  - Choose who sees other people's storage usage with `storage.others_visible_to`: by default, admins and each
    project's developers and owners from a grant, a group or *qaboard.yaml*, not every signed-in user.
  - Users' storage usage is kept up to date by the worker, and rebuilt nightly by a *Storage usage* schedule it creates
    (`QABOARD_STORAGE_USAGE_AUTO=0` to manage it yourself). A migration adds the `storage_usage` table, and an index on
    `ci_commits.latest_output_datetime`, built without blocking writes.
  - **Scan the storage** to find what QA-Board doesn't track, in the projects' folders or any other: untracked runs
    and exports, what deleted runs and artifacts left, other files, with their owners. Explore the results like `ncdu`:
    folders by size with what they're made of, or the biggest untracked things anywhere, by owner or age. Delete them,
    track the exports so their owners see them, or add the runs back to QA-Board. What QA-Board uses can't be deleted
    from there ([scanning the storage](/docs/backend-admin/storage#scanning-the-storage)).
  - Cancel a scan in seconds, even deep in a huge folder, and follow a running scan by the folders it has read.
  - Delete old scans' results from **Admin → Storage → Scans** or the scan's page (the files stay on disk). The list
    shows the latest scans, the older ones on demand.
  - Stop a job stuck cancelling with **Stop without waiting**, e.g. when its worker is stuck on a storage that doesn't
    answer: another job of its kind can then start.
  - See the schedules in a line (how many are enabled, the next one, those whose last run went wrong) when there are
    many, and their table when you open it.
  - Put the exports in one place with the `storage.exports_root` setting (`QABOARD_EXPORTS_ROOT`):
    `<root>/<user>/<project>/<date>-<id>`, instead of a `share/` folder next to the commit's results. QA-Board now
    tracks exports made from the web app, and their size.
  - Measure what runs deleted before this release left on disk with the *Measure what deleted runs left* job.
    A migration adds the `exports`, `storage_scans` and `storage_scan_entries` tables.
  - Jobs run in a worker the backend starts next to the web server (`QABOARD_JOBS_WORKER=0` to run it elsewhere), and
    resume after a restart. From the backend's container: `qaboard-admin jobs list|start|worker`.
- **Runs activity** for admins: everyone's waiting and running runs, the load over time, and the busiest projects, users
  and queues ([runs activity](/docs/user-guide/runs-activity)).
  - Mark the runs stuck as running (pending for over a week, or what you choose) as failed with the *Fail stuck runs*
    job, now or on a schedule; Runs activity offers it when it sees such runs ([fail stuck runs](/docs/backend-admin/storage#fail-stuck-runs)).
  - Runs now record when they were queued, started and ended. A migration adds three nullable columns to `outputs` (no
    table rewrite; it gives up after 10 seconds if it can't lock the table, run it again then), and small partial
    indexes built without blocking writes: expect a few minutes on big databases, as each index build reads the table.
- **Single sign-on** with OpenID Connect (Keycloak, Entra ID, Okta, Google...), next to LDAP, SAML and local accounts
  ([sign-in and single sign-on](/docs/backend-admin/sign-in)).
  - Set `QABOARD_OIDC_ISSUER`, `QABOARD_OIDC_CLIENT_ID` and `QABOARD_OIDC_CLIENT_SECRET`; add more providers from
    **Admin → Sign-in**.
  - Find what's wrong before users do: `qaboard-admin check-sign-in` and **Admin → Sign-in → Test** check that the server
    reaches your identity provider, the issuer, the signing keys, and whether the redirect URI is registered.
  - Keep users' accounts when they move to single sign-on: match them by user name when your identity provider shares
    LDAP's directory, or by verified email.
  - Send users straight to your identity provider with `auth.sso_auto_redirect`; `/login?local=1` keeps a way in for
    local admins.
- Decide who gets an account with `auth.access_policy`: everyone, emails of some domains, or after an admin approves.
  Admins get an email and a webhook message (Slack, Teams, Mattermost) when someone waits.
- Sessions are stored on the server: they end after `sessions.idle_days` without activity and `sessions.max_days` in any
  case, users and admins can end them, and disabling a user ends theirs. Nobody is signed out by the upgrade.
- Use LDAP over TLS: `ldaps://` in `QABOARD_LDAP_HOST`, or `QABOARD_LDAP_START_TLS=true`.
- Sign-in, sign-up and `qa auth login` are rate-limited by the shipped nginx configuration. Behind a load balancer or
  an ingress, set `QABOARD_TRUSTED_PROXY_HOPS=1` to record users' IPs in the audit log.
- Keep the commit lists of projects with many runs per batch fast: list them in `QABOARD_SKIP_METRICS_AGGREGATION` (project ids, or their start like `group/`), and their commit lists skip the batches' aggregated metrics, which commit pages still show ([environment variables](/docs/deploy#optional-environment-variables)).
- Jenkins builds started from QA-Board send the job's `token` from *qaboard.yaml*, else the server's new `JENKINS_BUILD_TOKEN`, else none, instead of the token `qaboard`. If your Jenkins jobs expect `qaboard` and your integrations don't set `token`, set `JENKINS_BUILD_TOKEN=qaboard` before upgrading ([Jenkins builds](/docs/triggering-third-party-tools#trigger-jenkins-builds)).
- Free more storage: the cleanup of old results (`qaboard_clean`) keeps only the batches that are milestones, not all the batches of their commit ([deleting old data](/docs/storage/deleting-old-data)).
- Delete a commit's runs from the web app even when it has milestones: its milestone batches are kept.
- Upgrade the database with a migration that moves shared milestones from the projects' data to their own table; the old data stays for rollbacks.
- Get your shared milestones back on servers where the upgrade failed to copy them because the projects' data was in an older format: the next upgrade converts it and copies them.
- **Before you upgrade**: settings to check and data to move first.
  - Records each existing project's git host, with a migration that uses the deploy's git host settings. **Before upgrading, keep `GITLAB_HOST` set**, or list your GitLab in `QABOARD_GIT_HOSTS` with the hostnames older projects used ([upgrading](/docs/backend-admin/git-hosts#upgrading-from-older-versions)).
  - Security: the server only writes, deletes or runs code in the folders listed in `QABOARD_STORAGE_ROOTS` (default: `/mnt/qaboard`), and refuses results stored elsewhere. **If your projects store results in other folders, set it before upgrading** (see [environment variables](/docs/deploy#optional-environment-variables)).
  - Security: the server only loads avatars and badges for the web app from your GitLab hosts and gravatar. **If your projects' `avatar_url` or badges (`integrations[].src`) come from other hosts, list them in `QABOARD_PROXY_HOSTS`** (see [environment variables](/docs/deploy#optional-environment-variables)).
  - Daily database backups older than 14 days are deleted after each successful backup, but never the newest 3, nor dumps with other names. Set `QABOARD_BACKUP_RETENTION_DAYS` to keep them longer (`0` keeps them all). **Before upgrading, move the old daily backups you want to keep** ([backups](/docs/backend-admin/deployment#backups)).
  - Versions from before October 2026 don't start on a database migrated by this one: to roll back to them, first undo the newer migrations ([rollbacks](/docs/backend-admin/deployment)).
  - The `website` image (the docs your server serves) is built from the repository's root, like the `frontend` image: if you build it without `docker compose`, run `docker build -f website/Dockerfile .`.
  - Local sign-up is off by default with LDAP or SAML: local accounts could take the name of directory users who never
    signed in. Turn on `auth.local_signup` in the admin panel if you need it.
  - **Name your first admins** in `QABOARD_ADMINS` (user names, or the emails of LDAP/SAML accounts), else nobody can
    open the admin panel. Without access to the web app: `qaboard-admin create-admin <user>` in the backend's container.
  - Existing API tokens are hashed by the migration and keep working, as "legacy" tokens (they can read, send results
    and act, not use the admin API). **After this upgrade, older versions can't use any API token**, even after a
    plain rollback of the code (and while old backends still run during the deploy), and they ignore what you set in
    the admin panel, like requiring sign-in, and disabled accounts. If you may roll back, set what matters with
    environment variables. Downgrading the database (`alembic downgrade`) deletes the tokens.
  - Results sent with an unknown, expired or revoked token are now refused, even when `ingest.auth` is `off`: before,
    the token was ignored. Check the `QABOARD_TOKEN`/`QA_TOKEN` of your CI jobs (and users' shell profiles).
  - The audit log records the address nginx sees, not `X-Forwarded-For`, unless you set `QABOARD_TRUSTED_PROXY_HOPS`:
    clients could choose what it says. Behind a load balancer or an ingress, set it to `1`.
  - `QABOARD_LOGIN_REQUIRED=true` now also blocks anonymous requests to the API, so CI jobs that read results
    (`qa gate`, `qa check-bit-accuracy`) need a token with the `read` scope. `QABOARD_LOGIN_REQUIRED=false` now allows
    anonymous users (any non-empty value used to block them), and an empty value lets you set it in the admin panel.
  - At SIRC, QA-Board no longer serves the storage over WebDAV (`/davs/algo/`): it let anyone write and delete files. `services/nginx/webdav.conf` explains how to bring it back.
- **Deploying: Compose, Kubernetes, quickstart**: zero-downtime deploys, published images, a Helm chart and a quickstart.
  - Zero-downtime deploys with [deployments/deploy.py](/docs/backend-admin/deployment): images tagged per version, several backend replicas behind nginx, rolling updates, `rollback`, `status` and `restore-db`.
  - `deploy.py seed-db` fills a staging database with only production's recent data.
  - Pull QA-Board's images from `ghcr.io/samsung/qaboard`: `docker-compose.yml` uses them by default, each release has its own tags (e.g. `backend-1.2.0`), and `QABOARD_IMAGE` picks another registry.
  - Run QA-Board on Kubernetes with the [Helm chart](/docs/backend-admin/kubernetes) published with each release, `oci://ghcr.io/samsung/charts/qaboard`.
  - Try QA-Board on your laptop with kind: `charts/qaboard/quickstart.yaml` and `charts/qaboard/kind.yaml` start a small cluster with the docs' demo projects (the chart's new `demoData` setting), where the `qa` CLI can save results (see [the quickstart](/docs/backend-admin/kubernetes)).
  - Mount the storage where runs save results with the chart's new `results` setting (an existing claim, a new volume, NFS or a node folder): the chart mounts it where the backend, nginx and Cantaloupe expect it, and sets `QABOARD_STORAGE_ROOTS`.
  - The Helm chart's migrations Job gets the chart's `config:` settings, which data migrations need ([Kubernetes](/docs/backend-admin/kubernetes)).
  - Try QA-Board on your computer with demo projects to look at: download one Compose file, `deployments/quickstart/compose.yml`, and run `docker compose up -d --wait` (see the [quickstart](/docs/get-started/quickstart)). It only answers on your computer.
  - Build the website image behind a proxy that blocks some of the docs' media: with `QABOARD_MEDIA_MISSING=remote`, readers' browsers load them from the media host or your mirror (`QABOARD_MEDIA_BASE_URL`), and with `placeholder` they render as placeholders, instead of failing the build.
  - The backend has a `/api/v1/health` endpoint, shuts down gracefully, and keeps working when redis is down.
  - The web app links to the docs served by your server at `/docs/`, which match its version, instead of the public website. Set `QABOARD_DOCS_ROOT` to use another docs site.
  - Add pages for your own users to the docs your server serves: put them in `website/site-docs/<site>/` and build with `QABOARD_SITE=<site>`. They get their own menu, and the installation page links to them. At SIRC, "At SIRC" has the install commands and SIRC specifics.
- **Git hosts and webhooks**: GitHub, GitLab, Gitea/Forgejo and Bitbucket, with safer tokens and webhooks.
  - Configure all your git hosts (GitHub and GitHub Enterprise, GitLab, Gitea/Forgejo, Bitbucket, other git servers), each with its own token and webhook secret, with `QABOARD_GIT_HOSTS` ([git hosts](/docs/backend-admin/git-hosts)).
  - Keeps your current git settings working: `GITLAB_HOST` (also without a scheme, or with credentials), `GITLAB_ACCESS_TOKEN`, `GITHUB_ACCESS_TOKEN`, `QABOARD_GITHUB_HOSTS` for GitHub Enterprise, and `QABOARD_GITLAB_HOSTS`, whose hostnames are other names of `GITLAB_HOST`. A GitLab and a GitHub host can share a hostname ([backward compatibility](/docs/backend-admin/git-hosts#backward-compatibility)).
  - Receives the push events of repositories on Gitea, Forgejo and Bitbucket Cloud, at `/webhook/gitea` (or `/webhook/forgejo`) and `/webhook/bitbucket` ([webhooks](/docs/backend-admin/git-hosts#webhooks), [project setup](/docs/project-init#optional-connect-your-git-host)).
  - Require a secret in push webhooks: set `QABOARD_WEBHOOK_SECRET`, and the same secret in your repositories' webhooks, so that only your git hosts can send push events ([webhooks](/docs/backend-admin/git-hosts#webhooks)).
  - Stops saving git tokens in new clones' `.git/config`, or showing them in error messages: git gets them from a credential helper, and only for their own host (it needs git 2.31 or newer). Clones made by older versions still have the token in their remote URL: [remove it](/docs/backend-admin/git-hosts#tokens).
  - Stops sending git tokens, and GitLab session cookies, to another host when git or API calls are redirected there, and reads tokens and webhook secrets only from its environment, not from the CLI's shared secrets file (`QA_SECRETS`).
  - Webhooks are stricter. They refuse push events: without a webhook secret once any host has one or `QABOARD_WEBHOOK_SECRET` is set (`401`), from git hosts the server doesn't know (`403`; pushes to `/webhook/gitlab` from unknown hostnames still go to your GitLab), that would move a project to another git host (`409`), or over 25 MB (`413`). They ignore other events, like GitHub's `ping`, and answer `503` while the git host settings are invalid, instead of the server failing to start.
- **Security and access to files**: logins for actions, and who can read which files.
  - Security: actions that run commands (redo, tuning, stopping or deleting batches...) now require a login and run as the logged-in user, and their inputs are escaped. See SECURITY.md.
  - Redoing, deleting or marking a run as failed now requires access to its project, for restricted projects.
  - Each batch started from QA-Board gets its own folder with its scripts and logs, under the batch's `qaboard-batches/`.
  - Restrict who can read the files of restricted projects, or of the folders you list under `paths` in `users_restrict.yml`: nginx asks the backend before sending each file (see [user management](/docs/backend-admin/user-management#restricting-who-can-read-files)). If you use your own nginx configuration, include `snippets/qaboard-files.conf` in the `/s/` locations to get the file browser.
  - In the folders listed in `QABOARD_FILES_UNIX_PERMISSIONS` (e.g. `/home`), users only read the files that their own Unix account can read (see [user management](/docs/backend-admin/user-management#unix-permissions)).
  - Without a complete `/etc/passwd`, e.g. with LDAP or SSSD, `QABOARD_ACCOUNTS_COMMAND` (and `QABOARD_GROUPS_COMMAND`) gives the backend the users' accounts, refreshed daily: the file browser shows owners' names instead of their ids (see [users' accounts](/docs/backend-admin/user-management#users-accounts)).
- **Settings**: support and login hints, simpler result uploads.
  - Configure the support link with `QABOARD_SUPPORT_URL`.
  - Tell users which credentials to use when they can't log in, with `QABOARD_LOGIN_HINT`, and where to install WebCDE, which opens runs with a `cde.sh`, with `QABOARD_WEBCDE_INSTALLER` ([environment variables](/docs/deploy#optional-environment-variables)). The tuning form's feedback link goes to `QABOARD_SUPPORT_URL`.
  - Email users when the batches they start end: set `QABOARD_SMTP_HOST`, and optionally the sender, reply-to address and email domain (`QABOARD_EMAIL_FROM`, `QABOARD_EMAIL_REPLY_TO`, `QABOARD_EMAIL_DOMAIN`). A migration adds a `batch_notifications` table and an index of the pending runs, built without blocking writes ([emails](/docs/deploy#emails)).
  - Scripts can send results that describe their commit with only `commit_sha` and `commit_authored_datetime`: the other `commit_*` fields (branch, message, committer, parents) are optional, and the server doesn't need access to the git repository.
- **Database**: faster commit lists, safer migrations, tunable PostgreSQL.
  - Lists of commits answer many times faster on big projects, and use much less memory: they no longer load every output of every commit.
  - Adds two indexes on `ci_commits`, to list commits faster. They are built without blocking writes, which can take a few minutes on big databases. If building one fails, the next deploy builds it again.
  - Starts even when the database has migrations it doesn't know, made by a newer version, e.g. after a rollback: it keeps them.
  - Tune PostgreSQL with a settings file: use `services/db/init.sh` as the database's entrypoint and it includes `services/db/qaboard.conf` (or your own, `QABOARD_DB_CONFIG`) in PostgreSQL's configuration at every start, and in new databases right away, with the `pg_stat_statements` extension ([database settings](/docs/backend-admin/deployment#database-settings)).
  - Size the backend's database connection pools with `QABOARD_DB_POOL_SIZE` and `QABOARD_DB_MAX_OVERFLOW` (default 4 and 2 per uwsgi process, instead of 10 and 5): PostgreSQL's `max_connections` can stay small. The backend checks connections before using them, so it keeps working after a restart of the database.
  - The database gets two minutes to stop cleanly (`stop_grace_period` in *production.yml*), instead of being killed after 10 seconds and replaying its log at the next start.
- **Monitoring with Sentry**: traces from the browser to the database.
  - See where the backend spends its time in Sentry: traces of API requests include their database queries, and a share of the backend's processes are profiled (`SENTRY_PROFILE_SESSION_SAMPLE_RATE`). Celery workers report their errors and tasks too ([Monitoring with Sentry](/docs/backend-admin/monitoring)).
  - See the web app's page loads, web vitals (LCP, CLS, INP) and the API requests they make in the same Sentry trace as the backend's work, with readable stack traces: set `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT` and `SENTRY_URL` when you build the `frontend` image to upload its source maps, that are then no longer served.
  - Sentry is enabled by `SENTRY_DSN` alone (it also required `FLASK_ENV=production`), tags events with `SENTRY_ENVIRONMENT` and the release, traces 20% of requests by default (`SENTRY_TRACES_SAMPLE_RATE`), and checks the Sentry server's certificate (`CA_CERT_URL` build argument or `SENTRY_CA_CERTS`). Users are identified by their username only, tokens are filtered out, and `SENTRY_FRONTEND_DSN` sends the web app's events to their own project.
- **API**: for scripts, agents and the image viewer.
  - Get the numbers of the Summary and Metrics Diff views from scripts and agents, with the experimental `/api/v1/commit/<sha>/compare`: each metric's median vs a reference, each run vs its reference run, and how many runs failed. See [Quality gate](/docs/quality-gate#from-scripts-and-agents).
  - API: page through `/api/v1/commits` with `limit` and `offset` (the `X-Has-More` header tells if there are more) and search them with `q`, find branches with `/api/v1/project/branches?q=...`, and get a much smaller list of projects with `/api/v1/projects?summary=true` ([lists of commits](/docs/apis#lists-of-commits-branches-and-projects)). Without these parameters, they answer as before.
  - The API reads the values of a region of an image, for the image viewer's pixel values: `GET /api/v1/output/image/pixels` with `image_url`, `x`, `y`, `w` and `h` (up to 256×256 pixels), as JSON, or as binary with `format=binary` (their type and shape in the `X-Pixels-Dtype` and `X-Pixels-Shape` headers). What the image's reader says of the sensor (CFA pattern and cell size, bit depth, black level) comes along in `sensor`, or the `X-Pixels-Sensor` header: readers with other field names can be added in `backend/backend/sensor.py`.
  - The API finding where two images differ (`POST /api/v1/output/image/diff`) returns regions as `x`, `y`, `w`, `h` with the peak's `value` (comparable across images) and its fraction of the largest (`diff`), instead of a center and radius. It takes the reference's file name as `path_ref`, answers 404 for a missing file and 400 for images of different sizes, and keeps its results.
  - Images whose pixel values users read are decoded once and kept on disk, up to `QABOARD_IMAGE_CACHE_GB` (20 GB by default, the least recently used are removed), in `QABOARD_IMAGE_CACHE_DIR`. See [the server's settings](/docs/deploy).
  - The server reads videos with FFmpeg (PyAV, in the backend's image), for the video viewer: what's in them (`GET /api/v1/output/video/info`), the decoded values of a frame's pixels (`GET /api/v1/output/video/pixels`, like images' with a `frame`), and where two videos differ, frame by frame (`POST /api/v1/output/video/diff`). Results are kept for a month in `videos/`, in `QABOARD_IMAGE_CACHE_DIR`.
- Before running from a commit's artifacts, the server checks they are usable (the subproject's *qaboard.yaml*, the files in the manifests), and never runs from an incomplete folder.
- The automated cleanup deletes artifacts again when `storage.garbage.artifacts.delete` is set: it was skipping every commit. Deleting a subproject's artifacts keeps the files the other subprojects of the commit still use.
- `qaboard_clean --dryrun` no longer marks outputs as deleted in the database, and prints a summary of what was (or would be) deleted.
- QA-Board's admins can open pgAdmin without a pgAdmin password: nginx asks QA-Board who is an admin (`services/nginx/snippets/pgadmin.conf`) and pgAdmin trusts it. The bundled pgAdmin also gets the database's password from `services/pgadmin/passfile` again.
- **Safer defaults**: review them before upgrading.
  - Keep RabbitMQ, Flower and pgAdmin to the server's host: Docker Compose now publishes them on 127.0.0.1 only. Set `QABOARD_RABBITMQ_HOST_IP` when Celery workers connect from other hosts ([passwords and admin services](/docs/deploy#passwords-and-admin-services)).
  - Mount only your results storage in the image server: Docker Compose no longer gives it the host's whole filesystem. If images stop loading after the upgrade, mount your storage in `cantaloupe` ([starting a server](/docs/deploy)).
  - Set the database password with `QABOARD_DB_PASSWORD` in `.env`: the database, the backend and the backups all use it ([database password](/docs/backend-admin/deployment#database-password)).
  - Protect the task queue: set RabbitMQ's account with `QABOARD_RABBITMQ_USER`/`QABOARD_RABBITMQ_PASSWORD`, and a login for Flower with `FLOWER_BASIC_AUTH`. The helm chart has `celery.rabbitmq.*` and reads `FLOWER_BASIC_AUTH` from its secret.
  - The Integrations menu's link checks and webhooks only reach the hosts in your projects' *qaboard.yaml*, your git and Jenkins hosts, and `QABOARD_PROXY_HOSTS`: add the hosts you only write as templates to `QABOARD_PROXY_HOSTS`.
  - See a warning in the admin checklist and in the server's logs when git webhooks are accepted without a secret.
  - Only QA-Board's admins can open Flower at `/flower/`: it can revoke tasks and shut the workers down.
  - Set `QABOARD_SANDBOX_HTML=true` so that the runs' HTML and SVG files can't act as whoever opens them: in the run cards their scripts run sandboxed, in an origin of their own, and opened in a tab they show without scripts. It's off by default for now: tell your users first ([HTML reports](/docs/viewers#html-reports)).
  - Files the server creates are no longer writable by everyone, except the run folders and manifests that users' runs write in.
  - Project names with `.` or `..` segments are refused: they could get around project access.
  - Only verified emails (directory accounts, or single sign-on with `email_verified`) count for `email_domain` group rules, the `domains` access policy and the emails in `QABOARD_ADMINS`, and local sign-up refuses the user names listed in `QABOARD_ADMINS` ([user management](/docs/backend-admin/user-management)).
  - Checking a Jenkins build's status needs the same access as starting one, and only reaches the Jenkins hosts of `JENKINS_AUTH`, on known ports.
  - Cookies from before stored sessions stop working once the user signs out or their sessions are ended, and 180 days after the upgrade ([sessions](/docs/backend-admin/sign-in#sessions)).
- Get `{"error": ...}` JSON answers and the right status codes from the batch, run and export APIs, and a 400 instead of a server error for invalid `metrics` or dates.
- Listing a batch's tests with the project's code, to start a batch from the web app, stops after 4 minutes with a message instead of holding a server worker.
- `QABOARD_DB_ECHO=0` (or `false`) turns the SQL logs off.

  cookies must come from QA-Board's own pages.
- Signing in with SAML only sends you back to QA-Board's own pages (open redirect), and lands on the home page instead
  of an empty error page when there's nowhere to go back to.
- Logging in no longer sends everything the directory knows about you to the browser.
- Reading the values of an image's or a video's pixels, what's in a video, and finding where images or videos differ now require a login, and only read files in the storage (`QABOARD_STORAGE_ROOTS`) that you're allowed to see. Signed out, the viewers show the displayed values and say to sign in for the rest. These endpoints could read images anywhere on the server, without a login.
- The unused PDF report of the regions where images differ (`/api/v1/output/diff/report`) is removed: it could write files anywhere on the server, without a login.
- Marking a run as failed or deleting it now requires a login.
- On servers that restrict projects to some users, only users allowed on a project can stop, rename, move or delete its batches, delete a commit's results, save its artifacts, or change its milestones. Exporting runs also checks you can access the reference's project.
- `QABOARD_LOGIN_RESTRICTED=false` (or `0`) turns project restrictions off, as you would expect: any non-empty value used to turn them on.
- Deleting results no longer deletes the contents of folders that they link to.
- When a restricted project saves its results in a folder per user (e.g. `/algo/outputs/{user}`), the project's files are now restricted in every user's folder, not only in the server's.
- The API `qa` uses to update batches no longer lets anyone without a login delete runs. `qa optimize` still replaces its previous best iteration's runs, and only those.
- When `qa` fails to update QA-Board, its warning no longer prints your API token (`QA_TOKEN`).
- When signing up with a user name or email that is already used, the server answers "already taken" instead of an error that included the password's hash, and no longer writes the password to its logs.
- Logging in with an empty password is refused, and LDAP logins escape the user name.
- The server only deletes the git clones it made: it refuses repository paths inside a clone, or that hold other clones.
- Error messages in run cards show as text, instead of being rendered as HTML.
- GitLab CI jobs in the Integrations menu only show and play jobs of the project's own repository, for people who can access the project.
- Starting batches from the web app no longer changes the server's umask for a while: other files it created meanwhile could become writable by everyone.
- Exporting into a folder that already exists never replaces or deletes what's in it, and only the folders exports create are listed in Storage usage ([exporting files](/docs/user-guide/sharing#exporting-files)).
- Importing the milestones saved in your browser needs access to their results, and the developer role.
- Editing a run from the web app no longer changes who sent it.
