## Web app

### Automated tuning
- Set up an automated tuning with a guided form in **Run Tests / Tuning**: the parameters to tune with their range or values, the metrics to improve with which way is better, and how many evaluations, with a recommendation. Pick any metric your runs return, or type another: there is nothing to declare first. The form checks the settings as you type and counts the runs; the YAML stays one click away, and keeps your comments ([find the best parameters automatically](/docs/user-guide/automated-tuning)).
- Read what an automated tuning found in **Tuning Analysis**: its status and progress, the best parameters within the ranges searched and how much each one matters, the convergence, one plot per parameter, and every evaluation in a table.
- Know what to do next: **What this tells you** says whether more evaluations would help, which best values are at the edge of their range, which parameters barely matter and which evaluations failed.
- Continue a search with **Continue the search…**, run the best parameters on other tests with **Run the best parameters…**, or copy them as `preset_params` or JSON.
- Find the best trade-offs between 2 or 3 metrics without choosing weights: **Tuning Analysis** shows the Pareto front, and runs any of its trade-offs.
- Start an automated tuning from the settings of a previous one on the same commit.
- See a failed evaluation of an automated tuning explained in **Tuning Analysis**, instead of listed among the batch's failed runs.

### Metrics
- See all the metrics of your runs, even those your project didn't declare: in the Summary, the Metrics Table, the Metrics Diff, the run cards and the History page. Before, metrics missing from the metrics file were hidden. See [metrics](/docs/computing-quantitative-metrics#what-qa-board-shows-by-default).
- Avoid misleading colors: when QA-Board doesn't know whether higher or lower is better, the Summary shows changes in gray and the Metrics Diff shades cells in blue by how much they changed, never green or red. Hover a metric's name to see why, and follow the Summary's link to declare it ([user guide](/docs/user-guide/metrics#summary)).
- Spot outliers in the Metrics Table: metrics without a target are shaded in blue, by how each value ranks among the runs.
- Get a useful Summary without configuration: when the project doesn't choose `summary_metrics`, it shows the 8 metrics that changed the most vs the reference.
- See a run's first metrics on its card when the project doesn't choose `main_metrics`.
- Plot any metric of the History page's commits when the project doesn't choose `main_metrics` or `dashboard_evolution_metrics`.
- Keep tables readable on runs with hundreds of metrics: without a selection, they show the declared metrics and others up to 20 columns, and say how many more you can pick.

### Navigation
- Ctrl/Cmd+click, or middle-click, the sidebar's results views (Summary, Metrics Table, Visualizations, Logs…) to open them in a new tab. Right-click copies their link.

### Storage usage
- Find the exports made before QA-Board tracked them in **Storage usage → Exports** after a storage scan, with the
  project, commit and batch they come from. Those in a folder someone chose are tagged: deleting one deletes the whole
  folder, so only admins and whoever owns all its files can ([exports](/docs/user-guide/storage-usage#exports)).
- Admins see everyone's untracked files in **Storage usage → Not tracked** when they choose *Everyone's*, with their owners.

### Image viewer
- Click a pixel to pin its values: they stay while you move the mouse away, so you can select and copy them. A **Pinned** tag and a framed crosshair show it; **Esc**, a click on the tag, or leaving the image and coming back follows the pointer again. In **Single** mode, where a click shows the other image, Shift+click pins ([pixel values](/docs/user-guide/image-viewer#pixel-values)).
- Shift+click a pixel of a video to pin its values the same way: they follow the frames as you step or play ([video pixel values](/docs/user-guide/video-viewer#pixel-values)).
- Switch the pixel values between decimal and hexadecimal with the **dec**/**hex** toggle at the end of the line, in the image and video viewers: clicking the line itself no longer switches them, so you can select its text.
- Look for differences of a given size in **Where they differ**: type the smallest and largest size in pixels above the regions, or in **Where they differ, in all N runs…**. The server keeps searching past the differences of other sizes, e.g. to find small defects next to a large change, and each region now says the size of its difference ([find where images differ](/docs/user-guide/image-viewer#find-where-images-differ)).
- Guess a raw image's CFA from the view and see what you get: **Guess from the view**, in the **Sensor** dialog, now uses the guess, also over the metadata, and the dialog and the card say what the pixels show and where they were read. Before, the guess was ignored whenever the metadata or your settings gave a CFA, with no feedback ([raw images](/docs/user-guide/image-viewer#image-values)).
- Highlight a range of the image's own values on the images: drag on the histogram of **Image values** (raw, 10-bit, 16-bit…), like on the displayed values. Pick channels of the sensor, e.g. **R** alone, to see which of its pixels are in the range ([raw images](/docs/user-guide/image-viewer#image-values)).

## CLI and project setup

### Declaring metrics in your code
- Declare your metrics where your code computes them instead of in a metrics file: return `Metric(value, suffix=" ms", smaller_is_better=True, target=15)`, call `define_metric("psnr", smaller_is_better=False)` next to the code that computes it, or write a *metrics_definitions.json* next to *metrics.json* from any language. QA-Board keeps the definitions with each commit. See [declaring metrics](/docs/computing-quantitative-metrics#declaring-metrics).
- Keep your metrics file while you move to definitions in code: for a metric declared in both, the fields from your code win.
- List metrics in `summary_metrics`, `main_metrics` and the other lists of your metrics file without declaring them.
- Write `smaller_is_better: null` in a metrics file for metrics where neither is better, like counts: their changes stay neutral. If your metrics file has `smaller_is_better: null` or `smaller_is_better:` with nothing after it, write `true`: they used to mean "smaller is better" ([metrics files](/docs/computing-quantitative-metrics#declaring-metrics-in-a-metrics-file)).
- Check *metrics_definitions.json* files in your editor with their JSON schema ([project setup](/docs/project-init#checking-qaboardyaml-and-batch-files-in-your-editor)).
- Start new projects with QA-Board's choices of metrics: the metrics file `qa init` creates no longer shows only `is_failed`.

### Quality gate and tuning
- Use the metrics your code declares in `qa gate`'s regression rules: the gate reads which way is better like the web app ([quality gate](/docs/quality-gate#rules)).
- Say which way is better in an automated tuning's configuration: `ap_small: max`, or `model_mb: {goal: min, weight: 0.005}`. Without it, `qa optimize` uses what your code declares where it computes the metric, even when it's only known once the code ran, then your metrics file ([the objective](/docs/auto-optimization#objective)).
- Get a clear error from `qa optimize` when nothing says which way is better for a metric, with what to write, instead of a crash. The web app shows it in **Tuning Analysis**.
- Give the target that `shift` and `relative` losses compare to in the objective, with `target`.
- Search with Optuna: `qa optimize` no longer uses scikit-optimize, which isn't maintained anymore. Configurations keep working except the `solver` settings, and `qa optimize` says what to write instead ([from scikit-optimize](/docs/auto-optimization#scikit-optimize)).
- Resume an automated tuning by running it again: it saves its progress and continues where it stopped, also with a bigger `evaluations` budget or wider ranges. `--checkpoint` is optional ([resume](/docs/auto-optimization#resume)).
- Run evaluations at the same time without waiting for the slowest: with `parallel_sampling`, a new one starts as soon as one ends.
- Stop a search that stopped improving with `early_stopping`, and look for the best trade-offs between metrics with `pareto: true` ([configuration](/docs/auto-optimization#configuration)).
- Keep searching when an evaluation fails: it's recorded as failed, and its runs are kept for their logs.
- Get every error of an automated tuning's configuration before the first evaluation, with where it is.
- Choose how the search picks parameters with `solver.sampler`: Gaussian processes (with PyTorch), TPE or random search ([solver](/docs/auto-optimization#solver)).

### Runners
- Run batches on Kubernetes with the `kubernetes` runner: each run is a pod of a Kubernetes Job, running as your own user, with your shared storage mounted, within your cluster's queues and quotas. When pods wait, `qa batch` says why and what to do ([Kubernetes](/docs/kubernetes-runner)).
- Keep GPU pods busy with short runs: `runs_per_pod` lets each pod do several runs, one after the other ([several runs per pod](/docs/kubernetes-runner#runs-per-pod)).
- Start Dask workers on Slurm, PBS, SGE, HTCondor, OAR, Moab or Kubernetes, not only LSF, with `runners.dask.cluster.type` ([other schedulers](/docs/dask-integration#other-schedulers)).
- Check everything a batch needs with `qa doctor`: *qaboard.yaml*, the server, the storage and the runner's permissions, with how to fix each problem. `qa doctor --test-job` also starts a small job ([qa doctor](/docs/doctor)).
- Stop a Celery batch with Ctrl+C: `qa batch` now drops its waiting tasks and stops the running ones, with everything their `qa run` started, instead of leaving them running ([stop a batch](/docs/celery-integration#stop-a-batch)).
- Keep more secrets out of your runs: the `celery` runner no longer forwards variables whose names contain `PASSWORD`, `PASSWD`, `KEY`, `PRIVATE`, `CREDENTIAL`, `DSN` or `DATABASE_URL`, besides `TOKEN`, `ACCESS`, `AUTH` and `SECRET`. Set those on the workers' machines ([Celery](/docs/celery-integration)).

## Server and administration
- Let users start, redo and stop batches on Kubernetes from the web app, as themselves, with `QABOARD_TUNING_RUNNER=kubernetes` ([Run batches from the web app](/docs/backend-admin/runners#kubernetes)).
- Stop Celery batches from the web app: **Stop runs** revokes the batch's tasks on the server's broker, and workers stop the running ones with what they started ([stop runs](/docs/backend-admin/runners#stop)).
- Stop the batches the server runs itself, with `QABOARD_TUNING_RUNNER=local` or `celery`: **Stop runs** stops their `qa batch` and the runs it started on the server. With several replicas of the backend, users are told when it runs on another one ([stop runs](/docs/backend-admin/runners#stop)).
- Keep the server's secrets out of the `qa batch` it runs for users with `local` or `celery`: it no longer gets the server's passwords, keys, tokens, database and sign-in settings. The projects' code still runs in the server's container: use `lsf` or `kubernetes` when you don't trust every developer with it ([security](/docs/backend-admin/runners#security)).
- Storage scans track the exports they find, so their owners see them: the scans' **Track** action is gone
  ([scanning the storage](/docs/backend-admin/storage#scanning-the-storage)).
- Check automated tuning configurations with `qa optimize`'s own checks before starting them: the server gives the same messages as the CLI. The backend installs Optuna instead of scikit-optimize.

## Fixes
- Batches started from the web app with `QABOARD_TUNING_RUNNER=local` or `celery`, and runs redone without an LSF bridge, are no longer killed after 5 minutes, and the web app no longer waits for them: `qa batch` runs in the background on the server ([on the server itself](/docs/backend-admin/runners#local)).
- The web app says where `qa batch` runs for batches started from QA-Board: on the server (with its process id), in a Kubernetes job, or in an LSF job, and shows stopped ones as **Stopped**.
- **Storage usage** no longer crashes when you go from the Batches tab to Commits.
- **Storage usage** and **Runs activity** no longer show your own numbers under **Everyone's** while everyone's load,
  nor everyone's runs as someone's when you pick a user.
- **Runs activity** shows why it could not load, instead of going back to a spinner every 15 seconds.
- Know what to do when a script that calls the API to start a Jenkins build is refused: the error now says how to send a token, not only how to sign in with `qa` ([authentication](/docs/apis#authentication)).
- `qa batch` with LSF no longer gets stuck after sending its runs when started from a Docker container: it waits for them with `bwait` instead of an interactive LSF job, and no longer adds a WAIT job to the queue.
