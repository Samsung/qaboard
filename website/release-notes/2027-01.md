## Web app
- Find who started a batch, redid or deleted runs, edited a run's metrics or changed milestones and roles in a project, as its developer or owner, in the project's **Admin → Audit log**, or from a batch's menu ([project audit log](/docs/user-guide/project-audit-log)).

## CLI and project setup
### Upgrading
- `qa` needs Python 3.11 or newer: on older Pythons, `pip install --upgrade qaboard` keeps the last version that supports them. Check your CI runners, cluster nodes and projects' virtual environments with `python3 --version`, and recreate the older ones, e.g. `uv venv --python 3.11` ([installation](/docs/installation#install)).

### Scripts and terminals
- Parse `qa`'s results in scripts and coding agents: `qa batch`, `qa doctor`, `qa auth status` and `qa version` take `--json`, which prints one JSON document on stdout and the rest on stderr, with the same exit codes. `qa batch --list-batches` names the batches ([JSON for scripts and agents](/docs/using-the-qa-cli#json-output)).
- Complete `qa`'s commands, options, batch names and `--input` paths in bash, zsh, fish or PowerShell: run `qa completion install` once. It reads your project's files, never the server, and `qa --help` starts about twice as fast ([shell completion](/docs/using-the-qa-cli#shell-completion)).
- See what `qa` does when it surprises you: `qa -v` logs the qaboard.yaml, project, commit, server and storage it found, its runners and uploads, `qa -vv` each request to QA-Board with its status and duration, without tokens. `QA_LOG_LEVEL` does the same in CI, `--log-file` keeps them in a file ([debug what qa does](/docs/using-the-qa-cli#debug-what-qa-does)).
- See what went wrong and how to fix it: `qa` says `error:`, `warning:` and `hint:` with the value involved, for an invalid *qaboard.yaml* (its line), an unknown batch (the closest names), a server it can't reach (in one line), a refused token, a failed run. Tracebacks are for bugs, or with `qa -v` ([troubleshooting](/docs/installation#troubleshooting)).
- Read how a batch went at the end of `qa batch`: how many runs passed or failed, and the failed runs' logs.
- Pipe `qa` without color codes: colors only on terminals and in CI logs, never with `NO_COLOR`, always with `FORCE_COLOR`. What scripts read on stdout doesn't change. `--help` has examples.

## Server and administration
- Find who ran, deleted or changed what in **Admin → Audit**: it now records batches started from the web app, redone and deleted runs, edited results, milestones, CI jobs started from the web app and retention cleanups, with their details. Filter by category and dates, export to CSV or JSON Lines, and send events to your SIEM with `QABOARD_AUDIT_STDOUT=1` ([the audit log](/docs/backend-admin/audit-log)).
- Follow each API request in the backend's logs: one line with its status, duration, user, project and a request id that its other lines carry, without the query string. `QABOARD_LOG_FORMAT=json` writes JSON lines for log collectors, `QABOARD_LOG_LEVEL` sets the level. They replace uWSGI's request lines: `UWSGI_REQUEST_LOGS=1` brings those back ([logs](/docs/backend-admin/logs)).
