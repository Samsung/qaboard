By default, runs save their files in a storage that the server mounts too. Turn uploads on, and runs that can't
mount it send their files to the server over HTTP: CI runners hosted by GitHub or GitLab, laptops, clusters without
the shared volume. The server saves them in one folder, and from there they are files like the others: the web app,
the image server, exports, deleting runs and the [retention rules](/docs/backend-admin/storage) treat them the same.
What projects set: [Send results without a shared storage](/docs/storage/uploads).

:::caution Experimental
Uploads are new. Start with a few projects.
:::

## Turn uploads on {#enable}
**They are on by default** where the server has the default storage: *docker-compose.yml* mounts a volume at
`/mnt/qaboard` (your site overlay can mount your storage there instead), and the Helm chart saves them in its
results volume. Check it in **Admin → Settings**, under *Uploads folder*, or with `qa doctor` in a project without
`storage`: it says whether the server takes its files, and why not.

**Choose another folder** when you set your own storage roots (`QABOARD_STORAGE_ROOTS`): the server then takes no
files until you set `QABOARD_UPLOAD_ROOT`. Pick a disk with room for the results, a storage root you already have or
a new one. The backend writes there; the proxy and the image server read it at the same path, like every
[results storage](/docs/deploy#2-create-the-results-storage):

<Tabs groupId="deployment">
<TabItem value="compose" label="Docker Compose" default>

```yaml title="Your overlay"
services:
  backend:
    environment:
      QABOARD_UPLOAD_ROOT: /mnt/results
    volumes:
      - /mnt/results:/mnt/results
  proxy:
    volumes:
      - /mnt/results:/var/qaboard/mnt/results:ro
  cantaloupe:
    volumes:
      - /mnt/results:/repository/mnt/results:ro
```

</TabItem>
<TabItem value="kubernetes" label="Kubernetes">

```yaml title="values.yaml"
results:
  enabled: true
  uploads: true     # the default: in the results volume, which the backend, the proxy and the image server mount
```

</TabItem>
</Tabs>

**Turn them off** with `QABOARD_UPLOAD_ROOT=off` (`results.uploads: false` with the chart): runs must then save
their results in a storage shared with the server, and the server tells those that send files why it refuses them.

Then:
- **Recommended: require tokens for all results**, if you don't yet: set **Authenticate results sent by qa** to
  *token* in **Admin → Settings** ([Results sent by qa](/docs/backend-admin/user-management#results-sent-by-qa)).
  Files need a token either way.
- **Before the server is reachable by people you don't trust** with each other's sessions, read
  [Keep it safe](#security).

<details>
<summary>Why these are environment variables, not settings in the web app</summary>

The storage roots and the uploads folder say where the server may write and delete files. If an admin's session were
stolen, a setting in the web app could point them at any folder of the server. Where *a project's* runs go, inside
those folders, is in the database: [storage locations](#storage-locations), changed without a restart.
</details>

## Where the files go {#layout}
```text
<QABOARD_UPLOAD_ROOT>/<project>/-/<first 2 characters of the commit>/<next 14>/output[/<batch>]/<configuration>/<input>/
/mnt/qaboard/kitefin/planner/-/3f/a91c02d4e7b815/output/linux-f0267280/unit-tests/junit.xml
```

- The server chooses the run's folder, and makes its names itself: what a client says about a run (its input, its
  batch, its configurations) becomes one folder name each, with a hash when it isn't one already. Clients only name
  files inside the run's folder, and can't write anywhere else. The default batch has no folder of its own.
- `-` separates a project from its runs, so a file's path says its project. Where you
  [restrict who reads files](/docs/backend-admin/user-management#restricting-who-can-read-files), who can read an
  uploaded file is who can [see its project](/docs/backend-admin/project-access). Projects with a folder named `-`
  in their name can't upload.
- The folder can be a storage root that runs also write to directly: uploaded runs are under `<project>/-/`, the
  others under `<project>/<commit>/`. The server refuses runs and artifacts that say they are in a project's uploaded
  runs or above them (the project's or its group's folder), since deleting them would delete uploaded runs.
- The files belong to the server's user. Users delete them from the web app, never by hand.

## Keep it safe {#security}
Whoever can send files can put any file on your server, which serves it to everyone who opens the run.

- **Files always need a token** with the *ingest* scope, from someone who can
  [send results to the project](/docs/backend-admin/project-access), whatever the setting for other results says.
  Give CI jobs [their own identity](/docs/ci-integration#ci-without-secrets) or a
  [service account](/docs/backend-admin/user-management#service-accounts) limited to their project.
- **Turn on `QABOARD_SANDBOX_HTML`** before the server is reachable from the internet, or by people you don't
  trust with each other's sessions: uploaded HTML and SVG files then can't act as whoever opens them
  ([HTML reports](/docs/viewers#html-reports)). It is off by default.
- **Images of restricted projects**: the image server (`/iiif/`) doesn't check who asks. If projects' visibility
  matters on your server, don't expose it beyond the people who may see every project.
- **Use HTTPS**: tokens and files travel in the requests.

## Limits and disk space {#limits}
| Setting | Default | |
|---|---|---|
| `QABOARD_UPLOAD_MAX_FILE_MB` | `1024` | The largest file. The proxy has its own limit, `client_max_body_size 1100m` for `/api/v1/output/<id>/files/` in its configuration: to accept larger files, raise both |
| `QABOARD_UPLOAD_MIN_FREE_GB` | `1` | Files are refused when the disk has less free space left |

- **The proxy receives each file whole** before the backend sees it, so slow clients don't hold the backend's
  workers. Its temporary folder needs room for the files being received.
- **Disk usage** shows in [Storage usage](/docs/user-guide/storage-usage) like other results, and projects'
  [retention rules](/docs/storage/deleting-old-data) delete old runs. There are no quotas per project yet.
- **Back the folder up** with your results. The database only has the runs' metrics.

## Use object storage: S3, GCS, Azure Blob {#object-storage}
The server needs a file system: it writes each file under a temporary name and renames it, appends to logs, and
nginx and the image server read plain files. It doesn't talk to buckets itself. To keep uploaded results in object
storage, mount it as a file system, on the backend, the proxy and the image server:

| | Fits | Notes |
|---|---|---|
| A managed file system: Amazon EFS, Google Filestore, Azure Files, your NFS | Yes | The simplest, when you don't need a bucket |
| [Amazon S3 Files](https://aws.amazon.com/about-aws/whats-new/2026/04/amazon-s3-files) | Yes | A bucket mounted over NFS, in its AWS region |
| [JuiceFS](https://juicefs.com/docs/community/introduction/) | Yes | A POSIX file system on any object store (S3, GCS, Azure Blob, Ceph, Garage...). It keeps files' names in a database you run (PostgreSQL, Redis...): back it up with the bucket |
| [rclone mount](https://rclone.org/commands/rclone_mount/) with `--vfs-cache-mode writes` | Try it first | Files go through a local cache before the bucket: size it, and run the check below |
| [Mountpoint for Amazon S3](https://github.com/awslabs/mountpoint-s3) | No | It can't rename files, nor change or append to existing ones |

We haven't tested each of these with QA-Board: check a mount before you rely on it. As the backend's user:

```bash
cd "$QABOARD_UPLOAD_ROOT" && mkdir -p .check && cd .check \
  && echo one > .tmp && mv .tmp log.txt && echo two >> log.txt \
  && [ "$(wc -l < log.txt)" = 2 ] && cd .. && rm -r .check && echo "The folder fits"
```

Then upload a run and open one of its images: the proxy and the image server must see the file right away.

### Let a project bring its own storage {#storage-locations}
To keep the results of a project, or of a group, on storage they pay for, e.g. their own bucket, add a **storage
location**: no restart needed, it applies within a minute.

1. Mount their storage on the server, in the backend, the proxy and the image server, at the same path, e.g. their
   bucket at `/mnt/kitefin-bucket`. Run the check above in it.
2. Add it, with the URL its runs will say they are in, and the projects whose runs go there:
   ```bash
   qaboard-admin storage-locations add s3://kitefin-bucket/qaboard/ /mnt/kitefin-bucket --project kitefin/
   ```
   `--project` takes a project, a group (`kitefin/`: all its projects), or `*`. The most specific location wins;
   projects that no location lists go to `QABOARD_UPLOAD_ROOT`, which you don't need to set if every project has
   a location.

The new runs of those projects are saved in the location, with the same layout (`<project>/-/...`), and each run
stores its full location, e.g. `s3://kitefin-bucket/qaboard/kitefin/planner/-/3f/.../junit.xml`. Their older runs
stay where they are, and both show in the web app.

| | |
|---|---|
| `qaboard-admin storage-locations list` | The locations, with how many runs are in each |
| `... set <url> --path /mnt/elsewhere` | The bucket is mounted elsewhere now: its runs don't change, the server finds them there |
| `... set <url> --project kitefin/ --project acme/` | Whose new runs go there. `--no-projects`: no new runs, the old ones stay readable |
| `... remove <url>` | Refused while runs are in it. With `--force`, their files can't be read until you add it back. The files stay |

<details>
<summary>Why runs store a URL, not the location's name</summary>

A run's location is all it needs to be found: changing how the server reaches a bucket (where it's mounted, later
its credentials) never makes runs point to nothing, and a location removed by mistake strands nothing once added
back. Only data that moves needs its runs' locations rewritten, like with any path. The server still reads and
writes plain folders: it doesn't talk to buckets itself, nor hold credentials, yet.
</details>

QA-Board still has the runs' metrics in its database when that storage loses files.

## When things go wrong {#troubleshooting}
- ***This server doesn't accept uploaded files***: `QABOARD_UPLOAD_ROOT` isn't set for the backend, and no
  [storage location](#storage-locations) lists the project.
- ***Sign in to do this***: files need a token, also when other results don't. `qa auth login`, or a token in the CI.
- **`413`, or *larger than what this server accepts***: raise `QABOARD_UPLOAD_MAX_FILE_MB`, and the proxy's
  `client_max_body_size` when the answer comes from nginx.
- **The run shows, its files don't**: the proxy doesn't mount the folder at `/var/qaboard<path>`, or the image
  server at `/repository<path>`.
- ***The server's storage for uploaded files is full***: free space, or lower `QABOARD_UPLOAD_MIN_FREE_GB`.
