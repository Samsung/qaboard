title: Running QA-Board on kubernetes
---
The helm chart is in `charts/qaboard`. SIRC's values are in `deployments/sirc/values.yaml`.

```bash
helm upgrade --install qaboard charts/qaboard --namespace qaboard --create-namespace \
     -f my-values.yaml --set image.version=<commit> --atomic --wait --timeout 15m
```

`--atomic` rolls back automatically if the new pods don't become ready. Database migrations run in a Job before upgrades: if they fail, the release fails and the running version is untouched.

## What runs
| Component | Kubernetes | Notes |
|-----------|------------|-------|
| backend | Deployment, 2+ replicas | Rolling updates with `maxUnavailable: 0`, readiness on `/api/v1/health`, a PodDisruptionBudget, spread on nodes. Optional HPA. |
| proxy (nginx) | Deployment, 2 replicas | Init containers copy the frontend and docs bundles. TLS is done by the ingress. |
| database | external, or CloudNativePG | `database.host` for a PostgreSQL managed by IT, or `database.cnpg.enabled` for an HA cluster (primary + replicas, automatic failover) with the [CloudNativePG operator](https://cloudnative-pg.io). `database.embedded` is only to try the chart. |
| redis | Deployment | A cache, no persistence |
| backups | CronJob (`backup.enabled`) | `pg_dump` to a volume. With CloudNativePG, prefer its continuous backups to S3/MinIO. |
| cantaloupe, rabbitmq/flower | optional | |

## Settings
- `config`: the backend's environment variables (see [server setup](../deploy)).
- `secret.existingSecret`: a secret with `SECRET_KEY` (signs sessions: must be the same for all replicas, and kept when migrating or everyone is logged out), `QABOARD_DB_PASSWORD`, `GITLAB_ACCESS_TOKEN`, LDAP credentials...
- `backend.data`: the application data volume (git clones, caches). With several replicas it must be `ReadWriteMany` (e.g. NFS).
- `backend.extraVolumes`/`extraVolumeMounts`: where users write outputs, as NFS volumes, or `hostPath` when nodes mount the storage themselves (autofs).
- `proxy.siteConfig`: extra nginx configuration files.

## Differences with docker compose
- **Old frontend bundles are not kept**: with compose, the bundles of previous versions stay in a volume, so clients that didn't reload keep working. On kubernetes each proxy pod only has the current bundle, so a client with an old tab gets errors when it lazy-loads a page, until it reloads. If it's a problem: put the bundles on a shared `ReadWriteMany` volume, or reload the app on chunk load errors.
- **The backend runs as root**: at SIRC it uses `sudo` to delete outputs as their owner, and uwsgi drops privileges (`UWSGI_UID`). Namespaces with the *restricted* Pod Security Standard won't accept it: ask for *baseline* or an exception.

## Migrating SIRC from docker compose
What we need from IT (the `TODO(sirc)` in `deployments/sirc/values.yaml`):
1. A namespace, an ingress class, a DNS name. Keep `qa` working as an alias: users and the CLI use `https://qa`.
2. The shared storage: either nodes that mount `/algo`, `/stage`, `/sim`, `/data`, `/raid`, `/home`, `/net` with autofs like the docker hosts (we use `hostPath` with `mountPropagation: HostToContainer`), or the NFS exports behind each path.
3. A `ReadWriteMany` storage class for the application data.
4. PostgreSQL: managed by IT, or the CloudNativePG operator installed in the cluster.
5. Network access from pods to `gitlab-srv`, LDAP, `ispq-vdi` (LSF bridge over ssh), Jenkins.
6. Permission to run the backend as root (see above).
7. For GitLab CI: `helm` on the runner and a kubeconfig (a CI/CD variable of type *File*), or the GitLab agent for kubernetes.

Then:
1. Create the secrets and config maps listed in `deployments/sirc/values.yaml` (registry credentials, `.env` secrets, `passwd`, LDAP restrictions, ssh key, TLS certificate).
2. Port the site's nginx locations (`deployments/sirc/nginx/*.conf`) to `proxy.siteConfig`.
3. Install the chart with a copy of production's database: `pg_dump -Fc` on the qa host (or the latest backup), `pg_restore --no-owner -d qaboard` into the new database. Test it on its temporary hostname.
4. Switch: make the compose deployment read-only or stop it, restore a fresh dump, point the `qa` DNS name to the ingress. Keep the compose deployment around for a quick way back.
5. Enable automatic deploys: set the CI/CD variable `QABOARD_K8S_DEPLOY=1` (or `=manual` to start), and remove `deploy:production`.

Effort: the chart covers the generic parts. The work is mostly the storage mounts and IT's prerequisites; expect a few days of iteration once they are available.

## Troubleshooting
```bash
kubectl -n qaboard get pods
kubectl -n qaboard logs deploy/qaboard-backend          # one of the replicas
kubectl -n qaboard logs job/qaboard-migrations          # failed migrations
kubectl -n qaboard exec -it deploy/qaboard-backend -- bash
helm -n qaboard history qaboard
helm -n qaboard rollback qaboard                        # previous release
```
