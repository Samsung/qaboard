Check that a change leaves your outputs identical, byte for byte: a refactoring, a compiler upgrade, or a model of a
chip that the silicon must match. `qa check-bit-accuracy` fails your CI when output files differ from the
reference's, and the web app's **Output Files** view shows which files changed, and how.

## Fail the CI when outputs change {#hard-qa-check-bit-accuracy-on-the-cli}
The camera ISP's fixed-point model must stay bit-accurate: the camera chip implements it. Its CI checks it on every
commit.

1. **Choose the files to check** with `bit_accuracy.patterns` in *qaboard.yaml* (all files by default, see
   [what files are checked](#what-files-are-checked)). The camera ISP checks its output image, the stages' images and
   16-bit buffers, and the register dump:

2. **Check after the batch, in the CI.** `qa check-bit-accuracy --batch <batch>` compares the runs of
   `qa batch <batch>` with the reference's (see [which reference](#which-reference)):

   `<your-qaboard>` is your server's address, like `localhost:5151`.

3. **Push a commit.** When files differ, `qa check-bit-accuracy` lists them, run by run, prints a link to the
   commit's **Output Files** view, and exits with an error. When they're all identical, it passes.

`qa check-bit-accuracy` also compares the runs' input files (see [manifests](#input-and-output-manifests)), so it
tells you when a change comes from the inputs. To fail on metrics instead of files, see the
[quality gate](/docs/quality-gate), whose `require_bit_accuracy` checks the same files.

## See which files changed {#soft-bit-accuracy-checks-from-the-ui}

Like `qa check-bit-accuracy`, the web app only checks the files selected by `bit_accuracy.patterns`. When all of them
are identical, the run is tagged **Bit-accurate**. The other files are still listed when they differ, greyed and
tagged **not checked**: for instance *metrics.json*, which has the run's measured run time. Unlike
`qa check-bit-accuracy` without `--strict`, checked files that exist in only one of the runs also make the web app
show differences.

## What files are checked? {#what-files-are-checked}
Files matching the patterns of `bit_accuracy.patterns` in *qaboard.yaml* are checked. Without patterns, all files
are checked.

```yaml title="qaboard.yaml"
bit_accuracy:
  patterns: ['out.png', 'stages/*.png', 'regs.txt']
  ignore: ['debug/']
```

- Patterns are glob patterns that match the end of a file's path in the run's output directory: `out.png` checks
  *out.png* and *some/folder/out.png*. `*` also matches `/`.
- Files whose path starts with one of the `bit_accuracy.ignore` patterns are not checked.
- Files that change at each run are never checked: *metrics.json* (it has the run time), *run.json*, *log.txt*,
  *log.lsf.txt* and *manifest.inputs.json* (`qa check-bit-accuracy` compares it on its own, see
  [manifests](#input-and-output-manifests)).

The web app's **Output Files** and the [quality gate](/docs/quality-gate)'s `require_bit_accuracy` check the same
files.

:::note
If you work with text files on both Linux and Windows, line endings can make identical files differ. Say which files
are text with `bit_accuracy.plaintext`, *or* which are binary with `bit_accuracy.binary`, like the camera ISP's
`plaintext: ['*.txt']`.
:::

## Which reference {#which-reference}
`qa check-bit-accuracy --batch <batch>` compares the results of `qa batch <batch>` with:
- the latest commit of `project.reference_branch` (default: `master`) on your git remote,
- or, in the CI of that branch, the commit's parents: a merge is compared with the commits it merges,
- or what you give with `--reference`: a branch, a tag or a commit. The camera ISP compares with its release,
  `qa --platform hw-model check-bit-accuracy --batch bitexact --reference <release-sha>`.

If the reference commit's CI isn't over, `qa` waits for it. It asks GitLab for the commit's pipeline jobs, or GitHub
for its statuses and check runs, so it needs a token (see [CI integration](/docs/ci-integration#commit-statuses));
without one, it doesn't wait. Skipped jobs, and jobs allowed to fail, count as successful.
`bit_accuracy.failed_ci_job_name` only looks at that job: in a subproject, it looks for the job
`<failed_ci_job_name> <subproject>` (with the name of the subproject's folder).

When the reference's CI failed, it's compared anyway. With `bit_accuracy.on_reference_failed_ci: compare-first-parent`,
`qa` goes back to its first parent instead, at most `bit_accuracy.max_parents_depth` times (default 5): useful when a
build failure left the reference without results.

### Where runs are found {#where-runs-are-found}
`qa check-bit-accuracy` looks for the runs that have the same input, configurations, platform and tuning parameters as
yours (with `--reference-platform`, on that platform), in the reference's batch with the same label (or
`--reference-label`). With `--reference-match closest`, it compares with the closest run on the same input instead,
like the web app picks reference runs (see [options](#options)):

1. **It asks QA-Board** where they are. It knows the runs of every CI and `qa --share` batch, wherever they were saved.
2. **Otherwise it looks in the storage**, where `qa` saves runs (`storage` in *qaboard.yaml*): offline (`qa --offline`),
   when QA-Board can't be reached, or for runs it doesn't know. If your storage settings have a folder per user, like
   `/mnt/outputs/{user}`, it looks in every user's folder: the reference's runs were saved by its CI's user. When a run
   is missing, it prints where it looked.

Your own runs are where `qa batch` saves them: in your project's `output/` folder, or with `qa --share` and in the CI,
in the storage. The reference's runs are CI runs, so their label isn't prefixed by your name like with `qa --share`:
to compare with runs you shared, use `--reference-label "@<your-user>| <label>"`.

## Options {#options}
- `--strict`: by default only the files that exist in both runs are compared. With `--strict`, files that exist in
  only one of the runs are errors too.
- `--reference-label`: compare with the reference's runs that used another [label](/docs/using-the-qa-cli#qa---label-my-label),
  e.g. `qa --label new check-bit-accuracy --batch all --reference-label old`.
- `--reference-match closest`: compare each run with the reference's closest run on the same input, like the web
  app: the one with the fewest different configurations, then tuning parameters, on the same platform if possible.
  Use it when the reference didn't run the same configurations, e.g. you're testing a new one. `qa` says which runs
  were compared with a different one, and how they differ. By default (`exact`) runs without an identical reference
  run fail.
- `--reference-platform`: compare with the reference's runs on another platform, e.g.
  `qa --platform hw-model check-bit-accuracy --batch <batch> --reference-platform linux`.
- `--batch` can be repeated, and `--batches-file` names the batches files, like for `qa batch`.

## Input and output manifests {#input-and-output-manifests}
Each run saves in its output directory a *manifest.outputs.json*, with a hash of each output file, and a
*manifest.inputs.json*, with a hash of the input files (at most 200 files for an input folder). `qa check-bit-accuracy`
compares both, so it also tells you if the inputs changed. To list other files as inputs, set
`context.obj['manifest-inputs']` to a list of paths in `run()`.

<details>
<summary>Compare with manifests saved next to the inputs</summary>

For specific use cases, `qa check-bit-accuracy-manifest --batch my-batch` (it also accepts `--strict`) checks the
results against manifests stored in the database next to the input files, instead of against another commit. To save
those manifests, use `qa batch my-batch --save-manifests-in-database` (the flag is forwarded to `qa run`). It only
works for inputs that are folders.

</details>

## Custom output comparisons {#custom-output-comparisons}
Bit accuracy checks compare the hashes of your output files, computed once and stored in the manifests. To compare
files another way, ignoring timestamps or comparing their meaning, supply your own comparison function:

1. Implement a `cmp` function in a Python file:

   ```python title="cmp.py"
   from pathlib import Path

   def cmp(path1 : Path, path2 : Path) -> bool:
     """Checks if the files have the same content, like QA-Board does by default"""
     return path1.read_bytes() == path2.read_bytes()
   ```

2. Ask `qa` to use it:

   ```bash
   export QA_BITACCURACY_CMP=/path/to/cmp.py
   qa check-bit-accuracy --batch <batch>
   ```
