Start a QA-Board server on your computer, run an example project, and look at its results in the web app. Most of the
time goes to downloading images.

You need [Docker](https://docs.docker.com/get-docker/),
[kind](https://kind.sigs.k8s.io/docs/user/quick-start/#installation),
[kubectl](https://kubernetes.io/docs/tasks/tools/) and [Helm](https://helm.sh/docs/intro/install/) 3.8 or later.
With Helm 4, avoid 4.2.1: it waits out the whole `--timeout` after the chart's database migrations
([helm#32214](https://github.com/helm/helm/issues/32214)).

1. **Get the chart and its quickstart settings:**

   ```bash
   git clone https://github.com/Samsung/qaboard.git
   cd qaboard
   ```

2. **Create a cluster.** `kind.yaml` shares your computer's `/tmp/qaboard` with the cluster, at the same path: that's
   where results go. Create the folder first, or Docker creates it, owned by `root`.

   ```bash
   mkdir -p /tmp/qaboard
   kind create cluster --name qaboard --config charts/qaboard/kind.yaml
   ```

   <details>
   <summary>What's in <code>kind.yaml</code></summary>

   <RepoFile path="charts/qaboard/kind.yaml" />

   </details>

3. **Install QA-Board.** The quickstart settings run one replica of each service, a PostgreSQL pod and the image
   server, without an ingress. The first install downloads QA-Board's images, which takes a few minutes.

   ```bash
   helm install qaboard charts/qaboard -f charts/qaboard/quickstart.yaml --wait --timeout 15m
   ```

   <details>
   <summary>What's in <code>quickstart.yaml</code></summary>

   <RepoFile path="charts/qaboard/quickstart.yaml" />

   </details>

4. **Open the web app.** Forward a local port to QA-Board, and leave the command running:

   ```bash
   kubectl port-forward svc/qaboard-proxy 5151:80
   ```

   Open [http://localhost:5151](http://localhost:5151): the projects list is empty until you save results.

<Clip id="quickstart/kind" />

:::note Tested in CI
On every commit, GitHub CI runs these commands with the images it built in the same run, runs a `qa batch` in
the cluster, checks its results through the web server, then upgrades the release (the `helm-e2e` job).
:::

## Save results from your computer
The `qa` command line runs your code where you start it. It saves the outputs in a folder that the server reads at
the same path, then sends the metrics to the server. Try it on the camera ISP example: it simulates a robot's camera
and runs its image pipeline on test charts and photos.

1. **Install `qa` and the example's dependencies**, from the `qaboard` folder you cloned:

   ```bash
   cd examples/image-quality
   python3 -m venv .venv
   source .venv/bin/activate
   pip install qaboard -r requirements.txt
   ```

2. **Point `qa` to your server and to the results folder.** On kind, it's `/tmp/qaboard`:

   ```bash
   export QABOARD_URL=http://localhost:5151
   export QA_STORAGE=/tmp/qaboard
   ```

3. **Run the example's CI batch:** 5 test charts and 4 photos, each at ISO 100 and 3200. The first time, the example
   downloads its photos and generates its charts.

   ```bash
   qa --share batch ci
   ```

4. **Open the link** that `qa` prints after `Results:`. It's the commit page of the `kitefin/camera-isp` project, with
   your 18 runs: their metrics, then their output images, which you can zoom into, all in sync.

Without `--share`, `qa` saves the results in `output/` and doesn't tell the server.

:::tip Clean up
`kind delete cluster --name qaboard` deletes the cluster. Your results stay in `/tmp/qaboard`.
:::
