**Tests tell you it runs. QA-Board shows you it's better.**

Every team that measures quality hits the same wall. The tests pass, the average moves a little, and the regression
that matters is in one image, one slice of the test set, one percentile, one task. QA-Board runs every change on your
test set, whether a person or a coding agent wrote it, and puts its outputs and metrics next to the reference's. The
team sees what changed, and agrees it's better before it ships.

It's been Samsung's central quality platform since 2018: about 50 projects, more than 40 million runs.

## What every team gets
The same review loop, whatever you measure:
- **Every commit against a reference**: the reference branch, or a release saved as a milestone. Metrics first, green
  when they got better and red when they got worse, then the outputs behind them.
- **Viewers built for heavy data**: images and videos synced down to the pixel, point clouds, trajectories, flame
  graphs, benchmark results, plots, test reports, logs, and the HTML reports your code writes.
- **History** to find the commit that changed a metric, input by input.
- **Tuning from the browser**: sweeps and automated tuning, run on the server, Celery or LSF, with an analysis of
  what matters.
- **A quality gate in CI**, `qa gate`: it fails the job, comments on the pull request, and checks rules a project's
  owners set in the web app. Experimental, it may change.
- **A record of every attempt**: a run done again keeps how its earlier attempts ended, their metrics and their logs.
- **People and coding agents on the same results**: agents run the same tests and read the same Metrics Diff; a
  person decides what ships. See [coding agents](/docs/agents).
- **Your compute, your storage, your network**: `qa` runs where your code already runs (a laptop, CI, LSF, Celery,
  Dask, Jenkins), outputs stay on your storage, and the server is self-hosted, open source (Apache 2.0).
