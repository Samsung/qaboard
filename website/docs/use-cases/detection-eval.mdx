For computer vision and ML engineers who ship models to devices, where quantization, input size and model size trade
off against accuracy.

**One mAP number hides where a model got worse.** Quantize a detector to int8 and it gets several times smaller,
while the average moves less than what you lost on one kind of scene, or on the objects far away. QA-Board compares
every candidate with the model you ship, slice by slice, class by class, down to the images where it went wrong.

<Clip id="commit/compare-tour" caption="From the Summary to each slice's change: sorting by mAP brings the indoor slice, 35% worse, to the top." />

## What it changes for your team
- **The truth per slice, not an average.** Every metric for every slice of your test set, against the release model,
  green when it got better and red when it got worse.
- **From a number to the images in one click.** Detections drawn on the images, precision-recall curves over the
  reference's, and the report your own code writes, in each run's card.
- **Tuning without notebooks.** Start sweeps or an automated tuning (`qa optimize`, with Optuna) from the browser; the
  analysis says which settings matter and what to try next.
- **Releases the team agrees on.** Save a model as a milestone and compare every candidate with it; `qa gate`
  (experimental) fails CI when a model regresses.
- **Next to your training stack.** Each run links to the model it evaluated: its model card, its training run. See
  [deep learning](/docs/deep-learning).

## How it's set up {#the-configuration}
`:image` in a path gives a slider over the slice's images, synced across runs. The plots set their traces' colors, so
with `side_by_side: false` the web app draws the reference dashed and faded on the same axes.

<RepoFile path="examples/detection-eval/qaboard.yaml" title="qaboard.yaml" section="inputs,outputs,gate" />

The variants are configurations (`fp32`, `int8`, `size-320`...), so each run shows them as tags. To compare int8
with fp32 on the same commit, select the commit as the reference too (**Also show in the bottom bar**), then filter each
bar's runs by configuration. See [choose another reference](/docs/user-guide/comparing-results#picking-a-reference).

## Try it on the demo {#run-this-example}
[`examples/detection-eval`](https://github.com/Samsung/qaboard/tree/master/examples/detection-eval) runs an
off-the-shelf detector (torchvision's SSDlite) on CPU with ONNX Runtime, in fp32 and int8, at several input sizes, on
four slices of images: indoor, outdoor, warehouse, and small objects. Each run measures COCO-style AP, AP per object
size and per class, model size and latency.

<details>
<summary>The story the pictures tell, and how the demo is built</summary>

1. The first int8 model is 3.5 times smaller, which is what the robot's accelerator needs. It loses 35% of its mAP
   on the indoor slice, and some of the small objects.
2. Per-channel weights and percentile calibration bring the indoor slice back.
3. `qa optimize` searches the quantization and post-processing settings. With what it finds, the int8 model finds
   small objects as well as the last fp32 release.
4. The tuned model ships as a milestone, the next reference.

The photos are public domain, and no detection dataset is: their labels come from a much larger model (Faster R-CNN),
not from people. The int8 model is scored with its reference arithmetic (quantization in float, as its graph says)
rather than with ONNX Runtime's int8 kernels, which round differently from one CPU to another, so its metrics don't
move from one CI runner to the next.

</details>

You need Python 3.10 or later and [uv](https://docs.astral.sh/uv/). The first run downloads the photos (about 20 MB)
and the model's weights, and exports the model to ONNX with PyTorch for CPU, which uv installs in its cache (about
200 MB).

```bash
cd examples/detection-eval
pip install qaboard -r requirements.txt
qa --config int8 --config size-320 run --input slices/small-objects
qa batch ci                     # 4 slices, fp32 and int8: about 30 s
```

Without `--share`, results stay in `output/`. To see them in the web app, run `qa --share batch ci`. With the
[quickstart](/docs/get-started/quickstart#save-results-from-your-computer)'s server, first
`export QABOARD_URL=http://localhost:5151 QA_STORAGE=/tmp/qaboard`. See the example's
[README](https://github.com/Samsung/qaboard/tree/master/examples/detection-eval#readme) for the other batches and the
tuning.
