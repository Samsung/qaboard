With the `celery` runner, `qa batch` sends its runs to [Celery](https://docs.celeryq.dev/) workers through a
message broker, and waits for them. Workers run each `qa run` in the folder where you started `qa batch`, with your
environment variables (except those whose names contain `TOKEN`, `ACCESS`, `AUTH` or `SECRET`): their machines need
that folder, your inputs and the results storage at the same paths, e.g. on shared drives.

## Start workers and send them runs {#starting-celery-workers}
1. **Get a broker.** QA-Board's Docker Compose deployment starts RabbitMQ on port `5672` (not the quickstart's). To
   start another one:

   ```bash
   docker run --detach -p 5672:5672 rabbitmq
   ```

2. **Start at least one worker**, in the Python environment of your code:

   ```bash
   pip install celery qaboard
   export CELERY_BROKER_URL=pyamqp://guest:guest@<broker-host>:5672//
   celery -A qaboard.runners.celery_app worker --concurrency=10 --loglevel=info
   ```

   `<broker-host>` is the broker's hostname, e.g. your QA-Board server's. Run workers as services, so that they
   restart after failures and reboots: see [Celery's daemonization guide](https://docs.celeryq.dev/en/stable/userguide/daemonizing.html).

3. **Make `qa batch` use Celery**, in *qaboard.yaml*:

   ```yaml title="qaboard.yaml"
   runners:
     default: celery
     celery:
       broker_url: pyamqp://guest:guest@<broker-host>:5672//  # or $CELERY_BROKER_URL
   ```

   Without `broker_url` or `CELERY_BROKER_URL`, `qa` looks for the broker on a host named `qaboard`.

4. **Run a batch**: `qa --share batch ci`. To see the runs' logs live in your terminal instead, run them on your
   machine: `qa batch --runner local ci`.

Without `--share` (or a CI), runs write their files in `output/`, in the folder where you started `qa batch`: use
`--share` so that they go to the results storage that the server reads.

## Monitor the workers {#monitoring}
QA-Board's Docker Compose deployment includes [Flower](https://flower.readthedocs.io/en/latest/), at
`http://<your-qaboard>/flower`, where `<your-qaboard>` is your server's address. See also Celery's [monitoring guide](https://docs.celeryq.dev/en/stable/userguide/monitoring.html).

## Celery settings {#advanced-celery-configuration}
Settings under `runners.celery` are given to Celery:

```yaml title="qaboard.yaml"
runners:
  default: celery
  celery:
    # assuming your QA-Board server's hostname is qaboard
    broker_url: pyamqp://guest:guest@qaboard:5672//  # also read from ENV vars with CELERY_BROKER_URL
    result_backend: rpc://                  # also read from ENV vars with CELERY_RESULT_BACKEND
    # Any of Celery's settings: https://docs.celeryq.dev/en/stable/userguide/configuration.html
    timezone: Europe/Paris

    # By default tasks will be named "qaboard" unless you define
    qaboard_task_name: qaboard
```

To send the runs to specific workers, e.g. if you manage different types of resources (GPUs, Windows/Linux/Android...),
start the workers with their queues, and route the runs there:

```bash
# On a server with a GPU:
celery -A qaboard.runners.celery_app worker --concurrency=1 --queues gpu,large-gpu
```

```yaml {3-4} title="qaboard.yaml"
runners:
  celery:
    task_routes:
      qaboard: gpu
```

Batches can't have their own Celery settings yet: `qa batch` ignores a batch's `celery:` settings, and uses
`runners.celery` from *qaboard.yaml* for all its runs.

Celery's [workers guide](https://docs.celeryq.dev/en/stable/userguide/workers.html) explains how to set their
concurrency, queues and limits.
