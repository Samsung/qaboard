Runs can send their files to the QA-Board server over HTTP, instead of saving them in a folder that the server
mounts too. Use it where a shared storage is hard to get: CI runners hosted by GitHub or GitLab, a laptop outside
the office network, a cluster without the shared volume.

:::caution Experimental
Sending results over HTTP is new. Tell us how it goes with your projects.
:::

## Set it up {#set-it-up}
1. **Ask your server's administrators whether it accepts files.** They turn it on with
   [one setting](/docs/backend-admin/uploads). In a project, [`qa doctor`](/docs/doctor) says whether it does.
2. **Leave `storage` out of *qaboard.yaml***, or say it. `qa init` writes a `storage`: replace it.

   ```yaml title="qaboard.yaml"
   storage: upload
   ```

   For one machine only, like a CI job in a project that otherwise uses a shared storage, set
   `export QA_STORAGE=upload`.
3. **Sign in**: files are always sent with a token. Run `qa auth login`, and in CI let the job
   [sign in as itself](/docs/ci-integration#ci-without-secrets) or [give it a token](/docs/ci-integration#tokens).

Then use `qa` as usual: `qa --share run`, `qa batch` in CI, [`qa upload`](/docs/upload-results) and
[`qaboard.start_run()`](/docs/log-from-code) all send their runs' files.

```bash
export QABOARD_URL=https://qaboard.example.com
qa --share run --input images/a.jpg
# ...
# Sent 12 files to QA-Board (3.4 MB)
```

## What is sent, and when {#what-is-sent}
A shared run is saved like a local one, in the project's *output/* folder on the machine that runs it. `qa` sends
its files from there, and the web app shows the run like any other: same pages, same viewers, same links.

| | When |
|---|---|
| The run's log, and the [series](/docs/log-from-code#series) it logs | While it runs, every few seconds |
| Its metrics | While it runs for `start_run()`, at the end for `qa run` |
| Files matching `outputs.live` in *qaboard.yaml* | While it runs, each time they change |
| All its other files | When it ends, before it shows as finished |

To look at some files before a long run ends, like plots it rewrites, list them:

```yaml title="qaboard.yaml"
outputs:
  live:
    - "plots/*.png"
    - "*.html"
```

- **A run that fails or is interrupted** still sends what it wrote, with its log.
- **A run that is done again** replaces the files the server had.
- **Files the server can't take**, e.g. larger than its limit (1 GB by default): `qa` names them, and the run still
  shows with its other files. In CI the command fails; elsewhere it prints the error and goes on. Save big outputs
  in a shared storage.
- **A server that doesn't accept files** refuses the run when it starts: in CI, `qa` stops there.
- **When the server doesn't answer**, `qa` tries again a few times, then says what is missing. The files stay in
  *output/*.

## What still needs a shared storage {#limits}
The server only has what runs sent it. It can't start your code where it has no build and no inputs.

| | Without a shared storage |
|---|---|
| See, compare, export and delete runs; the quality gate; History | Yes |
| [`qa save-artifacts`](/docs/storage/artifacts#uploaded) | Yes: it sends the commit's artifacts to the server |
| Start runs and [tuning from the web app](/docs/tuning-from-the-webapp), redo runs | Not yet: the runs QA-Board starts have no token to send their results with ([artifacts](/docs/storage/artifacts#uploaded)) |
| [`qa check-bit-accuracy`](/docs/bit-accuracy) | Yes: it compares the reference's manifests (its files' hashes), fetched from the server. Not with `QA_BITACCURACY_CMP`, which compares files |
| [`qa optimize`](/docs/auto-optimization) | Yes: it reads the iterations' metrics from the server. Its journal, to resume, stays on the machine that runs it |
| `qa batch` with a [cluster runner](/docs/runners) | When the cluster's nodes share the project's folder with the machine that starts the batch |
| Runs done again | In place: the server keeps the latest attempt's files |

A project can mix both: most machines save in the shared storage, and the ones that can't mount it set
`QA_STORAGE=upload`.

<details>
<summary>How it works</summary>

- `qa` creates the run on the server, which chooses its folder under the server's own uploads folder.
- Each file is a `PUT /api/v1/output/<id>/files/<path>`, with its SHA-256: the server checks what it received
  before the file shows. The log is sent by what was added. See [the HTTP API](/docs/http-api#upload-files).
- The run's files are all there before the run ends: from then on they don't change.
- A commit's artifacts are saved the same way, next to its runs, with
  `PUT /api/v1/commit/<commit>/artifacts/files/<path>`: see [the HTTP API](/docs/http-api#upload-artifacts).
- Runs send the state of their folder, not events: after a failed request, the next one sends what is missing.

</details>
