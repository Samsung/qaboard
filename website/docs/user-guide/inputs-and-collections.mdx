The **Inputs** page shows your project's inputs, those its runs used and those you added before any run, as
thumbnails: search them, open them full screen, see the runs that used them. Select some and save them as a **collection**, like `night/hard-cases`: a list of inputs with
a name, that batches and your scripts can use. Collections have their own page, **Collections**, next to **Inputs** in
the project's sidebar.

You'll do three things:

1. [Find inputs](#find-inputs): open **Inputs** in the project's sidebar.
2. [Save them as a collection](#save-a-collection): select them, click **Save as collection**.
3. [Use the collection](#use-a-collection): in a batch, or from Python. Find it again on the
   [Collections page](#find-collections).

## Find inputs {/* #find-inputs */}
Open **Inputs** in the project's sidebar. It lists the inputs of the runs of the project and of its subprojects, the
most recently used first, and the inputs you [added before any run](#add-inputs).

- **Search** paths, e.g. `night street`: every word must match, anywhere in the input's full path.
- Go into a **Folder**: the list shows the folders under the current one, with how many inputs each has. Folders
  start where your inputs are, e.g. `/mnt/data/projectX`, not at `/`, and folders with a single subfolder are
  skipped. The breadcrumb goes back up; its copy button copies the folder's path.
- Filter by **Metadata**: each key lists its most common values with how many inputs have them, like a dataset
  browser. Tick values to keep the inputs with any of them; ticking in several keys keeps the inputs with all.
  Inputs get metadata when runs send it or when you [add them](#add-inputs).
- **Hide inputs whose runs were deleted** is on by default. Inputs added before any run stay: see [add inputs before any run](#add-inputs).
- **Sort by** path instead of last use.

The page's link keeps the search, folder and metadata filters: copy it to share what you see.

Inputs show by their **full path**: their database's folder and their path in it, joined. Each tile says where the
input is from the folder you're in, so `frame_0001.jpg` in two folders can be told apart. **Copy path** copies full
paths, one per line; **Windows** copies them as Windows paths when your administrators set how Linux folders map to
Windows shares (`path_mappings`). Batch files and scripts still name inputs by a database and a path in it: the
viewer shows both under **In runs**.

### Add inputs before any run {/* #add-inputs */}
New data doesn't need runs to show here. From the project's folder, add the inputs a batch would run on, or paths
(with globs) relative to the database, like `qa batch` takes them:

```bash
qa inputs add night-captures
qa inputs add 'night/*.raw'
qa --dryrun inputs add night-captures   # only lists them
```

From Python: `qaboard.inputs.add(["night/0001.raw"], database="/mnt/data", metadata={"sensor": "imx766"})`. Adding
inputs needs the [developer role](/docs/user-guide/project-access). They're the same inputs your runs use later, not
copies: their runs show next to them.

Double-click an input, or press <kbd>Enter</kbd>, to open it full screen. Arrows (or <kbd>←</kbd> <kbd>→</kbd>) go to the
previous and next inputs, and **Used in runs** lists the latest runs that used it, with links to them. **Files with
it** lists the files that come with it, like `0001.metadata.yaml` next to `0001.raw`, and those your site configured
([sidecar files](/docs/backend-admin/thumbnails#sidecars)); scripts get them as `item.sidecars`.

<details>
<summary>Why an input shows a placeholder instead of a thumbnail</summary>

The placeholder says why; hover it for more.
- **No preview for .raw**: QA-Board makes thumbnails of the image formats browsers and Pillow read, and of videos'
  first frames. Other formats, like raw sensor files, need a small plugin your administrators install
  ([thumbnail decoders](/docs/backend-admin/thumbnails)).
- **Folder not readable**: the server reads only the folders in its storage: administrators add your data's folder
  to `QABOARD_STORAGE_ROOTS` or the storage locations.
- **File not found**: the file moved, or its folder isn't mounted on the server.
- **Not a file path**: the input's database isn't an absolute path, so the server can't find the file.
</details>

## Save a collection {/* #save-a-collection */}
1. Select inputs: click one, <kbd>Shift</kbd>-click to select a range, <kbd>Ctrl</kbd>-click (<kbd>⌘</kbd> on macOS) to add
   or remove one. To take every input your search and filters match, click **Select all N matching** above the grid:
   the grid loads inputs as you scroll, and this selects those not loaded yet too.
2. Click **Save as collection** in the selection bar.
3. Type a **Collection name**: `/` makes groups, e.g. `night/hard-cases`. Add a **Description**: what the inputs have
   in common, what they're for. The version's **Notes** already say how you chose the inputs, e.g.
   `From Inputs: search "night", folder /data/night/street, weather rain, hiding inputs whose runs were deleted — 212 inputs`: edit them as you like.
4. Click **Save**.

To add inputs to a collection that exists, select them and click **Add to collection…**: it says how many are already
in it, and adds only the others.

<details>
<summary>Selecting every match</summary>

- Filtering is how you describe a collection: search, pick a folder or metadata values, keep or leave out the inputs without
  runs, then select all that match and save them.
- A collection holds at most 50,000 inputs. When more match, **Select all matching** is off: narrow the filters.
- <kbd>Ctrl</kbd>+<kbd>A</kbd> in the grid selects the inputs loaded so far, <kbd>Esc</kbd> clears the selection.
  <kbd>Ctrl</kbd>-click still removes one input from a selection of every match.
- **Copy paths** needs the inputs loaded: after selecting every match, save them, then print the paths with
  `qa collections show <name>`.
- Sampling inputs, or balancing several groups, isn't in the web app. Scripts can save any list of inputs as a
  collection with the [HTTP API](/docs/http-api) (`POST /api/v1/collections`), and list the ids a filter matches with
  `GET /api/v1/inputs?project=...&fields=id`.

</details>

**Who sees it**: a new collection is yours only (**Only me**), in your lists and your batches, like a personal
milestone. To share it with **everyone on the project** and its subprojects, pick it when you save, or later click
**Share with the project** in its page's <kbd>…</kbd> menu: that needs the
[developer role](/docs/user-guide/project-access), and developers can then change it. Only you can make it personal
again.

### Versions {/* #versions */}
Collections never change behind your back: each change saves a new **version**, and older versions stay as they were.

To change a collection, open it, click **Edit**, select the inputs to remove or click **Add inputs**, then save the new
version with notes on what changed. If someone saved a version meanwhile, you're asked whether to reload theirs or save
yours anyway.

The version picker on the collection's page shows each version's inputs, who saved it, and when.

### The Collections page {/* #find-collections */}
Open **Collections** in the project's sidebar. It lists the collections the project can use: pinned ones first, then
your favorites, then all of the project's, by group (`night/hard-cases` is in `night`). Collections of parent projects
come last, marked with their project: the project can use them too. Each row shows the collection's description, its
latest version, how many inputs it has, and who updated it and when.

- **Search** names, descriptions and creators.
- **New collection** says how to make one: collections are made from inputs, on the **Inputs** page.
- Under **Collections**, the sidebar lists the pinned collections, then your favorites.
- Click the **heart** next to a collection, or on its page, to add it to your favorites.
- **Pin** it for one of your groups, or as the project's owner for **Everyone on the project**: it then shows in their
  sidebar.
- **Archive** collections nobody should pick anymore: they're hidden from the lists, and batches and scripts that use
  them keep working. **Show archived** lists them again.

## Use a collection {/* #use-a-collection */}
The collection's page shows the code to copy, in its **Python** and **Batch file** tabs.

In a batch, list it under `collections`, next to the batch's `inputs`:

```yaml title="qa/batches.yaml"
hard-cases:
  configurations: [base]
  collections:
    - night/hard-cases@2   # version 2
```

Without `@2`, batches use the latest version when they start. Pin a version in CI, so that results stay comparable.
More in [running on many inputs](/docs/batches-running-on-multiple-inputs#collections).

From Python:

```python
import qaboard

collection = qaboard.collections.get("night/hard-cases@2")
print(collection.version, len(collection))
for item in collection:
    print(item.absolute_path)  # item.database / item.path
```

Each `item` is an object, with `id`, `database`, `path` and `absolute_path`: later versions of QA-Board will add
more to it.

From the shell: `qa collections show night/hard-cases@2` prints the inputs, one per line.
