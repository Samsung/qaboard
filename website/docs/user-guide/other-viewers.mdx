Runs show more than images and videos: plots, CPU profiles, transcripts, the reports your code writes, 3D maps and
trajectories. Each viewer puts the reference's result next to the new one, or over it, so you see what the change did.

| If your outputs are… | you'll see… |
|---|---|
| Curves, bars, heatmaps: a detector's precision-recall curves, a server's latency percentiles | [Plots](#plots), the reference's drawn over the new ones, or next to them |
| Values logged while a run goes on: a training's loss and learning rate at each step | [Logged series](#logged-series): one plot per series, the reference's dashed on the same axes, live |
| Images, sounds, tables, histograms and texts a training logged at its steps | [Logged media](#logged-media): one timeline for all of them, each next to the reference run's at the same step |
| CPU profiles of a server or a pipeline | [Flame graphs](#flame-graphs), colored by what got slower or faster |
| Unit and integration test reports (JUnit XML) | [Test reports](#test-reports): each test against the reference, with what started failing, what got fixed and what disappeared |
| Benchmark results: pytest-benchmark, Google Benchmark, hyperfine, Criterion, JMH | [Benchmarks](#benchmarks): each one against the reference, what got slower or faster beyond noise |
| Text: an LLM agent's transcripts, logs, tables | [Text diffs](#text), line by line |
| Sounds: a TTS model's samples, a denoiser's outputs | [Audio](#audio): the waveform or spectrogram above the reference's; switch between them while it plays |
| Reports your code writes as web pages | [HTML reports](#html-reports), the new one above the reference's |
| A robot's maps and 6DoF trajectories | [Point clouds and trajectories](#point-clouds-and-trajectories), in 3D, with the ground truth |
| Many files per run: an ISP's stages, the frames of a sequence, the images of a test set | [A slider](#pipeline-stages-and-frames) that picks the file every card shows |
| Images and videos | The [image viewer](/docs/user-guide/image-viewer) and the [video viewer](/docs/user-guide/video-viewer) |

They all show in the **Visualizations** view of the [commit page](/docs/user-guide/commit-page#views), in each run's
card. Your project chooses what each card shows; what it hides by default has a switch in the
[View options](/docs/user-guide/commit-page#view-options), under **Visualizations**. The full-screen button at the top
right of a card gives its viewers the whole screen, e.g. for 3D views and deep flame graphs.

:::note
When the reference run's file is the same as the new one, the card says **Identical to the reference**: there is
nothing to look at in that viewer.
:::

## Plots {#plots}
Your project's code draws the plots: curves, bars, heatmaps, 3D plots... Each plot is either drawn **over the
reference's**, on the same axes, or **next to it**: the project picks, plot by plot.

Overlaid, the change is where the curves part. With a shared result cache, every latency percentile of the inference
gateway is a hundred times the reference's or more:

<Shot
  id="commit/latency-cdf"
  caption="The reference's latencies, dashed and faded, stay under the 12 ms SLO line until the far tail; the new ones are near a second from the median on."
/>

- **The legend says which curve is which**: `new | Latency` and `ref | Latency`, or the
  [names you gave](/docs/user-guide/comparing-results#naming-what-you-compare) what you compare.
- **When a plot picks its colors, the reference's curve is dashed and faded**, in the same color: with one curve per
  class, each class keeps its color. Otherwise, the curves take the colors of what you compare: blue for new, and each
  reference its own color.
- **The reference's lines are a bit wider**: where nothing changed, the new line runs right on top of it.
- **Hover** a curve for its values. **Drag** to zoom on a region, **double-click** to zoom back out. **Click a legend
  entry** to hide or show its curve, double-click it to show only that one. The toolbar that shows at the top right
  when you hover the plot saves it as a PNG.

<Shot
  id="commit/plotly-overlay"
  caption="One curve per class, the reference's dashed in the same color: quantized to int8, the detector's person curve on the indoor slice falls from an AP50 of 0.19 to 0.06."
/>

Side by side, the new run's plot comes first, then the reference's. Nothing on them says which is which, and each
zooms on its own. Projects use it for plots that would hide each other, like heatmaps:

<Shot
  id="commit/core-heatmap"
  caption="CPU per core, new on the left: with the shared cache, the cores idle while requests queue. Below, the batch sizes overlaid: every new batch is full."
/>

<details>
<summary>More about plots</summary>

- Plots saved as web pages (`*.plotly.html`) always show side by side, each in its own frame.
- When the project gives a ground truth, overlaid plots draw it too, in green, named `groundtruth`.
- When the reference run doesn't have the plot, the new one shows alone.
- In the dark theme, plots that don't choose their colors get colors that read on a dark background.
- Projects choose, with `side_by_side` in *qaboard.yaml*, how each plot compares: see
  [the Plot.ly viewer](/docs/viewers#plots).

</details>

## Logged series {#logged-series}
Runs can log values while they run: a training's loss at each step, its learning rate, a validation score at each
epoch. Their card plots each of these series, at the top, without the project having to set anything up.

1. **Read each plot**: the new run's curve is solid, the reference run's dashed, in the colors of what you compare.
   Series the reference didn't log show alone. Plots are grouped by the start of their name: `train/…`, then
   `val/…`.
2. **Smooth noisy curves** with the **Smoothing** slider: the curve becomes a moving average, and the values as
   they are stay behind, faded.
3. **Switch to a logarithmic scale** with **Log scale**, e.g. for a loss that drops by orders of magnitude.
4. **Compare by step or by time**: **By step** lines runs up on their steps, **By time** on the seconds since each
   started, to see which one got there faster.

Your choices apply to every card, and stay in the page's address when you share it.

- **A run that is still running says Live**: its plots follow it, every 10 seconds.
- **Each series' last value is one of the run's metrics** (or its minimum, when the project says so): you find it in
  the Summary, the tables and the **Trends** page.
- **Long runs stay readable**: past a thousand points, each point is the average of several steps, and a band shows
  the range of their values, so a spike isn't lost.
- **With many series**, the first 12 show; filter them by name, or show the others with the button under the plots.
- **A gap in a curve** is a value that wasn't a number: a loss that became NaN.

### Compare all the runs on the same plots {#compare-logged-series}
The **Summary** view has a **Logged series** card when runs of the batch logged series: one plot per series, one
line per run, each run in its color. Use it to compare the trainings of an experiment: learning rates, model sizes,
seeds.

1. **Find a run**: the list on the left names each run by what tells it apart from the others, e.g. `lr=0.01`.
   Hover a run to bring its curves forward in every plot; the others fade.
2. **Show and hide runs**: click a run to hide it, click again to show it. **only** shows that run alone; **Show
   all** and **Hide all** are at the top of the list.
3. **Color by a parameter**: pick **Color by lr** (any parameter that differs between the runs) to give the runs
   that share a value the same color, and show a group alone with its **only**.
4. **Add the reference**: **With the reference's runs, dashed** draws each run's reference run in the same color,
   dashed.

- Smoothing, the logarithmic scale and **By step** / **By time** are the same as on the cards, and shared with them.
- The plots follow the page's filter: filter the runs at the top of the page to compare some of them. Past 40 runs,
  the first 40 show.
- A plot's title says when only some of the runs logged its series.
- Past 12 runs, colors repeat with dotted lines.

Integrators: see [Log from your code](/docs/log-from-code) to log series from Python, and
[the file format](/docs/viewers#series) for other languages.

## Logged media {#logged-media}
Runs started from code can log images, sounds, videos, tables, histograms and texts at their steps: a model's
predictions on a few validation images every 1000 steps, a TTS sample, the distribution of a layer's weights. Their
card shows them under **Logged media**, with nothing to set up, each next to the reference run's at the same step.

1. **Pick a moment of the run on the timeline**: it shows where each key logged something, with the loss (or a series
   you pick) drawn behind it, so you see where the interesting steps are. Hover a step to preview its images; click,
   or use <kbd>←</kbd> <kbd>→</kbd>. **Latest** follows a run that is still running. Clicking a point of a
   [logged series](#logged-series) plot moves the media to that step, and once you picked a step the plots show it as a cursor.
2. **Compare with the reference run**: each sample sits next to the reference's same sample, matched by the name
   your code gave it, so samples that come in another order still match. When a run didn't log at the step you picked,
   you see its last item before it, with a chip that says from which step.
3. **Open an image** to compare it in the [image viewer](/docs/user-guide/image-viewer): zoom, pixel values, the
   difference. **Follow one sample over training** with the filmstrip button (<kbd>e</kbd>): every step it was logged
   at, new above reference.
4. **Read boxes**: show or hide predictions and ground truth, hide boxes under a score, and see one color per label.

Each kind has its view:
- **Tables**: sort, filter, and **Diff** against the reference's table, rows joined by a key column you can change:
  changed cells are tinted, with the old value on hover. Numeric columns show their distribution in their header.
- **Histograms**: the distribution over all the steps as a heatmap, with its median and 5–95% band; below, the
  step's histogram with the reference's outlined.
- **Sounds** open in the [audio viewer](#audio); several at a step are rows to play and switch A/B, expanded on
  click.
- **Texts** show as a diff against the reference's, or against the run's previous step.

<details>
<summary>Finding your way in many keys, sharing a view, and shortcuts</summary>

The section's header says what the run logged (*12 keys · steps 0–24 000 · images, audio, tables*). **Contents**
lists the keys grouped by the start of their name, with how many steps each logged; filter them as you type. Pin the
keys you look at most: they stay on top for you in this project, like the groups you collapse. Images
and videos come first, texts last.

The step you picked is in the page's address, shared by every card, and so is the sample you opened: copy the address
to send someone *this sample at this step*. <kbd>?</kbd> lists the shortcuts: <kbd>←</kbd> <kbd>→</kbd> between
logged steps, <kbd>e</kbd> the filmstrip, <kbd>space</kbd> swaps new and reference.

</details>

## Audio {#audio}
Sound files (*.wav*, *.mp3*, *.flac*, *.ogg*...) open in the audio viewer: the new run's above the reference run's, on
the same time axis.

1. **Play**, then **switch between A and B while it plays** (<kbd>a</kbd>, <kbd>b</kbd>): playback continues at the
   same position, in the other file. That is how you hear a difference.
2. **Match loudness** is on by default: the louder file is turned down to the other's level (the gain shows on its
   track, e.g. *−4.1 dB to match*), so that the louder one doesn't sound better only because it is louder.
3. **See the frequencies** with **Spectrogram** (<kbd>s</kbd>): both files share the same color scale.
4. **See what differs** with **Difference**: what is left once the reference is subtracted, sample by sample, or
   where their spectra differ, in blue where new is louder and orange where the reference is. You can play it too. It
   needs files of the same sample rate and length: otherwise its switch says why it is off.
5. **Zoom on a moment**: <kbd>Ctrl</kbd> + wheel or pinch zooms where the pointer is, dragging selects a region that
   loops, <kbd>z</kbd> zooms on it, a double-click shows everything again.

<details>
<summary>What the numbers say, and every shortcut</summary>

Each track shows its sample rate, channels, duration, peak and RMS levels (dBFS), its loudness (LUFS, measured like
broadcast loudness meters do), and how many samples clip, drawn red on the waveform. <kbd>?</kbd> lists the
shortcuts: <kbd>space</kbd> plays or pauses, <kbd>x</kbd> goes to the next track (A, B, difference), arrows move by a
second (five with <kbd>shift</kbd>), <kbd>0</kbd> goes back to the start, <kbd>l</kbd> loops, <kbd>m</kbd> matches
loudness. Files the browser can't decode play in its own player.

</details>

## Flame graphs {#flame-graphs}
A flame graph shows where a program spends its CPU time. Each bar is a function, as wide as the time spent in it, with
the functions it calls below it. Against the reference, QA-Board draws a **differential flame graph**: the new run's
profile, colored by what changed.

<Shot
  id="commit/flame-top-functions"
  caption="The inference gateway's workers now render responses under the shared cache's lock (orange, new), and the model's forward pass runs less (blue): cache hits skip it."
/>

- **Red** functions take a bigger share of the profile than in the reference, **blue** ones a smaller share: the
  darker, the bigger the change. **Orange** ones are new. Light gray ones didn't change. Look for the wide red and
  orange bars first: that's where the time went.
- **Hover** a function: its total time (with what it calls) and its self time (in the function itself), in the
  profile's unit and in %, and the same in the reference.
- **Click** a function to zoom into it and what it calls. **Zoom Out**, or <kbd>Esc</kbd> in the graph, goes back.
- The line under the graph says what's compared, and each profile's total.

To get flame graphs in your project's runs, integrators save what their profiler writes: see
[Profiles and flame graphs](/docs/flame-graphs).

### Find what got slower in the table
Below the graph, **Top functions** lists every function with its **Self** and **Total** time, over all the stacks it's
in, and its **Change** against the reference, the biggest increase first. Click a column to sort by it. Click a
function to highlight it in the flame graph; click it again to clear.

### Compare shares or absolute values
Two runs rarely record the same number of samples: a longer run has more of everything. By default, colors and
changes compare each function's **share** of its profile: "+2.3 pp" means it went from, say, 5% to 7.3% of the
profile. **Absolute** compares the values themselves: use it when your project saves values that compare across runs,
like the inference gateway example's microseconds of CPU per 1,000 requests.

### Search
Type in **Highlight frames**: the frames that match turn magenta, and next to the box you read how many there are and
what share of each profile they take. <kbd>Enter</kbd> and the arrows zoom on the next or previous match, the biggest
first. The table only lists the matching functions.

### Change the layout
- **Icicle** (the default) draws the program's entry point on top; **Flame** draws it at the bottom, like most flame
  graphs.
- **By name** (the default) orders the functions alphabetically, so the same function is in the same place in both
  profiles; **Heaviest first** puts the widest on the left.
- The menu below the graph picks what to draw:

| Choice | Widths | Colors |
|---|---|---|
| **What did happen** (the default) | The new run's profile | What changed |
| **What will happen** | The reference's profile | What changed: functions the change removed show here, in blue |
| **After**, **Before** | The new run's profile, or the reference's | By function, as in any flame graph |
| **After & Before** | Both, one above the other | By function |

<details>
<summary>More about flame graphs</summary>

- Functions are matched between the two profiles by their call stack: the same function, called from somewhere else,
  is another bar.
- **Highlight frames** reads regular expressions (`lock|wait` highlights both), and ignores case. The **.\*** button
  turns regular expressions off, to search for text like `Vec<u8>::push(`; **Aa** matches case. Text that isn't a
  valid regular expression is searched as text.
- With the keyboard: <kbd>Tab</kbd> to the graph, the arrow keys move between a function, its callers, what it calls
  and its neighbors, <kbd>Enter</kbd> zooms, <kbd>Esc</kbd> zooms out. Each function says its times when it's focused.
- In the table, a function's **Total** counts each stack once, also when the function is recursive. Functions are
  merged by name, wherever they're called from.
- Frames narrower than 0.002% of the profile aren't drawn, but they count in the search, the tooltips and the table.
- When a profile has several threads (speedscope files from py-spy), they're merged: a menu next to the comparison's
  picks one.
- Without a reference profile, the flame graph shows alone, by function.
- In the inference gateway example, widths are microseconds of CPU per 1,000 requests: the profile's unit is what your
  project records.
- Read Brendan Gregg's [flame graphs](http://www.brendangregg.com/flamegraphs.html) and
  [differential flame graphs](http://www.brendangregg.com/blog/2014-11-09/differential-flame-graphs.html).

</details>

## Test reports {#test-reports}
When a run is a test suite, its card shows the suite's tests compared with the reference run's: which ones started
failing, which got fixed, which are new, gone, skipped or flaky, and why each failure happened.

<Shot
  id="commit/junit-viewer"
  caption="No test fails after the change, and none was fixed: the chips say why the CI stayed green, 12 tests removed and 2 newly skipped."
/>

To review a change to the tests:
1. **Read the numbers at the top.** Each status has its count and its change vs the reference. The colored chips below
   name the changes: **new failures**, **fixed**, **added**, **removed**, **newly flaky**, **newly skipped**.
2. **Click a chip or a number** to see only those tests. Shift-click numbers to combine them, e.g. failed and errors.
3. **Click a test** to see its details on the right: its status here and in the reference, its time, the failure's
   message and trace, and its output. When the reference failed differently, its failure shows too.
4. **Press <kbd>n</kbd>** to go to the next failure, <kbd>p</kbd> to the previous one: the groups above it open.

The list opens on the first new failure, with the groups that have failures or changes open. A removed test is
struck through: the reference ran it, this run didn't, which a green CI doesn't tell you.

- **Search** tests by name, group or failure message: every word must match, and `-word` leaves out the tests that
  have it, e.g. `codec -fuzz`. <kbd>/</kbd> goes to the search, <kbd>Esc</kbd> clears it and the filters.
- **Sort** by failures first (the default), by name (tests stay in the order they ran), or slowest first.
- Groups are the packages, modules, classes or suites of the report. Each shows how many of its tests failed or are
  flaky, its most important change, a bar of its tests' statuses, how many tests it has and their time.
- **Much slower** tests took twice as long as in the reference and at least 100 ms more.

<details>
<summary>Keyboard shortcuts and more</summary>

Click in the list, then:

| Keys | What they do |
|---|---|
| <kbd>↑</kbd> <kbd>↓</kbd>, <kbd>Home</kbd> <kbd>End</kbd>, <kbd>PgUp</kbd> <kbd>PgDn</kbd> | Move in the list |
| <kbd>→</kbd> <kbd>←</kbd> | Open or close a group, or go to its first child or its parent |
| <kbd>Enter</kbd>, double-click | Open or close a group |
| <kbd>n</kbd> <kbd>p</kbd> | Next or previous failure: new failures, failures and removed tests |
| <kbd>c</kbd> | Copy the test's id, e.g. to run it alone |
| <kbd>/</kbd>, <kbd>Esc</kbd> | Search, clear the search and the filters |

- The ⌘ button above the list shows these shortcuts.
- A group's details have **Search this group**, to see only its tests, and **Open all below**.
- Tests are matched with the reference's by their id: their class (or file) and name. A renamed test shows as
  removed, and its new name as added.
- Flaky tests are those the report marks as failed, then passed when run again. Not every test runner says it.
- Without a reference report, the new one shows alone, without changes.
- The viewer stays fast with tens of thousands of tests: only the rows you see are drawn.

</details>

The viewer compares two commits. To see each test over a branch's commits, which fail since when and which are flaky,
open [Trends](/docs/user-guide/trends#each-test).

## Benchmarks {#benchmarks}
When a run saves a benchmark harness's results, its card shows each benchmark next to the reference run's: how long
it took, the change in %, and whether that change is larger than the noise the harness measured.
Integrators: see [Benchmark suites](/docs/benchmarks) to bring a suite in, and follow each benchmark as a metric.

<Shot id="commit/benchmarks" />

To review a change's performance:
1. **Read the line at the top**: how many benchmarks, then how many are **slower**, **faster**, **within noise**,
   **new** and **missing** compared with the reference. **overall** is the geometric mean of the changes: each
   benchmark weighs the same.
2. **Check the machines** below it. When the new and reference results come from different CPUs or CPU counts, a
   warning says so: their numbers aren't comparable, whatever the table says.
3. **Read the table from the top.** By default, the biggest regressions come first, then missing and new benchmarks.
   The bar on the right shows the change, worse to the right, with the noise as a gray band around the center.
4. **Click a benchmark** to see everything the harness measured, for both runs: mean, median, standard deviation,
   min, max, rounds, iterations, throughput.

**Within noise** means the change is no larger than the larger of the two spreads the files report: their standard
deviation, or when the harness doesn't report one, their interquartile range, median absolute deviation or error
margin. Those changes are gray, never red or green: run the benchmark again and they could go the other way. When
neither file reports a spread, any change counts: ask your project to repeat measurements in the harness, e.g.
Google Benchmark's `--benchmark_repetitions`.

- **Change** is the new time against the reference's: +12% takes 12% longer. For throughputs, where more is better,
  it's how much longer each operation takes, so red always means worse.
- **Spread** is the harness's spread relative to the value, new then reference: σ for the standard deviation.
- **Rounds** is how many times the harness measured, times the iterations in each measurement.
- **Filter** benchmarks by name, group or parameter: every word must match, `-word` leaves out those that have it.
  **Only changed** hides the benchmarks within noise. Click a count at the top to see only those benchmarks.
- **Sort** by biggest regressions, biggest improvements, name, or slowest first.

<details>
<summary>More about benchmarks</summary>

- Benchmarks are grouped by their module, class, family or group, as the harness names them. Click a group to close
  it. Groups come in the order of their first benchmark, so with the default sort the group with the worst regression
  comes first.
- Benchmarks are matched with the reference's by name. A renamed benchmark shows as missing, and its new name as new.
- QA-Board shows what the harness wrote: it doesn't run benchmarks again or average several runs.
- Without a reference file, the run's benchmarks show alone, sorted by name.
- <kbd>↑</kbd> <kbd>↓</kbd> move between benchmarks once you clicked the table, <kbd>Esc</kbd> closes the details.
- The table stays fast with thousands of benchmarks: only the rows you see are drawn.
- Your project can return each benchmark as a metric too, to follow it in [Trends](/docs/user-guide/trends#benchmarks).

</details>

## Text diffs {#text}
Text files are diffed with the reference's, line by line, in the code editor of VS Code: the reference on the left, the
new run's on the right, what was removed in red and what was added in green. It works for any text: logs, tables,
configuration files, an LLM agent's transcripts.

<Shot
  id="commit/transcript-diff"
  caption="The same task before and after the change: the reference's reboot is refused until the operator confirms, the new assistant reboots the robot without asking."
/>

- The tag next to the file name says which side is where, **reference ➡️ new**: press <kbd>t</kbd> to swap them.
- **Next diff** jumps to the next change.
- **Side-by-side** switches to an inline diff, removed lines above added ones, which reads better in a narrow card.
  Click it again (it says **Inline diff**) to go back.
- The lines that didn't change are folded, with 3 lines of context around each change: click **N hidden lines** to
  show them, or the arrows above and below it to show a few more.
- The editor shows up to 40 lines: scroll in it for the rest. Click in it and press <kbd>Ctrl</kbd>+<kbd>F</kbd>
  (<kbd>⌘</kbd>+<kbd>F</kbd> on a Mac) to search.

<details>
<summary>More about text diffs</summary>

- Files that no other viewer reads show as text.
- The color codes that terminals use are removed from logs. YAML, JSON, Python and JavaScript files are highlighted.
- Without a reference file, the new file shows alone.
- To diff any file a run wrote, not only those your project shows, use [Output Files](/docs/user-guide/commit-page#output-files).

</details>

## Point clouds and trajectories {#point-clouds-and-trajectories}
For robots and 3D sensors, QA-Board draws maps and trajectories in 3D: the new run's, the reference's, and the ground
truth when the project has one.

**Point clouds**, like the map a robot built, show on the same axes, in the colors of what you compare, like in the
other viewers: the new run's in blue, the reference's in its color (purple for the first reference), and the ground
truth in green. The checkboxes above the view name each cloud like the commit page does, e.g. with a milestone's name.

<Shot
  id="commit/pointcloud"
  caption="The reference hidden, the new map against where the points really are: false loop closures put shelves meters away."
/>

- **Drag** to orbit, **right-drag** to pan, **scroll** to zoom. **Reset view** goes back to the start.
- The checkboxes show or hide each cloud, with its number of points. Hide the reference to compare the new map with
  the ground truth alone.
- Where two clouds should overlap and don't, one of the maps is wrong.
- Point clouds are large: projects may hide them by default. Switch them on in the **View options**, under
  **Visualizations**.

**Trajectories** (6DoF: the position and orientation over time) show each value of the pose over time, on the left,
and the path in 3D, on the right, with x and y at the same scale.

<Shot
  id="commit/trajectory-6dof"
  caption="Each axis over time and the path in 3D, against the reference's and the ground truth: a false loop closure pulls the new trajectory away."
/>

- The legend names the new run, the reference and the ground truth: click one to hide it.

## Step through pipeline stages and frames {#pipeline-stages-and-frames}
Some visualizations have several files per run: one per stage of a camera pipeline, per frame of a sequence, per image
of a test set. A card shows one at a time, and **Files to show**, in the **View options**, picks which, for every run at
once.

<Clip
  id="commit/dynamic-outputs"
  caption="One slider over the ISP's stages, from the raw mosaic to the tone-mapped image: new and reference change together, in every run's card."
/>

1. Open the **View options** (press <kbd>o</kbd>). Under **Files to show**, each option is named after what varies in
   the files' names, like **Stage** or **Image**.
2. Move the slider, or pick a value in the list: a slider when the values are consecutive numbers, a list otherwise.
   Every card shows that file, new and reference, with its path above the viewer, like `stages/3.jpg`.
3. To follow one spot stage after stage, zoom in on an image first: the image viewers keep their zoom and region as
   you change files.

- Until you pick a value, each run shows its own default: its last one when the values are numbers (its last frame,
  for instance), else its first. The panel says so, for instance **Each run's last**. The reset button next to the
  option goes back to it.
- Runs don't need to have the same files. A run without the value you picked shows the closest number, and its card
  says which.
- To pick a different file in each card, turn on **Per run**: each card gets its own slider or list. **Same for all
  runs**, in a card, turns it off again.
- Hover an option's name to see which visualizations it's for, and the values found in the runs.
