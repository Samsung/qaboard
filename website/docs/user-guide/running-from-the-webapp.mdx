You don't need a terminal to start runs: the web app can redo runs, run a commit's code on new tests, start tuning experiments and trigger CI jobs.

:::info Before you start
- Most actions need you to be **logged in** (top of the sidebar). When you are not, they are greyed out, next to a **Log in** button. If your session expires, QA-Board tells you to log in again.
- Running code needs the commit's **artifacts** (its build and configuration files). When they are missing, the commit page says why, and redoing runs or starting tuning first brings them back: your project may have QA-Board [rebuild them with your CI](../storage/deleting-old-data.mdx#recreating-artifacts), otherwise only the files from the source code are restored. While the CI rebuilds them, QA-Board doesn't start anything: try again when the build is done.
- Your project needs a **task runner** (a cluster, Celery workers...) for runs to start. If none is set up, the tuning form warns you: ask whoever integrated QA-Board in your project.
:::

## Redo, stop and clean up runs

| To... | Where |
|---|---|
| Redo **one run** | On its card (Visualizations or Output Files views), ☰ menu → **Redo** |
| Redo the **failed** runs of a batch | Commit bar menu (☰) → **Redo Failed Outputs** |
| Redo **deleted** runs | Commit bar menu → **Redo Deleted Outputs**, or the button in the "N of the outputs below were deleted" message |
| Redo **all** runs of a batch | Commit bar menu → **Redo All Outputs** |
| **Stop** pending runs | The **Stop runs** button above the views, shown while runs are pending |
| Unblock a run stuck as pending | On its card, ☰ menu → **Mark as Failed** |
| Delete runs or only their files | Card ☰ menu (one run), or commit bar menu (failed runs, the batch, several batches) |

Redone runs use the commit's saved artifacts and the same input, configuration and parameters. They also use the runner they were started with, and the batch's runner settings, like how many runs can run at the same time: QA-Board starts them together, with a single `qa batch`. Its logs are in the [Logs](commit-page.mdx#logs) view, under "Started from QA-Board".

<Shot

When you filter the batch's runs, the commit bar menu's redo actions only redo the runs that match the filter: **Redo the N Filtered Outputs**, **Redo Filtered Failed Outputs**...

The page refreshes by itself while runs are pending: follow their progress with the counters next to the filter box, or in the [Logs](commit-page.mdx#logs) view.

:::caution
Delete actions are immediate. Milestones are protected: QA-Board won't delete batches or commits saved as [milestones](comparing-results.mdx#milestones).
:::

## Running tests and tuning
To run a commit's code on other inputs, or with other parameters, open the commit page and select **Run Tests / Tuning** in the sidebar.

1. **Experiment name**: the label of the new batch. Reusing the name of an existing experiment adds runs to it.
2. **Batch of inputs+configurations**: the name of a batch of tests, like `my-batch`, or several, like `batch-*`. Hover **N tests** to check which inputs and configurations it includes. When the batch has no tests, a warning under it says why (a batch file missing from the commit's artifacts, a batch defined nowhere, inputs not found...). The [Available Tests](commit-page.mdx#available-tests) view lists the batches you can use, and lets you define your own.
3. If the project supports several **platforms**, pick one.
4. Choose the parameters:
   - **Manual tuning**: write the parameters to try, as JSON. Click the examples (*simple-combinations*, *list-of-combinations*, *1x2 matrix*...) to get started. Choose **All combinations** (a grid) or **Sampling** a number of them. The total number of runs is shown before you send.
   - **Automated tuning**: describe the search space and the objective in YAML, and let the optimizer ([scikit-optimize](https://scikit-optimize.github.io/)) choose the parameters. It needs the project to compute metrics.
   - To just run the tests, without tuning, use the *no tuning* example.
5. **Send**. The runs start as you (the "Will run as" tag), and a message confirms the request.

While you fill the form, QA-Board checks it: **Fix this to start** lists what would make it fail (e.g. an unknown batch, an invalid automated tuning configuration, a platform the project doesn't have), and **Before you start** warns about the rest (e.g. missing artifacts that will be restored first).

Then select the new batch in the batch selector to follow it. When it's done:
- compare it with the CI batch (see the [tip in Comparing results](comparing-results.mdx#picking-a-reference)),
- open the **Analysis** view to see how metrics depend on the parameters, and the best parameters found by an automated tuning.

Batches started from QA-Board are listed in the [Logs](commit-page.mdx#logs) view with the command QA-Board ran and its logs:

:::tip
Turn on **Overwrite previous identical runs** to redo runs that already exist with the same input, configuration and parameters. Otherwise they are kept and not run again.
:::

## Integrations: CI jobs, links and webhooks
Projects can add buttons to the sidebar's **Integrations** menu (hover it to open). What you see depends on how your project is configured:

- **Links** to docs, dashboards, build artifacts or reports. A link is disabled when its target doesn't answer.
- **Badges**, like the pipeline status or the test coverage.
- **GitHub Actions workflows**, **GitLab CI manual jobs** and **Jenkins builds**: click to start them for this commit. A status tag shows whether the job is pending, running, successful or failed; click the tag to open the job's page and its logs. Once started, the icon changes to *repeat* so you can start it again. You need to be logged in to start GitHub Actions workflows and GitLab CI jobs.
- **GitHub Actions workflows** show the status of their latest run for the commit. GitHub runs them on the latest commit of the branch (or on the `ref` the project chose), not necessarily on the commit you're looking at; QA-Board then follows the run you started. Only the workflows declared in the project's *qaboard.yaml* can be seen and started.
- If the project configured nothing, the menu shows its git host's defaults on branch pages: GitLab's pipeline status, or a link to GitHub Actions. Badges that don't load are hidden.
- **Webhooks** that call other tools, with a tag showing the response.

Good to know:
- On the commit list, integrations act on the branch you're looking at. On a commit page, on the selected commit and batch.
- Statuses refresh every few seconds while the menu is open, and your browser remembers the jobs you started on each commit.
- With many entries, a search box appears at the top of the menu.
- Some projects show their most used integrations directly in the sidebar, outside the menu.

Project integration: see [Triggering external tools](../triggering-external-ci-tools.mdx) to configure integrations.

## Logs
- Each run's log is in the [Logs](commit-page.mdx#logs) view (**Show logs**), and updates live while the run is pending.
- The **Batch logs** at the bottom list the commands that started the batch, by whom and where, with an **Open Logs** link to the cluster or CI job.
- For CI jobs started from Integrations, click their status tag to open the job's own logs.
