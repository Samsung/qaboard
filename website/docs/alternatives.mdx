Choosing how your team tracks quality? This page says where QA-Board fits next to the tools you may be comparing it
with: what each does best, where QA-Board differs, and when to use both. It describes these tools as of November 2026.

QA-Board answers one question, for every change: **is it better than what we ship, on every input of our test set,
and if not, where and why?** Other tools answer neighboring questions, and some answer them better than QA-Board does.
Most teams end up with QA-Board next to one of them, not instead of it.

## The short answer
| If your main question is... | Reach for | Where QA-Board fits |
|---|---|---|
| Is this change better than what we ship, on every input, and why? | **QA-Board** | What it's built for. |
| Which training run converged best? | An experiment tracker: Weights & Biases, MLflow, TensorBoard | After training: the checkpoint you'd ship, against the model you shipped, input by input. |
| Which samples are mislabeled, and where does the model fail on our dataset? | Dataset curation: FiftyOne, or Voxel51 for teams | Every commit's evaluation against the release's, and the outputs of the code around the model. |
| What did the robot see and do in this recording? | A robotics data viewer: Rerun, Foxglove | Every sequence replayed on every commit, against the reference's and the ground truth. |
| Which data and parameters produced this model? | Data versioning: DVC, lakeFS | Reads your inputs where they are, and compares each commit's outputs in the browser. |
| How does our LLM app behave with real users? | An LLM observability platform: Langfuse, LangSmith, Arize Phoenix | Before release: your eval suite, task by task, on every commit. |
| Which of our 50,000 tests are flaky? | Test analytics: ReportPortal, Develocity, your CI's test insights | Suites next to your other metrics, tests against the reference's, a gate on deleted tests, retries on record. |
| Is this function 3% slower? | Continuous benchmarking: CodSpeed, Bencher, asv | Your harness's files against the reference's, within its spread or not; end to end, latency under load and flame graph diffs. |
| Is production healthy right now? | Monitoring and APM | Not QA-Board's job: it catches regressions before they ship. |

## What QA-Board does differently
<Clip id="landing/hero" caption="Metrics, then the outputs behind them: the new denoiser wins PSNR, and the images show the halos it adds." />

1. **The commit is the unit of review.** Every run belongs to a commit, and every commit is compared with the latest
   results of your reference branch, or with a release saved as a milestone, with no setup. Trackers collect runs that
   you then tag and filter; QA-Board opens on "what did this change do?".
2. **The outputs, not only the numbers.** Viewers built for heavy data put the new run next to the reference, in sync:
   images down to the pixel values your code saved, with deep zoom on 100-megapixel images, videos frame by frame,
   point clouds and trajectories, flame graph diffs, plots overlaid, test reports, logs, and the HTML your code writes.
3. **Anything you measure.** Your `run()` returns numbers and writes files. Camera pipelines, models, servers, embedded
   code, robots, test suites and LLM agents get the same review, on the same server.
4. **Your compute, your storage, your network.** `qa` runs where your code already runs: a laptop, CI, LSF,
   Kubernetes, Celery, Dask (on Slurm too), Jenkins. Runs save their outputs in a storage your server reads in place,
   like an NFS share, or, where it isn't mounted, send them to your server over HTTP (experimental, see
   [without a shared storage](/docs/storage/uploads)). No third-party service sees your results. The server is
   self-hosted and open source (Apache 2.0), with every feature, including on networks without internet access.
5. **The whole team, from the browser.** Everyone with the developer role on a project, not only those who write
   code, can rerun tests with other parameters, start a sweep or an automated tuning, and read what it found, without
   a terminal. This needs the shared storage, where the commit's build is.
6. **Built for releases.** Milestones for what shipped, bit-accuracy checks before a hardware handoff, and a quality
   gate in CI (`qa gate`, experimental) that comments on the pull request, with rules a project's owners set out of
   the commits' reach. Coding agents run the same tests and meet the same targets as people: they read results with
   `qaboard.runs(url)`, `qa runs` and the compare API, with [skills](/docs/agents) that teach them how. A run done
   again keeps the record of its earlier attempts.
7. **Proven in production.** Samsung's central quality platform since 2018: about 50 projects and more than 40
   million runs.

## Experiment trackers, for deep learning {#experiment-trackers}
**If your team's daily work is training deep networks, keep your experiment tracker: today it's the better tool for
that job.** Weights & Biases, MLflow, TensorBoard, Comet, ClearML and Aim are built around the training loop, and do
it very well:
- Two lines of code log a training script or a notebook, with nothing to configure first.
- Live training curves, per step, for hundreds of runs at once, with GPU and system metrics.
- Hyperparameter sweeps that stop bad trials early.
- Model registries and lineage: which data and code produced which checkpoint.
- Hosted services (Weights & Biases, now part of CoreWeave Forge; Comet; managed MLflow), or open source you run
  yourself (MLflow, TensorBoard, Aim). ClearML's server is source-available (SSPL), with single sign-on and roles in
  its paid plans. Neptune's hosted service closed in March 2026, after OpenAI acquired the company.

QA-Board's place is **after training**, when the question becomes "should we ship this model?":
- **Against the release, on every slice.** The candidate next to the model you shipped, per slice, class and object
  size, on every commit: see [model evaluation](/docs/use-cases/detection-eval).
- **The outputs, at full size.** Trackers log images and media too, and some compare them across runs in tables.
  QA-Board goes further for heavy outputs: synced deep zoom, image and video differences, the pixel values your code
  saved, point clouds and trajectories.
- **The code around the model.** Pre- and post-processing, quantization, the runtime on the device: the whole
  pipeline is evaluated per commit, like the rest of your product.
- **Your data stays in place.** Evaluations run on your cluster and read your test set where it is.

| | Experiment trackers | QA-Board, November 2026 |
|---|---|---|
| Training curves, logged per step | Their core, for hundreds of runs at once | Experimental: `run.log()` plots each run's series against its reference's, live, and the runs of a batch together, up to 40 |
| Logging from any script or notebook | Two lines of code | Experimental: `qaboard.start_run()` ([log from your code](/docs/log-from-code)), with a QA-Board server to send results to; or wrap your code with `qa run` |
| Comparing hundreds of runs at once | Their core | New against one reference at a time, or the image viewer with every stacked reference; a batch's logged series together; a tuning experiment's runs in **Tuning Analysis** |
| System metrics, media per step, sweeps with early stopping | Yes | Experimental: memory, CPU and GPUs are measured, and images, sounds, videos, tables and histograms logged per step show next to the reference run's, with a step slider. No early stopping: sweeps are batches and `qa optimize` |
| Hosted service | Weights & Biases, Comet, managed MLflow | Self-hosted only |
| Model registry and lineage | Yes | No: runs link to your registry with badges |
| Each commit against the release, by default | By convention | Yes |
| Heavy outputs in sync with the reference: 100 MP images, videos, point clouds, flame graphs | Media panels and tables | Yes, down to pixel values |
| Starting evaluations from the browser, on your own cluster | Some, with job launchers | Yes: on the server, LSF, Kubernetes, Dask or Celery |
| Beyond ML: imaging, performance, robotics, tests | Possible, not the focus | The same review for anything measured |
| Open source, with every feature | MLflow, TensorBoard, Aim | Yes, Apache 2.0 |

Many teams use both: the tracker for training, QA-Board to evaluate what they'd ship, each run linking to its
training page. See [deep learning and MLOps](/docs/deep-learning). Logging from training loops and notebooks, with
values per step, is experimental ([log from your code](/docs/log-from-code)), and so is logging with the code you
wrote for [W&B](/docs/from-wandb) or [MLflow](/docs/from-mlflow); importers of past runs are on the
[roadmap](/docs/roadmap#log-from-your-code).

## Visual data and robotics tools {#visual-data}
### FiftyOne and Voxel51 {#fiftyone}
FiftyOne is built around datasets for visual AI, and does what QA-Board doesn't:
- Browse images, videos and 3D scenes with their labels and predictions drawn on top, field by field, and query them
  from Python or a notebook: by label, confidence, tag or metadata.
- Find label mistakes, duplicates and edge cases, and search by similarity with embeddings.
- Evaluate detection, classification and segmentation on a dataset: true and false positives per sample, confusion
  matrices, precision-recall curves, and two evaluations compared in the Model Evaluation panel.
- Annotate in the app or in an annotation tool it connects to, and add features with plugins.

FiftyOne is open source (Apache 2.0) and runs on your machine, for one user. Voxel51, the commercial platform built on
it (named FiftyOne Enterprise until October 2026), adds work in teams, dataset versions, single sign-on and labeling
with models, hosted with a free tier, or deployed in your cloud, on premises or air-gapped.

QA-Board answers another question: did this commit make things better or worse?
- **The commit, not the dataset.** FiftyOne evaluates the predictions you add to a dataset, when you run it.
  QA-Board runs your evaluation on every commit, compares each input with the reference's, follows the metrics on
  **History**, and can fail the CI with `qa gate` (experimental).
- **The whole pipeline's outputs.** Beyond predictions: a camera pipeline's images down to pixel values, with deep
  zoom on a 113 MP image, videos frame by frame, latency and flame graphs, reviewed the same way.
- **Your code draws the labels.** Detections are images or HTML your code writes, compared with the reference's in
  sync ([model evaluation](/docs/use-cases/detection-eval)). FiftyOne draws labels itself, and filters them as you
  look.
- **Tuning from the browser.** Start a sweep or an automated tuning of thresholds and settings, and read which
  parameters matter.

Use both: FiftyOne or Voxel51 to build the test set, check its labels and dig into failure modes; QA-Board to run
the evaluation on every commit against the release. A [badge](/docs/deep-learning#workflows) on each run can link
to the matching dataset in FiftyOne.

### Rerun and Foxglove {#robotics-viewers}
Rerun and Foxglove are built to explore what a robot recorded, and do it better than QA-Board:
- Images, point clouds, transforms, time series and video on one timeline, in 3D and 2D views you arrange, live from
  a running robot or simulation, or from a recording. QA-Board's 3D viewer reads *.pcd* point clouds and 6DoF
  trajectories.
- **Rerun** logs from Python, Rust or C++ to *.rrd* files that you also query as dataframes, and opens MCAP and LeRobot
  data. Its SDK and viewer are open source (MIT or Apache 2.0); Rerun Hub, its commercial backend, keeps a catalog of
  recordings in your object storage. Its viewer shows one recording at a time.
- **Foxglove** reads ROS 1, ROS 2 and MCAP, has more than 20 panels, overlays several recordings on one timeline in
  its comparison mode (paid plans), and manages a fleet's recordings. It has a free plan; running its data plane in
  your own cluster takes the Enterprise plan. Its app has been closed source since 2024; MCAP stays open source.

QA-Board reviews each change, not each recording: every sequence of your test set, run again on every commit, with
its trajectory against the ground truth and the reference's, the map it built, sensor videos in sync, and
trajectory metrics on **History** with a gate when one sequence gets worse (see [robotics](/docs/use-cases/robotics-3d)).
Use both: let QA-Board say which sequences got worse with a change, and save the *.rrd* or *.mcap* with the run, so
people download it from **Output Files** and open it in Rerun or Foxglove to see why.

## Data versioning and experiments in git: DVC {#dvc}
DVC versions datasets and models next to your code, in git, and runs again the steps of a pipeline whose inputs
changed. Its metrics and plots live in git too: `dvc metrics diff` and `dvc plots diff` compare commits from the
terminal, and `dvc exp show` lists experiments in a table. DVC is open source (Apache 2.0), maintained by lakeFS
since it acquired the project in November 2025.

QA-Board compares commits too, on a server: every input's outputs in viewers, for the whole team without checking
out any commit, with **History** across commits, milestones, a gate, and runs started from the web app. It
doesn't version data: keep your test set in DVC or lakeFS, and have `run()` read it where it is.

## LLM and agent evaluation platforms {#llm-evals}
Langfuse, LangSmith, Braintrust and Arize Phoenix are built for LLM applications, and do what QA-Board doesn't:
- traces of every model and tool call, in development and in production;
- monitoring of production traffic, and eval datasets built from it;
- libraries of LLM-as-judge scorers, annotation queues for human review, prompt playgrounds.

QA-Board treats your eval suite like any other test set: each task against the reference, transcripts diffed, the
report your code writes, pass rates and cost per commit, and a gate that fails CI on an unsafe action, whoever wrote
the change (see [LLM agent evals](/docs/use-cases/agent-evals)). Eval runners like promptfoo or Inspect fit inside
your `run()`: QA-Board tracks what they score, commit after commit. Use an observability platform for production,
and QA-Board when the agent is one part of a product whose other parts you already review there.

## Test reports and coverage dashboards {#test-dashboards}
Allure Report, ReportPortal, Develocity and Codecov follow tests at scale: one test's history over thousands of
builds, failures grouped by cause, flaky tests across an organization, coverage comments on pull requests. Allure
Report 3 can also fail a run when too many tests fail.

QA-Board follows each suite as a run: counts, failures, flaky and skipped tests and coverage over time, next to your
other quality metrics, with each suite's tests compared with the reference's and a gate that catches tests deleted to
get a green CI (see [tests and coverage](/docs/use-cases/software-quality)). `qa upload junit.xml` brings a suite in
from any CI job, without a `run()` function (experimental, see [upload results](/docs/upload-results)). The gate
(experimental) comments on pull requests with its verdict, and lists the runs that only passed after a retry: a run
done again keeps how its earlier attempts ended and their logs. QA-Board has no history of a single test case, and
doesn't group failures by cause across builds.

## Benchmarking and profiling tools {#benchmarking}
CodSpeed and Bencher run your benchmarks on every change, on runners set up for stable measurements, flag
regressions of a few percent, and comment on pull requests; CodSpeed also draws differential flame graphs of each
benchmark. asv keeps a website of each benchmark's history and finds the commit that made one slower. Continuous
profilers and APM tools watch production.

QA-Board puts performance next to the rest of a change's review: latency distributions under the same load profiles
on every commit, flame graph diffs from the files your profiler writes (folded stacks, speedscope, `.cpuprofile`), CPU
per core, History per profile, and tuning frontiers (see [performance](/docs/use-cases/serving-latency)). The gate's
verdict goes to the pull request too, as [a comment](/docs/quality-gate-pull-requests) (experimental) that
also says when runs only passed after being done again. The gate doesn't decide whether a change is noise: repeat your
measurements, and set its thresholds above the noise.

QA-Board reads the files of the usual benchmark harnesses: pytest-benchmark, Google Benchmark, hyperfine, Criterion,
JMH and `go test` (Bencher reads more). Each benchmark shows next to the reference's, gray when the change is within the
spread the harness reported, and becomes a metric in one line (see [benchmarks](/docs/benchmarks)); `qa upload`
saves a benchmark file as a run from any CI job (experimental). It still doesn't run, repeat or stabilize benchmarks,
and doesn't estimate noise from past runs: that's the harness's job, and those tools' strength.

## Notebooks, spreadsheets and in-house dashboards {#in-house}
A notebook answers a new question in an afternoon, and nothing replaces that. Then results get pasted into a
spreadsheet, screenshots into a chat thread, and someone maintains a dashboard for one project. QA-Board is what
those tools become after years of use on dozens of projects: one place, the same for every project, for everyone on
the team. Notebooks stay useful next to it: `qaboard.runs(url)` gives a script or a notebook the runs a page shows
(see [runs in scripts](/docs/apis#runs-in-scripts)), and `qaboard.start_run()` saves what a notebook computes as a
run (experimental).

## What QA-Board doesn't do {#non-features}
- **CI.** Call `qa` from the CI you have: GitHub Actions, GitLab CI, Jenkins (see [CI integration](/docs/ci-integration)).
- **Production monitoring.** QA-Board compares commits before they ship.
- **Data versioning.** Keep your datasets in DVC, lakeFS or your own storage: QA-Board reads inputs where they are.
- **Dataset curation and labeling.** Use FiftyOne, Voxel51 or your annotation tool; the image viewer can show the
  regions people marked in another app ([annotations](/docs/user-guide/image-viewer#annotations)).
- **A model registry.** Runs can link to it with badges.
- **A hosted service.** You run the server: Docker Compose or Kubernetes (see [deploy](/docs/deploy)). Runs save
  their outputs in a storage the server mounts, like an NFS share, or send them to the server over HTTP
  (experimental). Starting runs from the web app still needs the shared storage, and object storage like S3 works
  when mounted as a file system: the server talking to buckets itself is on the [roadmap](/docs/roadmap#cloud-native).
