The `run()`function wrapping your code receives an `output_directory` where it can create all kinds of files. Usually, you only want to look at a few of those files, the rest being debug data. **Visualizations** help you declare pre-sets of relevant files. 

Here is a simple example, assuming your code an image named *output.jpg*.

```yaml title="qaboard.yaml"
outputs:
    visualizations:
    - path: output.jpg
```

:::note
For now, to debug your visualizations, you have to commit and push your new *qaboard.yaml*.
We plan on letting you edit simply *qaboard.yaml* locally, and update the visualizations when you use `qa --share`.
:::

You can provide multiple relevant files, and hide debug visualizations by default: 

```yaml {5-6} title="qaboard.yaml"
outputs:
    visualizations:
    - path: output.jpg
    - path: debug.jpg
      default_hidden: true
      # type: image/jpg # auto-guessed
```

## Available file viewers
QA-Board tries to guess the right image viewer depending on the file extension or a `type`

Extensions                                          | Type         | Viewer                                       |
----------------------------------------------------|--------------|----------------------------------------------|
`*.jpg*`, `*.png*`, `*.bmp*`, `*.tif*`, `*.pdf*`... |  `image/*`   | **Image**                                    |
`*.hex*`, `*.raw*`, `*.dng*`                        |  `image/*`   | **Image**, if the server has a reader for these raw formats (not included) |
`*.plotly.json`, `*.plotly.html`                    | `plotly/json` / `plotly/html`| **Plot.ly**                                  |
`*.flame.json`                                      | `flame/json` | **[Flame Graph](http://www.brendangregg.com/flamegraphs.html)**, [diffable](http://www.brendangregg.com/blog/2014-11-09/differential-flame-graphs.html)          |
`*.html`                                            | `text/html` | **HTML** (in a frame, scripts don't run)     |
`*.mp4`, `*.webm`, `*.mov`, `*.webp`, `*.gif`       | `video/*`    | **Video**: synced, side by side, wipe or difference |
`*.txt`, unidentified                               | `text/plain*`| **Text** (diffs, with VSCode's [Monaco Editor](https://microsoft.github.io/monaco-editor/))|
`</>`                                               | `pointcloud/txt` | ToF's **pointcloud** viewer (needs to be split) |
`</>`                                               | `6dof/txt`       | SLAM's **6DoF** viewer (needs to be split)      |


### Image viewer
  * Supports all common image formats, and raw images with an [IIIF](https://iiif.io) server that reads them.
  * Compares new and reference side by side, with a wipe, one at a time (single), or as their difference: perceptual (YIQ), ΔE 2000, absolute or signed per channel, or any change.
  * Fast and smooth zoom & pan, synced across runs and visualizations. Fast image streaming via IIIF.
  * The values of the hovered pixel in both images, and their difference, with a synced cursor on the other images. For 16-bit or raw images, the image's own values, read by the server.
  * Zoomed in, the values written on the pixels.
  * Regions of interest: the input's presets, or found where the images differ most, by a perceptual, SSIM or ΔE 2000 difference.
  * Display adjustments (brightness, contrast, gamma, sharpen, one channel, false colors).
  * Histograms per channel, of the region in view.
  * Copy or save the new, reference or difference image.

How to use it is described in the user guide: [comparing images](/docs/user-guide/comparing-results).

:::tip TIFF and PNG
If a run saved both *image.png* and *image.tiff*, a visualization of *image.png* shows the TIFF. When the reference run doesn't have the file, the viewer falls back to the reference's *.tiff*, then *.bmp*, of the same name: it helps comparing results across a change of output format.

### Regions of interest
The image viewer shows thumbnails to navigate between regions of interest. Give them in the [input's metadata](metadata-integration-external-databases), or in a configuration (`{"roi": [...]}`). With YAML syntax:

```yaml
width: 800   # optional, useful if your results are showed with downscaled resolution
height: 600  # optional, idem
roi:
- {x: 1408, y: 244, w: 121, h: 97, label: "Gradations and overshoots"}
- {x: 455, y: 651, w: 58, h: 58, label: "False colors"}
# you can override give the image dimension per ROI:
- {image_width: 1600, image_height: 1200, x: 351, y: 567, w: 45, h: 53, label: "Details fine line"}
```

### Plot.ly viewer
[The Plotly library](https://plot.ly/graphing-libraries/) has everything you need from bar charts to 3d plots.
- huge variety of plots
- interactive plots
- easy-ish to use with binding to [python](https://plot.ly/python/getting-started/)/JS/matlab...
- web-based
- open-source and popular
- performant

<Shot
  id="commit/plotly-overlay"
  caption="Precision-recall curves per class: the int8 model's, with the fp32 reference's drawn dashed on the same axes."
/>

<img alt="3d plot with plotly for LSF/Calibration" src={useBaseUrl('img/plotly-3d-example.png')} />

All you need is to save your plot data as JSON. 

```python
import plotly.graph_objects as go
fig = go.Figure(data=go.Bar(y=[2, 3, 1]))
with open('graph.plotly.json', 'w') as f:
  spec = fig.to_json() # '{"layout": {...}, "data": [{...}, {...}, ...]}'
  f.write(spec)
```

By default, the new and reference plots are shown side by side. With `side_by_side: false`, the reference run's traces are drawn on the same axes as the new run's (when your traces set their colors, the reference's are dashed and faded):

```yaml {4} title="qaboard.yaml"
outputs:
  visualizations:
    - path: latency_cdf.plotly.json
      side_by_side: false
```

<Shot

You can also save figures as stand-alone HTML, e.g. with `fig.write_html('graph.plotly.html')`. They are shown side by side (new and reference) in iframes, so the reference isn't overlaid on the same plot like with JSON.

### Video viewer
  * New and reference play in sync, frame by frame: paused, both show the same frame, and the viewer says which, numbered like in the file.
  * Compare them like images: side by side, with a wipe, one at a time, or as their difference (perceptual, ΔE 2000, absolute...), with display adjustments, full screen and a blind test.
  * Zoom with the mouse wheel or a pinch, drag to pan: both videos follow, even when their resolutions differ. Zoomed in, you see the actual pixels and their values: decoded (e.g. 10-bit Y′CbCr) or as displayed.
  * See what's in the files (codec, pixel format, color range, frame rate...) and find where and when two videos differ, frame by frame.
  * Step frame by frame, scrub, slow down to 0.1×, loop. Copy or save the current frame as a PNG.

How to use it is described in the user guide: [comparing videos](/docs/user-guide/comparing-results#video-viewer).

<Clip
  id="commit/video-compare"
  caption="The camera driving down an aisle in low light, new and reference: frame by frame, with a wipe, zoomed in, and their difference."
/>

Browsers play **H.264**, **VP9** and **AV1** videos, in *.mp4* or *.webm* files. Other codecs (e.g. HEVC/H.265, MPEG-4 part 2) or containers (e.g. *.avi*) show an error: convert them when your code writes them, for instance with:

```bash
ffmpeg -i input.avi -c:v libx264 -pix_fmt yuv420p -movflags +faststart output.mp4
```

`+faststart` lets a video start playing before it's fully downloaded. Animated *.webp* and *.gif* files are compared the same way, but your browser plays them on its own: they are not synced.

QA-Board's server reads the files with FFmpeg: the timestamp of every frame (frames are numbered like in the file,
also with variable frame rates), their decoded values, and where two videos differ. It reads any format FFmpeg reads,
but your browser still has to play the video.

To compare exact values, write lossless videos: lossy codecs change the values your code wrote, and 4:2:0 stores
colors at half resolution. Browsers play lossless VP9:

```bash
ffmpeg -i frames/%04d.png -c:v libvpx-vp9 -lossless 1 -pix_fmt yuv444p output.webm
```

Without the server's timestamps, QA-Board finds a video's frame rate when it plays, or when you step through its frames. If it guesses wrong, set it, with an optional image shown before the video loads:

```yaml title="qaboard.yaml"
outputs:
  visualizations:
  - path: camera.mp4
    fps: 30
    poster: camera.jpg  # default: poster.jpg, if the run created it
```

## Dynamic visualizations
You can use a [special syntax](https://github.com/pillarjs/path-to-regexp) to create dynamic visualizations at display-time. Users will be able to choose what to display using sliders / select options:

<Clip
  id="commit/dynamic-outputs"
  caption="One visualization per ISP stage: the slider steps from the raw mosaic to the tone-mapped image, on every run's card."
/>

```yaml {5,7} title="qaboard.yaml"
outputs:
    visualizations:
    - name: Movie Frames
      # you can use the `/user/:name` syntax to match part of filenames
      path: ":frame/output.jpg"
      # you can match part of filenames (experimental)
      path: ":frame/frame_:number.jpg"

      # For more examples, the full syntax is available at:
      # https://github.com/pillarjs/path-to-regexp
      # Note that for the most advanced syntax you need to escape strings like this
      # path: frames/:frame(\\d+).jpg 

```

You can also use regular expressions **(inside parentheses!)** to match which output files you want to view:

```yaml {4,6,8}
outputs:
    visualizations:
      # A common use case is matching file extensions
      path: "(.*\.jpg)"
      # ... or parts of filenames
      path: "(debug_.*\.jpg)"
      # you can mix with the previous syntax
      path: ":frame/(.*\.txt)"

      # If you use regular expressions, we aware that:
      # - You MUST use "( )" aka "capture groups" !
      # - While you can often get away "(.*)/output.jpg", in many cases you'd want "([^/]*)/output.jpg"
      # - Parts of paths matched via regular expressions are not synced with other outputs. Prefer the ":name" syntax
      #   Eg if you ask also to visualize "(.*)/debug_output.jpg" and "(.*)/output.jpg"
      #   you will get two select inputs for the frame.
```

By default, only one viewer/path is shown at a time, and you get sliders/select to decide what to show. They are in the **Files to show** section of the **View options**, and apply to all runs, but users can turn on **Per run** to choose the value in each run's card (see the [user guide](/docs/user-guide/commit-page#view-options)).

Each option is named after its part of the path, as a label: `:frame` shows as *Frame*, `:noise_level` as *Noise level*. Name the parts of your paths for your users: prefer `frames/:frame.png` to `frames/(.*)\.png`, whose option gets a name made up from the visualization's.

Runs don't need to have the same values: the **View options** offer the values of all runs, and numbers are sorted as numbers (`2` before `10`). Until users pick a value, each run shows its own default: its last value when the values are numbers (e.g. its last frame), else its first. When a run doesn't have the selected value, its card shows the closest number (or the default) and says so.

## Advanced Options [EXPERIMENTAL] 
### Custom Styles
You can style your visualizations. Without a `width`, run cards are as wide as the page allows, up to 1500px, and images
are 390px wide for a pair:

```yaml {3-7,10-12}
outputs:
    # define global or per-view styles
    style:
        # use any CSS properties
        width: 500px
        # the style will be applied to the outer-container
        # and passed down to the viewers
    detailed_views:
    - name: My debug visualization
      style:
        width: 400px   
```

### Viewer Configuration
Some viewers can read extra configuration parameters from their configuration: 

```yaml {5}
outputs:
    detailed_views:
    - name: My SLAM plot
      type: 6dof/txt
      show_3d: true
```

You can specify those parameters at "display-time" by defining controls:

```yaml {2-7}
outputs:
  controls:
    - type: toggle
      label: Debug
      name: show_debug
      default: false
```
