Your runs write files in `context.output_dir`. List the ones people should look at in *qaboard.yaml*: the commit
page's **Visualizations** view shows them on each run's card, next to the reference run's, in a viewer picked from
the file's extension.

## Show an image {#show-an-image}
If your code writes *out.png*:

```yaml title="qaboard.yaml"
outputs:
  visualizations:
    - name: Output
      path: out.png
```

`path` is relative to the run's output directory. Run a batch with `qa --share batch <batch>`, open the link it
prints, then the **Visualizations** view: each run's card shows its *out.png* next to the reference's, and zooming one
zooms the other.

  id="commit/visualizations"

/>

:::note When the web app sees your changes
A commit keeps the *qaboard.yaml* that `qa` sent with its first results. To try new visualizations, edit
*qaboard.yaml* and run `qa --share batch <batch>` again: the batch keeps your edited *qaboard.yaml*, and the web app
shows its new visualizations for that batch. The commit's other batches, like the CI's, keep the commit's.
`qa --share run` doesn't change which *qaboard.yaml* a batch uses.
:::

## Which viewer opens a file {#available-file-viewers}
The extension picks the viewer. Set `type` when it doesn't say, e.g. `type: 6dof/txt` for a trajectory saved as
*poses.tsv*.

| Files | `type` | Viewer | In the user guide |
|---|---|---|---|
| *.png*, *.jpg*, *.jpeg*, *.bmp*, *.tif*, *.tiff*, *.pdf* | `image/*` | **Image**: side by side, wipe, difference, pixel values | [The image viewer](/docs/user-guide/image-viewer) |
| *.raw*, *.dng*, *.hex* | `image/*` | **Image**, if the image server reads these raw formats (not included) | [The image viewer](/docs/user-guide/image-viewer) |
| *.mp4*, *.webm*, *.mov*, *.mkv*..., animated *.webp* and *.gif* | `video/*` | **Video**: in sync, frame by frame | [The video viewer](/docs/user-guide/video-viewer) |
| *.plotly.json*, *.plotly.html* | `plotly/json`, `plotly/html` | **Plot**, side by side or on the same axes | [Plots](/docs/user-guide/other-viewers#plots) |
| *.flame.json* | `flame/json` | **Flame graph**, differential | [Flame graphs](/docs/user-guide/other-viewers#flame-graphs) |
| *.html* | `text/html` | **HTML**, in a frame, without scripts | [HTML reports](/docs/user-guide/other-viewers#html-reports) |
| *.pcd* | `pointcloud/pcd` | **Point cloud** in 3D, with the reference's and a ground truth | [Point clouds](/docs/user-guide/other-viewers#point-clouds-and-trajectories) |
| any, e.g. *.tsv* | `6dof/txt` | **6DoF trajectory**, with the reference's and the ground truth | [Trajectories](/docs/user-guide/other-viewers#point-clouds-and-trajectories) |
| any | `pointcloud/txt` | A time-of-flight camera's frames: point clouds and depth maps (legacy layout) | |
| anything else: *.txt*, *.json*, *.log*... | `text/plain` | **Text**, diffed with the reference's | [Text](/docs/user-guide/other-viewers#text) |

<Anchor id="video-viewer" /><Anchor id="point-clouds-and-trajectories" />
What each viewer reads (video codecs, point cloud formats, the trajectories' columns...) and its options are in
[Viewers and file formats](/docs/viewers).

## Show several files, hide the debug ones {#hidden-by-default}
Cards show the visualizations in the order of the list. Those with `default_hidden: true` start hidden: people turn
them on in the **View options**. Hide the debug plots and the large files.

```yaml title="qaboard.yaml" {7-9}
outputs:
  visualizations:
    - name: Output
      path: out.png
    - name: Edge profile
      path: edge.plotly.json
    - name: Color errors
      path: color.plotly.json
      default_hidden: true
```

<Shot
  id="commit/controls-panel"
  caption="The View options list every visualization: Color errors and Noise vs signal are hidden until someone turns them on."
/>

Give each visualization a `name`: the View options list it by its name (or by its `label`, if you give one), and the
web app shows and hides visualizations by name. Visualizations without a name are shown and hidden together.

## Every file your run writes {#output-files}
A visualization only chooses what shows on the cards: QA-Board keeps every file your run writes in
`context.output_dir`.
- The **Output Files** view lists all of a run's files, and which differ from the reference's: see
  [the commit page](/docs/user-guide/commit-page#output-files). `qa` writes their sizes and hashes in
  *manifest.outputs.json* at the end of each run, next to the run's log (*log.txt*) and metrics (*metrics.json*).
- The [file browser](/docs/user-guide/files) opens any run's folder.
- `qa run` empties the output directory before it runs your code. To keep what's there, e.g. your own cache, use
  `qa run --keep-previous`.
- Where the files are saved and when they are deleted: [Where is the data saved?](/docs/storage/where-is-the-data) and
  [Deleting old data](/docs/storage/deleting-old-data).

## Show a file per frame, stage or step {#dynamic-visualizations}
When runs write one file per frame, pipeline stage or iteration, one visualization can offer them all. Name the part
of the path that changes with `:`, here `:stage`:

```yaml title="qaboard.yaml"
outputs:
  visualizations:
    - name: ISP stage (1 raw, 2 demosaic, 3 denoise, 4 sharpen, 5 tone map)
      path: "stages/:stage.jpg"
```

The **View options** get a **Files to show** section, with a slider when the values are consecutive integers, else a
select. The value applies to all the runs' cards, unless people choose it **Per run** (see
[the commit page](/docs/user-guide/commit-page#view-options)).

<Clip
  id="commit/dynamic-outputs"
  caption="One visualization for the 5 ISP stages: the slider steps from the raw mosaic to the tone-mapped image, on every run's card."
/>

- **Name the parts of your paths** for your users: each option is labeled after its part, `:stage` as *Stage*,
  `:noise_level` as *Noise level*. Visualizations that use the same name share the option.
- **Runs don't need the same values.** The View options offer the values of all runs, and sort numbers as numbers
  (`2` before `10`). Until people pick a value, each run shows its own default: its last value when the values are
  numbers (e.g. its last frame), else its first. When a run doesn't have the selected value, its card shows the
  closest number (or the default) and says so.
- **Show all the matching files** at once, one after the other, with `display: all`.

<Shot
  id="commit/dynamic-options"
  caption="Files to show picks the stage: synced, the slider on 3 shows stages/3.jpg on every card. Changing it keeps the zoom."
/>

<details>
<summary>Patterns: several parts, parts of names, regular expressions</summary>

Paths are patterns in the syntax of [path-to-regexp](https://github.com/pillarjs/path-to-regexp):

```yaml title="qaboard.yaml"
outputs:
  visualizations:
    - name: Frames
      path: ":frame/output.jpg"           # a folder per frame
    - name: Frames, by number
      path: ":frame/frame_:number.jpg"    # part of a file name
    - name: Debug images
      path: "(debug_.*\\.jpg)"            # a regular expression, in parentheses
    - name: Logs per frame
      path: ":frame/(.*\\.txt)"           # both
    - name: Numbered frames
      path: "frames/:frame(\\d+).jpg"     # a named part that only matches digits
```

With regular expressions:
- write them in parentheses: they are "capture groups";
- `(.*)/output.jpg` also matches folders inside folders: you often want `([^/]*)/output.jpg`;
- their options are named after the visualization, and not shared with other visualizations: prefer named parts. Two
  visualizations of `(.*)/debug_output.jpg` and `(.*)/output.jpg` get two selects for the frame.

</details>

## Preset regions of interest {#regions-of-interest}
The image and video viewers show thumbnails of regions of interest above the images, to jump to the details that
matter: your presets, and the regions where the images differ most. The viewer opens on the first preset.

<Shot
  id="commit/auto-roi"
  caption="The input's preset regions, and below them the regions where the server finds that the images differ most."
/>

Presets are a list of regions under the key `roi`. Each run gets its own, from two places:

| Where | Use it for | The same for |
|---|---|---|
| [The input's metadata](#regions-per-input) | What matters in this input: a face, a window frame, a chart's patches. | Every run on the input. |
| [A configuration](#regions-per-batch) | What a test looks at, whatever the input: the corners, the center. | Every run of the batch. |

A run with both shows both, the input's first. Runs on other inputs, or of other batches, show their own on the
same page: you don't need a *qaboard.yaml* per batch.

### Regions of an input, in its metadata {#regions-per-input}
Your entrypoint's `metadata(context)` returns what you know about an input, as a dict: put the regions under `roi`.
The camera ISP example reads them from a YAML file next to each photo, when there is one:

<RepoFile path="examples/image-quality/qa/main.py" title="qa/main.py" lines="57-60" />

<RepoFile path="examples/image-quality/inputs/photos/facade.metadata.yaml" title="inputs/photos/facade.metadata.yaml" />

The regions can come from anywhere `metadata()` can read: a file next to the input, a spreadsheet, your database of
test charts. More on metadata: [Input metadata](/docs/metadata-integration-external-databases).

### Regions of a batch, in a configuration {#regions-per-batch}
Add a mapping with a `roi` key to the batch's configurations. This batch checks the corners of every photo:

```yaml title="qa/batches.yaml"
corners:
  inputs:
  - photos/*.png
  configs:
  - base
  - roi:
    - {x: 0, y: 0, w: 200, h: 200, label: Top left}
    - {x: 1024, y: 616, w: 200, h: 200, label: Bottom right}
```

With `qa run`, give the mapping as JSON: `qa --config base --config '{"roi": [{"x": 0, "y": 0, "w": 200, "h": 200}]}' run ...`.

- The web app doesn't show `roi` in the runs' configuration tags, and ignores it when it matches runs with the
  reference's.
- Like any mapping in the configurations, your code gets it too, as `context.params['roi']`.
- The regions are part of the runs' configuration: with other regions, `qa batch` makes new runs. For regions that
  change often, prefer the input's metadata.

### What a region is {#region-format}

| Key | What it is |
|---|---|
| `x`, `y` | The region's top-left corner, in pixels from the image's top-left corner. |
| `w`, `h` | Its width and height, in pixels. |
| `label` | Optional: its name, on its thumbnail and its outline. |
| `color` | Optional: the color of its outline, as in CSS (`orange`, `#f5498b`). |
| `image_width`, `image_height` | Optional: the size of the image the region was drawn on, when it's not the image shown. |

Regions are in the pixels of the image shown. When that image is smaller than the one the regions were drawn on,
e.g. a downscaled output, the viewer scales them if it knows the original size: give `image_width` and
`image_height` on a region, or `width` and `height` in the input's metadata, for all the input's regions.

```yaml title="An input's metadata, for outputs smaller than the input"
width: 4896     # the regions below are in the pixels of the 4896x3264 raw photo
height: 3264
roi:
- {x: 400, y: 160, w: 640, h: 800, label: Window frame (halos), color: orange}
```

### Write presets from the web app {#copy-a-region}
Zoom on what you want to keep, then pick **Copy the view as a region** in the regions menu. You get the size of the
image and the region's line:

```yaml
width: 1224
height: 816
- {x: 100, y: 40, w: 160, h: 200, label: ""}
```

Paste the line under `roi`, and give it a label. Regions are saved with the runs: they show on the runs made after
you add them. How people use regions: [the image viewer](/docs/user-guide/image-viewer#find-where-images-differ).

## Make room on the cards {#styles}
<Anchor id="custom-styles" />

Cards are as wide as the page allows, up to 1500 px. Set a width for all of them in `outputs.style`, or for one
visualization in its `style`. Widths are a maximum: cards get narrower when the window is.

```yaml title="qaboard.yaml"
outputs:
  style:
    width: 1180px    # new and reference images about 600 px wide each
  visualizations:
    - name: Report
      path: report.html
      style:
        width: 840px
```

## Viewer options {#viewer-options}
<Anchor id="viewer-configuration" />

Other keys of a visualization go to its viewer: `side_by_side: false` draws a plot over the reference's, `fps` sets a
video's frame rate, `point_size` a point cloud's. Each viewer's options are in
[Viewers and file formats](/docs/viewers).

<details>
<summary>Every key of a visualization</summary>

| Key | What it does |
|---|---|
| `name` | How the View options list it, and the key that shows or hides it. |
| `label` | Shown instead of the name. |
| `path` | The file, relative to the run's output directory, or a [pattern](#dynamic-visualizations). |
| `type` | The viewer, when the extension doesn't say it: see [the table](#available-file-viewers). |
| `default_hidden` | `true` to start hidden. |
| `display` | With a pattern: `single` (default) shows the file picked in the View options, `all` every matching file, `viewer` gives the pattern to the viewer. |
| `style` | CSS for the viewer, e.g. `width`. |
| Other keys | Options of the viewer: see [Viewers and file formats](/docs/viewers). |

</details>

`outputs.controls` adds switches to the **Viewers** section of the View options. Each viewer gets the switch's value as
an option of the same name, which overrides the visualizations' own. The 6DoF viewer, for instance, reads
`show_debug`, which adds plots of *DebugExtensions.txt*:

```yaml title="qaboard.yaml"
outputs:
  controls:
    - type: toggle
      label: Debug
      name: show_debug
      default: false
```

## When nothing shows {#troubleshooting}
- **Invalid visualization path** on the cards: the web app can't read a `path` pattern. Hover the tag for the error.
- A line like **2 more without files in these runs**, under the visualizations of the View options: hover it to see
  which visualizations found no file in the runs shown. Compare their `path` with the run's files in **Output Files**.
- A run without the file shows nothing for that visualization. A file only the new run has shows alone, without the
  reference's.
- You changed *qaboard.yaml* but the cards didn't: see [when the web app sees your changes](#show-an-image).
