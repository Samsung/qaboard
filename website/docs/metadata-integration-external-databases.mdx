Inputs often come with what you know about them: the scene, the lighting, the sensor, where a test chart's patches
are. Give that to QA-Board as **metadata**, and you can filter batches by it, show labels instead of paths, preset
regions of interest in the image viewer, and let your code decide what to measure. When your inputs aren't files,
read them from your own database.

## Give inputs metadata {#creating-metadata}
Define a `metadata(context)` function in your project's entrypoint: it returns a dict for each input. The camera ISP reads
a *.metadata.yaml* file next to each input, when there is one:

<RepoFile path="examples/image-quality/qa/main.py" title="qa/main.py" lines="57-60" />

`context` is the same as `run(context)` gets: `context.input_path`, `context.rel_input_path`, `context.database`,
`context.configurations`, `context.params`, `context.platform`, `context.batch`... When `qa batch` filters inputs,
the runs don't exist yet: `context.output_dir` isn't set, and `context.input_metadata` is empty.

## What metadata does {#what-metadata-does}

| Key | What QA-Board does with it |
|---|---|
| `label` | Shown instead of the input's path, on run cards and in tables. |
| `roi` | Regions of interest preset in the image viewer, see [Visualizations](/docs/visualizations#regions-of-interest). |
| `tags` | A list, like `[low-light, motion]`: the History page summarizes metrics per tag with `dashboard_breakdown_by_tag: true` in your [metrics file](/docs/computing-quantitative-metrics). |
| `id` | Runs on different inputs are compared when they have the same `metadata.id`: for instance images from two sensors, taken in the same conditions. |
| anything else | Filters for batches (below), and shown in the run card's menu, under **Metadata**. |

Keys that start with `_` only serve to filter batches: `run()` doesn't get them, and they're not saved with the runs.

## Filter batches with metadata {#using-metadata-to-filter-batches-of-inputs}
`only` keeps the inputs that match all its conditions, `exclude` leaves out those that match all of its own:

```yaml title="qa/batches.yaml"
night-outdoor:
  inputs:
    - photos
  only:                     # all these conditions
    location: outdoor
    camera:                 # one of these values
      - k3
      - k3-v2
    scene: 'night*'         # wildcards
    stabilized: false       # booleans and numbers
    lux: '<10'              # also >, >=, =, ==, <=
    rel_input_path: 'photos/*'  # the path relative to the database (input_path: the absolute path)
  exclude:
    scene: night-rain
```

```bash
qa batch night-outdoor
```

Without `inputs`, `only` and `exclude` pick from all the inputs of the database. Text matches ignore case. On big
databases, keep `metadata()` fast: `qa batch` calls it for every input it lists when the batch has `only` or
`exclude`, and each run calls it again for its input.

## Read inputs from your own database {#integrating-with-external-input-databases}
Inputs are not always files. They can be rows of a test database, or the names of unit tests, listed by something
like `gtest_project --gtest_list_tests`. Define an `iter_inputs()` function in your project's entrypoint, that yields
the inputs matching a query:

```python title="qa/main.py"
def iter_inputs(path, database, only, exclude, inputs_settings):
  """
  path: what the batch lists under `inputs` (None: all the inputs of the database)
  database: the database's path, from qaboard.yaml or the batch
  only, exclude: the batch's filters
  inputs_settings: qaboard.yaml's `inputs` settings (globs, use_parent_folder, your own keys...)
  """
  # For instance, query your database:
  #   SELECT test, metadata FROM tests WHERE path LIKE ...
  # Filtering with only/exclude here is optional: qa filters what you return again, on its metadata.
  for test in tests:
    yield {"input_path": test.path, "database": database, "metadata": test.metadata}
```

`qa` reads the `input_path` (relative to `database`), `database` and `metadata` keys.
