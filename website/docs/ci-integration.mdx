Run your tests on every commit you push: each commit then has results, and the web app compares them with the
reference, the latest results of your reference branch. `qa` reads the commit, the branch and the CI job from the
CI's environment variables, so the job only installs `qaboard` and runs `qa batch`.

:::info Before you start
- A QA-Board server, and its address for `QABOARD_URL` (see [Installation](/docs/installation)).
- A batch of tests to run on every commit, like `ci` (see [Batches of inputs](/docs/batches-running-on-multiple-inputs)).
- A CI runner that can write in the results storage, at the same path as the server (like */mnt/qaboard*, an NFS
  share): a self-hosted GitHub Actions runner, a GitLab runner or a Jenkins agent on your network. GitHub-hosted
  runners can't save results yet: see the [roadmap](/docs/roadmap#http-upload-of-outputs).
:::

## Link commits to their results {#commit-statuses}
When `qa` has a token for your git host, `qa batch` sets a **commit status** named `QA` on the commit, with a link
to its results and the number of runs. It's `failed` when runs failed. Batches with another label than `default`
get their own status, like `QA | nightly`, and in a [subproject](/docs/monorepo-subprojects) the name is
`QA <folder>`, with the name of the subproject's folder.

| CI | Token |
|---|---|
| GitHub Actions | `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` in the job's `env`, and `statuses: write` in its `permissions`. GitHub Actions doesn't put its token in the environment by itself. |
| GitLab CI | A `GITLAB_ACCESS_TOKEN` CI/CD variable (masked), a project access token with the `api` scope. |
| Other CIs | The token of the git host in `QABOARD_GIT_HOSTS`, else `GITLAB_ACCESS_TOKEN` or `GITHUB_ACCESS_TOKEN` (see [other CI tools](#other-ci-tools)). |

Without a token, `qa batch` works the same and sets no status.

## Send verified results {#tokens}
Give your CI jobs a token, so that the results they send show who sent them, and so that they keep working once your
server requires tokens to send results, or requires signing in (see
[Results sent by qa](/docs/backend-admin/user-management#results-sent-by-qa)):
1. In the web app, open **Settings → Access tokens** and create a token with the `read` and `ingest` scopes,
   restricted to your project (e.g. `group/repo`). Long-lived tokens are fine for CI, stored as protected secrets.
2. Store it in your CI's secrets as `QABOARD_TOKEN`: `qa` sends it. In GitHub Actions, add
   `QABOARD_TOKEN: ${{ secrets.QABOARD_TOKEN }}` to the job's `env`. In GitLab CI, add a masked, protected CI/CD
   variable named `QABOARD_TOKEN`.

Tokens tied to the CI itself (no stored secret) and tokens owned by an organization rather than a person are coming
next.

## GitHub Actions {#example-with-github-actions}
`qa` reads the commit from `GITHUB_SHA`, and the branch from `GITHUB_HEAD_REF` or `GITHUB_REF_NAME`. For tags, it
records the tag. It calls the API at `GITHUB_API_URL` (else derived from `GITHUB_SERVER_URL`) for the repository
`GITHUB_REPOSITORY`, so it works with GitHub Enterprise too. The token is `GITHUB_TOKEN`, else
`GITHUB_ACCESS_TOKEN`, or the host's token in `QABOARD_GIT_HOSTS`.

**Pull requests.** Results belong to commits, so `on: push` is enough: pull requests from the repository's own
branches get a run for each commit pushed to them. With `on: [push, pull_request]`, those would run twice. If you
add `pull_request` (for forks, for instance), check out the pull request's last commit: GitHub runs on a temporary
merge commit, and `qa` records the pull request's last commit, whose details (message, author, parents) it reads
from git.

**Waiting for the reference.** [`qa check-bit-accuracy`](/docs/bit-accuracy) waits for the end of the reference
commit's CI: give the job `checks: read` too.

## GitLab CI {#example-with-gitlab-ci}
`qa` reads the commit and the branch from `CI_COMMIT_SHA` and `CI_COMMIT_REF_NAME`, and records tags from
`CI_COMMIT_TAG`. For commit statuses, give it a `GITLAB_ACCESS_TOKEN` with the `api` scope (`read_api` is enough to
wait for the CI of reference commits), as a CI/CD variable or in your site's shared secrets. It calls the API of
`GITLAB_HOST` if it's set, else of `CI_SERVER_URL`.

The GitLab runner must mount the results storage: with the docker executor, add it to the runner's `volumes`.

## Jenkins and other CI tools {#other-ci-tools}
`qa` knows that it runs in a CI when the `CI` environment variable is set (GitLab CI, GitHub Actions, CircleCI and
Travis CI set it), or `GIT_COMMIT` (set by Jenkins' git plugin). It reads the commit and the branch from:

| CI | Commit | Branch | Tag |
|---|---|---|---|
| Jenkins | `GIT_COMMIT` | `GIT_BRANCH`, or `gitlabBranch` (GitLab plugin) | `GIT_TAG_NAME` |
| CircleCI | `CIRCLE_SHA1` | `CIRCLE_BRANCH` | `CIRCLE_TAG` |
| Travis CI | `TRAVIS_COMMIT` | `TRAVIS_BRANCH` | `TRAVIS_TAG` |

With another CI, set `CI=true` and `GIT_COMMIT`, `GIT_BRANCH` in the job.

Outside of GitHub Actions and GitLab CI, `qa` finds your git host from `project.url` in *qaboard.yaml* and the hosts
listed in `QABOARD_GIT_HOSTS` (see [Git hosts](/docs/backend-admin/git-hosts#the-cli)), and uses the host's token
there, or `GITLAB_ACCESS_TOKEN`, or `GITHUB_ACCESS_TOKEN`. It only sends `GITHUB_ACCESS_TOKEN` to github.com and the
GitHub hosts listed in `QABOARD_GITHUB_HOSTS` or `QABOARD_GIT_HOSTS`. Projects whose `project.url` is on an unknown
host are assumed to be on `GITLAB_HOST` (if the hostname contains "github", `qa` warns instead and sends no token).

## Fail the CI on regressions {#failing-the-ci-on-regressions}
`qa batch` fails when runs fail. To also fail when results get worse, add a step after it:
- [`qa gate`](/docs/quality-gate) (experimental) fails when metrics regress against the reference, with rules in
  *qaboard.yaml*.
- [`qa check-bit-accuracy`](/docs/bit-accuracy) fails when output files differ from the reference's.

## Save the build for runs started from the web app {#saving-artifacts}
To let people [tune and run more tests from the web app](/docs/tuning-from-the-webapp), the CI saves what runs need,
like your build, with `qa save-artifacts` after it builds (see [Artifacts](/docs/storage/artifacts)):

```bash
make
qa save-artifacts
qa batch ci
```

## Without a CI {#without-a-ci}
Runs started from your computer with `--share` are saved like CI runs, and show in the web app in a batch named
after you, with a warning that they may not match the committed code:

```bash
qa --share batch ci
```

If you don't have a CI yet, see [GitHub Actions](https://docs.github.com/en/actions/quickstart) or
[GitLab CI](https://docs.gitlab.com/ee/ci/quick_start/).

<details>
<summary>Run some tests only on some branches, from a Python script</summary>

This logic is usually better in your CI's configuration (rules, `if:` conditions). If your CI can't express it,
`qaboard.ci_helpers` runs the functions you decorate only on the branches they name:

```python title="ci.py"
import sys
from qaboard.ci_helpers import on_branch, run_tests

@on_branch('develop')
def my_tests():
  return 0 # 0 for success

# Also supported:
# @on_branch(["develop", "master"])
# @on_branch("feature/*")

if __name__ == '__main__':
    # run_tests() returns True if all the tasks succeeded
    sys.exit(0 if run_tests() else 1)
```

```bash
python ci.py
```

</details>
