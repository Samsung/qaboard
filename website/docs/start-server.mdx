Set up a QA-Board server for your team: by the end, your users sign in to the web app, and `qa` saves their results
to it. This page uses Docker Compose on one Linux host. On Kubernetes, follow
[Running QA-Board on Kubernetes](/docs/backend-admin/kubernetes) instead.

:::tip Try it first
The [quickstart](/docs/get-started/quickstart) starts QA-Board on your computer with one Compose file, and demo
projects to look at.
:::

## What you need {#prerequisites}
- **A Linux host** with [Docker Engine](https://docs.docker.com/engine/install/), docker compose 2.24 or newer
  (`docker compose version`), `git` and `python3`. For its size: *deployments/production.env* runs 2 backend
  replicas of up to 8 uwsgi processes each, the [Helm chart](/docs/backend-admin/kubernetes) asks for 1 CPU and 4 GiB
  of memory per replica, and `services/db/qaboard.conf` has PostgreSQL settings for an 8-core, 32 GB host.
- **Disk on the host**, in Docker's volumes and images (`/var/lib/docker` by default): QA-Board's images
  (`deploy.py` keeps those of the last 3 versions), the database, the clones of your git repositories, and caches:
  decoded images, up to 20 GB (`QABOARD_IMAGE_CACHE_GB`), and the image server's tiles, kept 5 days.
- **The results storage**: a folder that the server and every machine that runs `qa` (CI runners, workstations,
  cluster nodes) mount **at the same path**, e.g. an NFS share at `/mnt/qaboard`. `qa` writes the output files there
  itself, and only sends their path to the server, which reads them there.
- **A hostname** that your users, CI runners and git hosts reach, e.g. `qaboard.example.com`, and a TLS certificate
  for HTTPS.
- **One port**: the web app, the API and the webhooks answer on port 5151 (`QABOARD_PORT_HTTP`), or 443 with HTTPS.

:::danger Close the other ports
*docker-compose.yml* also publishes, on all the host's interfaces: pgAdmin on 5050, with a default login that opens
the database; RabbitMQ on 5672 and 15672, with `guest:guest` (anyone who reaches it can run commands on Celery
workers); and Flower on 8888, without a login. Firewall them, or remove them in your overlay ([step 3](#3-describe-your-site)).
See the [known issues](https://github.com/Samsung/qaboard/blob/master/SECURITY.md#known-issues) in *SECURITY.md*.
:::

## 1. Get QA-Board {#1-get-qa-board}
On the host:

```bash
git clone https://github.com/Samsung/qaboard.git
cd qaboard
```

You deploy from this checkout: it has the compose files, nginx's and PostgreSQL's configuration, and
`deployments/deploy.py`. The code comes from the images. To deploy a release, check out its tag
(`git checkout v<version>`), so that both match.

## 2. Create the results storage {#2-create-the-results-storage}
<Anchor id="create-a-directory-to-store-results" />

To start on a single host, a local folder works. Share it later:

```bash
sudo mkdir -p /mnt/qaboard
sudo chmod 777 /mnt/qaboard
```

If your storage is a share, mount it on the host at the path the runners use. To use another path than
`/mnt/qaboard`, use it in the overlay below, list it in `QABOARD_STORAGE_ROOTS`, and set `storage` in your projects'
*qaboard.yaml* (see [where is the data saved](/docs/storage/where-is-the-data)).

:::note Shared storage
Read how to set up [**NFS**](https://www.digitalocean.com/community/tutorials/how-to-set-up-an-nfs-mount-on-ubuntu-18-04)
or [**Samba**](https://www.digitalocean.com/community/tutorials/how-to-set-up-a-samba-share-for-a-small-organization-on-ubuntu-16-04),
and the [options for NFS volumes](https://docs.docker.com/compose/compose-file/#volume-configuration-reference) in
compose files. In the cloud, use a file storage like [AWS EFS](https://aws.amazon.com/en/efs/) or
[GCP Filestore](https://cloud.google.com/filestore). Object storage, like S3, is on the
[roadmap](/docs/roadmap#object-storage-for-results).
:::

## 3. Describe your site {#3-describe-your-site}
A **site overlay** adds your volumes, settings and nginx configuration to *docker-compose.yml*, without changing it.
Create one in a folder for your site, starting from `deployments/example.yml`:

```yaml title="deployments/mysite/mysite.yml"
services:
  backend:
    volumes:
    # The results storage, at the same path as on the runners
    - /mnt/qaboard:/mnt/qaboard
    environment:
    # The address users open: links in emails, single sign-on redirects
    - QABOARD_URL=http://qaboard.example.com:5151
    # Your user name: you're an admin once you sign in (step 6)
    - QABOARD_ADMINS=alice
  proxy:
    volumes:
    # nginx serves /s/<path> from /var/qaboard/<path>
    - /mnt/qaboard:/var/qaboard/mnt/qaboard:ro
  # The ports to close (see above)
  pgadmin:
    profiles: [disabled]
  rabbitmq:
    ports: !reset []  # keep them if Celery workers on other hosts use it
  flower:
    ports: !reset []
```

- **The storage** is mounted at the same path in the backend, and under `/var/qaboard/` in nginx, which serves it at
  `/s/`: browsers that open a folder there get QA-Board's [file browser](/docs/user-guide/files).
- **`QABOARD_URL`**: use `https://` only once HTTPS works ([below](#using-ssl--hosting-behind-a-reverse-proxy)):
  session cookies are then only sent over HTTPS.
- **Other settings** go in `services.backend.environment` too: see [environment variables](#optional-environment-variables).

## 4. Write the env file and the secrets {#4-write-the-env-file-and-the-secrets}
`deploy.py` reads an **env file** per environment: the compose files, the compose project, and the settings docker
compose reads itself. Copy `deployments/production.env` and add your overlay:

```bash title="deployments/mysite/production.env"
COMPOSE_PROJECT_NAME=qaboard
COMPOSE_FILE=docker-compose.yml:production.yml:deployments/mysite/mysite.yml
QABOARD_BACKEND_REPLICAS=2
QABOARD_UWSGI_PROCESSES=8
QABOARD_UWSGI_CHEAPER=4
QABOARD_UWSGI_CHEAPER_INITIAL=8
# QABOARD_PORT_HTTP=5151
```

Put the secrets in `.env`, at the root of the checkout (`chmod 600 .env`). Generate them with
`openssl rand -base64 32`:

```bash title=".env"
# Push webhooks must send it (step 8)
QABOARD_WEBHOOK_SECRET=...
# Signs sessions. Generated and kept in the backend's data volume if unset: set it to move hosts without signing everyone out
# SECRET_KEY=...
```

:::caution Where each setting goes
- **`.env`**: secrets. The backend gets all its variables.
- **The env file**: what docker compose reads itself: `COMPOSE_*`, `QABOARD_PORT_HTTP`, `QABOARD_BACKEND_REPLICAS`,
  `QABOARD_IMAGE`... `deploy.py` gives it to docker compose, which then doesn't read `.env` for those.
- **The overlay's `services.backend.environment`**: the other settings. *docker-compose.yml* sets
  `QABOARD_LOGIN_TYPE`, `QABOARD_LOGIN_REQUIRED`, `QABOARD_LOGIN_RESTRICTED`, `QABOARD_LOGIN_RESTRICTED_YAML`,
  `QABOARD_ADMINS` and `QABOARD_INGEST_AUTH` from the env file, which wins over `.env`: set them in the overlay or in
  the env file, never in `.env`.
:::

## 5. Deploy {#5-deploy}
<Anchor id="starting-the-server" /><Anchor id="deployment" />

```bash
# The first time: --init allows a new compose project, with an empty database
deployments/deploy.py deployments/mysite/production.env up --version <version> --init
```

`<version>` is a [release](https://github.com/Samsung/qaboard/releases), like `1.2.0`. `deploy.py` pulls its images
(`ghcr.io/samsung/qaboard:<service>-<version>`), runs the database migrations, starts the services, and records the
version, so that `rollback` can come back to it. Without `--version`, it deploys the latest images of `master`;
with `--build`, it builds the images from your checkout. Plain
`docker compose --env-file deployments/mysite/production.env up -d` works too, without zero-downtime upgrades.

**Check it worked:**

```bash
deployments/deploy.py deployments/mysite/production.env status
curl -fsS http://localhost:5151/api/v1/health
```

`status` lists the containers: all running, and the backend replicas `healthy`. The health check answers
`"status": "ok"` once the backend reaches its database. Open `http://<your-host>:5151`: the web app opens, with no
projects yet. If something is wrong, see [Troubleshooting](/docs/backend-admin/troubleshooting).

## 6. Make yourself an admin {#6-make-yourself-an-admin}
Admins see **Admin** in the user menu: users, sign-in, settings, and the jobs that clean the storage.

- The user names in `QABOARD_ADMINS` ([step 3](#3-describe-your-site)) are admins as soon as they sign in.
- To sign in before LDAP or single sign-on work, create a local admin account. It asks for the password:

  ```bash
  deployments/deploy.py deployments/mysite/production.env compose exec backend qaboard-admin create-admin admin --password
  ```

**Check it worked:** sign in with **Sign in**, at the top right, and open **Admin**. Its **Overview** has a security
checklist of what to look at next. More in [User management](/docs/backend-admin/user-management).

## 7. Choose how users sign in {#7-choose-how-users-sign-in}
<Anchor id="managing-access-rights-and-users" />

By default, users have local accounts, and anyone can create one from the sign-in page (**Create one**). Instead:
- **Single sign-on** with OpenID Connect (Keycloak, Entra ID, Okta, Google...): see
  [Sign-in and single sign-on](/docs/backend-admin/sign-in).
- **LDAP** or **SAML**: set `QABOARD_LOGIN_TYPE` and their settings in the overlay, see
  [authentication providers](/docs/backend-admin/user-management#authentication-providers).

Then decide [who gets an account](/docs/backend-admin/sign-in#decide-who-gets-an-account), and whether
[anonymous users](/docs/backend-admin/user-management#blocking-anonymous-users) see anything.

To apply changes to `.env` or to the overlay, deploy again: `deploy.py <env file> up` recreates the backend with them,
without downtime. **Check it worked:** `qaboard-admin check-sign-in` in the backend's container, or **Admin → Sign-in
→ Test**, then sign in.

## 8. Connect your git hosts {#8-connect-your-git-hosts}
QA-Board reads your repositories for committers' avatars and each pushed commit's *qaboard.yaml*, and learns about
pushes from webhooks.

1. **Tokens**: add them to `.env`, e.g. `GITHUB_ACCESS_TOKEN`, or `GITLAB_HOST` and `GITLAB_ACCESS_TOKEN`. For other
   hosts, or several, see [Git hosts](/docs/backend-admin/git-hosts).
2. **Webhooks**: in each repository, send push events to `<QABOARD_URL>/webhook/github` (or `gitlab`, `gitea`,
   `bitbucket`), with your `QABOARD_WEBHOOK_SECRET`: see
   [Connect your git host](/docs/project-init#optional-connect-your-git-host).

**Check it worked:** push a commit. The git host shows that the webhook's latest delivery got `200`.

## 9. Save the first results {#9-save-the-first-results}
On a machine that mounts the results storage at the same path as the server, e.g. a CI runner, install `qa` and point
it to the server:

```bash
pip install qaboard
export QABOARD_URL=http://qaboard.example.com:5151
```

In a project wrapped with `qa`, `qa --share batch <batch>` saves the results and prints a link to them:
[Your project on QA-Board](/docs/get-started/tutorial) walks through it. **Check it worked:** the link opens the
commit page with your runs and their output files.

## 10. Secure the server {#10-secure-the-server}
Before you open it to your team:
- **Serve it over HTTPS** ([below](#using-ssl--hosting-behind-a-reverse-proxy)), with `QABOARD_URL=https://...`.
- **Require tokens to send results**: by default, anyone who can reach the server can send results. Move
  `ingest.auth` from `off` to `warn` to `token` once your CI jobs have tokens
  ([results sent by qa](/docs/backend-admin/user-management#results-sent-by-qa)).
- **Set `QABOARD_WEBHOOK_SECRET`** ([step 4](#4-write-the-env-file-and-the-secrets)), and the same secret in your
  webhooks: without it, anyone can send fake push events.
- **Turn off local sign-up** (`auth.local_signup`) if only admins create accounts, and require signing in if
  anonymous users shouldn't see results.
- **Close the other ports** ([above](#prerequisites)), and only expose QA-Board to networks you trust.
- **Show only the storage to the image server**: *docker-compose.yml* mounts the whole host in Cantaloupe, which
  doesn't check who can read images. In your overlay:

  ```yaml title="deployments/mysite/mysite.yml"
  services:
    cantaloupe:
      volumes: !override
      - cache_cantaloupe:/var/cache/cantaloupe
      - /srv/cantaloupe
      # Each storage root, read-only: Cantaloupe reads /iiif/2/<path> from /repository/<path>
      - /mnt/qaboard:/repository/mnt/qaboard:ro
  ```

The security checklist in **Admin → Overview** checks the sign-in, token and HTTPS settings. *SECURITY.md* lists the
[known issues](https://github.com/Samsung/qaboard/blob/master/SECURITY.md#known-issues) and their mitigations.

## HTTPS and reverse proxies {#using-ssl--hosting-behind-a-reverse-proxy}
Use your own copy of *services/nginx/conf.d/qaboard.conf* in the site overlay (keep its `include snippets/...` lines:
they serve the files and the file browser). Files mounted under `/tmp/deployment/nginx/conf.d/` in the `proxy`
container are added to (or replace) *services/nginx/conf.d/*:

```nginx title="deployments/mysite/nginx/qaboard.conf (copied from services/nginx/conf.d/qaboard.conf)"
server {
  # ...
  listen 443 ssl;
  ssl_certificate_key /ssl/cert.key;
  ssl_certificate /ssl/cert.pem;
  # ...
}
```

Mount it, and the key and certificate:

```yaml title="deployments/mysite/mysite.yml"
services:
  proxy:
    ports:
    - "443:443"
    volumes:
    - "./deployments/mysite/nginx/qaboard.conf:/tmp/deployment/nginx/conf.d/qaboard.conf:ro"
    - "somewhere/cert.key:/ssl/cert.key"
    - "somewhere/cert.pem:/ssl/cert.pem"
```

Then set `QABOARD_URL=https://...`, and deploy again.

:::tip Getting a certificate from your IT
Generate a key and a certificate signing request (CSR), and send the CSR to your IT:
```bash
openssl genrsa -out cert.key 2048
openssl req -new -sha256 -key cert.key -out cert.csr
```
If they send back a `.cer` certificate in the DER format, convert it to PEM: `openssl x509 -in cert.cer -inform der -outform pem -out cert.pem`.
:::

To use your own reverse proxy instead, e.g. nginx, set `QABOARD_PORT_HTTP=8080` in the env file and:

```nginx
server {
  listen 80;
  server_name default_server;
  location / {
    proxy_pass http://localhost:8080/;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
}
```

Behind your proxy, a load balancer or an ingress, set `QABOARD_TRUSTED_PROXY_HOPS=1`, so that the audit log records
users' IPs (see [rate limits and proxies](/docs/backend-admin/sign-in#rate-limits-and-proxies)).

## Run it day to day
<Anchor id="optional-for-production" />

- **Upgrade**: read the [release notes](/release-notes) ("Before you upgrade"), check out the new release, then
  `deploy.py <env file> up --version <version>`. If it goes wrong, `rollback`: see
  [Upgrades and rollbacks](/docs/backend-admin/deployment).
- **Back up the database**, and test a restore: see [Backups](#backups).
- **Free disk space** in the results storage: see [Cleanup](#optional-cleanup).
- **Follow errors** in Sentry ([monitoring](/docs/backend-admin/monitoring)), and the runs stuck as running in
  [Runs activity](/docs/user-guide/runs-activity).

### Backups
The `cron-backup-db` service in *production.yml* makes daily backups of the database to `/backups`, and keeps those of
the last 14 days (`QABOARD_BACKUP_RETENTION_DAYS`). Mount a host directory there, in the `db` service too
(`restore-db` reads the backups from it), and copy the backups off the host. Without it, the backups fail.

```yaml title="deployments/mysite/mysite.yml"
services:
  cron-backup-db:
    volumes:
    - /srv/qaboard/backups:/backups
  db:
    volumes:
    - /srv/qaboard/backups:/backups
```

To restore one: `deployments/deploy.py <env file> restore-db <file>.dump`. See [Backups](/docs/backend-admin/deployment#backups).

### Cleanup {#optional-cleanup}
Schedule the cleanup in **Admin → Storage**: delete old results as each project's *qaboard.yaml* says, delete for good
the runs users deleted, delete old artifacts, with each run's log and errors. See
[cleaning the storage](/docs/backend-admin/storage).

Or use cron jobs on the host:

```cron
# Weekly cleanup of old results, on Saturdays
# https://samsung.github.io/qaboard/docs/storage/deleting-old-data
59 1 * * 6 cd qaboard && docker compose --env-file deployments/mysite/production.env exec -T backend qaboard_clean

# Weekly removal of unused docker images, on Sundays, so that they don't fill the disk
59 1 * * 0 docker image prune --force
```

`qaboard_clean --help` lists the command's options.

## Environment variables {#optional-environment-variables}
Set them in `services.backend.environment` in your site overlay, and the secrets in `.env`: see
[where each setting goes](#4-write-the-env-file-and-the-secrets). With the Helm chart, in `config` and the secret
([Kubernetes](/docs/backend-admin/kubernetes#on-a-real-cluster)). Many settings can also be changed in
**Admin → Settings**, without a deploy: see [settings](/docs/backend-admin/user-management#settings).


| ENV Variable           | Default | Usage                                                |
-------------------------|-------- |------------------------------------------------------|
| `QABOARD_URL` | `http://qaboard` | The address users open, e.g. `https://qaboard.example.com`: links in emails, single sign-on redirects. With `https://`, session cookies are only sent over HTTPS |
| `SECRET_KEY`           | _generated_ | Signs the sessions. If unset, a key is generated once and saved in the backend's data volume. With several hosts/kubernetes, set the same value everywhere. |
| `QABOARD_ADMINS` | _none_ | User names of admins, or emails of directory and single sign-on accounts, comma-separated. See [user management](/docs/backend-admin/user-management) |
| `QABOARD_GIT_HOSTS`    | _none_  | Your git hosts (GitHub, GitLab, Gitea/Forgejo, Bitbucket...) with their tokens and webhook secrets: a JSON list, or the path to a JSON/YAML file. See [Git hosts](/docs/backend-admin/git-hosts) |
| `GITLAB_HOST`          | *https://gitlab.com*, if `QABOARD_GIT_HOSTS` isn't set either | Your GitLab, e.g. *https://gitlab.example.com*. It's the default git host: for projects that don't say where they are hosted, and for pushes to `/webhook/gitlab` from hostnames the server doesn't know. **Keep it set when you upgrade**, see [Git hosts](/docs/backend-admin/git-hosts#upgrading-from-older-versions) |
| `GITLAB_ACCESS_TOKEN`  | _none_  | Token for `GITLAB_HOST`: `read_repository` scope to clone private repositories, `read_api` to show GitLab CI job statuses and committers' avatars, `api` to play manual jobs, and to retry the jobs that [recreate deleted artifacts](/docs/storage/deleting-old-data#recreating-artifacts) |
| `GITHUB_ACCESS_TOKEN`  | _none_  | Token for github.com (always known, even without a token) and the hosts of `QABOARD_GITHUB_HOSTS`: to clone private repositories, look up committers' avatars and use GitHub Actions (see [GitHub integration](/docs/project-init#github)) |
| `QABOARD_GITLAB_HOSTS` | _none_  | Comma-separated. Hostnames (e.g. `gitlab-alias`) are other names of `GITLAB_HOST`. URLs (e.g. `https://gitlab2.example.com`) are other GitLab servers, that get `GITLAB_ACCESS_TOKEN`. `QABOARD_GIT_HOSTS` lets you give each its own token |
| `QABOARD_GITHUB_HOSTS` | _none_  | Comma-separated hostnames of GitHub Enterprise servers, that get `GITHUB_ACCESS_TOKEN`. `QABOARD_GIT_HOSTS` lets you give each its own token |
| `QABOARD_PROXY_HOSTS` | _none_  | Comma-separated hostnames the web app may load avatars and badges from through the backend, besides your git hosts (`QABOARD_GIT_HOSTS`, `GITLAB_HOST`...), the host of `QABOARD_AVATAR_URL`, and gravatar. Add the hosts of your projects' `project.avatar_url` and `integrations[].src` images |
| `QABOARD_STORAGE_ROOTS` | */mnt/qaboard* | Folders where your projects store outputs and artifacts, separated by `:` (e.g. `/mnt/qaboard:/mnt/datasets`). The backend refuses results stored elsewhere, and never writes, deletes or runs code outside these folders |
| `QABOARD_FILES_UNIX_PERMISSIONS` | _none_ | Folders, separated by `:` (e.g. `/home`), where users only read the files under `/s/` that their Unix account can read. See [user management](/docs/backend-admin/user-management#unix-permissions) |
| `QABOARD_ACCOUNTS_COMMAND` | _none_ | Command printing the users' accounts like `/etc/passwd` (e.g. `ssh host getent passwd`), for file owners and Unix permissions, when you can't mount a complete `/etc/passwd`. See [users' accounts](/docs/backend-admin/user-management#users-accounts) |
| `QABOARD_GROUPS_COMMAND` | _none_ | Same for the groups, like `/etc/group` |
| `QABOARD_ACCOUNTS_REFRESH` | 86400 | How often (seconds) the backend runs these commands |
| `QABOARD_WEBHOOK_SECRET` | _none_ | Secret that push webhooks must send (GitLab's *Secret token*, GitHub's *Secret*...), unless their host has its own `webhook_secret` in `QABOARD_GIT_HOSTS`. Recommended: without it anyone who can reach the server can send fake push events |
| `QABOARD_PORT_HTTP`    | 5151    | Port mapped to the app on the host. Read by docker compose: set it in the env file |
| `QABOARD_DB_HOST`      | db      | Connect the backend to another database host, e.g. a database managed by your IT. Read by docker compose: set it in the env file |
| `QABOARD_DB_PORT`      | 5432    | Connect to a non-default database port. Read by docker compose: set it in the env file |
| `QABOARD_DB_USER` / `QABOARD_DB_PASSWORD` / `QABOARD_DB_NAME` | qaboard / password / qaboard | The database's credentials and name. Keep the password in `.env` |
| `QABOARD_DB_POOL_SIZE` / `QABOARD_DB_MAX_OVERFLOW` | 4 / 2 | Database connections kept open by each uwsgi process (it runs 4 threads), and extra ones it may open. PostgreSQL's `max_connections` must cover them, see [Database settings](/docs/backend-admin/deployment#database-settings) |
| `JENKINS_AUTH`         | _none_  | Credentials used to [trigger jenkins jobs](/docs/triggering-third-party-tools) on 1 or many jenkins servers. The format is a JSON string looking like `{"hostname_1": {"user": "jenkinsuser", "token": "xxxxx", "crumb": "yyy"}}` (see [Jenkins builds](/docs/triggering-third-party-tools#trigger-jenkins-builds) for the token and crumb)               |
| `JENKINS_BUILD_TOKEN`  | _none_  | The authentication token of **Trigger builds remotely** sent to the Jenkins jobs whose integration has no `token`. Without it, they get none. Older versions sent `qaboard`: if your jobs expect it, set `JENKINS_BUILD_TOKEN=qaboard` |
| `QABOARD_LOGIN_TYPE`   | _LOCAL_  | `LOCAL`, `LDAP` or `SAML`. Single sign-on (`QABOARD_OIDC_*`) comes on top of any of them. See [user management](/docs/backend-admin/user-management#authentication-providers) |

### Emails
QA-Board can email users when the batches they start end, from the web app or with `qa --share batch` ([what users get](/docs/user-guide/running-from-the-webapp#emails-when-batches-end)). Once the backend has an SMTP server, everyone gets them, except in CI. Users turn them off in the terminal with `QA_NOTIFY=none`. Configure it in your overlay, and the SMTP password, if any, in `.env`:

```yaml title="deployments/mysite/mysite.yml"
services:
  backend:
    environment:
    - QABOARD_SMTP_HOST=smtp.example.com
    - QABOARD_EMAIL_FROM=QA-Board <qaboard-noreply@example.com>
    - QABOARD_EMAIL_REPLY_TO=qaboard-support@example.com
    # Users without an email address in their account get emails at <username>@example.com
    - QABOARD_EMAIL_DOMAIN=example.com
    - QABOARD_URL=https://qaboard.example.com
```

- The emails are designed for Outlook 2016/2019 as well as recent clients, in HTML with a plain text version. They are marked as automated (`Auto-Submitted`), so out-of-office replies aren't sent back, and have `X-QABoard-Project`, `X-QABoard-Batch` and `X-QABoard-Status` headers for mail rules.
- They're sent by the backend when it saves the last run of a batch. If the SMTP server fails, the error is in the backend's logs and in the `batch_notifications` table, and the run is saved anyway.
- To check how they look, or test your SMTP settings, run `uv run backend/backend/notifications/preview.py`: it renders examples, and `--send you@example.com` emails them to you.
- Like results, the requests to email users when their `qa batch` ends come from the CLI without a login: anyone who can reach the server could have QA-Board email a user about a batch. QA-Board only emails the address of the user's account (or `<username>@$QABOARD_EMAIL_DOMAIN`), and at most once per `qa batch`.
