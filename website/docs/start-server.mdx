## Create a directory to store results
QA-Board expects that all clients can access a shared storage to save and read results.

To get started quickly on a single server, create a *local* folder. Worry about sharing it later:

```bash
mkdir -p /mnt/qaboard
chmod -R 777 /mnt/qaboard
```

The base `docker-compose.yml` doesn't mount any results storage. Mount it in your site overlay (start from `deployments/example.yml`): the backend needs it at the same path as the clients, nginx serves files under `/s/` from `/var/qaboard/` (`/s/mnt/qaboard/...` is read from `/var/qaboard/mnt/qaboard/...`), and the image server reads images from `/repository/` (`/iiif/2/mnt%2Fqaboard%2F...` from `/repository/mnt/qaboard/...`):

```yaml title="deployments/mysite.yml"
services:
  backend:
    volumes:
    - /mnt/qaboard:/mnt/qaboard
  proxy:
    volumes:
    - /mnt/qaboard:/var/qaboard/mnt/qaboard:ro
  cantaloupe:
    volumes:
    - /mnt/qaboard:/repository/mnt/qaboard:ro
```

:::note Upgrading from older versions
`docker-compose.yml` used to mount the host's whole filesystem in the image server. If the image viewers show no images after you upgrade, mount your storage in `cantaloupe` like above, at the same paths as in `proxy`.
:::

:::tip
If you want to use a different folder, use your path in the overlay, and set `storage` in your projects' *qaboard.yaml* (see [where is the data saved](storage/where-is-the-data)).
:::

When users open a folder under `/s/` in their browser, they get QA-Board's [file browser](user-guide/files). nginx still sends the files, but the backend lists the folders: it lists those inside `QABOARD_STORAGE_ROOTS`, at the same paths as in the URLs. Other clients (`curl`, `wget`...) still get nginx's index. To restrict who can read the files of some projects, see [user management](backend-admin/user-management#restricting-who-can-read-files).

:::note Shared Storage?
Later, read how to setup [**NFS**](https://www.digitalocean.com/community/tutorials/how-to-set-up-an-nfs-mount-on-ubuntu-18-04) or [**Samba**](https://www.digitalocean.com/community/tutorials/how-to-set-up-a-samba-share-for-a-small-organization-on-ubuntu-16-04). If you need fine-tuning read about [options for NFS volumes](https://docs.docker.com/compose/compose-file/#volume-configuration-reference) in *docker-compose.yml*.
:::

:::note Working in the cloud?
Use file-base storage like [AWS EFS](https://aws.amazon.com/en/efs/) or [GCP Filestore](https://cloud.google.com/filestore).

We plan on supporting blob-stores like AWS **S3**. <a href="mailto:arthur.flam@gmail.com">Contact us</a> or [create an issue](https://github.com/samsung/qaboard/issues) if it would help.
:::

## Starting the server

### Prerequisites
You need Linux, [`docker`](https://docs.docker.com/engine/install/), [`docker compose`](https://docs.docker.com/compose/install/) and `git`.

### Deployment
QA-Board uses **compose overlays** in the `deployments/` directory to adapt the stack to different environments, and an **env file** per environment that lists them:

```bash
git clone https://github.com/Samsung/qaboard.git
cd qaboard
```

Add your overlay to `COMPOSE_FILE` in a copy of `deployments/production.env` (the examples use the file as it is), then:
```bash
# first time
deployments/deploy.py deployments/production.env up --build --init
# upgrades (git pull first), with zero downtime
deployments/deploy.py deployments/production.env up --build
```

If you prefer plain docker compose, `docker compose -f docker-compose.yml -f production.yml up -d` still works, without zero-downtime upgrades.

A site overlay adds your site's services, volumes, environment variables and nginx configuration without modifying the base `docker-compose.yml`. Start from `deployments/example.yml` for the overlay, and from `deployments/production.env` for the env file.

`deployments/deploy.py` runs several backend replicas and replaces them one version at a time, runs database migrations once, and keeps the previous images for rollbacks. Read [Deployments, rollbacks and high availability](backend-admin/deployment) for the details.

:::tip
The application is live at `localhost:5151` by default (set `QABOARD_PORT_HTTP` to change it).
:::

:::note Kubernetes
A helm chart is available in `charts/qaboard`, see [Kubernetes](backend-admin/kubernetes).
:::

## Managing access rights and users
QA-Board can connect to external authentication systems (LDAP, SAML). If needed, access can be restricted to logged-in users. To know more about this, or create a test user, refer to the docs on [user management](backend-admin/user-management).

### Emails
QA-Board can email users when the batches they start end, from the web app or with `qa --share batch` ([what users get](user-guide/running-from-the-webapp#emails-when-batches-end)). Once the backend has an SMTP server, everyone gets them, except in CI. Users turn them off in the terminal with `QA_NOTIFY=none`. Configure it e.g. in your env file:

```bash title=".env"
QABOARD_SMTP_HOST=smtp.example.com
QABOARD_EMAIL_FROM=QA-Board <qaboard-noreply@example.com>
QABOARD_EMAIL_REPLY_TO=qaboard-support@example.com
# users without an email address in their account get emails at <username>@example.com
QABOARD_EMAIL_DOMAIN=example.com
QABOARD_URL=https://qaboard.example.com
```

- The emails are designed for Outlook 2016/2019 as well as recent clients, in HTML with a plain text version. They are marked as automated (`Auto-Submitted`), so out-of-office replies aren't sent back, and have `X-QABoard-Project`, `X-QABoard-Batch` and `X-QABoard-Status` headers for mail rules.
- They're sent by the backend when it saves the last run of a batch. If the SMTP server fails, the error is in the backend's logs and in the `batch_notifications` table, and the run is saved anyway.
- To check how they look, or test your SMTP settings, run `uv run backend/backend/notifications/preview.py`: it renders examples, and `--send you@example.com` emails them to you.
- Like results, the requests to email users when their `qa batch` ends come from the CLI without a login: anyone who can reach the server could have QA-Board email a user about a batch. QA-Board only emails the address of the user's account (or `<username>@$QABOARD_EMAIL_DOMAIN`), and at most once per `qa batch`.

> Consult the [Troubleshooting](backend-admin/troubleshooting) page for examples that show how to get logs from the various services composing QA-Board.
>
> For development, consult the READMEs for the [backend](https://github.com/Samsung/qaboard/tree/master/backend) and the [frontend](https://github.com/Samsung/qaboard/tree/master/webapp).


## (Optional) For "production"
### Backups
The `cron-backup-db` service in *production.yml* makes daily backups of the database, and keeps those of the last 14 days (`QABOARD_BACKUP_RETENTION_DAYS`). Mount a host directory at `/backups` in your site overlay, and copy the backups off the host. To restore one: `deployments/deploy.py <env file> restore-db <file>.dump`. See [Backups](backend-admin/deployment#backups).

### Passwords and admin services
Put the passwords in `.env`, at the root of the checkout, before the first start. The backend reads `.env`, and so does `docker compose` for the `${...}` of the compose files. `deployments/deploy.py` runs compose with your environment's env file instead, so it passes it the ones it needs from `.env`: those below.

```bash title=".env"
QABOARD_DB_PASSWORD=...
# Only if Celery workers connect to RabbitMQ (QABOARD_TUNING_RUNNER=celery). URL-safe characters
QABOARD_RABBITMQ_USER=qaboard
QABOARD_RABBITMQ_PASSWORD=...
# Optional: Flower (the task queue's UI) also asks for this login. At /flower/, only QA-Board's admins get it
FLOWER_BASIC_AUTH=admin:...
PGADMIN_DEFAULT_EMAIL=admin@example.com
PGADMIN_DEFAULT_PASSWORD=...
```

- **The database** is created with `QABOARD_DB_PASSWORD` (default: `password`), and the backend and the backups use it. To change the password of an existing database, see [Database password](backend-admin/deployment#database-password).
- **RabbitMQ** is created with `QABOARD_RABBITMQ_USER` and `QABOARD_RABBITMQ_PASSWORD` (default: `guest:guest`). Celery workers run the commands of the tasks they get: anyone who can connect to RabbitMQ can run commands on them. For an existing RabbitMQ, add the user with `docker compose exec rabbitmq rabbitmqctl add_user` and `set_permissions`, or change the password with `rabbitmqctl change_password`. Workers then use `pyamqp://<user>:<password>@<qaboard-host>:5672//` (see [Celery](/docs/celery-integration)).
- **The admin services are only published on the host itself** (`127.0.0.1`): RabbitMQ (`QABOARD_PORT_RABBITMQ`, 5672, and its management UI on `QABOARD_PORT_RABBITMQ_MNGT`, 15672), Flower (`QABOARD_PORT_FLOWER`, 8888, also at `/flower/`) and pgAdmin (`PGADMIN_PORT`, 5050). From another computer, use an ssh tunnel, e.g. `ssh -L 5050:localhost:5050 <qaboard-host>`. When Celery workers run on other hosts, publish RabbitMQ on the network with `QABOARD_RABBITMQ_HOST_IP=0.0.0.0` (or one of the host's addresses) in your env file, with a password. To publish another port, replace its `ports` in your site overlay: `ports: !override`.

### Using SSL / hosting behind a reverse proxy
What we do is use our own copy of *services/nginx/conf.d/qaboard.conf* in the site overlay (keep its `include snippets/...` lines: they serve the files and the file browser). Files mounted under `/tmp/deployment/nginx/conf.d/` in the `proxy` container are added to (or replace) *services/nginx/conf.d/*:

```nginx title="deployments/nginx/qaboard.conf (copied from services/nginx/conf.d/qaboard.conf)"
server {
  # ...
  listen 443 ssl;
  ssl_certificate_key /ssl/cert.key;
  ssl_certificate /ssl/cert.pem;
  # ...
}
```

And mount keys with:

```yaml title="deployments/mysite.yml"
services:
  proxy:
    ports:
    - "443:443"
    volumes:
    - "./deployments/nginx/qaboard.conf:/tmp/deployment/nginx/conf.d/qaboard.conf:ro"
    - "somewhere/cert.key:/ssl/cert.key"
    - "somewhere/cert.pem:/ssl/cert.pem"
```

:::tip Getting a certificate from your IT
Generate a key and a certificate signing request (CSR), and send the CSR to your IT:
```bash
openssl genrsa -out cert.key 2048
openssl req -new -sha256 -key cert.key -out cert.csr
```
If they send back a `.cer` certificate in the DER format, convert it to PEM: `openssl x509 -in cert.cer -inform der -outform pem -out cert.pem`.
:::

If you want to use your own reverse proxy, with `nginx` for instance you can set `QABOARD_PORT_HTTP=8080` and the config below. QA-Board's nginx passes the `X-Forwarded-Proto` and `X-Forwarded-Host` headers your proxy sets to the backend (the SAML login builds its URLs from them), else the scheme and host of the request it got:

```nginx
server {
  listen 80;
  server_name default_server;
  location / {
    proxy_pass http://localhost:8080/;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Host $http_host;
  }
}
```

## (Optional) Cleanup
We run those cron jobs:
```cron
# Weekly cleanup of old results
# https://samsung.github.io/qaboard/docs/storage/deleting-old-data
59 1 1 * * cd qaboard && docker compose --env-file deployments/production.env exec -T backend qaboard_clean

# Weekly removal of old docker images, helps to avoid filling the disk on the host
59 1 2 * * docker image prune --force
```

:::tip
Instead of cron jobs, admins can schedule the cleanup in **Admin → Storage**, with each run's log and errors, and also delete for good the runs users deleted: see [cleaning the storage](/docs/backend-admin/storage). Check `qaboard_clean --help` for the command's options.
:::
