QA-Board's run-wrapper, `qa`, will sync with a central server that tracks and displays results.

:::note Need a hosted version?
We're considering offering a hosted solution to help you get started. If you are interested, contact the <a href="mailto:arthur.flam@gmail.com">maintainers</a>.

Until then, please [fill issues](https://github.com/Samsung/qaboard/issues) or <a href="mailto:arthur.flam@samsung.com">send an email</a> to maintainers if you run into issues starting a server. We're responsive.

:::

## Create a directory to store results
QA-Board expects that all clients can access a shared storage to save and read results.

To get started quickly on a single server, create a *local* folder. Worry about sharing it later:

```bash
mkdir -p /mnt/qaboard
chmod -R 777 /mnt/qaboard
```

The base `docker-compose.yml` doesn't mount any results storage. Mount it in your site overlay (start from `deployments/example.yml`): the backend needs it at the same path as the clients, and nginx serves files under `/s/` from `/var/qaboard/` (`/s/mnt/qaboard/...` is read from `/var/qaboard/mnt/qaboard/...`):

```yaml title="deployments/mysite.yml"
services:
  backend:
    volumes:
    - /mnt/qaboard:/mnt/qaboard
  proxy:
    volumes:
    - /mnt/qaboard:/var/qaboard/mnt/qaboard:ro
```

:::tip
If you want to use a different folder, use your path in the overlay, and set `storage` in your projects' *qaboard.yaml* (see [where is the data saved](storage/where-is-the-data)).
:::

When users open a folder under `/s/` in their browser, they get QA-Board's [file browser](user-guide/files). nginx still sends the files, but the backend lists the folders: it lists those inside `QABOARD_STORAGE_ROOTS`, at the same paths as in the URLs. Other clients (`curl`, `wget`...) still get nginx's index. To restrict who can read the files of some projects, see [user management](backend-admin/user-management#restricting-who-can-read-files).

:::note Shared Storage?
Later, read how to setup [**NFS**](https://www.digitalocean.com/community/tutorials/how-to-set-up-an-nfs-mount-on-ubuntu-18-04) or [**Samba**](https://www.digitalocean.com/community/tutorials/how-to-set-up-a-samba-share-for-a-small-organization-on-ubuntu-16-04). If you need fine-tuning read about [options for NFS volumes](https://docs.docker.com/compose/compose-file/#volume-configuration-reference) in *docker-compose.yml*.
:::

:::note Working in the cloud?
Use file-base storage like [AWS EFS](https://aws.amazon.com/en/efs/) or [GCP Filestore](https://cloud.google.com/filestore).

We plan on supporting blob-stores like AWS **S3**. <a href="mailto:arthur.flam@gmail.com">Contact us</a> or [create an issue](https://github.com/samsung/qaboard/issues) if it would help.
:::

## Starting the server

### Prerequisites
You need Linux, [`docker`](https://docs.docker.com/engine/install/), [`docker compose`](https://docs.docker.com/compose/install/) and `git`.

### Deployment
QA-Board uses **compose overlays** in the `deployments/` directory to adapt the stack to different environments, and an **env file** per environment that lists them:

```bash
git clone https://github.com/Samsung/qaboard.git
cd qaboard
```

**Open-source (default):** add your overlay to `COMPOSE_FILE` in a copy of `deployments/production.env`, then:
```bash
# first time
deployments/deploy.py deployments/production.env up --build --init
# upgrades (git pull first), with zero downtime
deployments/deploy.py deployments/production.env up --build
```

If you prefer plain docker compose, `docker compose -f docker-compose.yml -f production.yml up -d` still works, without zero-downtime upgrades.

**SIRC:** deployed by GitLab CI, see [Deployments](backend-admin/deployment). By hand: `deployments/deploy.py deployments/sirc/production.env up`.

**DSK:**
```bash
docker compose -f docker-compose.yml -f production.yml -f deployments/dsk/dsk.yml up -d
```

The overlay files in `deployments/` add site-specific services, volumes, environment variables, and nginx configuration without modifying the base `docker-compose.yml`. See `deployments/example.yml` as a template for creating your own overlay, and `deployments/production.env` or `deployments/sirc/production.env` for the env file.

`deployments/deploy.py` runs several backend replicas and replaces them one version at a time, runs database migrations once, and keeps the previous images for rollbacks. Read [Deployments, rollbacks and high availability](backend-admin/deployment) for the details.

:::tip
The application is live at `localhost:5151` by default (set `QABOARD_PORT_HTTP` to change it).
:::

:::note Kubernetes
A helm chart is available in `charts/qaboard`, see [Kubernetes](backend-admin/kubernetes).
:::

## Managing access rights and users
QA-Board can connect to external authentifications systems (LDAP, SAML). If needed, access can be restricted to logged-in users. To know more about this, or create a test user, refer to the docs on [user management](backend-admin/user-management).

## (Optional) Environment variables
> To configure your installation, set `services.backend.environment` in your site overlay (see `deployments/example.yml`).
> An [`.env` file](https://docs.docker.com/compose/environment-variables/#the-env-file) only sets the variables used by the compose files: the ports (`QABOARD_PORT_*`), and those that *docker-compose.yml* or your overlay forward to the backend (e.g. `SECRET_KEY`, `GITLAB_ACCESS_TOKEN`, `QABOARD_DB_HOST`, `QABOARD_LOGIN_*`). Others, like the LDAP settings, must be listed in the overlay.


| ENV Variable           | Default | Usage                                                |
-------------------------|-------- |------------------------------------------------------|
| `GITLAB_ACCESS_TOKEN`  | _none_  | Optional for some extra features. Get it with a `read_repository` scope at https://$gitlab-server/profile/personal_access_tokens |
| `SECRET_KEY`           | _generated_ | Signs the sessions. If unset, a key is generated once and saved in the backend's data volume. With several hosts/kubernetes, set the same value everywhere. |
| `GITLAB_HOST`          | *https://gitlab.com* | e.g. *https://gitlab.com* or *http://my-gitlab-srv/*. Also used for git links in the UI |
| `QABOARD_GITLAB_HOSTS` | _none_  | Comma-separated extra gitlab hostnames the backend may send `GITLAB_ACCESS_TOKEN` to |
| `GITHUB_ACCESS_TOKEN`  | _none_  | Token used to clone private GitHub repositories and look up committers' avatars (see [GitHub integration](project-init#optional-integration-with-github)) |
| `QABOARD_GITHUB_HOSTS` | _none_  | Comma-separated GitHub Enterprise hostnames the backend may clone from and send `GITHUB_ACCESS_TOKEN` to, besides github.com |
| `QABOARD_STORAGE_ROOTS` | */mnt/qaboard* | Folders where your projects store outputs and artifacts, separated by `:` (e.g. `/mnt/qaboard:/mnt/datasets`). The backend refuses results stored elsewhere, and never writes, deletes or runs code outside these folders |
| `QABOARD_FILES_UNIX_PERMISSIONS` | _none_ | Folders, separated by `:` (e.g. `/home`), where users only read the files under `/s/` that their Unix account can read. See [user management](backend-admin/user-management#unix-permissions) |
| `QABOARD_ACCOUNTS_COMMAND` | _none_ | Command printing the users' accounts like `/etc/passwd` (e.g. `ssh host getent passwd`), for file owners and Unix permissions, when you can't mount a complete `/etc/passwd`. See [users' accounts](backend-admin/user-management#users-accounts) |
| `QABOARD_GROUPS_COMMAND` | _none_ | Same for the groups, like `/etc/group` |
| `QABOARD_ACCOUNTS_REFRESH` | 86400 | How often (seconds) the backend runs these commands |
| `QABOARD_WEBHOOK_SECRET` | _none_ | Secret that the GitLab and GitHub webhooks must send (GitLab's *Secret token*, GitHub's *Secret*). Recommended: without it anyone who can reach the server can send fake push events |

| `QABOARD_LDAP_HOST`   | _none_  | Server hostname (including port)                   |

## (Optional) For "production"
### Backups
The `cron-backup-db` service in *production.yml* makes daily backups of the database. Mount a host directory at `/backups` in your site overlay (see `deployments/sirc/prod.yml`), and copy the backups off the host. To restore one: `deployments/deploy.py <env file> restore-db <file>.dump`.

### Using SSL / hosting behind a reverse proxy
What we do is use our own copy of *services/nginx/conf.d/qaboard.conf* in the site overlay (keep its `include snippets/...` lines: they serve the files and the file browser). Files mounted under `/tmp/deployment/nginx/conf.d/` in the `proxy` container are added to (or replace) *services/nginx/conf.d/*:

```nginx title="deployments/nginx/qaboard.conf (copied from services/nginx/conf.d/qaboard.conf)"
server {
  # ...
  listen 443 ssl;
  ssl_certificate_key /ssl/cert.key;
  ssl_certificate /ssl/cert.pem;
  # ...
}
```

And mount keys with:

```yaml title="deployments/mysite.yml"
services:
  proxy:
    ports:
    - "443:443"
    volumes:
    - "./deployments/nginx/qaboard.conf:/tmp/deployment/nginx/conf.d/qaboard.conf:ro"
    - "somewhere/cert.key:/ssl/cert.key"
    - "somewhere/cert.pem:/ssl/cert.pem"
```

If you want to use your own reverse proxy, with `nginx` for instance you can set `QABOARD_PORT_HTTP=8080` and:

```nginx
server {
  listen 80;
  server_name default_server;
  location / {
    proxy_pass http://localhost:8080/;
  }
}
```

## (Optional) Cleanup
We run those cron jobs:
```cron
# Weekly cleanup of old results
# https://samsung.github.io/qaboard/docs/storage/deleting-old-data
59 1 1 * * cd qaboard && docker compose --env-file deployments/production.env exec -T backend qaboard_clean

# Weekly removal of old docker images, helps to avoid filling the disk on the host
59 1 2 * * docker image prune --force
```

:::tip
Check `qaboard_clean --help` to implement complex cleanup strategies.
:::
