By default, if you don't configure an async task queue, QA-Board will use [`joblib`](https://joblib.readthedocs.io/en/latest/) and **local** multiprocessing to run your batches.

## Running batches locally
If you configured an another runner, you can always:

```bash
qa batch --runner=local my-batch
```

## Configuration
The main option is `concurrency` (joblib's `n_jobs`): how many runs run at the same time. If it is not set, runs are
done one at a time; `-1` runs one per CPU, as in the sample *qaboard.yaml* created by `qa init`. You can set it:

- In *qaboard.yaml*, for all batches:

```yaml title="qaboard.yaml"
runners:
  default: local  # default
  local:
    concurrency: 1 # serially
```

- Per batch, in a batches file:

```yaml title="qa/batches.yaml"
large-images:
  inputs:
  - charts/test-wall-113mp.tiff
  local:
    concurrency: 1 # needs all the memory
```

- On the CLI, for all batches:

```bash
qa batch --local-concurrency 1
```

The command line wins, then the batch's setting, then *qaboard.yaml*. The `QA_BATCH_CONCURRENCY` environment variable
replaces the value from *qaboard.yaml*.

You can also set a `timeout`, in seconds, for each run (0 means no timeout): `runners.local.timeout`, `timeout` under
a batch's `local:`, `qa batch --local-timeout` or `QA_BATCH_TIMEOUT`. When a run takes longer, `qa batch` kills it
(and what it started), marks it as failed, and goes on with the other runs.

When batches have their own concurrency or timeout, `qa batch` runs them one after the other, each with its own.

:::tip
Read [joblib's docs](https://joblib.readthedocs.io/en/latest/generated/joblib.Parallel.html)
:::
