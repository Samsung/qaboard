Scripts, notebooks and agents can use QA-Board's results: `qaboard.runs(url)` gives the runs a web app page shows,
the `qa` CLI says where a batch's runs save their files, and the HTTP API gives everything else.

## Work on the runs you see in the web app {#runs-in-scripts}
To post-process runs, e.g. to compute a metric on their images that the CI didn't, start from the web app: find the
commit, pick the batch, filter the runs you want, and copy the page's address. `qaboard.runs()` reads the project,
commit, batch and filter from it, and asks the server for those runs:

```python
# /// script
# dependencies = ["qaboard", "numpy", "imageio"]
# ///
import imageio.v3 as iio
import qaboard as qb

url = "https://qaboard.example.com/kitefin/detector/commit/7622c337?batch=ci&filter=night%20-crash"
for run in qb.runs(url):
    image = iio.imread(run.dir / "output.png")
    print(run.input, run.configurations, run.metrics["psnr"], image.mean())
```

In the **Visualizations** and **Output Files** views, **Script** shows this snippet with the page's address, ready to
copy. The filter is applied like in the web app ([filter syntax](/docs/user-guide/finding-results#filter-syntax)),
so the script works on exactly the runs you looked at. Each `Run` has:

| Attribute | What it is |
|---|---|
| `input`, `database`, `input_path` | The input's path relative to its database, the database, and the full path. |
| `configurations`, `params`, `parameters` | The configurations, the tuning parameters, and every parameter as the web app shows them. |
| `metrics` | The metrics the run returned. |
| `dir` | Where its files are, as a `Path`. |
| `state`, `is_failed` | `pending`, `running` or `finished`; whether it failed. |
| `id`, `commit`, `batch`, `project`, `url` | Where it is in QA-Board, and its link in the web app. |
| `input_metadata`, `data`, `created_at`, `finished_at` | The input's metadata, what else the server knows (who ran it, where...), when. |

You can also name the runs instead of giving a URL: `qb.runs(project="kitefin/detector", commit="main", batch="ci",
filter="night")`. `commit` can be a branch or a tag; without it, you get the latest commit with results. Keyword
arguments override what a URL says, and `reference=True` gives the runs of the reference bar (`?reference=`).

From the shell, `qa runs <url>` prints the runs' folders, one per line, and `--json` everything above. It works
outside a project, without a *qaboard.yaml*:

```bash
qa runs "https://qaboard.example.com/kitefin/detector/commit/7622c337?batch=ci&filter=night" | while read dir; do
  python compute_sharpness.py "$dir"
done
```

Reading needs the `qaboard` package (`pip install qaboard`) and, when the project isn't public, to be signed in:
`qa auth login https://qaboard.example.com`, or a token in `QABOARD_TOKEN` (see [Authentication](#authentication)).
When the server is behind a path prefix like `https://tools.example.com/qaboard/`, pass `server=` (`--server`): the
address alone can't say where the project's name starts.

:::note Writing to runs
`run.log(...)` and `run.save_file(...)` are on the [roadmap](/docs/roadmap): QA-Board will merge the metrics you
compute into the run and remember your script added them. Until then, compute new metrics with your project's
`postprocess()`: `qa batch ci --action-on-existing postprocess` redoes it on existing results (see
[Postprocessing](/docs/running-your-code#postprocess)). Runs' folders are shared: don't change or delete what the CI
wrote.
:::

## Find where runs save their outputs {#cli-api}
`qa batch <batch> --list-output-dirs` prints the output directory of each run, one per line, without running
anything. In the detector's project:

```bash
qa batch ci --list-output-dirs
```

```text
/home/arjun/detector/output/7622c337-20/slices-indoor
/home/arjun/detector/output/7622c337-20/slices-outdoor
...
```

`--list` prints the runs as JSON, with what each one would run:

```bash
qa batch ci --list
```

```json
[
  {
    "type": "default",
    "input_path": "inputs/slices/indoor",
    "database": "inputs",
    "platform": "linux",
    "configurations": ["fp32", "size-320"],
    "extra_parameters": {},
    "batch": "ci",
    "output_dir": "/home/arjun/detector/output/7622c337-20/slices-indoor",
    "command": "qa --configuration fp32:size-320 run --input \"slices/indoor\"",
    "rel_input_path": "slices/indoor"
  }
]
```

`--list-inputs` only prints the inputs. These are local runs' directories: runs in the CI, or with `--share`, save
their files under the project's `storage` (see [where is the data](/docs/storage/where-is-the-data)), and
`qa --share batch ci --list-output-dirs` prints those.

For other values, `qa get` prints the variables `qa` uses:

```bash
qa get commit_id
qa get --input slices/indoor output_dir
```

## Read results over HTTP {#http-api}
The web app reads everything from the API at `/api/v1`, and so can your scripts. For instance, the latest commits of
the detector, with their CI batch:

```bash
base_url=http://localhost:5151/api/v1
curl "$base_url/commits?project=kitefin/detector&only_ci_batches=true&limit=10" | jq
```

<details>
<summary>The answer: a list of commits</summary>

```js
[
  {

    "branch": "quant/int8",

    "committer_avatar_url": null,

    "authored_date": "<day>",
```

### Lists of commits, branches and projects {#lists-of-commits-branches-and-projects}
`/commits` gives the commits with results, newest first: by default those of the last days with commits, or of
`?from=&to=` (dates). Use `/commits/<branch>` for a branch's, `?committer=<name>` for a committer's. It accepts:
- `?limit=` (at most 1000) and `?offset=`, to get pages. The `X-Has-More` response header (`true` or `false`) tells
  if there are more.
- `?q=` to search all the project's commits, with the
  [syntax of the web app's search box](/docs/user-guide/finding-results#searching-commits), e.g.
  `q=branch:release -wip`. Searches ignore the date range, unless you give `from` or `to`.
- `?batch=<label>` for only that batch of each commit, or `?only_ci_batches=true` for the CI batch.
- `?with_outputs=true` to add each batch's runs.

Without `limit`, it answers with at most 1000 commits, and no `X-Has-More` header.

```bash
curl -i "$base_url/commits?project=kitefin/detector&q=committer:arjun&limit=50&offset=50"
```

`/project/branches?project=kitefin/detector` lists all the branches with results, by name. With `&q=quant`
(branches whose name contains it) or `&limit=` (default 50, at most 1000), you get the most recently active branches
first.

`/projects` gives the projects with results that you can access, with their data. With `?summary=true`, it only
gives what lists of projects need (git info, *qaboard.yaml*'s `project` section): it's much smaller. Use
`/project?project=kitefin/detector` for the rest.

### A commit's runs and metrics {#a-commits-runs}
`/commit/<sha>?project=<project>` gives a commit with all its batches and their runs:

```bash
curl "$base_url/commit/<sha>?project=kitefin/detector" | jq '.batches.default.outputs'
```

Each run (an "output" in the API) has its input (`test_input_path`, `test_input_database`, `test_input_metadata`),
its `configurations`, `extra_parameters` (the tuning parameters) and `platform`, its `metrics`, its state
(`is_pending`, `is_running`, `is_failed`) and its `output_dir_url`.

### Compare with a reference {#compare}
`/commit/<sha>/compare` gives the numbers of the **Summary** and **Metrics Diff** views: each metric's median
against a reference, and each run against its reference run. It's experimental, see
[Quality gate](/docs/quality-gate#from-scripts-and-agents).

### Milestones {#milestones}
`/milestones?project=<project>` lists the project's shared milestones, and yours when you send a token: each with
its `label`, `group`, `notes`, `commit`, `batch` and `filter`. See
[References and milestones](/docs/references-and-milestones#milestones).

There is no OpenAPI description of the API yet: see the [roadmap](/docs/roadmap).

## Authentication {#authentication}
Reading data doesn't need to be signed in (unless the server
[blocks anonymous users](/docs/backend-admin/user-management#blocking-anonymous-users)). Some actions do, like
starting tuning runs. From scripts, use an API token: create one in the web app, in **Settings → Access tokens** (or
use the one of `qa auth token`), then send it with an `Authorization: Bearer` header:

```bash
curl -H "Authorization: Bearer $QABOARD_TOKEN" "$base_url/user/me/"
```

- Give tokens only the **scopes** they need: `read`, `ingest` (send results), `act` (redo runs, start or delete
  batches, save milestones). You can also restrict them to some projects, e.g. `group/repo` or `group/*`.
- When a token can't be used, the answer says why, e.g.
  `{"error": "This token expired...", "reason": "token_expired"}`. `/user/me/` says which token you use and its scopes.
- Tokens in URLs (`?token=`) are only accepted to read: URLs end up in logs.
- To start a Jenkins build through QA-Board with its Jenkins credentials, send a token with the `act` scope:
  ```bash
  curl -X POST -H "Authorization: Bearer $QABOARD_TOKEN" -H "Content-Type: application/json" \
       -d '{"build_url": "https://jenkins/job/my-job", "params": {"key": "value"}}' \
       "$base_url/jenkins/build/trigger/"
  ```
  Without a token, QA-Board only starts the jobs listed in a project's *qaboard.yaml*.
- The `qa` CLI sends its token automatically (see [Sign in](/docs/installation#signing-in)).
