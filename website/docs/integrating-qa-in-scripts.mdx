Scripts, notebooks and agents can use QA-Board's results: the `qa` CLI says where a batch's runs save their files,
and the HTTP API gives the commits, batches, runs and metrics that the web app shows.

## Find where runs save their outputs {#cli-api}
`qa batch <batch> --list-output-dirs` prints the output directory of each run, one per line, without running
anything. In the detector's project:

```bash
qa batch ci --list-output-dirs
```

```text
/home/arjun/detector/output/7622c337-20/slices-indoor
/home/arjun/detector/output/7622c337-20/slices-outdoor
...
```

`--list` prints the runs as JSON, with what each one would run:

```bash
qa batch ci --list
```

```json
[
  {
    "type": "default",
    "input_path": "inputs/slices/indoor",
    "database": "inputs",
    "platform": "linux",
    "configurations": ["fp32", "size-320"],
    "extra_parameters": {},
    "batch": "ci",
    "output_dir": "/home/arjun/detector/output/7622c337-20/slices-indoor",
    "command": "qa --configuration fp32:size-320 run --input \"slices/indoor\"",
    "rel_input_path": "slices/indoor"
  }
]
```

`--list-inputs` only prints the inputs. These are local runs' directories: runs in the CI, or with `--share`, save
their files under the project's `storage` (see [where is the data](/docs/storage/where-is-the-data)), and
`qa --share batch ci --list-output-dirs` prints those.

For other values, `qa get` prints the variables `qa` uses:

```bash
qa get commit_id
qa get --input slices/indoor output_dir
```

## Read results over HTTP {#http-api}
The web app reads everything from the API at `/api/v1`, and so can your scripts. For instance, the latest commits of
the detector, with their CI batch:

```bash
base_url=http://localhost:5151/api/v1
curl "$base_url/commits?project=kitefin/detector&only_ci_batches=true&limit=10" | jq
```

<details>
<summary>The answer: a list of commits</summary>

  {

    "branch": "quant/int8",
    "message": "feat(quant): percentile calibration (99.99)\n\nMinmax let a few outliers set the scale...",

    "authored_date": "<day>",

The `*_url` fields are paths on the server: add your server's address before them to download files, like
`http://localhost:5151/s/mnt/qaboard/.../metrics.json`.

### Lists of commits, branches and projects {#lists-of-commits-branches-and-projects}
`/commits` gives the commits with results, newest first: by default those of the last days with commits, or of
`?from=&to=` (dates). Use `/commits/<branch>` for a branch's, `?committer=<name>` for a committer's. It accepts:
- `?limit=` (at most 1000) and `?offset=`, to get pages. The `X-Has-More` response header (`true` or `false`) tells
  if there are more.
- `?q=` to search all the project's commits, with the
  [syntax of the web app's search box](/docs/user-guide/finding-results#searching-commits), e.g.
  `q=branch:release -wip`. Searches ignore the date range, unless you give `from` or `to`.
- `?batch=<label>` for only that batch of each commit, or `?only_ci_batches=true` for the CI batch.
- `?with_outputs=true` to add each batch's runs.

Without `limit`, it answers with at most 1000 commits, and no `X-Has-More` header.

```bash
curl -i "$base_url/commits?project=kitefin/detector&q=committer:arjun&limit=50&offset=50"
```

`/project/branches?project=kitefin/detector` lists all the branches with results, by name. With `&q=quant`
(branches whose name contains it) or `&limit=` (default 50, at most 1000), you get the most recently active branches
first.

`/projects` gives the projects with results that you can access, with their data. With `?summary=true`, it only
gives what lists of projects need (git info, *qaboard.yaml*'s `project` section): it's much smaller. Use
`/project?project=kitefin/detector` for the rest.

### A commit's runs and metrics {#a-commits-runs}
`/commit/<sha>?project=<project>` gives a commit with all its batches and their runs:

```bash
curl "$base_url/commit/<sha>?project=kitefin/detector" | jq '.batches.default.outputs'
```

Each run (an "output" in the API) has its input (`test_input_path`, `test_input_database`, `test_input_metadata`),
its `configurations`, `extra_parameters` (the tuning parameters) and `platform`, its `metrics`, its state
(`is_pending`, `is_running`, `is_failed`) and its `output_dir_url`.

### Compare with a reference {#compare}
`/commit/<sha>/compare` gives the numbers of the **Summary** and **Metrics Diff** views: each metric's median
against a reference, and each run against its reference run. It's experimental, see
[Quality gate](/docs/quality-gate#from-scripts-and-agents).

### Milestones {#milestones}
`/milestones?project=<project>` lists the project's shared milestones, and yours when you send a token: each with
its `label`, `group`, `notes`, `commit`, `batch` and `filter`. See
[References and milestones](/docs/references-and-milestones#milestones).

There is no OpenAPI description of the API yet: see the [roadmap](/docs/roadmap).

## Authentication {#authentication}
Reading data doesn't need a login (unless the server
[blocks anonymous users](/docs/backend-admin/user-management#blocking-anonymous-users)). Some actions do, like
starting tuning runs. From scripts, use an API token: create one with a `POST` to `/api/v1/user/token/` while logged
in, then send it with an `Authorization: Bearer` header, or as a `?token=` URL parameter:

```bash
curl -H "Authorization: Bearer $QA_TOKEN" "$base_url/user/me/"
curl "$base_url/user/me/?token=$QA_TOKEN"
```

The `qa` CLI sends `QA_TOKEN` automatically, from the environment or from *~/.qaboard/secrets.yaml* (see
[Installation](/docs/installation#api-token)). Tokens don't expire, so keep them private.
