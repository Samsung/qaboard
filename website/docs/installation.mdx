You need to install QA-Board's CLI client: `qa`. It wraps and runs your code.

<SiteInstructions page="installation" />

```bash
pip install qaboard
```

### With your organization's site package
Your organization may publish a *site package* that configures `qa` for its server. Install it too, e.g.:
```bash
pip install --upgrade 'qaboard-site-mysite @ git+ssh://git@git.example.com/infra/qaboard#subdirectory=deployments/mysite/cli'
```

The site packages auto-configure defaults such as the API URL, port, and other site-specific settings. You do not need to manually set environment variables for standard deployments. They can also provide [default `qaboard.yaml` settings for all projects](project-init#site-defaults), like where results are stored or the LSF queue.

:::tip
Environment variables (e.g. `QABOARD_HOST`, `QABOARD_PROTOCOL`) **always override** site package defaults. This lets you point at a different server during development or testing without changing the installed package.
:::

To make sure the installation was successful, try printing a list of `qa`'s CLI commands:

```bash
qa --help

# If you get errors about not using a utf8 locale, you can likely:
#   export LC_ALL=C.utf8 LANG=C.utf8
```

## Connecting to a custom QA-Board server
If you installed `qaboard` without a site package (or want to override the defaults), set these environment variables:

```bash
export QABOARD_HOST=my-server:5151
export QABOARD_PROTOCOL=http
# or, equivalently:
export QABOARD_URL=http://my-server:5151
```

Without any of them, `qa` uses `http://localhost:5151` and prints a warning.

## Signing in
Sign in once per server, so that the results you send are signed with your name, and so that `qa` can do what needs a
logged-in user (e.g. start tuning or "redo" runs from scripts):

```bash
qa auth login
# Your one-time code: WDJB-MJHT
# To sign in, open https://qaboard.example.com/device and enter the code
```

Open the link in any browser, even on another computer: it works over SSH. Sign in to QA-Board as usual, check the
code and approve. `qa` saves a token for this server in *~/.config/qaboard/hosts.yaml*, readable only by you
(*%APPDATA%\qaboard* on Windows). It's for all your checkouts and worktrees: it's never saved in your projects.

```bash
qa auth status   # which server, which user, which token
qa auth logout   # revokes the token, and forgets it
qa auth token    # prints the token, e.g. for curl
```

The token expires after 180 days without use (admins can change it): run `qa auth login` again. You can also see and
revoke it in the web app, in **Settings → CLI & devices**.

**In CI and scripts**, give `qa` a token in `QABOARD_TOKEN` (create one in **Settings → Access tokens**, see
[CI integration](ci-integration#tokens)), or save it with `qa auth login --with-token < token.txt`.
`qa` uses `$QABOARD_TOKEN` (or `$QA_TOKEN`), then the login of `qa auth login`, then `QA_TOKEN` in
*~/.qaboard/secrets.yaml* (the older way: it still works).

If your server uses HTTPS with a certificate your machines don't trust (e.g. from an internal CA), point `QABOARD_API_VERIFY` to the CA bundle, or disable the checks for requests to the API:

```bash
export QABOARD_API_VERIFY=/etc/ssl/certs/internal-ca.pem
export QABOARD_API_VERIFY=false
```
