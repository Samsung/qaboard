`qa` runs your code through one Python function that you write: `run(context)`, in `qa/main.py`. The `context` says
which input to work on, with which configuration, and where to save the output files. `run()` returns the metrics.

## Write run() {#write-run}
If your code is in Python, import it and call it:

```python title="qa/main.py"
from my_project import process  # your code


def run(context):
    result = process(context.input_path, params=context.params)
    result.image.save(context.output_dir / "out.png")
    return {"psnr": result.psnr, "is_failed": False}
```

Then run it on one input, with its path relative to your inputs' folder (see [Inputs](/docs/inputs)):

```bash
qa run --input charts/slanted-edge.png
```

In the camera ISP example, `qa` prints where the outputs go, then what the code prints, then the metrics `run()`
returned:

The example's [`qa/main.py`](https://github.com/Samsung/qaboard/blob/master/examples/image-quality/qa/main.py) is a
complete `run()` to copy from: it simulates the camera, runs the pipeline, saves the output image and each stage, then
measures PSNR, sharpness and halos.

Results stay on your computer, in `output/`. To see them in the web app, add
[`--share`](/docs/using-the-qa-cli#qa---share): `qa --share run --input charts/slanted-edge.png`. In CI, `qa` always
sends them.

## What `qa` does around `run()` {#wrapping-your-code}
1. It reads *qaboard.yaml* and imports the file named by `project.entrypoint`. That file's folder is on Python's
   import path, so `qa/main.py` can import the modules next to it.
2. It creates `context.output_dir`, empties it, and calls `run(context)`.
3. It saves the metrics `run()` returns in *metrics.json*, everything printed in *log.txt*, and the lists of input and
   output files in *manifest.inputs.json* and *manifest.outputs.json*.
4. With `--share` or in CI, it sends the metrics to QA-Board, which shows the output files from where they are.

What `run()` returns is a dict of metrics: the web app shows the numbers, compared with the reference's. See
[Metrics](/docs/computing-quantitative-metrics) for strings, units, and which way is better. A run fails when `run()`
returns `"is_failed": True`, raises an exception (`qa` prints its traceback in the log), or returns something else
than a dict. `qa run` then exits with 1.

## Run an executable {#run-an-executable}
`qa` doesn't build your code: build it first, in CI too. Then start it from `run()`, and read what it wrote:

```python title="qa/main.py"
import json
import subprocess


def run(context):
    process = subprocess.run(
        ["build/my-tool", "--input", str(context.input_path), "--output", str(context.output_dir)],
        stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True,
    )
    print(process.stdout)  # saved in the run's log
    if process.returncode != 0:
        return {"is_failed": True}
    metrics = json.loads((context.output_dir / "metrics.json").read_text())
    return {**metrics, "is_failed": False}
```

:::caution
`qa` saves in *log.txt* what Python prints. An executable that writes to the terminal itself isn't in the log: capture
its output and print it, like above.
:::

To see the log while the executable runs, print its output line by line. The inference gateway example starts its
benchmark this way, and fails the run when the benchmark crashes:

Arguments after the input are forwarded to your code, as `context.forwarded_args`. It's handy to try a flag of your
executable:

```bash
qa run --input profiles/steady-high.yaml --verbose
#=> context.forwarded_args == ['--verbose']
```

## Compute metrics in a second step {#postprocess}
Some projects run their code, then compute metrics from its output files. Put that second step in a `postprocess()`
function, next to `run()`:

```python title="qa/main.py"
def postprocess(runtime_metrics, context):
    detections = load_detections(context.output_dir / "detections.json")
    return {**runtime_metrics, **evaluate(detections, context.input_path), "is_failed": False}
```

- `qa run` calls `postprocess()` with what `run()` returned, unless the run failed or you give `--no-postprocess`.
- `qa postprocess --input <input>` redoes only the second step, on the files of the previous run. `runtime_metrics` is
  then empty, and the metrics of the previous run are kept unless `postprocess()` returns new values.
- For a whole batch: `qa batch <batch> --action-on-existing postprocess`, see
  [existing results](/docs/using-the-qa-cli#dealing-with-existing-results).

## Import results computed elsewhere {#import-existing-results}
To compare your code with a benchmark or a reference implementation, import their results as runs. Say they are
next to your images, in a folder per input:

```text
<database>
├── images
│  ├── A.jpg
│  └── B.jpg
└── standard-benchmark
   └── images
      ├── A
      │  └── output.jpg
      └── B
         └── output.jpg
```

Give the benchmark as a configuration, in a batch:

```yaml title="qa/batches.yaml"
import-standard-benchmark:
  configs:
  - benchmark: standard-benchmark
  inputs:
  - images
```

When it's set, `run()` copies the benchmark's files instead of running your code:

```python title="qa/main.py"
import shutil


def run(context):
    benchmark = context.params.get("benchmark")
    if benchmark:
        outputs = context.database / benchmark / context.rel_input_path.with_suffix("")
        shutil.copytree(outputs, context.output_dir, dirs_exist_ok=True)
        return {"is_failed": False}
    # otherwise, run your code, which writes output.jpg
```

Run `qa --share batch import-standard-benchmark`, then make that batch a
[milestone](/docs/references-and-milestones) to compare with it in a click.

## Reference
### The context {#useful-context-properties-reference}
| Property | What it is |
|---|---|
| `input_path` | The input's absolute path. |
| `rel_input_path` | The input's path relative to the database, as you give it to `qa run --input` and in batches. |
| `database` | The folder with your inputs (absolute), see [Inputs](/docs/inputs#the-database). |
| `type` | The input type, see [input types](/docs/inputs#advanced-handling-multiple-input-types). |
| `input_metadata` | The input's metadata, if your entrypoint has a `metadata()` function: see [Metadata](/docs/metadata-integration-external-databases). |
| `configs` | The list of configurations, then the tuning parameters. Your code decides what they mean: see [Configurations](/docs/specifying-configurations). |
| `params` | The mappings of `configs`, merged: often all you need. |
| `platform` | `linux` or `windows`, or what `qa --platform` sets, e.g. `hw-model`. |
| `forwarded_args` | The arguments after the input: `qa run --input A.jpg --verbose`. |
| `output_dir` | Where to save the output files. `qa` creates it, and empties it before the run. |
| `dryrun` | `True` with `qa --dryrun run`: print what you would do, without doing it. |
| `id` | The run's id in QA-Board. `None` when results aren't sent: without `--share` outside CI, with `--offline`, or when the server can't be reached. |
| `configurations`, `extra_parameters` | `configs` in two parts: the configurations, and the tuning parameters with the forwarded arguments. |

### Environment variables {#environment-variables}
- `qa` sets `QA_LABEL` to the run's label (from `qa --label`), e.g. for your code's own logs.
- `QA_USER` overrides the user name `qa` uses (by default, the logged-in user), e.g. for `{user}` in
  [storage locations](/docs/storage/where-is-the-data).
- `GIT_MESSAGE` and `GIT_AUTHORED_DATETIME` override the commit message and date sent to QA-Board, e.g. when your code
  isn't in a git repository.

### qa's settings in your code {#accessing-the-qa-board-configuration}
Your code can read what `qa` knows:

```python
from qaboard.config import config, project, commit_id, commit_branch, is_ci
```

- `config`: the project's *qaboard.yaml*, merged with the [site defaults](/docs/project-init#site-defaults), as a dict.
- `project`: the project's name, as a path, e.g. `kitefin/camera-isp`.
- `commit_id`, `commit_branch`: the commit and branch being run.
- `is_ci`: whether `qa` runs in CI (the `CI` or `GIT_COMMIT` environment variable is set).
