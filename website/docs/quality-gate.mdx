`qa gate` fails your CI job when a commit's results regress against a reference: a metric's median gets worse than
you allow, one test gets much worse, runs fail, or output files stop being bit-accurate. It decides on the numbers
that the commit page's **Summary** and **Metrics Diff** show, and links to the Metrics Diff, so that whoever reviews
the change sees why.

## Write rules {#rules}
Each rule names a metric, and one or more limits:

| Limit | Fails when |
|---|---|
| `max_regression: 5%` | The metric's median over the batch's runs is more than 5% worse than the reference's. |
| `per_test_max_regression: 10%` | One run is more than 10% worse than its reference run. |
| `min: 0.42` | The median is under 0.42. |
| `max: 12` | The median is over 12. |

The detector combines them: an absolute floor for its mAP, at most 10% less AP on small objects, and no slice much
worse than in the reference.

<RepoFile path="examples/detection-eval/qaboard.yaml" title="qaboard.yaml" section="gate" />

- **Worse** comes from your metrics' definitions, in your code or your metrics file (see
  [Declaring metrics](/docs/computing-quantitative-metrics#declaring-metrics)): with `smaller_is_better: false`, a
  smaller value is worse. Regression rules need to know which way is better: they fail with an error for metrics that
  were not declared, declared in code without `smaller_is_better`, or with `smaller_is_better: null`. In a metrics
  file, metrics without `smaller_is_better` are "smaller is better". `min` and `max` work with any metric.
- Give regressions as percentages (`5%`) or fractions (`0.05`), relative to the magnitude of the reference's value.
- Give `min` and `max` in the unit the runs return, like `target`: before `scale` is applied.
- Combine limits in one rule: `{metric: psnr, max_regression: 1%, per_test_max_regression: 5%}`.
- A metric that none of the new runs return fails its rules. A metric that the reference's runs don't have yet, like
  a new one, skips its regression rules.

Medians and per-test limits keep noisy metrics from failing the gate: one slow run moves a mean, not a median. Use
`per_test_max_regression` for regressions that only hurt a few inputs, which a median hides.

### Pass/fail metrics {#passfail-metrics}
The median of a metric that is 0 or 1 in each test says little: `{metric: unsafe_actions, max: 0}` passes as long as
fewer than half of the tests are unsafe. Choose another `aggregate`: `median` (the default), `mean`, `min` or `max`.
The fleet assistant's gate fails as soon as one task has an unsafe action, and lets its pass rate drop by 5% of itself
at most:

<RepoFile path="examples/agent-evals/qaboard.yaml" title="qaboard.yaml" section="gate" />

With `mean`, `min` or `max`, the gate aggregates each test's values, as the **Metrics Diff** shows them: the new runs'
values, and those of the reference runs they're compared with. Regressions are relative to the reference's aggregate:
from a pass rate of 80%, `max_regression: 5%` allows 76%. When the reference's aggregate is 0, any change for the
worse fails. `aggregate` applies to `max_regression`, `min` and `max`: it can't be used with
`per_test_max_regression`, which checks each test, so give that one its own rule.

## Choose the reference and the batches {#set-the-rules}
The other keys of the `gate:` section:

| Key | Default | Meaning |
|---|---|---|
| `reference` | `project.reference_branch`, else `master` | What to compare with: the name of a shared [milestone](/docs/references-and-milestones) (or `#12` for the milestone whose link is `/<project>/milestone/12-...`), a commit's sha, or a branch. A branch means its latest commit with runs in the batch, other than the commit you check. If that commit is on the same branch, the latest one before it. |
| `batches` | `[default]` | The labels of the batches to check, as `qa --label` sets them. The CI batch's label is `default`, and the web app shows it as **CI**: `ci` names it too. Each batch is compared with the reference's batch that has the same label. |
| `max_failed_runs` | `0` | How many runs may fail in each batch. `null` doesn't check. |
| `require_bit_accuracy` | `false` | Fail when a run's output files differ from its reference run's, like [`qa check-bit-accuracy`](/docs/bit-accuracy): files that match `bit_accuracy.patterns`, ignoring the logs. Runs without a *manifest.outputs.json* make the gate undecidable. |

<details>
<summary>Which numbers the gate compares</summary>

The gate uses the numbers of the commit page, so that what it says is what reviewers see:
- **Medians**, as in the **Summary**: over the batch's finished runs, including failed runs that returned the metric
  (tuning iterations are left out), and over the reference's runs on the same inputs.
- **Each test**, as in the **Metrics Diff**: each run is compared with the reference run that matches it best (the
  same input, then the closest configuration and tuning parameters, then the same platform).
- The table shows each check's values, and how much worse or better they are.

</details>

## Exit codes {#exit-codes}

| Code | Verdict | When |
|---|---|---|
| `0` | pass | Every rule passes. |
| `1` | fail | A rule fails, or the `gate:` section has an error. |
| `2` | undecidable | There is no reference (or no runs to check), runs are still running, or QA-Board can't be reached. |

With `--wait`, `qa gate` checks again every `--interval` seconds (30) while it's undecidable, until `--timeout`
(1800). Use it when the reference's CI may still be running.

## Commit statuses {#commit-statuses}
The job's exit code already acts as a check. `--post-status` also posts a commit status named `qaboard/gate`
(`qaboard/gate/<subproject>` in a [subproject](/docs/monorepo-subprojects)), that links to the Metrics Diff. Require
it in your branch protection rules if you like.

- **GitHub:** set `GITHUB_TOKEN`, and give the workflow `statuses: write`. `qa gate` reads the repository and the API's
  URL from `GITHUB_REPOSITORY` and `GITHUB_API_URL`, that GitHub Actions sets (GitHub Enterprise included). The
  status is `success`, `failure`, or `error` when undecidable.
- **GitLab:** set `GITLAB_ACCESS_TOKEN`. In GitLab CI, `qa gate` uses `CI_API_V4_URL` and `CI_PROJECT_ID`.
  Elsewhere it uses `GITLAB_HOST` (default `https://gitlab.com`) and the project's name from *qaboard.yaml*. The
  status is `success`, or `failed`.

:::note
With `on: pull_request`, GitHub Actions runs on a temporary merge commit (`GITHUB_SHA`): `qa` uses the pull request's
last commit instead, for the results and the status. Check it out too, see
[GitHub Actions](/docs/ci-integration#example-with-github-actions). `on: push` is usually enough.
:::

## Options

| Option | Meaning |
|---|---|
| `--reference <ref>` | Compare with this branch, milestone or commit instead of `gate.reference`. |
| `--batch <label>`, `-b` | Check this batch instead of `gate.batches`. Repeat it for several batches. |
| `--commit <sha>` | Check this commit instead of the current one. |
| `--format text\|markdown\|json`, `--json` | The output: a table (default), a Markdown table, or JSON for scripts and agents. |
| `--wait`, `--timeout`, `--interval` | Check again while undecidable, see [exit codes](#exit-codes). |
| `--post-status github\|gitlab` | Post a commit status, see [commit statuses](#commit-statuses). |
| `--server <url>` | The QA-Board server, instead of `QABOARD_URL` or your site's settings. |

`qa gate` prints a reminder that it's experimental on stderr: stdout only has the result.

## From scripts and agents
`qa gate --json` prints the verdict, each check with its values, and the link to the Metrics Diff. The numbers come
from an HTTP API that you can use too:

```bash
curl "http://localhost:5151/api/v1/commit/<sha>/compare?project=<project>&reference=main&batch=default"
```

| Parameter | Default | Meaning |
|---|---|---|
| `project` | required | The project's name, as in *qaboard.yaml*. |
| `batch` | `default` | The batch's label. |
| `reference` | the commit's `gate.reference`, else `project.reference_branch` | A shared milestone's name (or `#<id>`), a commit or a branch. |
| `reference_batch` | `batch` | The reference's batch label, to compare two different batches. |
| `metrics` | all | Metrics to compare, separated by commas. |
| `bit_accuracy` | `false` | `true` compares the runs' output files. |

The answer has the `status` of the comparison (`complete`, `running`, or `missing` with `messages` saying why), the
`commit` and `reference` with their counts of runs, and:
- `metrics`: for each metric, the median, the number of values and the share of runs that meet the target, for the
  new and the reference runs, and the change (`delta`, `delta_relative`);
- `tests`: each run, its reference run (`reference_id`, and `reference_mismatch` when they don't have the same input,
  configuration, platform or parameters), and the change of each metric.

Like the rest of the API, reading doesn't need a login unless your server restricts the project. Scripts can send
an API token, see [the HTTP API](/docs/apis#authentication).

## Known limitations
- Tags can't be references yet: use the tagged commit's sha.
- A branch's commits are those QA-Board first saw on that branch. A commit pushed to a feature branch, then
  fast-forwarded to `main`, stays on the feature branch.
- Milestones must be shared to be found by name (`#<id>` finds any). The gate compares with the milestone's batch
  (unless you set `reference_batch`), but not with its filter: all the runs of the batch are compared.
