A batch is a named list of inputs and configurations, in a YAML file. `qa batch ci` runs them all, in parallel or on
a cluster, and the web app shows their runs together. Your CI runs a batch on every commit; others run nightly, before
a release, or to try parameters.

## Write a batch {#write-a-batch}
The inference gateway example measures its latency on 5 load profiles in CI:

<RepoFile path="examples/serving-latency/qa/batches.yaml" title="qa/batches.yaml" section="ci" />

Inputs are paths relative to your [database](/docs/inputs#the-database), `inputs/` here. A batch can also list
folders and wildcards like `profiles/*.yaml`: `qa` finds the inputs in them with
[`inputs.globs`](/docs/inputs#identifying-inputs).

Batches are in `qa/batches.yaml`, or in the files that `inputs.batches` lists in *qaboard.yaml*.

## Run a batch {#run-a-batch}
To see what a batch would run, without running anything, use `--dryrun`. It prints the `qa run` command of each run,
and where its outputs go:

```bash
qa --dryrun batch ci
```

```text
qa run --input "profiles/steady-low.yaml"
   /home/kaito/kitefin/inference-gateway/output/linux/profiles-steady-low
qa run --input "profiles/steady-mid.yaml"
   /home/kaito/kitefin/inference-gateway/output/linux/profiles-steady-mid
[...]
qa run --input "profiles/heavy-tail-high.yaml"
   /home/kaito/kitefin/inference-gateway/output/linux/profiles-heavy-tail-high
```

Then run it, with `--share` to see the results in the web app. `qa` prints the link to the commit's results first:

```bash
qa --share batch ci
```

<Clip
  id="cli/batch"
  caption="qa --share batch ci on the camera pipeline: qa prints the link to the results, then runs each input and configuration of the batch."
/>

- Run several batches at once: `qa batch ci capacity`, or with a wildcard: `qa batch 'sweep-*'`.
- Arguments after `--` are given to each run, and to your code as `context.forwarded_args`:
  `qa batch ci -- --verbose` runs `qa run --input "profiles/steady-low.yaml" --verbose`...
- Runs remember the name of their batch: the web app shows it, and you can filter runs by it.
- By default, `qa batch` runs on this machine. To run several runs at the same time, or on a cluster, see
  [runners](/docs/using-the-qa-cli#batch-runners).

## Configurations in a batch {#specifying-test-configurations}
`configs` gives the [configurations](/docs/specifying-configurations) the batch's inputs run with. The camera ISP
example checks the fixed-point model of its camera chip, the `hw-model` platform, at ISO 100 (`base`):

<RepoFile path="examples/image-quality/qa/batches.yaml" title="qa/batches.yaml" section="bitexact" />

To run each input with several configurations, give them in a `matrix`. Its CI runs 9 images at ISO 100 and 3200:
18 runs.

<RepoFile path="examples/image-quality/qa/batches.yaml" title="qa/batches.yaml" section="ci" />

A matrix can also combine values, which `${matrix.<name>}` puts in the configurations. The detector example runs 4
slices of its test set with the fp32 model and the int8 model:

<RepoFile path="examples/detection-eval/qa/batches.yaml" title="qa/batches.yaml" section="ci" />

```bash
qa --dryrun batch ci
```

```text
qa --configuration fp32:size-320 run --input "slices/indoor"
   /home/arjun/kitefin/detector/output/7622c337-20/slices-indoor
[...]
qa --configuration int8:size-320 run --input "slices/small-objects"
   /home/arjun/kitefin/detector/output/6d41e2b9-20/slices-small-objects
```

Its `sizes` batch adds `size: [320, 416, 512]` to the matrix: 4 slices × 2 models × 3 sizes, 24 runs. See
[matrices](/docs/batches-advanced#matrix-batches) for more.

An input can add its own configurations to the batch's:

```yaml title="qa/batches.yaml"
my-batch:
  configs: [int8]
  inputs:
  - slices/indoor                                      #=> [int8]
  - slices/outdoor: [size-416, {score_threshold: 0.2}] #=> [int8, size-416, {score_threshold: 0.2}]
  - slices/small-objects: {nms_iou: 0.7}               #=> [int8, {nms_iou: 0.7}]
```

<details>
<summary>The same input twice, with other configurations</summary>

An input can appear several times, each time with its own configurations. These forms are the same:

```yaml title="qa/batches.yaml"
crops:
  configs: [base]
  inputs:
  - image.raw: {crop: A}       #=> [base, {crop: A}]
  - image.raw: {crop: B}       #=> [base, {crop: B}]
  - [image.raw, {crop: C}]     #=> [base, {crop: C}]
```

</details>

## Database and platform {#setting-a-custom-database}
A batch can set its own `database`, where its inputs are, and its `platform`, like the camera ISP's `bitexact` batch
above. Runs are compared with the reference's runs on the same platform. At the top of a batch file, `database`,
`configs` and `platform` are defaults for the file's batches that don't set their own:

```yaml title="qa/batches.yaml"
database: /mnt/datasets          # for all the batches of this file

my-batch:
  inputs:
  - images/A.jpg                 #=> /mnt/datasets/images/A.jpg

archive:
  database:                      # this batch's inputs are elsewhere
    linux: /mnt/archive
    windows: '\\storage\archive'
  inputs:
  - images/A.jpg
```

## Runner settings per batch {#runner-settings-per-batch}
Under the name of a runner, a batch changes the settings of its runs, e.g. how much memory LSF gives them. The camera
ISP's 113 MP test wall needs more memory than the other images:

```yaml title="qa/batches.yaml"
deep-zoom:
  configs: [base]
  inputs:
  - charts/test-wall-113mp.tiff
  lsf:
    max_memory: 3072   # MB
```

Runner settings are merged in this order, the last one wins:
1. `runners.<runner>` in *qaboard.yaml* (e.g. `runners.lsf.queue`),
2. `runners.<runner>` in the [input type](/docs/inputs#advanced-handling-multiple-input-types),
3. `<runner>:` in the batch, as above,
4. command line options, like `qa batch --lsf-queue`.

A batch can also limit how many of its runs run at the same time, with `concurrency` under `local:`, `lsf:` or
`dask:`, and set the local runner's `timeout`. How batches with their own limit share the resources depends on the
runner:
- [local](/docs/local-multiprocessing): they run one after the other.
- [LSF](/docs/lsf-integration#limiting-concurrency): each gets its own job arrays (or waves), sent at the same time,
  so their limits add up.
- [Dask](/docs/dask-integration): their runs share the workers, and `qa batch` never has more runs in flight than the
  largest concurrency.

:::caution
A batch can't choose its runner yet: `qa batch --runner`, or `runners.default` in *qaboard.yaml*, does, for all
batches. A batch's `runner:` doesn't change it. With Celery, a batch's `celery:` settings are ignored too: the
Celery configuration comes from *qaboard.yaml*.
:::

## Avoid mistakes {#avoid-mistakes}
- Inputs are paths. Put in quotes those YAML would read as something else, like numbers (`"20260223"`), dates
  (`"2026-02-23"`) or `yes`/`no`. A `-` with nothing after it is an empty input: `qa batch` stops and says on which
  line it is.
- Check which inputs a batch finds with `qa batch <batch> --list-inputs`: it prints each input once per
  configuration. `--list` and `--list-output-dirs` print more, see the [API page](/docs/apis).
- Get completion and warnings in your editor with [the batch files' schema](/docs/project-init#checking-qaboardyaml-and-batch-files-in-your-editor).
