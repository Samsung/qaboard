QA-Board can use the LSF job management system to submit batch jobs.

:::important Reminder
If you don't want to use LSF, [read here how to make `qa batch` use a different backend](using-the-qa-cli#batch-runners).
:::

:::tip
LSF jobs with have your project name as LSF project (`-P`).
:::

## LSF project options
You can change the default LSF configuration with:

```yaml title="qaboard.yaml"
runners:
  # In doubt, ask advice from your manager / CAD / bqueues.
  lsf:
    queue: your_queue
    # max_threads: 8              # ask for eg 8 max threads when sending jobs to LSF (0=default)
    # max_memory: 8000            # ask for eg 8000M memory when sending jobs to LSF (0=default)
    # queue: my_queue
    # resources: RESOURCE_STRING
    # options: "-W 24:00"         # Specifiy freely other LSF options that bsub accepts
                                  # Will be added after all other CLI flags.
```

## Limiting concurrency
By default all the runs from a `qa batch` are sent at once. To limit how many run at the same time:

```yaml title="qaboard.yaml"
runners:
  lsf:
    concurrency: 20              # 0=unlimited (default)
    # concurrency_strategy: array  # default
```

or `qa batch --lsf-concurrency 20 my-batch`.

Two strategies are available:
- `array` (default): runs with identical LSF options are sent as a single [job array](https://www.ibm.com/docs/en/spectrum-lsf/10.1.0?topic=arrays-create-job-array) with a slot limit (`-J "name[1-n]%20"`). It's a sliding window, and a single `bsub` call. Each run's output is in its `log.lsf.txt`. If runs need different LSF options (e.g. per input type), each group gets its own array and its own limit.
- `waves`: runs are sent by groups of `concurrency` jobs, each group waiting for the previous one to end (`-w "ended(...)"`). Slow runs delay the next wave. Use it only if job arrays don't work for you.

In both cases job names keep the batch prefix, so stopping a batch from QA-Board still works.

## Running on a pool of Dask workers
With LSF each run is an LSF job, and pays the scheduling overhead. If you have many short runs, you can instead run them on a few long-lived [Dask](https://distributed.dask.org) workers, themselves started as LSF jobs via [dask-jobqueue](https://jobqueue.dask.org/en/latest/generated/dask_jobqueue.LSFCluster.html).

```bash
pip install "qaboard[dask]"
```

```yaml title="qaboard.yaml"
runners:
  default: dask
  lsf:
    queue: your_queue      # used by default for the worker jobs (also: project, resources, max_memory, options)
  dask:
    concurrency: 20        # max runs in flight for a `qa batch` (or --dask-concurrency)
    cluster:               # dask_jobqueue.LSFCluster arguments
      cores: 4             # runs per worker job
      memory: 32GB         # per worker job: it should cover `cores` runs
      # walltime: "24:00"  # by default the queue decides
      # interface: ib0     # if workers can't reach the scheduler's default address
    # To use an existing cluster, instead of starting workers for each batch:
    # scheduler_address: tcp://my-host:8786
```

- By default, `qa batch` starts the Dask scheduler, bsubs `ceil(concurrency / cores)` worker jobs named `{batch-prefix}_dask`, and stops them when done. Workers must be able to open a TCP connection to the host running `qa batch`, and use the same python environment. Worker logs are in `~/.qaboard/dask-logs`.
- Each run's output is in its `log.dask.txt`.
- `--no-wait` is only supported with `scheduler_address`, and then `concurrency` is not enforced.
- LSF "bridges" are not supported: `bsub` must be available where `qa batch` runs.

## LSF options per batch

```yaml {3-5} title="qa/batches.yaml"
you-can-give-an-LSF-configuration:
  lsf:
    max_memory: 10000
    max_threads: 4
  configurations:
    - base
  inputs:
  - images/A.jpg
  - images/B.jpg
```

```yaml {2-3,8-10}
you-can-give-an-LSF-configuration-per-input:
  lsf:
    max_memory: 1000
  configuration:
    - base
  inputs:
    images/A.jpg:
    images/B.jpg:
      lsf:
        max_memory: 200
```

## LSF options on the CLI
You can use CLI options to override the defaults:

```bash
qa batch --help
# --snip--
  --lsf-threads INTEGER        restrict number of lsf threads to use. 0=no
                               restriction
  --lsf-max-memory INTEGER     restrict memory (MB) to use. 0=no restriction
  --lsf-queue TEXT             LSF queue (-q)
  --lsf-fast-queue TEXT        Fast LSF queue, for interactive jobs
  --lsf-resources TEXT         LSF resources restrictions (-R)
  --lsf-priority INTEGER       LSF priority (-sp)
  --lsf-options TEXT           Other LSF options (as 1 string, like '-W
                               24:00') that bsub can understand. Will be added
                               after all other CLI flags.
  --lsf-sequential / --lsf-parallel
```

## Connecting to LSF via a "bridge" host
It's needed for the server, that runs in a container, and sometimes to send LSF jobs from windows. There are two options:

1. Via environment variables:
```bash
export QA_RUNNERS_LSF_BRIDGE='ssh my_host_with_lsf_access {bsub_command}'
export QA_RUNNERS_LSF_BRIDGE='ssh my_host_with_lsf_access su {user} {bsub_command}'
```

1. Via project configuraton:
```yaml {5} title="qaboard.yaml"
runners:
  lsf:
    # --snip--
    bridge: 'ssh bridge_host'
```

:::tip
When using bridges, `qa` will explicitely ask LSF to run in your current working directory, so no need to play games with `ssh 'cd {cwd} && {bsub_command}'`...
:::
