Algorithms are evaluated with metrics: KPIs, objective figures of merit, errors, run times... QA-Board shows the
metrics your runs return in summaries, tables, run cards and plots over time, and compares them with a reference.

## Returning metrics
Your `run()` function returns a dict of metrics. That's all QA-Board needs to show them:

```python title="qa/main.py"
def run(context):
    # --snip--
    return {
        "psnr": psnr,
        "latency": latency_ms,
        "frames": len(frames),
        "is_failed": False,
    }
```

Every metric with a number is shown, there is nothing else to configure. `qa` adds `compute_time`, the run's duration
in seconds. Metrics can also be strings and [rich metrics](#rich-metrics), and `is_failed` says whether the run
[failed](#failed-runs).

:::tip
If your code is not in Python, or runs in another process, it can write a *metrics.json* file in `context.output_dir`:
`qa` merges it with what `run()` returns (`run()` wins for the same key). It can declare these metrics in a
[metrics_definitions.json](#from-any-language-metrics_definitionsjson).
:::

### What QA-Board shows by default
Until you tell it more, QA-Board doesn't know whether higher or lower values of a metric are better. So it shows them
**in neutral colors**:
- the **Summary** shows up to 8 metrics: those whose median changed the most vs the reference (without reference runs,
  the first ones). Their changes are gray, neither green nor red. `compute_time` is left out: pick it if you need it;
- the **Metrics Diff** shades cells in blue: the darker, the larger the change;
- the **Metrics Table** shades cells in blue: the darker, the larger the value compared with the other runs;
- both tables show the declared metrics, and others up to 20 columns: pick more above them;
- each **run card** shows the run's first 6 metrics;
- the **History** page lets you plot any metric of its commits.

Hovering a metric's name says when QA-Board doesn't know which way is better, and the Summary lists those metrics
with a link to this page. To see improvements in green and regressions in red, labels and units,
[declare your metrics](#declaring-metrics). For the tables to color values by how good they are, give them a `target`.

## Declaring metrics
Declaring a metric tells QA-Board how to show it. All the fields are optional:

| Field | What it does |
|---|---|
| `smaller_is_better` | `True` if smaller values are better (an error, a run time), `False` if larger values are (PSNR, accuracy). Without it, changes stay neutral, e.g. for a count of frames. In a metrics file, leaving it out means `True`: write `null` when neither is better. |
| `target` | The value to reach. Table cells are colored by how far they are from it, and the Summary shows the share of runs that meet it. Needs `smaller_is_better`. |
| `target_passfail` | With `True`, values that meet the target are green, the others red, without shades. |
| `label` | A readable name. Default: the metric's key. |
| `short_label` | For tables and small spaces. Default: the label. |
| `description` | Shown when hovering the metric's name. |
| `suffix` | Shown after the values, e.g. `"%"` or `" ms"`. |
| `scale` | Values are multiplied by it when shown, e.g. `100` to show a fraction in percent. |
| `precision` | The number of significant digits shown. Default: 3. |
| `plot_scale` | `"log"` or `"linear"`, for the axis of the plots. Default: log in the Summary's box plots, linear on the History page. |

The best place to declare a metric is where your code computes it, so that the metric and its definition change
together. There are three ways: pick the one that fits your code. They need an up-to-date `qa`
(`pip install --upgrade qaboard`) and QA-Board server: older servers ignore the definitions.

### In the returned values
Wrap the value in a `Metric`, with the fields above:

```python title="qa/main.py"
from qaboard import Metric

def run(context):
    # --snip--
    return {
        "psnr": Metric(psnr, label="PSNR", suffix=" dB", smaller_is_better=False, target=30),
        "latency": Metric(latency_ms, suffix=" ms", smaller_is_better=True),
        "frames": len(frames),  # not declared: shown in neutral colors
        "is_failed": False,
    }
```

A `Metric` behaves like a `float`: your `postprocess()` function can still compute with it. The result of a
computation is a plain `float`, without the definition: if `postprocess()` replaces a value, wrap it again.

### Once, next to the code that computes them
When a function computes the same metric in many places, or when a module computes many metrics, declare them once
with `define_metric`, at the top of the module:

```python title="my_algo/quality.py"
from qaboard import define_metric

define_metric("psnr", label="PSNR", suffix=" dB", smaller_is_better=False, target=30)
define_metric("ssim", label="SSIM", smaller_is_better=False)

def quality_metrics(output, reference):
    return {"psnr": psnr(output, reference), "ssim": ssim(output, reference)}
```

`define_metric` only counts when it runs in `qa`'s process: the module must be imported, directly or not, by your
*qa/main.py*. Calls in other processes, like a subprocess or `multiprocessing` workers, are not seen. If the module
is also used without `qa`, keep the import optional:

```python
try:
    from qaboard import define_metric
except ImportError:
    define_metric = lambda *args, **kwargs: None
```

### From any language: metrics_definitions.json
If a program in another language computes the metrics, it can write a *metrics_definitions.json* file next to its
*metrics.json*, in `context.output_dir`:

```json title="metrics_definitions.json"
{
  "psnr": {"label": "PSNR", "suffix": " dB", "smaller_is_better": false, "target": 30},
  "latency": {"suffix": " ms", "smaller_is_better": true}
}
```

Editors can check the file and complete its fields with its
[JSON schema](pathname:///metrics_definitions.schema.json):
`https://samsung.github.io/qaboard/metrics_definitions.schema.json`.

### How it works
At the end of each run, `qa` gathers the definitions of the metrics the run returned, field by field: from
`define_metric`, then *metrics_definitions.json*, then `Metric`, the last one winning. Fields with a wrong type are
left out, with a warning. `qa` sends the definitions to QA-Board with the run's metrics.

QA-Board keeps them with the commit: commit pages show the metrics as they were defined at the time. Lists of commits
use the definitions from the latest runs on the reference branch, and the History page those of its latest commit.
QA-Board writes a commit's definitions only when they're new or changed: give all the runs the same definitions,
e.g. don't compute a different `target` for each input.

## Declaring metrics in a metrics file
Projects can also declare metrics in a file, listed in *qaboard.yaml*:

```yaml title="qaboard.yaml"
outputs:
  metrics: qa/metrics.yaml
```

```yaml title="qa/metrics.yaml"
# yaml-language-server: $schema=https://samsung.github.io/qaboard/metrics.schema.json
available_metrics:
  psnr:
    label: PSNR
    suffix: " dB"
    smaller_is_better: false
    target: 30
  loss:
    label: Loss function
    description: Mean error on the validation set
```

It works with the definitions from your code: for a metric declared in both, the fields from your code win, in the
web app and in [quality gates](/docs/quality-gate). [`qa optimize`](/docs/auto-optimization) only
reads the metrics file: declare there the metrics you optimize, with `smaller_is_better`.

:::caution
In metrics files, metrics that leave out `smaller_is_better` are "smaller is better", like `loss` above. Write
`smaller_is_better: null` for metrics where neither is better. Until November 2026, `null` (or `smaller_is_better:`
with nothing after it) also meant "smaller is better": if your metrics file has some, write `true`.
:::

## Choosing the metrics shown by default
Without configuration, QA-Board picks the metrics it shows, see [above](#what-qa-board-shows-by-default). To choose
them, list metrics in your metrics file. They don't have to be declared:

```yaml title="qa/metrics.yaml"
# the metric used to sort runs, shown in lists of commits and plotted over time on their page
default_metric: psnr
# shown in the Summary
summary_metrics: [psnr, ssim, latency]
# shown in the tables and on the run cards, and offered in the plot over time of the lists of commits
main_metrics: [psnr, latency]

# Optional, for the History page: the metrics in its summary and tables (default: main_metrics, else QA-Board picks),
# those you can plot over time (default: main_metrics, else all the metrics of its commits)
# dashboard_metrics: [psnr, latency]
# dashboard_evolution_metrics: [psnr, ssim, latency]
# also summarize the metrics per tag of the inputs, from the "tags" of their metadata
# dashboard_breakdown_by_tag: true
```

Users pick other metrics in the Summary and the tables. Run cards always show the `main_metrics`. Lists of commits
only show metrics over time with a `default_metric` or `main_metrics`.

## Moving metrics from a metrics file to your code
Long metrics files are hard to maintain: nobody owns the hundreds of metrics they list, and they're out of date as soon
as the code changes. You don't have to move everything at once:

1. Keep the metrics file: it keeps working, and its definitions still apply.
2. Delete the definitions of metrics your runs don't return anymore: search your code for their names.
3. Declare new metrics in your code, and move the others when you change the code that computes them: once your code
   declares a metric, delete it from the metrics file.
4. Keep in the metrics file the lists of metrics to show by default (`summary_metrics`, `main_metrics`...). Once
   QA-Board's choices suit you, delete the file and `outputs.metrics` in *qaboard.yaml*.

:::caution
A definition in a metrics file without `smaller_is_better` means "smaller is better". When you move it to your code,
write `smaller_is_better=True`, else QA-Board shows the metric in neutral colors, and [quality gate](/docs/quality-gate)
rules about its regressions fail.
:::

## Failed runs
The metric `is_failed` is boolean. If true, QA-Board will consider the run as "failed".
The main uses cases are:
  * highlight in the UI
  * failing runs that don't achieve a basic target quality (or where things just crash...)
  * simplifying the control flow, instead of raising an exception from `run()`
  * remembering if the `run` was successful, when users split between `run/postprocess` stages

## Rich metrics
If you return string metrics, they will be shown in the UI's tables and cards like this:

<img alt="Rich metrics in a card" src={useBaseUrl('img/rich-metrics-in-card.png')} />

You can return "rich" metrics to customize the display:

```python
def run(context):
    # ...
    metrics = {
        "loss": 1.345, # regular metric
        "status": "unstable", # string metric
        # you can have more complex metrics..
        "rich_status": {
            "text": "unstable",
            # link to somewhere
            "href": "https://example.com",
            "icon": "settings", # choose from https://blueprintjs.com/docs/#icons
            "intent": "WARNING", # or PRIMARY|SUCCESS|DANGER
            # the rendered "tag" supports all parameters of
            #   https://blueprintjs.com/docs/#core/components/tag
            # like "style" for CSS properties, large, minimal....
        } 
    }
    return metrics
```

## Metrics shown as a "run-time" configuration
It is possible to add at run-time parameters to the run. The use-cases are:
1. **making very visible a few key parameters** nested deep in a config-file, and enabling **filtering** by them
2. **displaying links** next to runs, grouped with the configuration (and not the metrics like above!). Users often use those badges to do deep-learning inference on QA-Board, and easily link back to the training page, managed by a different product. They'll give a model ID as configuration, their `run()` will fetch the training page URL, and it enables smooth workflows.

<Shot
  id="commit/run-badges"
  caption="The model badge sits with the run's configuration tags, and links to the model's card."
/>

To make it happen, return in your metrics a `params` key:

```python
def run(context):
    return {
        # ...
        "params": {
            # in the UI users will see "mode" as part of the run parameters
            "mode": "GAN",
            # they will also see a "badge" linking to the model training page:
            "badges": [
                {
                    "text": "Training",
                    "href": "https://wandb/run/<some-id>",
                    "icon": "settings",
                    # for more info on available key see above
                }
            ]
        }
    }
```
